# v0.5.0 Final State

Developer Memory: what people know about the project, kept beside the evidence and
never treated as it. This file is the record of what v0.5 is — what it contains,
what holds it in place, what it costs, and what it does not do. Everything in it
is a fact about the tree it was written in, and the numbers are measurements
taken with the commands named beside them, so they can be taken again.

## What it is

v0.4 gave the tool a reading of the evidence. The reader could not answer back:
why a rule exists, what was tried and abandoned, which constraint is load-bearing
and for whose benefit — none of that is in git, and all of it is what a person
joining the project needs.

v0.5 is the first part of the store the tool did not derive. The definition is
`docs/v0.5-design.md` §3.1:

> **A Developer Memory is a statement a person made about this project, admitted
> by that person's explicit act, kept with the subject it is about and the
> evidence it was made from (which may be none), and stored apart from the
> evidence layer — knowledge the tool cannot derive from the repository, cannot
> verify, and must never present as derived.**

The test that makes it operational is one sentence, and it has one answer:

> **If the tool can derive it, it is not memory.**

Its corollary: **evidence does not become memory by accumulating.** A file that
changed two hundred times is a fact about two hundred commits, not knowledge.

**The three kinds, and what separates them:**

| | Historical fact | Model interpretation | Developer memory |
|---|---|---|---|
| Who produces it | the tool, from git or an AST | a model, per run | a person |
| Derivable again | yes, byte for byte | no | no |
| Stored | the evidence tables | never | the memory tables |
| Usable as evidence | it is evidence | never | **never** |
| How it ends | it does not; it is history | discarded at the end of the run | superseded or invalidated |

## Memory is not evidence — the five rules, each with its test

The phase's real risk is not that a memory cannot be written; it is that memory
leaks the other way, because every leak is invisible — a bundle with a memory row
in it looks exactly like a bundle. The five rules are
`docs/v0.5-design.md` §13.2, and `tests/test_memory_boundaries.py` is where each
one is held:

1. **Evidence never depends on memory.** The evidence modules do not import the
   memory ones — read out of the package's own sources, the way
   `tests/test_offline.py` holds the provider boundary — and, behaviourally,
   every evidence command (`analyze`, `ast`, and all nine reading invocations,
   `explain` included) is run against a database whose memory store is
   unreadable. All of them have to work: a newer memory stamp must never cost a
   reader an explanation.
2. **Memory never enters the evidence tables.** Nothing in the memory path writes
   a row in `commits`, `commit_files`, `file_versions` or `definition_versions`,
   and nothing adds a column to them.
3. **Memory is never evidence for a memory.** The citation vocabulary has no
   memory kind, a memory's id is refused as a citation of every one of the six
   kinds, and the only memory-to-memory edges are the lifecycle links — the two
   foreign keys into `memories`, and nothing else.
4. **The model never writes memory, and the tool never writes memory on its own.**
   `provider.py` imports nothing from the package at all, so "the model never
   writes memory" is a statement about what the provider *is*; exactly one module
   (`cli.py`) calls `admit`, `supersede` or `invalidate`; and a model run whose
   answer restates a memory, proposes one and relates itself to one leaves both
   memory tables byte-identical.
5. **Memory never overrides evidence.** Nothing in the evidence path reads the
   store, so a memory cannot filter, reorder or reinterpret a bundle — held as
   text: for two databases differing in one thing, the bundle, the model's view
   and the output of all eight reading commands are compared byte for byte, and
   the offline `explain` answer is held to a single added key.

**The one thing the tool cannot catch, stated rather than hidden.** A model that
paraphrases a memory into an `observed_changes` entry with a real citation beside
it passes every pass there is. What holds instead is the structure: the section is
a sibling of `evidence` and never a key inside it, the statement is printed from
the store rather than from the model's words, and the block labels all three
kinds. `tests/test_memory_boundaries.py` pins the limit as a known limit, and both
READMEs state it under *Known limitations*.

## AI is not memory

The v0.4 contract — an answer is an interpretation of the evidence, never a
record of what happened — is unchanged. v0.5 adds a second kind of input to the
prompt, and one field to the answer:

- **The model is shown the memory section**, under a heading that says what it
  is, in the same words the offline path prints. The section is capped at five
  and every dropped count is stated, the v0.4 selection discipline unchanged.
- **A memory may inform a candidate reason and may never be cited as evidence or
  written as something observed.** An answer that names a memory id in
  `evidence[]` is refused by the semantic pass, which never learns what a memory
  is — the caller passes the ids it showed the model.
- **`related_memory` is the only way an answer may point at a memory.** The id is
  checked against the section the model was actually shown, and the statement is
  then printed from the store — the tool's own bytes, never the model's
  paraphrase — with the model's sentence under it, marked as the reading it is.
- **Nothing a model writes is stored.** An explanation is printed and read, and
  the store is unreachable from the provider. Whether an explanation is ever
  stored remains an open question, and it is not a small one.

## The cache exception

This is the one architectural sentence v0.5 changes, and the one thing about the
database a reader has to know:

> The evidence tables are a cache over the repository — every row in them can be
> rebuilt by reading git again. **The memory tables are not a cache**: no row in
> them can be rebuilt from anything, and every path that rebuilds or discards the
> evidence must preserve it.

What that means in the tree:

- **The memory tables are deliberately not in `storage.TABLES`** — that tuple is
  what a schema rebuild drops, and a "drop everything except memory" condition
  would be one edit away from dropping memory.
- **A rebuild carries the memory stamp across** (`storage._foreign_meta` /
  `_restore_meta`): a rebuild recreates `meta`, and a key this module does not own
  is kept. Without that, a rebuild would leave the memory tables *unstamped* — a
  state the store refuses to read — and would brick every memory silently.
- **The corruption sentence no longer says to delete the file.** It names the file
  and says to copy it before changing it, because that advice now destroys
  knowledge rather than a cache.
- **A database holds one repository's memories.** `--db` pointed at another
  repository's file takes the evidence over and leaves the memories; a write is
  refused with the foreign path and the two ways forward, and a read reports the
  count and the paths rather than mixing them in.
- **A moved repository is three steps** — `analyze --db <old file>`, then
  `memory adopt --from <old path>` — and all three are tested end to end. Finding
  the old file by itself would mean guessing that two paths are one project, which
  this tool does not do.
- **Deleting the file destroys the memories in it.** Nothing else holds them, and
  export/import is not here yet. Both READMEs say so wherever the database is
  described.

## Lifecycle, and time

- **Three states, two endings, no delete.** `active` is the only state an act can
  be performed on; `superseded` (with a successor) and `invalidated` (with a
  reason) are terminal; there is no in-place edit, and a rule that comes back is a
  new memory. A cycle cannot be built out of acts — a successor is always a memory
  the act has just admitted — and the schema does not pretend to see what a hand
  writes.
- **Three timestamps, three meanings.** `admitted_at` and `ended_at` are facts
  about the store; `since` is the author's claim about the project, set by
  `--since-commit` or `--since-date`, and absent means unknown rather than
  defaulted.
- **In force is compared by time, not by ancestry** — a known start at or before
  the commit, and not ended before it. The limit is named rather than hidden:
  reachability would be exact and would make every read walk the parent graph.
- **The two groups are never merged**: *in force at this commit* is what provably
  held when the code was written, and *related, not provably in force* is
  everything else. Merging them would let a rule from 2026 read as the reason for
  a commit from 2023.
- **Provenance is checked twice and repaired never.** A citation is a historical
  reference, not a live link: it is resolved when the memory is admitted and
  re-checked every time it is read, and the three states — resolves, no longer
  resolves, not checked — are rendered differently. A list checks the cheap kinds
  and says `not checked` for the range and the co-change pair rather than reading
  as though everything had been verified.

## What it costs

**The store, measured** with `benchmarks/memory_benchmark.py` (fastest of three;
`create` is one admission timed over a batch of twenty):

| Memories | Database | `create` | `memory list` | `memory list --json` | `memory show` | `explain`'s section |
|---|---|---|---|---|---|---|
| 10 | 120 KB | 14.0ms | 35.0ms | 37.3ms | 35.7ms | 0.5ms |
| 100 | 156 KB | 13.8ms | 36.4ms | 41.1ms | 33.9ms | 1.0ms |
| 1,000 | 484 KB | 14.5ms | 37.6ms | 76.6ms | 33.1ms | 8.2ms |
| 10,000 | 3.7 MB | 14.1ms | 40.2ms | 453ms | 35.0ms | 82ms |
| 100,000 | 37.2 MB | 20.4ms | 78.4ms | 4.74s | 46.6ms | 1.11s |

A memory costs about 380 bytes. Writing does not get dearer and neither does
reading one, because `show` looks one row up by id. `memory list` was linear until
it was measured — 843ms at ten thousand memories, because it read the whole store
to print twenty — and it is flat now: the read stops at the slice, the count
behind it is a query of its own, and the child rows are fetched by the ids that
were read.

**Two costs are measured and left alone, with the fix named.** `memory list --json`
is linear by contract (4.74s at a hundred thousand memories — a program that asked
for the list asked for all of it; subject filtering is the first thing queued
after v0.5.0), and `explain`'s section reads the whole store once (1.11s at the
same scale, because a file's earlier names and a definition's name are not a query
the schema can answer alone; a SQL prefilter is the second). Both are in the
READMEs' table with the numbers.

## Known limitations

- **A memory is a statement, not a fact.** The tool did not derive it and cannot
  check it; it checks the citations, and a citation that resolves does not make
  the sentence true.
- **A model can restate a memory as an observation, and no check catches that.**
  The structural defence is the labelled section, the verbatim statement and the
  citation check — not a semantic one.
- **A memory exists in exactly one place.** Deleting the database destroys it;
  export/import is not here yet.
- **A memory has two ways to end and no way to be edited**, and both are terminal.
- **A moved repository needs three steps**, and the tool cannot shorten them.
- **`memory list --json` and `explain`'s section are linear in the store's size**,
  with the measured numbers above.
- **Nothing is incremental**, unchanged from v0.3: `analyze` rescans the whole
  history and the AST pass reads every Python file version each time.
- **`commit` has no `--json`**, the one v0.3 interface gap, still open, still
  stated in both READMEs and pinned by `tests/test_contract.py` as a gap.
- **The `--db` refusal is per write, and the read reports rather than refuses** —
  a database can hold two repositories' memories, and the tool says so instead of
  pretending it does not.
- Tested on Linux and Windows, on Python 3.11 and 3.13, by CI. macOS is untested.

## What is not here

The v0.5 boundary, from `docs/v0.5-design.md` §15.4 and the CLI freeze §15:

| Not in v0.5.0 | Why |
|---|---|
| AI proposals of memories | The floor first; the proposal route is where the self-reinforcement risk lives, and it needs its own unit. |
| Memory types (Decision, Constraint, …) | No behaviour branches on a type, so the statement's own words carry its force. |
| Editing or deleting a memory | A correction is a supersede; an ending is an invalidate. |
| Export, import, sharing, sync | The move hazard is the argument that it will be needed; it is a later unit. |
| Memory in any command's output other than `explain` | Every other command is about the evidence. |
| Semantic search over memories | SQLite-only, no embeddings; retrieval is by subject and citation, which is deterministic and checkable. |
| Subject filtering on `list` | A filter is a query and the listing commands are listings; queued first after v0.5.0. |
| `--json` on the writing acts | The tool's writer convention; a machine-readable write would be a project-wide change. |
| `--no-memory` on `explain` | For a reader who wants the answer without the section. |
| A prompt unit | The prompt now carries a second kind of input, and the question is more pressing than it was in v0.4. |

## The release

The order is a rule, and it exists because v0.3.0's tag had to be moved once:

```text
commit  →  push  →  all four CI jobs green on that commit  →  tag  →  GitHub Release
```

**What happened:** the release commit is `9d81acf`, and its first push was **red
on all four jobs**. What the runners found was a real defect — in the tests
rather than in the tool: three assertions read the colourised bytes of a usage
error instead of the sentence a person reads, so they passed on the machine they
were written on and failed wherever colour is on (trap 41 in `PROGRESS.md`). The
fix is `e3c55d0`, and **all four jobs passed on it** — ubuntu-latest and
windows-latest, Python 3.11 and 3.13 — before anything was tagged. `v0.5.0` is an
annotated tag on that commit, with a GitHub Release beside it.

That is the order working as intended, and it is worth saying what it avoided:
tagging the release commit directly would have put `v0.5.0` on a tree that fails
on every runner the project tests on, and the tag would have had to move — which
is what v0.3.0's did, and the reason the order is a rule rather than a
preference.

## v0.6 preconditions

What has to be true before AI-assisted change analysis and replay starts, so a
later session does not begin on assumptions:

1. **The boundary holds.** The evidence layer is deterministic and does not read
   memory; memory is not evidence and is never written by a model; both are held
   by tests that fail if they stop being true.
2. **The cache exception is respected everywhere.** Any new path that rebuilds or
   discards the evidence must preserve the memory tables, and the docs must say so
   wherever the database is described.
3. **The two measured linear costs are the known debt**, and the fixes are named:
   subject filtering on `list`, and a SQL prefilter for `explain`'s section.
4. **The open questions are answered or explicitly deferred**: export/import and
   repository identity, the proposal route, `--json` on the writing acts,
   `--no-memory`, the prompt unit, and whether an explanation is ever stored.
5. **The release order is followed again**, with the tag on a commit whose own CI
   is green on all four jobs.
