# The v0.5 product audit — does the value hold, and does memory need to travel?

**Status: an audit, not a plan, and not a change.** No production code, schema,
CLI, provider, evidence bundle, memory semantics, test or README contract was
touched by the unit that produced this file. It is one document. Everything in it
is either a fact read out of the tree, an argument built on those facts, or a
question this tree cannot answer — and each one says which.

**Date:** 2026-10-08. **Tree audited:** `1c2bebd`, `main = origin/main`, working
tree clean, tag `v0.5.0` at `e3c55d0`.

---

## How to read the markers

Every substantive claim below carries one of three words, and the three are not
decoration — the whole point of this audit is that the project's own standard
("every conclusion must be traceable") has been applied to the tool and not to
the product claim.

| Marker | Means | How a reader checks it |
|---|---|---|
| **CONFIRMED** | A file, a test, a measurement or a command output in this tree proves it. | Re-read the file or re-run the command named beside it. |
| **INFERRED** | It follows from confirmed facts by argument. No experiment or measurement supports it. | Attack the argument. If it holds, it is still only an argument. |
| **UNKNOWN** | This tree cannot settle it. It needs an experiment, a measurement, or a decision by the user. | Nothing to check — that is what the word means. |

Where a claim is a **defect**, it is recorded here and **not fixed**, per the
unit's boundary. Appendix B is the list.

## 1. Executive Summary

**The tool is finished and correct. Its value is unverified, and one design
property — that a memory cannot travel — caps the value of the newest layer.**

Five findings, in the order they matter:

1. **There is no evidence of any kind that CodeArchaeology improves anyone's
   understanding of a codebase.** 921 tests and five benchmarks all measure the
   tool against its own design. The repository is public and has **2 stars, 0
   forks, and 0 issues ever** — no external user has said anything about it.
   Every value claim in the READMEs is the author's argument. This is
   **CONFIRMED** (the absence is measurable) and it is not a criticism of the
   engineering; it is the observation that the project's evidence-first rule has
   never been pointed at the project's own premise.

2. **Memory's content is project-scoped and its custody is personal**, and the
   design says so out loud (`docs/v0.5-design.md` §18 case 6: "Content: the
   project's. Custody: the person running the tool, locally"). The moments when
   that knowledge is worth the most — a newcomer arrives, a colleague inherits
   the module — are exactly the moments it is invisible. **CONFIRMED** as a
   property; the size of the loss is **INFERRED**.

3. **The data model was already built for export and import, and then export and
   import were deferred.** `docs/v0.5-storage-design.md` §1 chose UUIDs for
   memory ids *specifically so that a re-import would not have to renumber and
   rewrite every lifecycle link*. That is a design paying in advance for a
   feature it did not ship. **CONFIRMED** — it is the strongest single argument
   in this document, because it means portability is not a new direction, it is
   an unfinished one.

4. **The cold start does not need AI.** The brief asks whether the AI proposal
   route is needed to fill an empty store. The answer is that the *trigger* can
   be deterministic: the tool can see a definition that was deleted and restored,
   a file that changed two hundred times with nothing explaining why, a commit
   whose message is one word — and it can ask a person about it. A question
   cannot be mistaken for a fact, needs no new epistemic category, and satisfies
   "the model never writes memory" more strongly than a draft-and-accept route.
   **INFERRED**, and it is the cheapest large improvement available.

5. **The two "known debts" (`memory list --json`, `explain`'s section) are
   measured at a scale nobody reaches.** At 1,000 memories both are under 80ms.
   They become real at 10,000+, which no person writes by hand — but a store
   that *imports* could hold thousands. So P1/P2 are not performance debt; they
   are **contingent on finding 3**, and they should be sequenced behind it.
   **CONFIRMED** from the benchmark table in `docs/v0.5-final-state.md`.

**What the audit recommends, subject to the user's ruling:** run the
understanding pilot (§4) before building anything, because it gates the
portability question — there is no point making knowledge travel that has not
been shown to be worth carrying. Then decide portability (§3), which the schema
already anticipates. Do not build AI proposals; build the deterministic question
route if the cold start is judged a problem.

## 2. Current Product Thesis

What the project claims, in its own words, and what the tree shows about each
claim.

**The claim** (`README.md`, "Why this project exists"): "Git already tells you
**what** changed, **when**, and **who** changed it. What it cannot tell you is
**why** the code looks the way it does today. […] CodeArchaeology tries to put
the story back."

**The mechanism, in four layers**, each of which is a distinct product bet:

| Layer | The bet | What the tree shows |
|---|---|---|
| v0.1–v0.3 — the deterministic layer | Reconstructing history *better than `git log`* is useful: lifecycles across renames, hotspots, co-change, AST evolution. | Built, tested, benchmarked. **The bet itself is untested.** |
| v0.4 — the interpretation layer | A model reading a *checked evidence bundle* is more honest than a model reading a diff, and the honesty is structural rather than a disclaimer. | Built. The structure is real and tested (`test_boundaries.py`, 13 cases). Whether a reader prefers it to `git show` is **UNKNOWN**. |
| v0.5 — the memory layer | Some knowledge is not in the repository, and it is worth keeping beside the evidence with provenance and a lifecycle. | Built. The boundary is enforced. **The premise — that people will write memories — is untested and unmeasured.** |
| v0.6 — "AI-assisted change analysis and replay" | Not defined anywhere in the tree. | **UNKNOWN.** One row of the roadmap table. |

**The thesis has a shape worth naming**, because it determines what counts as
success. The tool is not a *productivity* tool (it does not make you type less)
and it is not a *quality* tool (it does not find bugs). It is a **comprehension**
tool: it is supposed to make a person understand a codebase they did not write.
That is a real category, and it has a specific falsification condition — which
the project itself wrote down, in `docs/v0.4-problem-definition.md` §8, as
acceptance criterion 5:

> "The answer contains at least one thing that reading the commit message alone
> would not give. Otherwise it is a summarizer."

**That is a product criterion, and no test can check it.** A fixture can check
that an answer cites `oc1`; only a person can check that the answer told them
something they did not know. **CONFIRMED** — the criterion is written in the
problem definition and there is no test anywhere in the tree that evaluates it
against a human reader.

**Two structural facts about the thesis that constrain every answer below:**

- **The tool is read-only over git and writes only its own cache.** A repository
  is never modified (the design rejects a UUID in `.git/` for exactly this
  reason: "The tool never writes to the repository"). Any portability option that
  puts memory *inside* the tree therefore breaks a rule that is currently true,
  and the break has to be argued for rather than assumed. **CONFIRMED.**
- **The unit of analysis is a commit, and the unit of knowledge is a statement.**
  There is no whole-repository conversation, no agent, no multi-turn anything
  (`docs/v0.4-problem-definition.md` §9). This is a boundary, not a backlog, and
  it means the tool answers *pointed* questions well and *open* questions not at
  all — which is what the experiment in §4 has to respect.

## 3. Memory Portability Audit

### 3.1 The facts, before any opinion

| Fact | Where | Marker |
|---|---|---|
| A memory row's identity is `str(Path(repository_path).resolve())` — a plain absolute path string. | `memory.py` `_resolved`, `docs/v0.5-storage-design.md` §2.1 | **CONFIRMED** |
| The database *file* is named after `sha256(casefolded resolved path)[:16]` in the OS cache directory. | `cache.py:31-45` | **CONFIRMED** |
| The database directory is `%LOCALAPPDATA%\codearchaeology` (Windows), `~/Library/Caches/codearchaeology` (macOS), `~/.cache/codearchaeology` (Linux). | `cache.py:12-28` | **CONFIRMED** |
| A write from a second repository's path is **refused**; a read filters and **reports** what it hid. | `memory.py` `_writable_repository`, `foreign_memories` | **CONFIRMED** |
| `memory adopt --from <old path>` rewrites `repository_path` on the matching rows, records the act in `meta`, refuses when nothing matches, and refuses when the destination already holds memories. | `memory.py:409-452` | **CONFIRMED** |
| Memory ids are UUID4, chosen so a copied row keeps its id and its lifecycle links. | `docs/v0.5-storage-design.md` §1 | **CONFIRMED** |
| There is no export, no import, no sync, no second store, and no repair command. | `docs/v0.5-storage-design.md` §9 | **CONFIRMED** |
| The remote URL was **rejected** as an identity, partly because it "would silently join two clones — a sharing decision that belongs to the export unit, not to a side effect of a stored field". | `docs/v0.5-storage-design.md` §2.2 | **CONFIRMED** |
| The docs instruct that the store must not be presented as a shared team record. | `docs/v0.5-design.md` §18 case 6 | **CONFIRMED** |

**One documented hazard is smaller than the documentation implies.** The storage
freeze records an asymmetry — "The cache filename casefolds on Windows and the
meta comparison does not" — and leaves it as a pre-existing hazard. Measured on
this machine: `Path('D:/agent/project/CodeArchaeology').resolve()` and
`Path('d:/AGENT/PROJECT/codearchaeology').resolve()` return the **same string**,
because Windows `realpath` canonicalises case through the file handle. Since a
memory command can only run against a path that exists, the asymmetry is
**not reachable in practice**. It is a latent inconsistency in two rules, not a
defect a user can hit. **CONFIRMED by measurement** (2026-10-08, win32,
Python 3.13). Worth recording so that nobody spends a unit "fixing" it.

### 3.2 Six scenarios

#### Scenario A — A newcomer arrives

Developer A analyses a repository and writes twelve memories. Developer B clones
it and runs the tool for the first time.

**What B gets: nothing.** A different machine has a different cache directory;
even on the same machine a different checkout path produces a different digest,
so B gets a new empty database. If B were handed A's `.db` file and pointed at it
with `--db`, B's read would **filter A's rows out** and print a note saying the
database holds memories about another path. B would then have to run
`memory adopt --from /A/machine/path/to/project`.

**What that costs.** The memory layer exists for "knowledge the tool cannot
derive" — the *why*. The moment that knowledge has the highest value is the
moment someone who does not know it starts working on the code. Today that
moment is precisely when the knowledge is invisible. **INFERRED**: the feature's
value is concentrated in the case it does not serve, and this is the single
strongest product argument in this audit.

**The counter-argument, stated fairly.** v0.5's definition is deliberately not
"team knowledge base": it is "a statement a person made, admitted by that
person's explicit act". Under Core First and Local First, a local store is the
floor and the design says the floor comes first ("v0.5.0 ships C only. That is
not a retreat from B; it is the order the project already follows everywhere
else: the floor first, the layer on top after the floor has tests"). The current
state is therefore **coherent**. The question is not whether v0.5 is wrong — it
is not — but whether the *product* is finished, and it is not.

**One thing the single user does get**, and it should not be dismissed: the
author's own memory, six months later. That is real value and it is what v0.5
ships. But it is also the case where a memory competes most directly with
things that already work — a code comment, a note in `docs/`, a `CONTRIBUTING`
paragraph. **INFERRED**: the marginal value of Memory over existing project
documentation is *smallest* in the single-user case and *largest* in the
multi-person case, which is the case the architecture does not serve. That
sentence is the crux of Question A.

#### Scenario B — Team collaboration

A writes, B modifies. Today B cannot see it at all, so review, diff, blame and
history are **moot until portability exists** — there is nothing to review.

**If memory enters git, it inherits all four for free**, and that is the
strongest argument for a repository-native option: this project's entire thesis
is "use the machinery git already has to explain code", and git's review
machinery applies to knowledge about code exactly as it applies to code. A pull
request that adds a memory would be reviewed like a code change, blamed like one,
and its history would be a history.

**The three things that argument has to survive:**

- **Secrets.** A memory is plain text in a file, and the docs already say "a
  memory must not hold credentials" — the tool has no secret detection and "will
  not pretend to". A secret in a memory that reaches a public repository is
  permanent and is a *worse* leak than a secret in code, because people are
  careful with code and casual with notes. **CONFIRMED** as a documented absence
  of protection; the exposure is **INFERRED**.
- **Merge semantics.** Two people superseding the same memory produce a
  semantic conflict that no line-based merge resolves. Appending admissions
  merges cleanly; lifecycle edges do not.
- **Whether it is a shared record at all.** `docs/v0.5-design.md` §18 case 6
  explicitly instructs the documentation not to present the store as a shared
  team record. Making it one is a *product decision*, not a storage decision, and
  it has not been taken.

#### Scenario C — The repository moves

`~/work/proj` becomes `~/src/proj`.

**What happens: the memories appear to vanish.** The digest changes, so the tool
opens a new empty database. The old file is still there — a 16-hex-character name
inside an OS cache directory — and the recovery is `analyze --db <old file>` then
`memory adopt --from <old path>`. All three steps are tested end to end
(`tests/test_memory_adopt.py`, 12 tests). **CONFIRMED.**

**What `adopt` solves:** it is the explicit act that says "these are the same
project at a new path", it is per-row and refuses to merge two projects, and it
records that it happened. It is a good act. **CONFIRMED.**

**What it does not solve:** *finding the old file*. The design's justification —
"the tool never infers it" — is correct about **identity** and irrelevant to
**discoverability**. These are different problems and only one of them has been
answered.

**A cheap, honest improvement exists and is not a feature.** The database already
stores `meta.repository_root` for every database it has ever written. A read of
the tool's *own cache directory* — listing the databases and the repository each
one names — would let the tool say "this cache holds memories made about
`/old/path/to/proj`" without inferring anything. That is not guessing that two
paths are one project; it is reading a label the tool wrote itself. **INFERRED**
that this closes most of the practical gap, and **UNKNOWN** whether it is enough
for a user who has moved a repository twice.

**Verdict on naturalness:** the mechanism is honest and the default experience is
data loss by appearance. A developer who moves a checkout and sees an empty store
will conclude the memories are gone, and the tool will not tell them otherwise.
**INFERRED** — but the mechanism is confirmed, and the conclusion follows from
how people behave with cache directories, not from anything measured here.

#### Scenario D — Backup

A user backs up the Git repository. The cache is not backed up. The project is
restored; the memories are gone.

**Is that reasonable semantics or a design defect?** The argument for reasonable:
the docs say so, twice, in both READMEs and in the final-state record ("Deleting
the file destroys the memories in it. Nothing else holds them"). A user who reads
the documentation knows.

**The argument that it is a defect, which I find stronger:**

- The storage location **contradicts the semantics**. v0.5's headline sentence is
  "a database is no longer only a cache", and the file sits in a directory named
  `Caches` (macOS) or `%LOCALAPPDATA%` (Windows). Those names carry one meaning
  to every developer and to every OS utility: *disposable*. A user who reads the
  documentation and then runs a disk cleaner has been told one thing and taught
  another by the layout.
- "Copy the file before replacing it" is a **ritual**, not a workflow. There is
  no command that does it, no `.bak` on write, no "export before you upgrade"
  step in the release notes. The advice is correct and unactionable at the moment
  it is needed.
- The failure is **silent and delayed**. Nothing is lost at the moment of the
  mistake; the loss is discovered weeks later when a memory is expected and
  absent. Silent, delayed losses are the ones users attribute to the tool being
  unreliable rather than to their own backup policy.

**Verdict:** reasonable semantics, defect-grade ergonomics. **INFERRED**, and it
is the second independent argument for a portable form — the first being the
newcomer case. Two unrelated scenarios pointing at the same missing capability is
what makes this a product gap rather than a preference.

#### Scenario E — A fork

Project A forks to B. Today: a different checkout, a different path, a different
database, no inheritance. The design names this and points at export/import as
"the later, explicit answer".

**The four possible semantics, and what the tree already supports:**

| Semantics | Argument | What it needs |
|---|---|---|
| Inherit automatically | Matches git's model (a fork carries the history, so it carries the *citations*). | An identity that survives a path change — rejected in v0.5 (§2.2), and the root commit is explicitly rejected because it "breaks on rebase and squash". |
| Do not inherit (today) | A fork's history may not contain the cited commits, so the citations may be lies. | Nothing. Shipped. |
| **Explicit import, with per-memory filtering** | The person decides, and the tool shows what would not resolve. | **The mechanism already exists and is unused.** Every citation carries a resolution state — `resolved` / `unresolved` / `not_checked` (`memory_checks.py`, `docs/v0.5-storage-design.md` §4.3) — so an import can report "of 12 memories, 9 cite commits this repository does not have" *before* anything is written. |
| Only some inherit | The same as above with a rule attached. | The same mechanism plus a policy decision. |

**Finding:** the fork case does not need a new identity, a new table, or a new
check. It needs an import act that runs the check the tool already runs, and
shows the result as a **preview** rather than as a repair. The expensive half of
import is already built. **CONFIRMED** that the resolution states exist and are
tested; **INFERRED** that they are sufficient for a fork preview.

#### Scenario F — Version and release

A project releases v1.0. Which memories were in force at the tag?

**What exists:** a memory may carry `since_commit` or `since_date`, and
`memory_section.py` splits a section into "in force at this commit" and "related,
not provably in force", comparing by **time rather than ancestry**, with that
limit named in the storage freeze. `supersede` and `invalidate` close a span with
`ended_at`. So "which memories were in force on 2026-03-01" is answerable today,
and reading an old commit already shows a superseded rule as superseded.
**CONFIRMED** — tested in `tests/test_memory_lifecycle.py` and
`tests/test_memory_explain.py`.

**What does not exist:** any way to *publish* that set. There is no export, so
"the memory set as of the release" cannot be attached to a tag, shipped in a
release artifact, or diffed against the previous release's set. For a project
that wants to hand a version's knowledge to the people who will maintain it, the
temporal machinery is sufficient and the transport is missing — **again the same
missing capability, for the third time.**

**Is the temporal semantics itself sufficient?** Mostly, with two named limits
that the docs already record and that matter more at release granularity:

- **Time, not ancestry.** A memory dated after a commit is shown as "not
  provably in force" rather than as false. Correct and conservative, but it means
  a release-line rule ("this holds for the 1.x line") has no way to be expressed
  except as a date range, which drifts from the release it means.
- **A rule that comes back is a new memory.** `supersede` is terminal and there
  is no reactivation. For release semantics — a constraint that holds in 1.x,
  lapses in 2.0, returns in 2.1 — this produces a chain of three rows rather than
  a statement about a range. **INFERRED** that this is acceptable; it is
  certainly not elegant.

### 3.3 Five options, and the dimensions that separate them

Portability is not one question. The brief is right to insist that "portable"
≠ "git-tracked", and the table below is where that shows.

**Option A — Memory stays only in SQLite** (today).

**Option B — Export to a file in the project (`.jsonl` / `.json`), not
necessarily tracked.** The database stays authoritative; the file is an artifact.

**Option C — Memory lives natively in the repository.** The file *is* the system
of record; the database is a cache over it, or does not hold memory at all.

**Option D — Repository-local, with explicit export and import.** The database
remains the system of record, and export/import are *acts* a person performs, in
the same family as `adopt`.

**Option E — A shared/team store** (a server, or one file on a network share).

| Dimension | A — SQLite only | B — export file | C — repository-native | D — explicit export/import | E — shared store |
|---|---|---|---|---|---|
| **Portability** | none (manual file copy) | good — a file, placeable anywhere | perfect | good, on demand | perfect, within the team |
| **Reviewability** | none | good if committed | perfect — it is a PR | depends on where the file lands | none (no review step) |
| **Diffability** | none (binary SQLite) | good if line-oriented and canonically ordered | perfect | good | none |
| **Mergeability** | none — `adopt` refuses to merge two sets | append-only admissions merge cleanly; **supersede edges do not** | same as B, but mandatory on every branch merge | import is a person's act, so conflicts become visible choices rather than conflict markers | SQLite over SMB/NFS has locking hazards; a server is a new system |
| **Blame / history** | none | via git, if tracked | perfect | via git, if tracked | none |
| **Privacy** | best — never leaves the machine | the user decides per export | **the repository's visibility becomes the memory's visibility** | the user decides per export | the team's, and the server's |
| **Secrets risk** | lowest | moderate, only when exported | **highest and permanent** (git history) | moderate, opt-in | high — one store, many readers |
| **Repository pollution** | none | one generated file, plus a `.gitignore` decision per project | a file the tool must write into the user's tree | none unless the user chooses | none |
| **Fork semantics** | no inheritance (defined) | the file travels; citations may not resolve — and the tool already reports that | inherited automatically, wanted or not | explicit, previewable with the existing resolution states | shared, which is the point |
| **Backup** | **bad** — a cache directory | solved — "back up the repo" now works | solved | solved | the server's problem |
| **Migration** | bad — path digest plus per-row path | good — the format is path-independent or the path is rewritten on import | perfect | good — import rewrites the path, as `adopt` does | good |
| **Corruption** | single point of failure | a bad file is refused at import; the store is unharmed | a bad edit breaks a file the tool must refuse to read | the store is unharmed | a single store, a single blast radius |
| **Offline use** | perfect | perfect | perfect | perfect | **needs a service** — violates Local First and SQLite-only for v0.x |
| **Implementation complexity** | zero (shipped) | low for export; **the whole cost is in import** | highest — the tool becomes a writer of the user's source tree, and must handle dirty trees and branch switches | moderate, and additive: nothing existing changes | out of scope for v0.x |

**Three things the table makes visible that a prose comparison would hide:**

1. **The cost of every option is in import, not export.** Writing a file is a
   query and a `json.dumps`. Reading one back requires conflict rules, an
   identity rule, and an answer for "the file and the store disagree".
2. **Option C buys something no other option can, and pays for it with something
   no other option costs.** It makes "in force at this commit" *exact* — the
   memory set as of any commit is `git show <sha>:memories.jsonl`, a fact rather
   than a time comparison — which would retire the `not_provably_in_force`
   category entirely. It also means **a memory written today is invisible when
   reading a commit from last year**, which is the opposite of what the feature
   is for: the whole point of reading an old commit is to bring today's knowledge
   to it. That trade is a genuine architectural fork in the road and it has not
   been argued anywhere in the tree. **CONFIRMED** that the trade exists;
   **INFERRED** that it is a bad one for this tool.
3. **Option E is not a v0.x option**, and the reason is already frozen: Local
   First and SQLite-only. It should be assessed only for whether Option D's
   format would *foreclose* it. A line-oriented text format does not.

### 3.4 What the schema already paid for

This is the finding that changes the shape of the decision.

`docs/v0.5-storage-design.md` §1, on why memory ids are UUID4 rather than
autoincrement integers:

> "an export and re-import — the sharing path Unit 1 §21.1 already knows will be
> wanted — would have to renumber it, which means every `superseded_by` link
> would have to be rewritten. A UUID is the same value in every database it is
> copied into, so a lifecycle link survives the copy."

**CONFIRMED.** The v0.5 data model was designed so that a memory can be copied
into another database without breaking its lifecycle links — and then export and
import were deferred to "a later unit".

Three further properties of the shipped schema that a portable format needs, all
already present:

- **`repository_path` is a column on the row, not an attribute of the database.**
  That is what makes mixing *detectable* (the design says so explicitly: "Per-row
  is what makes mixing detectable"), and it is also what makes an export
  *self-describing* — every row carries the repository it was made about.
- **Every citation is a row in `memory_citations` with a kind and a target**, and
  every citation has a resolution state that is recomputed on read. An imported
  memory's citations can therefore be checked *before* anything is written.
- **`adopt` is already the shape of an import that rewrites identity**, including
  the record of the act in `meta` (`memory_adopted_from`, `memory_adopted_at`) so
  the store "says that an adoption happened rather than looking as though the
  rows were always this repository's". An import act has a working precedent to
  copy, including its refusal to merge two projects.

**Conclusion (INFERRED, and the user's to rule on):** Option **D** is the path of
least resistance and the one the schema already anticipates. It is additive — it
changes no existing rule, breaks no existing behaviour, and requires no new
identity decision. Its export format should be chosen so that Option C remains
possible later: plain text, one memory per line, canonically ordered by
`memory_id`, with the repository path carried on the row. A user who *wants* to
commit that file to their repository can; the tool does not require it, and does
not write into the tree.

**Two things Option D does not solve, and must not be oversold as solving:**
merging two divergent sets (the lifecycle edges still conflict), and the team
question, which is a product decision and not a storage one.

## 4. Understanding Value Experiment

### 4.1 The distinction the brief asks for, and why it matters here

```text
Correctness validation     (what 921 tests and 5 benchmarks do)
  input → tool → expected output
  The tool is measured against its own design.

Product value validation   (what has never been done)
  developer → tool → understanding → faster / more accurate / more confident
  The tool is measured against a person.
```

**The gap is not a small one, and the project's own standard is what makes it
visible.** Evidence First requires that every conclusion be traceable to a
commit, a diff or an AST node. The conclusion "this tool helps people understand
code" is traceable to nothing. It is the one claim in the project that would fail
the project's own audit.

**CONFIRMED:** 921 tests, five benchmarks, and zero human-subject data of any
kind. The public repository has 2 stars, 0 forks and 0 issues. There is no
feedback loop of any kind between the tool and a person who did not build it.

### 4.2 The pilot, designed to be run in a day

**This is a pilot, not a study.** With the sample sizes available to one person
it cannot produce a statistical result, and pretending otherwise would be worse
than not running it. What it *can* do: find out whether the questions are
answerable at all, whether the tool is usable by someone who did not write it,
and whether any signal is large enough to justify a real study. **Report
per-participant results and no p-values.** If any conclusion needs a number with
an error bar, the pilot cannot supply it.

#### Participants

- **Six to eight people**, split by experience: at least three who have never
  read the target repository, and at least two who are experienced Python
  developers.
- **The author may run the protocol once as a logistics pilot** — to find out
  whether the questions take ten minutes or forty — and **that run's data is
  discarded**. An author who knows the answers measures nothing.
- **A hard constraint that shapes recruitment, CONFIRMED:** the tool is not on
  PyPI, so a participant must `git clone` the tool and run `uv sync`. Participants
  are therefore limited to Python developers with `uv` available. This is a real
  limitation on who can be recruited and it should be stated in any result.
- **Do not use a single group.** A one-group design cannot separate "the tool
  helped" from "the person is good at this".

#### Design: crossover, two repositories, order counterbalanced

A within-subject design controls for skill; a between-subject design controls for
learning. The cheap way to get both with six people:

- Two repositories, **X** and **Y**, comparable in size and age.
- Each participant answers five questions about X using **git + source +
  existing documentation**, and five about Y using **the same plus
  CodeArchaeology**.
- The assignment of tool-to-repository is **counterbalanced**: half do X with the
  tool, half do Y with the tool. This separates the tool's effect from the
  repositories' difficulty, which is otherwise the largest confound in the design.
- **A participant must never answer questions about a repository they know.**

#### Repository

**Criteria (CONFIRMED as the reason each matters):**

- **Real git history: at least 1,000 commits and at least three years.** Below
  that, `hotspots`, lifecycles and co-change have nothing to say, and the
  experiment measures the tool with its main instruments switched off.
- **Python.** The AST layer is Python-only in v0.x; a non-Python repository would
  remove the structure and definition features from the treatment condition and
  make the two conditions unequal.
- **Complexity with visible historical reasons** — the property being measured is
  "can a person recover a reason from history", and a clean, well-documented
  project has no reasons to recover.
- **Not CodeArchaeology itself.** This is not a bias preference, it is a
  **CONFIRMED disqualification**: the tool's own repository has **39 commits
  spanning 2026-09-28 to 2026-10-07** — ten days, one author, no legacy. There is
  no archaeology to do in it, and any question about "why is this like this" has
  the answer "because it was written that way last week". Using it would produce
  a null result that says nothing.
- **Candidates** (criteria applied, not vetted here): a mid-size, long-lived
  Python project with a decade of history and a reputation for historical
  oddities — the class `psf/requests`, `pytest-dev/pytest` and `celery/celery`
  belong to. **The five questions must be derived by running the tool against the
  chosen repository and reading its log**, not from anyone's memory of the
  project; deriving them from a description would make the ground truth a
  recollection, which is exactly what this project's rules forbid.

#### The five questions

They must be **"why" questions with a checkable answer**, and every one of them
must be answerable with "the historical evidence is insufficient to determine
this" — that answer is a *correct* answer, and the study must score it as one.
Without that escape hatch the participants will confabulate, and the experiment
will measure their fluency rather than their understanding.

Five templates, each with the kind of evidence that settles it:

| # | Question shape | What settles it |
|---|---|---|
| 1 | "Why is this module split the way it is?" | The commit that split it, or the absence of one (it was never split — it grew). |
| 2 | "This logic looks redundant. What is it protecting against?" | A commit that added it, with a message or a test that names the case — or the honest answer "nothing in the history says". |
| 3 | "Why does this call site not use the obvious API?" | A commit showing the API arrived later, or a constraint that predates it. |
| 4 | "When did this constraint form, and what enforced it?" | A commit or a file's lifecycle: the rule appears at a specific version. |
| 5 | "If I change this now, what historical background do I need?" | A lifecycle plus a co-change pattern plus whatever the memories say. |

**Each question needs a ground truth established *before* the run, from a source
that is not the tool**: the project's own documentation, its CHANGELOG, its issue
references in commit messages, or — best — the actual behaviour of the code,
checkable by running a test. **The tool must never grade its own answers**; if
the ground truth is "what `explain` said", the experiment measures agreement with
itself and is worthless. **CONFIRMED** as a methodological requirement, and it is
the easiest thing to get wrong.

#### Control and treatment

- **Control:** git + source + the repository's existing documentation. The
  participant may use `git log`, `git blame`, `git show`, the code, and anything
  in the tree. This is a *strong* control — a competent developer with git is
  exactly what the tool claims to beat.
- **Treatment:** the same, plus CodeArchaeology (`analyze`, `ast`, `structure`,
  `file`, `hotspots`, `cochange`, `explain`). **The tool must not be demonstrated
  beyond a five-minute orientation**, or the experiment measures the
  facilitator's explanation.

#### Metrics

The primary endpoint must be declared before the run, or the pilot will be read
as confirming whatever it happens to show. **Declare: correct-and-evidenced
answers per question.** Everything else is secondary.

| Metric | How it is measured | Why it is here |
|---|---|---|
| **Correctness** | Scored against the pre-established ground truth: *correct* / *partially correct* / *wrong* / **correctly-uncertain**. | "Correctly-uncertain" must be a scored success; without it the study rewards guessing. |
| **Time to answer** | Wall clock per question, **capped at ten minutes**. A capped answer counts as not answered. | The comprehension claim is partly a speed claim. A cap is required or a stuck participant distorts everything. |
| **Evidence quality** | Did the participant name a specific commit, file version, or definition? Does the named evidence exist, and does it actually support the claim? | **This is the metric that separates understanding from guessing.** A right answer with no evidence is a lucky guess. |
| **Uncertainty calibration** | Ask for a 0–100 confidence per answer; compare with the correctness score. | The interesting signal is *overconfidence*. A tool that makes people confidently wrong is worse than one that makes them say "I don't know". |
| **Perceived usefulness** | A short post-hoc rating and two open questions. | **The weakest metric and it must be labelled as such** — self-report, politeness bias, and the participant knows what is being evaluated. |
| **Commands run** | Recorded by the facilitator, not by the tool (instrumenting the tool would be a code change). | A cheap proxy for whether the tool was actually used, and which parts. |

**Do not use answer accuracy alone.** A tool that makes a person answer faster and
more confidently while being *wrong* would score well on accuracy-plus-time and is
a product failure. Calibration is what catches it.

#### The Memory-specific experiment

The claim to test is narrow and worth testing separately: **Memory is a better
place for knowledge that cannot be derived from git than existing documentation
is.** The measurable difference is not *content* — it is **findability at the
point of need**.

- Pick one piece of knowledge that satisfies three conditions: it is **not
  derivable from the history**, it is **true**, and it is currently written
  *somewhere* (a comment, a docstring, a `CONTRIBUTING` note) or is known by a
  maintainer and written nowhere.
- **Condition 1:** the participant has the repository and its documentation, and
  must answer a question that depends on that piece of knowledge.
- **Condition 2:** the same, plus a memory stating it, written by the facilitator
  before the run (the participant did not write it — that is the newcomer case,
  which is the case that matters).
- **Measure:** whether they found it at all, and how long it took. The predicted
  mechanism is that documentation requires *knowing where to look* whereas the
  memory is surfaced by the tool at the commit being read — so the treatment
  should win on time-to-find, not on answer quality.
- **The falsification condition, stated in advance:** if the pilot shows no
  difference, then the value claim for Memory is unsupported, and the portability
  question in §3 becomes considerably less urgent. **This is the single most
  important sentence in this document**: Question B gates Question A. Building
  transport for knowledge that has not been shown to be worth carrying would be
  the same mistake the project's own rule against mid-phase features exists to
  prevent.

### 4.3 What this pilot cannot show

- **Nothing about a team.** Six people in two conditions says nothing about
  shared knowledge, review, or forks — the multi-person scenarios in §3 stay
  **UNKNOWN** after this pilot.
- **Nothing about long-term retention.** The Memory claim is about knowledge
  surviving *time*, and a same-day pilot cannot measure that. A real test of the
  Memory value proposition would need a return visit weeks later, which is a
  different and much more expensive study.
- **Nothing statistical.** With n≈6, a difference must be very large to be
  visible. Its absence proves nothing.

## 5. Memory Cold Start Audit

**The problem is real and it is arithmetic.** `explain` shows a memory only when
one exists that relates to the commit being read. An empty store means the
section is absent and the whole layer is invisible. Filling the store requires a
person to (a) know what a memory is, (b) have something worth stating, (c) type a
statement of up to 4,000 characters with a subject and optionally citations.
Nothing in the tool ever *asks*. **CONFIRMED.**

**But "the store is empty" is not the only cold-start failure, and the other one
is worse.** A store with three memories about one file is nearly as invisible as
an empty one, because `explain`'s section is capped at five and relates memories
to a commit by subject, path, definition or citation — a memory about a file
nobody is reading appears nowhere. So the cold start is not "zero memories"; it
is **"fewer memories than the reading surface needs"**, and it is a distribution
problem as much as a volume problem. **INFERRED** from the selection rule in
`memory_section.py` and the cap of 5.

**Therefore the question "does the cold start need AI?" has to be split in two:**

1. **Does something need to *trigger* the writing?** Yes. Nothing in the tool
   asks a person anything. **CONFIRMED.**
2. **Does the trigger need a model?** **No, and this is the finding.** The tool
   can already *see* the situations where knowledge is missing, deterministically:

| Observable gap | What the tool already holds | Why a person might have an answer |
|---|---|---|
| A definition was deleted and later restored | `definition_versions.change_type`, fingerprints, `end_lineno` | Restorations usually mean someone tried removing it and it broke something. |
| A file changed 200 times with nothing explaining why | `hotspots`, lifecycles | Churn without a stated reason is exactly the "why" git loses. |
| A commit's message is one word | `commits.message` | The reason existed; it was not written down. |
| A path's history shows a name change with no explanation | `lifecycle.py`, rename similarity | The rename's reason is not in the repository. |
| A file is always changed together with another, and nobody knows why | `cochange` | Coupling without a documented cause. |
| A definition carries a decorator or a guard whose purpose is not in the history | the AST layer | Defensive code whose reason was an incident. |

Every one of these is **derived**, which is the crucial property: the *gap* is
evidence, and the tool is allowed to derive evidence. Only the *answer* is
memory. **CONFIRMED** that all six observations are derivable from shipped
tables; **INFERRED** that a person, shown one, would often have something to say.

**The shape this implies — a question, not a draft** — is developed in §6,
because it is the answer to the AI-proposal question as well. In short: **the
tool asks; the person answers; the answer is wholly the person's.** That
satisfies "the model never writes memory" more strongly than a draft route,
because nothing a model wrote ends up in the stored statement — and it needs no
new epistemic category, because a question cannot be mistaken for a fact.

**Core First is satisfied by construction.** The gap detection is a query. The
question's phrasing can be a template. **A cold-start fix therefore does not
require a model, a network, or a new dependency** — which moves it out of the AI
question entirely and into the deterministic layer where the project's rules are
easiest to keep.

## 6. AI Proposal Analysis

### 6.1 The two candidate routes

**Route 1 — draft and confirm** (the brief's sketch):

```text
evidence → model → proposed statement → person reviews
        → accept / reject / edit / ignore → only accept produces memory
```

**Route 2 — ask and answer:**

```text
evidence → tool finds an unexplained gap → tool asks a question about it
        → person answers (or declines) → the answer is the memory
```

They differ in one thing, and it is everything: **in Route 1 the model's text can
end up in the store; in Route 2 it cannot.**

### 6.2 The five questions the brief asks, answered

**Can the AI propose a statement?** Mechanically yes — it can draft text. But
"candidate" is a status, and the v0.5 freeze is explicit that there is no
`candidate` state in the store: "nothing unconfirmed is persisted, so nothing
unconfirmed can be read, counted or mistaken for knowledge" (§8.1). So a drafted
statement would have to be marked *outside* the store — in the command's output,
in the prompt, in the rendering — which is doable but means the marking lives in
presentation rather than in the data. **Route 2 removes the problem instead of
managing it:** a question is not a candidate statement, so there is nothing to
mark.

**Can the AI auto-save a proposal, and where?** Three answers, and the trade is
sharp:

| Where | What it buys | What it costs |
|---|---|---|
| In the memory tables as a `candidate` state | Nothing new to build | **Refused by the freeze**, and correctly: unconfirmed rows would be readable, countable and mistakable for knowledge. |
| In a separate proposal table | Stability — the same proposal comes back next run — plus the ability to record rejections. | Something unconfirmed is persisted, which is the rule's letter; the table needs its own version stamp, its own lifecycle (accept / reject / expire), and an answer for "does a rejected proposal return?". |
| **Nowhere** — the proposal exists only inside the run that produced it | Keeps the rule exactly as written; costs nothing; needs no schema change. | **The same proposal cannot be reproduced.** A model is not deterministic ("one input can produce two answers"), so "not now" means "never the same proposal again". |

The third row is the v0.5-consistent answer, and its cost is real: a person who
declines is not declining *a* proposal, they are declining *an instance* of one.
**INFERRED** that for Route 2 this cost largely disappears, because a *gap* is
deterministic even when a *sentence* is not — the tool can ask the same question
tomorrow, and only the wording changes.

**What happens after a rejection?** If nothing is stored, it returns every run,
which trains people to ignore proposals — the classic failure of every
"AI suggests" feature. If rejections are recorded, the record is knowledge.
**The clean distinction:** *rejecting a proposal's content* ("X is not a
constraint") is a statement a person made about the project and is therefore a
memory — an invalidated one, or a new one superseding the old. *Rejecting a
proposal as uninteresting* ("not now, stop asking") is a statement about the
tool's behaviour, not about the project, and is **not** a memory; it belongs in
`meta` as a preference, or nowhere at all. Conflating the two would put UI state
into the knowledge layer. **INFERRED.**

**After a human edit, whose memory is it?** The v0.5 rule already answers the
author question: the author is the person whose act it was ("the person running
the command is the one whose act it is"), and when the tool cannot determine one
it records `unknown` rather than inventing an author. So the author is the human
— but **the record then loses the fact that a model drafted it**, and that is a
real loss for a reader judging the statement. The missing field is not `author`,
it is **`origin`**.

**CONFIRMED defect-in-waiting:** the `memories` table has **no column** recording
that a statement began as a model draft. The v0.5 design promised the opposite in
two places — §4.3, "the memory records that this happened", and §5, "with the
interpretation's origin recorded beside it" — and the implementation does not
have it, because the route does not exist so nothing needs recording. That is
consistent, not wrong. But it means **the proposal route requires
`memory_schema_version` 1 → 2**, and a schema bump after memories exist is a
migration. If the user believes Route 1 is likely, the decision to add a nullable
`origin` column should be taken *deliberately and early*, not discovered by
whoever builds the route.

**Must a proposal carry evidence, and is that evidence the AI's or the tool's?**
The existing machinery answers this cleanly and needs no extension. A memory's
citations are checked **at admission** and **re-checked at read**, and the tool —
not the model — performs both. So a proposal's citations are resolved by the tool
before the proposal is shown; a proposal whose citations do not resolve is not
shown, exactly as a memory whose citations do not resolve is reported rather than
repaired. The model's *observations* are not evidence and are never stored as
such — which is v0.4's rule unchanged ("a memory is never citable as evidence"
costs nothing to enforce because memory is not in the bundle). **CONFIRMED** that
`memory_checks.py` performs exactly this check; **INFERRED** that it is reusable
unchanged for proposals.

### 6.3 What is worth proposing

The brief lists candidate triggers and is right to insist they are candidates,
not facts. The list, with what the tool can actually establish about each:

| Trigger | Derivable today? | Strength as a question |
|---|---|---|
| A constraint that is long-lived and unexplained | Partly — a stable file with no memory and high age is derivable; "constraint" is not. | **Strong**, if phrased as "this has not changed in four years and nothing says why". |
| An unusual history pattern | Yes — deletions, restorations, renames, churn. | Strong. |
| An API repeatedly avoided | **No.** The tool has no call graph and no call sites; this is not derivable in v0.x. | Not available. |
| Code deleted and later restored | **Yes** — `definition_versions` with fingerprints across versions. | **Strongest single trigger.** A restoration is a decision that was reversed, and the reason is almost never in the message. |
| A repeated workaround | **No** — needs semantic similarity, which the project explicitly does not do ("AST 相似度推断文件身份" is out of scope). | Not available. |
| A commit message inconsistent with long-term behaviour | Partly — the message is stored; "inconsistent" needs a judgement. | Weak. The judgement is the model's, which is exactly the thing that should not be durable. |
| A high-impact, low-explanation change | Partly — impact is derivable (lines, files, co-change); explanation is not. | Moderate. |

**The honest reading:** of the seven triggers the brief lists, **two are fully
derivable today, three are partly derivable, and two need capabilities the
project has deliberately excluded.** That is enough to build a question route on
— the restoration trigger alone would find real cases in any long-lived
repository — and it is not enough to build a general "the AI notices things"
feature. **CONFIRMED** as a survey of what the shipped tables hold; **INFERRED**
as an assessment of each trigger's value.

### 6.4 The conclusion

**Do not build AI proposals. Build the deterministic question route, if the cold
start is judged a problem.** The reasoning, in order of weight:

1. **It satisfies the hard rules more strongly.** In Route 2 nothing a model
   wrote can reach the store, so rule 4 is a statement about what the system
   *is* rather than about what it refrains from doing — the same style of
   guarantee `provider.py`'s import list already provides. No `origin` column is
   needed, no `candidate` status, no new table.
2. **It is Core First by construction** — the gaps are queries, the questions are
   templates, and the whole route runs with no network. The AI-proposal question
   can then be deferred without deferring the cold-start fix.
3. **The cost of being wrong is asymmetric.** A bad question costs a person five
   seconds. A bad draft costs a durable statement that *reads* as knowledge, and
   the design already names the residual risk this creates ("a person can be
   persuaded by a wrong draft — named, not engineered away").
4. **It fits the project's own diagnosis.** The v0.5 design says the proposal
   route "is where the self-reinforcement risk lives, and it needs its own unit
   and its own UX decisions". Route 2 has no self-reinforcement loop to speak of,
   because the model never supplies the content.

**What this defers rather than decides:** whether a model may ever *draft* a
memory. That remains open, and it should stay open until the question route has
been used enough to show what people actually write down. **UNKNOWN** whether
people would answer a tool's questions at all — which is itself a cheap thing to
find out, and the pilot in §4 can carry it as a secondary observation.

## 7. Interpretation Persistence Analysis

### 7.1 The state today

**Nothing a model writes is stored.** The v0.5 freeze calls this "one v0.4 open
question **is** answered here: an explanation is still never stored" — and the
*reason* given in v0.4 is a consequence, not a principle:

> "An explanation is printed and read; it is not written back to the database, so
> no interpretation can later be found by a command that treats rows as facts."
> — `docs/v0.4-problem-definition.md` §12

The related reason, from the context-budget unit: derived-per-run "is what keeps
a rule change from leaving rows nobody can correct". **CONFIRMED** as the stated
reasoning.

**What is missing from the record:** the *value* argument for storing was never
made and never refused. There is no comparison of options anywhere in the six
v0.4 documents — the subagent search found none — and the v0.5 freeze answers the
question by restating the decision rather than by arguing it. The decision may
well be right. **It is under-argued, and that is different from being wrong.**

### 7.2 Why this must be settled before v0.6, and the honest limit on that claim

The roadmap's v0.6 row is "AI-assisted change analysis and replay". **Replay**
implies reproducing or re-examining a past analysis. If nothing is stored, there
is nothing to replay; you can only re-run, and a re-run gives a different answer —
the docs say so in as many words ("one input can produce two answers"). So v0.6's
central verb may be unbuildable under the current rule.

**But that argument rests on a word nobody has defined.** "Replay" appears once,
in a roadmap table, and nowhere else in the tree. It could mean *replaying the
change* (re-examining a commit's changes, which needs no stored explanation at
all) or *replaying the explanation*. **UNKNOWN** — and this is the first thing to
settle, because the persistence decision follows from it rather than preceding
it.

**The sequencing conclusion is nevertheless firm:** the persistence question must
be *decided* before v0.6 *starts*, even if the decision is "still not stored".
Because if it is ever to be stored, the storage shape is a schema change, and
schema changes are cheapest before there is data to migrate. **INFERRED.**

### 7.3 The five options

| Option | What it stores | What it buys | What it costs |
|---|---|---|---|
| **A — Never store** (today) | nothing | The contract stays clean; no stale, uncorrectable rows; no interpretation can be mistaken for a record. | No replay, no audit trail, no comparison of two readings of the same commit, no way to see whether an answer *changed* when the tool changed. |
| **B — Store the raw output** | the model's text | Full auditability. | Breaks the contract at its weakest point: a stored answer is indistinguishable from a record, and it is not reproducible, so the store accumulates text nobody can regenerate or check. |
| **C — Person confirms → Memory** | the *person's* statement | Already shipped in spirit (this is the proposal route). | **This is not a persistence path for interpretations.** What is stored is the person's statement; the model's text is not stored even then. Worth stating plainly because it is easy to mistake for option D. |
| **D — A separate Interpretation Artifact table** | the answer, labelled, never evidence, with its own lifecycle | Replay becomes possible; two readings of one commit can be compared. | A new durable class, a schema bump, and a new answer to "how long does an artifact live" — plus it re-creates the "a wrong reading becomes durable" risk the design names. |
| **E — Store the run's provenance, not its text** | the bundle hash, provider, model id, prompt version, timestamp | Answers "was this explanation produced from the bundle I have now?" — which is a *replay* capability — without storing a single sentence. | Requires nothing new conceptually: the bundle is deterministic and byte-identical, so a hash of it is a real, checkable identity — the project's own Evidence First rule applied to the run. |

**Option E deserves the most attention**, because it is the one that fits the
project's existing principles rather than trading against them. The evidence
bundle is the only deterministic thing in the AI layer — `test_memory_boundaries`
holds it byte-identical with and without memories, and the whole selection
discipline exists to keep it reproducible. A hash of it is therefore a *fact*, not
an interpretation, and storing facts is what this project does. It would let a
person ask "is this explanation stale?" and get an answer the tool can defend.
**INFERRED**, and it needs the user's ruling.

**What none of the five options solves:** whether an explanation *should* be
compared across time at all. That is a product question about v0.6's purpose, and
it is upstream of all of this.

### The three concept debts, assessed

The brief that produced this audit names three items as concept debts numbered
12, 13 and 14. **Those numbers are not in this tree** — searched for across every
`*.md` and `*.py`, and the only numbered lists are `PROGRESS.md`'s "Next" items
and its trap list, neither of which contains these three. The numbering comes
from outside the repository, so the three are addressed here by name and the
numbering is not carried forward. Each was checked against the tree before being
assessed, and one of the three turned out to be **smaller than its reputation**.

#### 1. The memory boundary — "if the tool can derive it, it is not memory"

**Is the definition too narrow?** **INFERRED: no**, and the argument is that the
three kinds partition on two properties that are exhaustive together:

| | Who produces it | Can it be re-derived |
|---|---|---|
| Historical fact | the tool, from git or an AST | yes, byte for byte |
| Model interpretation | a model, per run | no |
| Developer memory | a person | no |

A fourth category would need a **fourth producer** — some other entity that can
make a statement about a repository — and there is none. So the partition is
complete, and adding a category would mean adding a producer, not a label.

**The candidates that look like they need a fourth kind, and where each actually
goes:**

| Candidate | Where it belongs | Why |
|---|---|---|
| A fact the tool *could* derive but only at great cost (a 200,000-commit walk) | The **cache**. | Storing a derivation as knowledge is the exact mistake the rule exists to prevent; the answer to "expensive to derive" is a faster derivation, not a new category. |
| A convention the team follows but nobody has written down | Memory — the moment someone states it. | The gap is that nothing **prompts** the statement, which is §5's cold start, not a missing category. |
| A decision and the alternatives that were rejected | Memory. | Not derivable, and a person can state it. |
| A machine-readable project fact that is not in git (the pinned deploy target) | Memory. | Same. |
| A plan, or a prediction ("we will split this next quarter") | **The one real gap** — and it is a wording question, not a category. | It is stated by a person, it is about the project, it is not derivable, and `supersede` / `invalidate` are exactly how a plan ends. Read literally, the definition already admits it; what the tool has no place for is a statement whose *subject* does not exist yet. |

**Verdict: do not add a knowledge category.** The definition is not too narrow;
the missing thing is a **trigger**, which is the same conclusion §5 reaches from
the other direction. **INFERRED** — and the brief asked for the opposite
conclusion to be considered seriously, so it is recorded as considered and
rejected rather than skipped.

#### 2. `confidence` — the name, and why the damage is smaller than it looks

**What it actually is, checked in the tree.** `explanation.Confidence` is a
frozen dataclass holding **`observed_changes: int` and `commits: tuple[str, ...]`**
(`explanation.py:207-216`). It is derived by the validator from the candidate's
`based_on` and never reported by the model; a `confidence` arriving in a model's
answer is **refused**, not dropped, with a message saying the model does not
write it. Three tests hold that: the derivation
(`test_validation.py::test_the_confidence_is_counted_from_what_the_candidate_rests_on`),
a per-reason refusal, and a top-level refusal. **CONFIRMED.**

**Does the name risk being read as a probability?** The name invites it — and
then the **shape refuses it**. In `explain --json` the value is an *object*
(`{"observed_changes": 3, "commits": [...]}`), not a number, so a program writing
`reason["confidence"] > 0.8` gets a `TypeError` rather than a plausible wrong
answer. Both READMEs call it "the count the tool made, not a number the model
chose" (the Chinese says the same). And the renderer prints the sentence the
schema document requires — that it "measures how much evidence there is, not how
good the reason is".

So the honest assessment is **counterintuitive**: the name is the loaded kind of
name, but three other things — the object shape, the two READMEs, and the
rendered warning — are already doing the work the name should do. The residual
risk is narrow: a reader who sees the **key name alone**, in JSON, without the
documentation. **INFERRED**, and it is a smaller debt than its reputation
suggests. **CONFIRMED** that the shape and the refusals are as described.

**If it were renamed — the candidates, and the cost.**

| Candidate | Why it is better | Why it might not be |
|---|---|---|
| `support` | A noun meaning "what it rests on", not "how sure we are". Self-describing, and the warning sentence becomes optional rather than load-bearing. | Slightly vague on its own. |
| `evidence_count` | Literally what it is: a count. Cannot be misread. | Loses the `commits` half, which is part of the value. |
| `rests_on` | Matches the existing `based_on`, so the pair reads as one idea: what it rests on, and how much. | A third near-synonym in a schema that already has `based_on`. |

**Migration cost, itemised (nothing is stored, so there is no data migration):**
the JSON key under `explain --json` — **a program-visible break**; the schema
document (`docs/v0.4-explanation-schema.md` §8, which is a *frozen* document and
would need a recorded amendment); the validator's refusal message; the renderer's
sentence; one prose line in each README; and four tests
(`test_explain.py:605` pins the value, `test_validation.py` pins the derivation
and both refusals). No schema version moves, because nothing is stored.
**CONFIRMED** as the full list.

**Recommendation (INFERRED):** rename it **only alongside another
`explain --json` change**, and decide *before* v0.6 adds consumers. A standalone
rename would spend a contract break to fix a name whose damage is already
mitigated three ways. If no other JSON change is planned, the honest option is to
keep the name and keep the warning — and to record that the decision was made
deliberately rather than by inertia.

#### 3. Interpretation persistence

Assessed in full in §7. The short form for this list: **it is the one of the
three that is genuinely blocking**, because v0.6's own name contains a verb
("replay") that may be unbuildable under the current rule, and because the
decision has been deferred through two releases by restating it rather than by

## 9. Strategic Risks

Ordered by how much they would cost if they materialised.

1. **The value claim has never been tested, and the project's own standard
   exposes it.** Every other claim in this tree is traceable; this one is not.
   The risk is not that the tool does not work — it does — but that a fifth
   release is built on an unexamined premise. **CONFIRMED** as an absence.
2. **Three independent scenarios — a newcomer, a backup, a move — point at the
   same missing capability.** Individually each is arguable. Together they say
   the memory layer's custody model is narrower than its content model, and the
   gap shows up at the moments the feature matters most. **CONFIRMED** as
   properties; **INFERRED** as a product risk.
3. **A wrong v0.6 definition.** "AI-assisted change analysis and replay" is
   undefined, and it may require the interpretation-persistence decision that has
   been deferred through two releases. If it is started without a definition, the
   project will do what it has correctly refused to do four times: build before
   freezing. **UNKNOWN** until the phase is defined.
4. **Secrets, if memory becomes portable.** A memory is free text with no
   detection and no redaction, and the docs say the tool "will not pretend to"
   check. The moment memories travel — especially into a public repository — the
   blast radius changes permanently, because git history is forever.
   **CONFIRMED** as an absent protection; **INFERRED** as a risk that scales with
   portability.
5. **One user, and the roadmap is built from one person's model of a user.**
   Every "the user's call" in `PROGRESS.md` is the same person. That is fine for
   a tool being built for its author; it is a risk for a tool whose newest layer
   only pays off with more than one person. **CONFIRMED** (0 forks, 0 issues, 2
   stars).
6. **Benchmark-driven priorities.** The two items the project itself calls "the
   known debt" are measurable at a scale no user reaches. Measuring at 100,000
   rows is good practice; letting the measurement set the roadmap is not.
   **CONFIRMED** from the published table.
7. **The memory section can be silently small.** `explain` caps the section at
   five and counts what it dropped — but a *reader* who never sees a memory
   because it is about a file this commit did not touch has no signal at all that
   knowledge exists elsewhere. **CONFIRMED** as the selection rule; **INFERRED**
   as a discoverability risk, and it is the same shape as the cold-start problem
   in §5.

## 10. Recommended Priority

**Subject to the user's ruling. Nothing here is started.**

**First — run the understanding pilot (§4), before building anything.** It is
the cheapest item on this list, it gates the largest question, and its result
changes what everything after it is worth. If the pilot shows no difference
between git alone and the tool, then the portability question, the cold-start
question and the P1/P2 question all become considerably less urgent — and the
project will have learned that for the cost of a day.

**Second — define v0.6's question, in a document, before any v0.6 code.** The
project's own rule, followed four times, is that a phase starts with a freeze.
"AI-assisted change analysis and replay" is one row of a table. It needs a
problem definition in the shape of `docs/v0.4-problem-definition.md`, and its
first output will be the answer to §7 (does anything get stored?) — because
"replay" cannot be designed around an undefined persistence rule.

**Third — decide memory portability (§3), with Option D as the recommendation
and the schema's UUID decision as the argument.** If the pilot supports the value
claim, this is the highest-value unfinished work in the tree: three scenarios
point at it, the data model already paid for it, and it is additive. Design the
export format so Option C stays possible; do not make the tool write into the
repository.

**Fourth — the two small real items, which are cheap and user-facing:** the
`--db` semantics question (it must be answered before import is designed, §8.8)
and a macOS CI job (§8.6, an untested branch).

**Fifth — the cold-start question route (§5, §6.4), if the cold start is judged
a problem.** Deterministic, Core First, no new category. It should be designed
after the pilot, because the pilot's secondary observation — do people answer a
tool's questions — is what decides whether it is worth building.

**Not now — P1 and P2.** Reversed from the recorded order, with the measurement
as the reason: they are real at a scale only import creates, so they follow the
portability decision rather than preceding it.

**Not now — AI proposals, in any form.** §6.4.

7. **Whether the tool should ever write to the repository.** Currently a flat no,

   anyone, including its author. **CONFIRMED** as a fact; **UNKNOWN** what it
   implies.

   weight to give the absence of feedback.
10. **Whether the memory definition's "if the tool can derive it, it is not
    memory" is too narrow.** Assessed in this audit as **not** too narrow — the
    three kinds partition on who produced a statement and whether it can be
    re-derived, which is exhaustive, and a fourth kind would need a fourth
    producer. The real gap is a *trigger*, not a *category*. Marked **INFERRED**,
    and the brief asked for the opposite conclusion to be considered seriously,
    so it is recorded as considered and rejected rather than skipped.
