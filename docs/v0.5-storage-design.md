# v0.5 storage design freeze — how a memory is kept

## Status

**Design freeze. Nothing here is written to any file, and no table is created.**
This is Unit 2 of v0.5. Unit 1 (`docs/v0.5-design.md`) said what a Developer
Memory *is*; this says how one is kept in SQLite without ever being mistaken for
evidence, and what happens to it when the evidence around it is rebuilt.

Written on 2026-10-06 against `f27ebbf` (version 0.4.0, schema 4, 660 tests,
`main` level with `origin/main`). The DDL below is the freeze; it is written in
this document and nowhere else.

## The tree it was written against, and what reading it changed

The storage path was read line by line before any of this was decided, and four
things in it decide parts of the design rather than being decorated by it.

| Read | Found | What it decides here |
|---|---|---|
| `cache.py` | `database_path` is a digest of the resolved repository path, **casefolded on Windows**, 16 hex characters, in the cache directory | §2: the digest is a filename convenience, not an identity; memory must not invent a second identity |
| `analysis.py` | `open_analysis` refuses a database whose `meta.repository_root` is not the resolved path of the repository being read — **the evidence side already isolates by repository** | §2, §8: memory inherits that rule instead of writing a new one |
| `analysis.py` | `analyze` calls `prepare_database`, then `write_commits`, then `set_meta("repository_root")` — **it takes a database over** | §7, §8: the takeover is the case memory has to survive, and it is where foreign rows come from |
| `storage.py` | `prepare_database` rebuilds by dropping every table in `TABLES`, then `create_schema` stamps the version; `connect` sets `PRAGMA foreign_keys = ON` | §7: the exception is enforced by the table list, not by a condition; §3: a foreign key into the evidence tables would block a rebuild |
| `tests/test_storage.py`, `tests/test_ast_storage.py`, `tests/test_analyze.py` | column lists are pinned by tests; `test_a_database_of_schema_version_two_is_rebuilt` asserts "rebuilt, not migrated"; a comment records the trap that `CREATE TABLE IF NOT EXISTS` cannot add a column | §3, §7, §12: the memory column list gets the same test; the rebuild rule is preserved for evidence and **replaced** for memory |

Two facts worth stating before the design, because they are what "absolute
isolation" has to work with:

- **A database already belongs to one repository.** `open_analysis` enforces it
  on every read, and `analyze` rewrites it on every write. Memory does not need
  to invent an identity; it needs to keep that one honest when the evidence
  around it is thrown away.
- **The evidence side is allowed to destroy itself.** `analyze` on a database
  that holds another repository's commits replaces them; a schema bump drops
  every evidence table. That is correct for a cache and fatal for memory, and
  every decision below follows from the difference.

## 1. Memory identity

**A memory is identified by a UUID, in the canonical text form, generated when
it is admitted.**

```text
memory_id  TEXT  PRIMARY KEY      e.g. 3f2a9c1e-8b47-4d6a-9f10-2c5e7a0b41d9
```

**Why a UUID and not the rowid.** The rowid is an implementation detail of one
file: it is not portable, it is assigned by insertion order, and an export and
re-import — the sharing path Unit 1 §21.1 already knows will be wanted — would
have to renumber it, which means every `superseded_by` link would have to be
rewritten. A UUID is the same value in every database it is copied into, so a
lifecycle link survives the copy. It is generated by the standard library
(`uuid.uuid4`), which keeps the no-dependency rule.

**Why not a content hash.** Two people can write the same sentence, and a
correction must be a new identity even when the text is identical (§5). A
content-addressed id would collide exactly where the design needs two rows.

**Why not a time-ordered id (ULID or UUIDv7).** Ordering is already carried by
`admitted_epoch`, which is a fact the tool sets and can explain. A second
ordering source would be a second thing to disagree with it.

**Stability.** The id is assigned once, never changes, and is never reused — no
act creates a second memory with an existing id, and there is no delete. What
changes over a memory's life is its `state`, and the id is what the state
changes are recorded against.

**How it is addressed.** Commands take the id or any unique prefix of it, the
way every command in this tool already takes a commit sha — `memory show 3f2a`
resolves if exactly one memory starts with `3f2a`, and an ambiguous prefix is
refused rather than guessed at. That is the same UX the project has used since
v0.1, and it means a person never has to copy 36 characters to read one memory.

## 2. Repository ownership, and how isolation is enforced

### 2.1 The identity is the path, and it is the one the evidence side already uses

Every memory row carries:

```text
repository_path  TEXT  NOT NULL     str(Path(repository_root).resolve())
```

This is **the identical string** that `meta.repository_root` holds and that
`open_analysis` compares against. Memory does not compute a second identity, and
it does not hash the path: a report has to be able to *name* the repository it is
talking about, and an adopt act has to be able to be typed by a person.

The rules that follow, in one place:

1. **One database holds memories for one repository.** The first memory written
   into a database fixes its repository; a later write from a different path is
   refused (§8).
2. **The comparison is exact string equality**, the same comparison
   `open_analysis` makes. The memory layer introduces no third rule. (The cache
   filename casefolds on Windows and the meta comparison does not; that asymmetry
   is pre-existing, it is recorded in §13, and it is not memory's to fix.)
3. **A row is never rewritten to match a repository.** `analyze` may change
   `meta.repository_root`; it may not change a memory.

### 2.2 What was researched, and what was rejected

| Candidate identity | Verdict | Why |
|---|---|---|
| **The resolved absolute path** | **Adopted** | Already the evidence side's identity; human-readable; nameable in a report and an act. |
| The cache filename's digest | Rejected | A digest cannot be read, compared to a path a person typed, or reported usefully. It stays what it is: a filename. |
| The root commit sha | Rejected | Breaks on rebase and squash, is absent or wrong in a shallow clone, and differs between two clones of one project — every one of those is a case where the *person* knows the repository is the same and the tool would guess. |
| The remote URL | Rejected for v0.5.0 | Absent for local-only repositories (Local First), changeable, and it would silently join two clones — a sharing decision that belongs to the export unit, not to a side effect of a stored field. |
| A repository UUID written into `.git/` | Rejected | The tool never writes to the repository. |
| A UUID in `meta` as the owner, with rows carrying no path | Rejected | It cannot survive the takeover: after `analyze` sets `meta.repository_root` to another repository, the rows would have no marker of their own and two projects' memories would be indistinguishable. Per-row is what makes mixing *detectable*. |

### 2.3 The four cases, decided

| Case | What happens |
|---|---|
| **A repository and its own database** | `open_analysis` matches, every row's path matches the current root, nothing is filtered. The normal case. |
| **The repository moves** | The digest changes, so the tool looks for a new, empty database and the memories appear to vanish. They are still in the old file. Recovery is explicit: point `--db` at the old file and run `memory adopt --from <old path>` (§8.3), which is a person saying "this is the same project at a new path". The tool never infers it. |
| **A fork** | A different checkout, therefore a different path, therefore a different database. Memory does not follow a fork, and a fork's history is not the original's, so a copied memory's citations may not resolve — which is reported, not repaired. Following it deliberately is export/import, a later unit. |
| **`--db` shared across repositories** | Decided in §8: the write is refused, the read is filtered and reported, and `adopt` is the way through. |

## 3. The schema

### 3.1 The freeze, as DDL

Two tables. **They are not in `TABLES`** — the evidence table list — which is the
whole of the mechanism that keeps them across a rebuild (§7). No evidence table,
column, index or constraint is touched by any of this, and `SCHEMA_VERSION` does
not move (§7.2).

```sql
-- Frozen in this document. Not written to any file in this unit.

CREATE TABLE IF NOT EXISTS memories (
    memory_id          TEXT    PRIMARY KEY,
    repository_path    TEXT    NOT NULL,
    statement          TEXT    NOT NULL
                               CHECK (length(trim(statement)) > 0),
    author_name        TEXT    CHECK (author_name IS NULL
                                      OR length(trim(author_name)) > 0),
    author_email       TEXT    CHECK (author_email IS NULL
                                      OR length(trim(author_email)) > 0),
    admitted_at        TEXT    NOT NULL,
    admitted_epoch     INTEGER NOT NULL,
    subject_kind       TEXT    NOT NULL
                               CHECK (subject_kind IN ('repository', 'path',
                                                       'definition', 'commit')),
    subject_path       TEXT,
    subject_qualname   TEXT,
    subject_commit_sha TEXT,
    since_commit_sha   TEXT,
    since_date         TEXT    CHECK (since_date IS NULL OR since_date GLOB
                                      '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'),
    state              TEXT    NOT NULL
                               CHECK (state IN ('active', 'superseded',
                                                'invalidated')),
    ended_at           TEXT,
    ended_epoch        INTEGER,
    end_reason         TEXT,
    superseded_by      TEXT    REFERENCES memories(memory_id),

    CHECK (
        (subject_kind = 'repository'
             AND subject_path IS NULL AND subject_qualname IS NULL
             AND subject_commit_sha IS NULL)
     OR (subject_kind = 'path'
             AND subject_path IS NOT NULL AND subject_qualname IS NULL
             AND subject_commit_sha IS NULL)
     OR (subject_kind = 'definition'
             AND subject_path IS NOT NULL AND subject_qualname IS NOT NULL
             AND subject_commit_sha IS NULL)
     OR (subject_kind = 'commit'
             AND subject_path IS NULL AND subject_qualname IS NULL
             AND subject_commit_sha IS NOT NULL)
    ),
    CHECK (since_commit_sha IS NULL OR since_date IS NULL),
    CHECK (state = 'active'
           OR (ended_at IS NOT NULL AND ended_epoch IS NOT NULL)),
    CHECK (state <> 'active'
           OR (ended_at IS NULL AND ended_epoch IS NULL
               AND end_reason IS NULL AND superseded_by IS NULL)),
    CHECK (state <> 'superseded' OR superseded_by IS NOT NULL),
    CHECK (state <> 'invalidated'
           OR (end_reason IS NOT NULL AND length(trim(end_reason)) > 0)),
    CHECK (superseded_by IS NULL OR superseded_by <> memory_id)
);

CREATE TABLE IF NOT EXISTS memory_citations (
    memory_id TEXT    NOT NULL REFERENCES memories(memory_id) ON DELETE CASCADE,
    position  INTEGER NOT NULL,
    kind      TEXT    NOT NULL
                      CHECK (kind IN ('commit', 'file', 'definition',
                                      'range', 'cochange', 'absence')),
    ref       TEXT    NOT NULL CHECK (length(trim(ref)) > 0),
    PRIMARY KEY (memory_id, position),
    UNIQUE (memory_id, kind, ref)
);

CREATE INDEX IF NOT EXISTS memories_repository
    ON memories (repository_path, admitted_epoch);
CREATE INDEX IF NOT EXISTS memories_subject_path
    ON memories (subject_path);
CREATE INDEX IF NOT EXISTS memories_superseded_by
    ON memories (superseded_by);
CREATE INDEX IF NOT EXISTS memory_citations_ref
    ON memory_citations (kind, ref);
```

### 3.2 The columns, one rule each

| Column | Rule |
|---|---|
| `memory_id` | §1. Immutable. |
| `repository_path` | §2. Required — a memory always belongs to a checkout. |
| `statement` | The author's words, immutable (§5). Non-empty after trimming: an empty memory is a row with nothing in it. Maximum length is checked by the act, not by the schema (§3.5). |
| `author_name`, `author_email` | The identity the tool could determine, from the environment's git configuration, or NULL when it could not. Two columns rather than one rendered string, matching `commits`, so a later reader gets the parts. NULL renders as "unknown" and is never guessed at. |
| `admitted_at`, `admitted_epoch` | The same pair the commits table keeps: ISO text with the offset the machine had, plus the integer that sorts across offsets. §6. |
| `subject_kind` + the three subject columns | §3.3. |
| `since_commit_sha`, `since_date` | §6. At most one of the two. |
| `state`, `ended_at`, `ended_epoch`, `end_reason`, `superseded_by` | §5. |
| (`memory_citations`) | §4. |

### 3.3 The subject is structured, not a string

The subject is one of four kinds, and each kind fills exactly the columns it
needs — enforced by the CHECK rather than by the writer, so a row that says
`definition` without a path cannot exist:

| `subject_kind` | `subject_path` | `subject_qualname` | `subject_commit_sha` |
|---|---|---|---|
| `repository` | NULL | NULL | NULL |
| `path` | the path | NULL | NULL |
| `definition` | the path it is in | the qualified name | NULL |
| `commit` | NULL | NULL | the sha |

**Why structured rather than one text form.** A subject is queried, not just
printed: `explain` asks "which memories are about one of the paths this commit
touched", and a file's earlier names count, so the query joins the subject to a
set of paths. A composite string would need `LIKE` or parsing, and neither can
use an index. This is the opposite decision from v0.4's citation forms, and
deliberately so: a citation is *compared for equality* against a known set, and a
form string is exactly right for that; a subject is *looked up by*, and a column
is right for that.

**Why `definition` carries the path too.** A qualified name alone is ambiguous
across files, and v0.3's identity rule is already "a definition is its kind and
qualified name *within one version of one file*".

**Why `repository` is a subject kind rather than "no subject".** A memory like
"we do not add runtime dependencies casually" is about the project, and it has to
be storable, findable and shown — as the least specific subject, ordered after
the specific ones when a commit is read (Unit 1 §15.3).

### 3.4 What is deliberately absent from the schema

| Absent | Why |
|---|---|
| **Any foreign key into the evidence tables** | A rebuild deletes commits (`write_commits` removes the ones git no longer has) and drops whole tables. An FK with `ON DELETE CASCADE` would delete memories when the history is rewritten; an FK without it would make `analyze` fail on a repository whose history moved. Neither is acceptable, and `connect` turns foreign keys on, so this is a live constraint and not a formality. A citation is a value, checked at admission and re-checked at read (§4.3) — a historical reference, not a live link (Unit 1 §7.1.6). |
| `has_citations`, `citation_count`, `supersedes_count` | Derivations of rows that are right there. Storing them would be two places for one fact, free to disagree — the rule `storage.py` already states for identities. |
| A memory type / kind column | Unit 1 §14 froze the taxonomy out of v0.5.0. |
| A stored `candidate` state | Unit 1 §8.1: an unconfirmed draft is never persisted, so it cannot be a state of a stored row. |
| A producer marker (`parsed_at_version`'s analogue) | The AST tables record who parsed a blob because a change of parser invalidates the rows. A memory is not a derivation, so there is no producer whose change would make it stale. The *shape* is versioned instead (§7.2). |
| An events / audit table for the acts | The project's model is a snapshot, not a change log (v0.3 rule 1). A memory's whole history is its row: `admitted_at`, `ended_at`, `end_reason`, `superseded_by`. |
| `deleted`, `archived`, any soft-delete flag | Unit 1 §8.1: no delete, no archive. |
| A `repository_digest` | §2.2: the digest is a filename. |

### 3.5 The statement's length

**The act caps the statement at 4,000 characters** — the same constant
`selection.py` already uses for a commit message, and the same reasoning: it is
the longest thing a model is shown of one item, and a memory is a paragraph, not
an essay. The cap is enforced when the memory is admitted, so no row in the table
can be too long, and the view that sends memories to a model never has to
truncate a statement — **a half-statement is a different claim**, which is the
same reason a silently truncated diff is forbidden.

**The view caps the section by count and drops whole memories** (Unit 1 §15.3),
never by cutting a statement. Every dropped memory is counted in the `selection`
block, as v0.4's view does.

## 4. Provenance

### 4.1 Zero to many citations, and absence that speaks

```text
memory ──┬── subject                     required, exactly one kind (§3.3)
         └── 0..N memory_citations       optional, ordered by position
```

- **No citation rows is the statement "no evidence was attached."** Nothing is
  written to spell it out, exactly as a deleted definition gets no row: the
  absence is the evidence, and the reader is told it in words.
- **Three states are rendered differently**, and running any two together is the
  failure this section exists to prevent:

| The state | What the reader is told |
|---|---|
| No citation rows | "no evidence attached" |
| Citations that resolve | each citation, with what it names |
| Citations that no longer resolve | each citation, marked as no longer resolvable, and never dropped from the display |

### 4.2 The vocabulary is v0.4's, unchanged

The six kinds and their forms are `explanation.py`'s, so the whole tool points at
evidence in one way:

| Kind | Ref form | Resolved against |
|---|---|---|
| `commit` | a sha (a unique prefix is accepted) | `commits` |
| `file` | a path | `commit_files.path` or `.old_path` |
| `definition` | a qualified name | `definition_versions.qualname` (any path) |
| `range` | `<path>:<start>-<end>` | the diff of a commit the memory also cites |
| `cochange` | `<path> -> <partner>` | the co-change analysis for `<path>` |
| `absence` | one of the four kinds (`merge_no_diff`, `parse_failed`, `no_version_stored`, `not_in_this_commit`) | the context builder's own list |

Two of these are weaker than the rest, and the document says so rather than
implying otherwise: a `definition` citation is resolved as "a definition with
this name appears somewhere in this history", because a memory is not about one
version; and a `range` citation has no meaning without a commit, so **a memory
that cites a range must also cite the commit it is a range of** — the act refuses
one without the other, with a message saying why.

### 4.3 Checked twice, repaired never

- **At admission**, every citation is resolved against the store, and an
  unresolvable one is refused with a message naming it and what would make it
  resolvable ("run `archaeology ast` first" when the definitions are not stored
  yet). A memory is admitted only with citations that meant something when it was
  written.
- **At read**, the same checks are re-run and their outcome is reported. The
  cheap kinds (`commit`, `file`, `definition`) are re-checked everywhere; the
  expensive ones (`range`, `cochange`) are re-checked by `memory show`, and a
  list that skipped them says so on the row rather than implying they were
  checked.
- **A citation is never repaired, rewritten or dropped.** A commit that a
  rebase removed stays in the citation and is reported as unresolvable — the
  memory is not a cache and does not follow the repository (Unit 1 §7.2).

### 4.4 The direction, once more, because it is easy to get backwards

`memory → evidence` is allowed: a memory cites commits, paths and definitions,
and the memory module reads the evidence tables to resolve them. `evidence →
memory` is forbidden: no module of the evidence layer imports the memory module
(Unit 1 §13.2, and the structural test in §12). The memory module may import
`storage`, `cochange` and the other evidence modules; none of them may import it.

## 5. Lifecycle

### 5.1 What a state change writes

| Act | Columns written |
|---|---|
| **admission** | a new row: `state = 'active'`, `admitted_at`/`admitted_epoch`, everything else from the author |
| **supersede** | the old row: `state = 'superseded'`, `ended_at`/`ended_epoch`, `superseded_by` = the successor; the successor row is written as a new admission |
| **invalidate** | the row: `state = 'invalidated'`, `ended_at`/`ended_epoch`, `end_reason` (required) |

**Both directions of a supersede are visible, and only one is stored.** The old
row carries `superseded_by`; the reverse — "which memory supersedes this one" —
is a query (`WHERE superseded_by = ?`, which is what the index is for). Storing
both would be two rows saying one thing, free to disagree, and the project
already derives the other direction wherever it has this choice.

**States are terminal.** A rule that comes back into force is a *new* memory, not
a reactivation: the record then reads "in force, then not, then in force again",
which is the truthful account, and nothing has to un-end a row. A reactivation
would also have to decide what `ended_at` means afterwards, and there is no
answer that keeps the span readable.

### 5.2 The rules the schema enforces, and the one it cannot

Enforced by CHECK: a superseded row names a successor; an invalidated row has a
reason; an active row has no end and no successor; a non-active row has an end
time; no row supersedes itself.

**Not enforceable in SQL, and therefore the acts' responsibility:** the successor
must be an `active` memory that is not the memory being superseded, and a
supersede chain must not close into a cycle. A CHECK cannot see another row's
state or walk a chain, so the act enforces both — and the design says so here so
a later unit does not assume the schema has it.

## 6. Temporal semantics at the data layer

| Field | Set by | Meaning | Absent means |
|---|---|---|---|
| `admitted_at` + `admitted_epoch` | the tool | when the row entered the store | never absent — every memory was admitted at a time |
| `since_commit_sha` / `since_date` | the author | from when the statement held of the project | **unknown**, and rendered as unknown; never defaulted to the admission time |
| `ended_at` + `ended_epoch` | the tool, on supersede or invalidate | when the statement stopped being current | still current (state `active`) |

**In force at a commit** — the computed property Unit 1 §9.2 defines, now with
its exact rules:

```text
in force at C  ⇔  the start is known and at or before C
                  and (the memory is active or it ended after C)

start:  since_commit_sha → compare committed_epoch of that commit with C's
        since_date       → compare the first ten characters of C's committed_at
        neither          → unknown, so not provably in force
```

**Both comparisons are by time, not by ancestry**, and this is a decision with a
cost that is named rather than hidden: git history is a graph, a commit on a side
branch can carry an earlier timestamp than its merge base, and reachability would
be the exact answer. It would also make every read of every memory walk the
parent graph, which the project's own timings (a 200,000-commit history) rule
out for an interactive command. A `since` is a coarse statement about the
project's history in the first place; a time comparison is what the tool can
afford, and Unit 1 §9.2 is the rule that keeps it honest — a memory whose span
cannot be shown to cover the commit is *related, not provably in force*, and
says so rather than being merged into the ones that are.

**A date is compared as the commit recorded it**: the first ten characters of
`committed_at`, which is the date in the committer's own offset. Day granularity,
inclusive at both ends of the day.

## 7. Migration and rebuild — the centrepiece

### 7.1 The two kinds of data, and the one sentence that separates them

```text
evidence tables   a cache over the repository — every row can be rebuilt from git
memory tables     knowledge — no row can be rebuilt from anything
```

Everything below is the consequence.

### 7.2 Two version stamps, owned by two modules

| Stamp | Where | Owns |
|---|---|---|
| `schema_version` = `"4"` | `meta`, written by `storage.create_schema` | the shape of the evidence tables |
| `memory_schema_version` = `"1"` | `meta`, written by the memory module | the shape of the memory tables |

**v0.5 does not move `SCHEMA_VERSION`.** It adds no evidence table, no column
and no row, so the evidence version has nothing to say about it — and this
refines one sentence of Unit 1 §12.2, which said the schema version that adds the
table would be the first bump that has to carry something across. It does not
have to: the memory tables carry their own version, so the evidence rebuild never
has to know that memory exists, and a future change to memory's shape never
triggers an evidence rebuild.

The rules, all four:

| State found | What happens |
|---|---|
| No memory tables, no `memory_schema_version` | The memory module creates both and stamps `"1"` — on first use, in one transaction. Nothing is created by `analyze`, `ast` or any evidence-only command. |
| Stamp equals the tool's | Read and write normally. |
| Stamp older than the tool's | **Migrate forward.** No migration exists yet (v1 is the first shape); the rule is stated now so the first one has a home, and it is the same rule as the evidence side's except in the one way that matters: a memory migration moves rows, it never drops them. |
| Stamp newer than the tool's | **Refuse to read or write memory**, and say so, naming the file. Evidence is unaffected: `analyze`, `ast` and the reading commands still work, because none of them touches memory. A newer tool wrote these rows and an older one cannot know what they mean. |
| Tables present, stamp missing | **Refuse**, and say so. The tool cannot know the shape of a table it did not stamp — this cannot happen through the tool's own paths, since it creates the table and the stamp together, and the honest answer to "I do not know what this is" is not a guess. |

### 7.3 The rebuild path, exactly

`prepare_database` today:

```python
stored = read_schema_version(connection)
if stored is not None and stored != SCHEMA_VERSION:
    drop_tables(connection)          # every table in TABLES
create_schema(connection)            # CREATE IF NOT EXISTS, then stamp
```

**The memory tables are not in `TABLES`.** That is the whole mechanism, and it is
deliberately a list rather than a condition inside the drop: a list can be read
and checked ("is `memories` in it? no"), while a condition like "drop everything
except memory" is one edit away from dropping it. `drop_tables`'s docstring
changes to say what it is — the evidence rebuild — and that memory is not in the
list on purpose.

What each path does to memory, all of them "nothing":

| Path | Today | With memory |
|---|---|---|
| `analyze` on the same repository | rewrites commits, keeps AST rows keyed by sha | unchanged; memory untouched |
| `analyze` on a different repository with `--db` | takes the database over, replacing the evidence | unchanged for evidence; **memory is kept and never rewritten**, and the rows now name a repository the database no longer claims (§8) |
| `analyze` after a schema bump | drops and recreates every table | drops and recreates the **evidence** tables; memory kept |
| `ast` | fills `file_versions` / `definition_versions` | unchanged; memory untouched |
| `clear_history` | deletes every evidence row | unchanged; its docstring gains the sentence that memory is not evidence and is not touched. A future "delete everything" is a different function and has to say so in its name. |

### 7.4 What a rebuild does to a memory's meaning

Nothing is rewritten, and the citations may stop resolving — which is a
*reported* state, not a repair (§4.3). A history rewrite that removes a cited
commit leaves the citation exactly as the author wrote it; the read says it can
no longer be resolved. Deleting or editing the memory to match the repository
would be the tool destroying knowledge because the repository moved, which is the
one thing this layer exists to prevent.

### 7.5 Atomicity

Every act writes its rows in one transaction — a memory and all of its citations
together, and a supersede's two rows together — the way `write_ast_batch` does
for a version and its definitions. An interrupted act leaves nothing; there is no
half-memory and no memory whose citations were never written.

## 8. `--db` across repositories, decided

### 8.1 The decision

> **A database holds memories for one repository. The first memory written fixes
> it; a write from a different repository is refused; a read filters to the
> current repository and reports what it hid; and `adopt` is the explicit act
> that says "these are the same project, at a new path".**

The three options the brief named, and why this is the third:

- **Reject the read** — refused, because recovery *requires* reading a database
  whose rows name another path. A moved repository is read this way, and a tool
  that refuses to open its own store cannot be recovered with.
- **Allow storage and report the mismatch** — refused, because reporting after
  storing is too late: the mixed state exists, and every later read has to filter
  anyway. Refusing the write is what keeps the store from ever being mixed by the
  tool.
- **Per-row ownership with refusal on write, reporting on read, and an explicit
  adopt** — adopted, and it is the only one of the three that keeps the store's
  invariant true while leaving a way through.

### 8.2 What the user sees

| Situation | Behaviour |
|---|---|
| Reading memories in a database whose rows all name the current repository | Nothing is filtered, nothing is reported. |
| Reading when some rows name another path | Those rows are hidden from the current repository's output, and the command prints how many and **which paths** they belong to. `memory show <id>` works by id regardless of repository — the id is the address, and a person who has an id has it for a reason. |
| Writing when any row names another path | **Refused**, naming the foreign path and the two ways forward: use this repository's own database (drop `--db`), or `memory adopt --from <that path>` if the repository moved. |
| `explain` on a database holding foreign rows | The memories shown are the current repository's; a one-line note on stderr says the database also holds memories for another path. The answer itself is untouched — the note is for the person, and stdout stays parseable, as everywhere else. |

### 8.3 `adopt` — one act added to Unit 1's set

Unit 1 froze five acts (create, list, show, supersede, invalidate) and recorded
the move hazard as an open question. Closing it needs a sixth:

```text
memory adopt --from <path>     # the memories made about <path> are this repository's
```

- It rewrites `repository_path` on the rows whose path matches `--from`, and on
  no others. The path must be given in full: the act requires the person to name
  what is being adopted, which is what stops it being a silent mass rewrite.
- It never touches a statement, an author, a time, a citation or a state.
- It records the act once, in `meta` (`memory_adopted_from`, `memory_adopted_at`),
  so the store says that an adoption happened rather than looking as though the
  rows were always this repository's.
- It refuses when `--from` matches nothing, and says how many rows it would move
  before moving them (a confirmation line, and the same count after).

This is an amendment to Unit 1's act list, and it is recorded as one (§10).

## 9. Recovery

| Failure | Behaviour, decided |
|---|---|
| **The file is not a database, or is corrupt** (`sqlite3.DatabaseError` on open or on a query) | A sentence naming the file and what it means — not a traceback, and **not the old advice**. Until v0.5 the fix for a broken cache was "delete it"; now deleting destroys knowledge, so the message says the file could not be read and that the file should be copied before anything is done to it. This is the one evidence-side behaviour v0.5 changes, it changes a message and not a fact, and it is required by memory: a recovery instruction that destroys the thing being recovered is worse than no instruction. |
| **Memory tables present, `memory_schema_version` missing** | Memory refuses and says so; evidence works. (§7.2.) |
| **`memory_schema_version` newer than the tool** | Memory refuses and says so; evidence works. (§7.2.) |
| **`schema_version` older than the tool** | Evidence is rebuilt, as today. Memory is untouched, and its citations are re-checked at read — a rebuild can make one unresolvable, and that is reported, not repaired. |
| **Evidence tables missing or short** | `open_analysis` already refuses with the actionable message ("run `archaeology analyze`"). The memory commands inherit it, because they open the database the same way. |
| **An interrupted act** | Nothing was written: one transaction per act (§7.5). |
| **A memory whose citations no longer resolve** | Not a failure of the store. Reported at read (§4.3). |
| **Never** | Drop a memory table, rewrite a statement, "fix" a citation, or decide a memory is stale and remove it. The tool's recovery is *reporting*; the person's is a new memory, a supersede, an invalidate, or a copy of the file. |

**What is not recovery, and is deliberately absent:** there is no `--rebuild-memory`,
no import, no export, no repair command. Export and import are a later unit
(Unit 1 §21.1); until they exist, the backup is the file, and the documentation
must say so.

## 12. Acceptance criteria

What the implementing unit must be able to show, written as the tests this
project holds everything to.

1. **The column lists are pinned**, the way `FILE_VERSION_COLUMNS` and
   `DEFINITION_VERSION_COLUMNS` are: `memories` and `memory_citations` compared
   against the agreed lists, so a column added later fails the build instead of
   quietly becoming part of the model.
2. **The memory tables hold no derivation**: no `has_citations`, no counts, no
   type — the analogue of `test_the_tables_hold_no_derived_identity`.
3. **A rebuild keeps every memory.** A database with memories, an old
   `schema_version`, and a call to `prepare_database`: the evidence is rebuilt
   (as the existing test asserts) **and every memory, citation and state is
   byte-identical afterwards**. This is the unit's central test.
4. **`clear_history` does not touch memory**, and `analyze` does not either — a
   second `analyze` leaves the memory rows exactly as they were.
5. **The evidence layer never reads memory**: a structural test in the shape of
   `tests/test_offline.py`'s — the modules of the evidence layer do not import
   the memory module.
6. **The subject's shape is enforced**: a `definition` subject without a path, a
   `commit` subject without a sha and a `path` subject with a qualname are all
   refused by the database, not only by the writer.
7. **The lifecycle's rules are enforced**: an invalidated row without a reason, a
   superseded row without a successor, an active row with an end time and a
   self-supersede are all refused; and the acts refuse a successor that is not
   active.
8. **No foreign key reaches the evidence tables**, and the test says why: a
   `write_commits` that removes a commit must not fail and must not cascade.
9. **A citation that names nothing is refused at admission**, with a message
   naming it; a citation that stops resolving is reported at read and stays in
   the row.
10. **The repository rules hold**: a write from another repository is refused;
    a read filters and reports the count and the paths; `adopt --from` moves
    exactly the rows of that path and records the act in `meta`.
11. **`memory_schema_version` is honoured**: newer than the tool → memory refuses
    and evidence still works; missing with tables present → refuses; missing with
    no tables → creates and stamps.
12. **One transaction per act**: an act interrupted between the memory and its
    citations leaves neither.
13. **No new dependency, no network** in the memory path, and `SCHEMA_VERSION`
    is still `"4"` with the evidence tables' column lists unchanged.

## 13. Open questions

1. **The Windows case-folding asymmetry.** `cache.database_path` casefolds the
   path on Windows; `meta.repository_root` and memory's `repository_path` compare
   exactly. So `D:\Repo` and `d:\repo` share a database file but not an identity.
   Pre-existing, inherited, and the memory layer deliberately does not add a
   third rule — but the fix, if there is one, belongs to a unit that touches
   `open_analysis`, and it should be made once for both.
2. **Whether `adopt` should be able to merge two paths' memories** (a database
   that somehow holds two) rather than one `--from` at a time. v0.5.0's rule
   makes that state unreachable through the tool; the question is only whether
   the act should be able to repair a state reached by hand.
3. **Export and import**, which is where the identity decision (§1) pays off and
   where the fork case (§2.3) is actually answered.
4. **The cost of re-checking `cochange` citations at read time** on a large
   history, and whether the read side should cache the analysis per command.
5. **Whether `explain` should show a repository-subject memory at all when
   nothing more specific matches.** Unit 1 §15.3 orders by specificity (the most
   specific subject first, then the most recent admission) and caps the list, but
   it does not say whether the least specific subject is shown when it is the
   only thing there — and whether the cap should count it.
6. **What the memory section costs** in the prompt, and whether it needs a
   measured budget the way the evidence bundle has one
   (`docs/v0.4-context-budget.md` is the shape to follow).
