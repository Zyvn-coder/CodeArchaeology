# v0.4.0 Final State

The AI layer, on top of the frozen evidence layer. This file is the record of what
v0.4 is: what it contains, what holds it in place, what it costs, and what it does
not do. Everything in it is a fact about the tree it was written in, and the
numbers are measurements taken with the commands named beside them, so they can be
taken again.

## What it is

v0.3.x proves what happened. It never says why, and that boundary was its freeze.
v0.4 is the other half: an explanation of what one commit did and which candidate
reasons the evidence is consistent with, written by a model from the evidence the
tool already holds.

**The boundary moved, and it moved in one direction only.** The deterministic
layer is still the only thing that produces facts — a commit, a diff, an AST node,
each with a test behind it. The AI layer produces a *reading of those facts*, and
it is never presented as a record of what happened. That is the contract the whole
phase is held to, and it is written down in `docs/v0.4-problem-definition.md` §12
in the user's own words:

> **CodeArchaeology 的 AI 输出是 interpretation，不是 historical fact。**

## The contract: interpretation, not historical fact

| | Historical fact | Model output |
|---|---|---|
| Where it comes from | git, or an AST of a stored blob | a model's text |
| What backs it | the row itself | a citation the tool checked against the bundle |
| What "wrong" means | a defect in the tool | a sentence that overstates its citation |
| Reproducible | yes — the same database gives the same bytes | no — one input can produce two answers |
| Held by | its own tests | the validator, for shape and for citations |

Four consequences, and the layer is built around them:

1. **The citations are the facts; the sentences around them are the reading.**
   Every claim prints what it rests on, down to the span of a diff and the
   direction of a co-change pair.
2. **A checked citation does not make the sentence true.** The validator holds
   every `ref` against the bundle; a sentence that stays inside a citation and
   still overstates it is not something a program catches, and
   `docs/v0.4-explanation-schema.md` §6 says so where the check is defined.
3. **The same commit explained twice may be explained differently.** That is what
   an interpretation is. What has to be identical between two runs is the
   evidence.
4. **Nothing a model writes is stored.** An explanation is printed and read; it is
   never written back to the database, so no interpretation can later be found by
   a command that treats rows as facts.

**And the tool says so where the misreading would happen.** The block opens with
the sentence; the same statement is the seventh principle in both READMEs, part of
`archaeology explain --help`, and a section of the CHANGELOG.

## What holds it in place

Six decisions, each with the test that fails if it stops being true:

1. **The evidence is deterministic and the model is not.** `context.py` builds the
   bundle from the database and git with no model anywhere near it, and the same
   commit with the same database produces the same bytes — `tests/test_context.py`,
   including the two assertions that two builds of one commit are identical.
2. **One bundle, two paths — with one stated exception.** What the offline path
   prints is what the model is shown, byte for byte, for every commit that fits.
   A commit too large to send whole is reduced *for the model*, and every dropped
   row is counted in the prompt — `tests/test_selection.py`, which also pins the
   bundle's bytes as unchanged.
3. **Observed, Possible and Unknown are structural.** The model cannot put a
   candidate under `Observed` because the renderer decides where each list goes,
   and a reason repeated in the summary is refused — `tests/test_validation.py`,
   `tests/test_explain.py`.
4. **Every claim carries citations, checked against what the model saw.** A
   citation of a row the model was not shown is refused even though the tool holds
   it — `tests/test_explain.py`, `tests/test_validation.py`.
5. **The answer is never repaired.** It is asked for once more and then refused
   whole; nothing of a broken answer is printed — `tests/test_boundaries.py`.
6. **The core does not need a model.** Held twice: structurally, by reading every
   module in the package and naming `provider.py` as the only one allowed to
   import a networking module, and behaviourally, by running every reading command
   with `socket.socket`, `create_connection` and `getaddrinfo` taken away —
   `tests/test_offline.py`.

## What the validator can see, and what it cannot

Written here because the difference is the honest limit of the whole layer.

**Checked:** every citation names something in the bundle the model was shown; a
`possible_reason` rests on at least one observed change and every id it names
exists; the summary cites ids that exist; a reason does not appear in the summary;
an unknown field — including `confidence`, which the tool derives — is refused.

**Not checked:** whether an observed change is *true of the repository* (that is
`analyze`'s and `ast`'s contract, held by their own tests); and whether a sentence
stays inside the citation it names. `tests/test_boundaries.py` is the seven ways a
model can be wrong, and each one carries the honest verdict — refused, marked, or
not catchable.

## What it costs

**The evidence, measured** with `benchmarks/context_benchmark.py` over generated
histories (bytes are the bundle's own JSON, tokens the tool's estimate at four
characters per token):

| Shape | Bundle | Sent to the model |
|---|---|---|
| five files, two hunks each | 18,182 B / ~4,545 | the same — nothing is dropped |
| two hundred files | 495,954 B / ~123,988 | 40,545 B / ~10,136 |
| a thousand files | 1,492,002 B / ~373,000 | 29,228 B / ~7,307 |
| one file, five hundred hunks | 36,130 B / ~9,032 | 3,266 B / ~816 |
| one file, three hundred definitions | 118,645 B / ~29,661 | 9,668 B / ~2,417 |
| two hundred files, twenty hunks and ten definitions each | 1,431,464 B / ~357,866 | 45,079 B / ~11,269 |

So a commit of any size is bounded at about 11,000 estimated tokens of view, and
the bundle it was cut from is unbounded on purpose — it is what the reader gets.

**The call**, from the architecture freeze and implemented in `provider.py`: a
60-second wall-clock deadline around the whole call rather than a socket timeout,
two retries with 1s and 2s backoff on connection, DNS, timeout, 429 and 5xx
failures, and a refusal — never a truncation — past
`CODEARCHAEOLOGY_AI_MAX_CONTEXT_TOKENS`. A response past a megabyte is refused
rather than read.

## Known limitations

- **Nothing is incremental, in either direction.** Unchanged from v0.3: `analyze`
  rewrites the whole history on every run, and the AST pass reads every Python
  file version each time.
- **`commit` has no `--json`.** The one v0.3 interface gap, still open, still
  stated in both READMEs. The other seven reading commands have one, and every one
  of them was checked end to end before this release.
- **The selection keeps the largest changes, which is a rule about size and not
  about importance.** A pure rename moves no lines, so on a commit large enough to
  be reduced it sorts last and is the first thing left out.
- **An explanation is an interpretation, not a historical fact, and it is checked
  for its citations rather than for its truth.** The block says so in its first
  line.
- **Nothing a model writes is stored.** Whether an explanation is ever stored is
  an open question, and it is not a small one.
- **There is no prompt unit.** The wording the model reads is Unit 4's plus the
  rule about `selection`; whether it deserves a unit of its own is open.
- **No flag for seeing the evidence alone in the block form** once a model is
  configured — the offline path is the only way to that.
- **`explain` needs a network only when a model is configured.** With no endpoint
  set it prints the evidence and exits 0.
- Tested on Linux and Windows, on Python 3.11 and 3.13, by CI. macOS is untested.

## What is not here

The v0.4 boundary, which is the user's list rather than a backlog:

| Not in v0.4 | Why |
|---|---|
| Whole-repository chat, automatic Q&A, multi-turn | The unit is a commit; there is no conversation. |
| An agent | Nothing is executed, nothing is written, nothing is fixed. |
| A web UI | v0.1–v0.3 are a CLI and v0.4 stays one. |
| Automatic repair of an answer | Repairing is the tool inventing content, which is the one thing this layer exists to prevent. |
| Call graphs, complexity scores | Different features; the v0.3 freeze already ruled them out of the evidence layer. |
| Languages other than Python | Python-only holds in v0.4 as it did in v0.3. |

## The release

The order is a rule, and it exists because v0.3.0's tag had to be moved once:

```text
commit  →  push  →  all four CI jobs green on that commit  →  tag  →  GitHub Release
```

A tag whose own CI is red is worse than a tag that moves, and a tag that moves is
a tag nobody can trust to name a tested tree. v0.3.1 followed this order and its
first push was red on Windows anyway, which is why the tag names the fix commit
rather than the release commit.

**What happened:** the release commit is `07e3da7`, and **all four CI jobs passed
on it** — ubuntu-latest and windows-latest, Python 3.11 and 3.13 — before the tag
was made. `v0.4.0` is an annotated tag on that commit, with a GitHub Release
beside it. That is the order working as intended, and it is worth saying what it
avoided: v0.3.0's tag had to move once because it was made before CI finished, and
v0.3.1's release commit was red on Windows — a real defect the runner found, which
put the tag on the fix commit instead. This release needed no second commit,
because the first one was checked before anything was tagged rather than after.

## v0.5 preconditions

What has to be true before Developer Memory starts, so a later session does not
begin on assumptions:

1. **The AI layer's contract holds.** Not "the answers are good" — the answers are
   interpretations and cannot be judged that way — but that the evidence is
   deterministic, the citations are checked, and the block says what it is. The
   six decisions above, each with its test.
2. **The evidence layer is untouched.** v0.4 added no table, no column and no row.
   A v0.5 that needs the AI layer to have stored something is a v0.5 that has to
   argue for it first.
3. **The release order is followed again**, with the tag on a commit whose own CI
   is green on all four jobs.
4. **The three open questions are answered or explicitly deferred**: whether an
   explanation is ever stored, whether the prompt gets a unit of its own, and how
   the evidence alone is read once a model is configured.
