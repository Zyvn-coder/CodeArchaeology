# `files` / `hotspots` semantics freeze

**Unit 14.** Written 2026-09-30. This unit writes no production code: this file
is the deliverable, and it is what the implementation unit is checked against.

The decision it records is the user's, made after reading what the two commands
actually did: **方案 B, 已删除文件默认出现, 路径升序, `hotspots` 不加 `--deleted`**.
Section 6 answers the one question they left open, and section 9 is the impact
list for whoever builds it.

---

## 1. What the two commands were

Read from the code rather than remembered. Before this freeze, `hotspots` and
`files` were not "two views of one ranking" in a loose sense — they were the
same call:

| | `hotspots` | `files` |
|---|---|---|
| function | `rank_hotspots(lives)` | `rank_hotspots(lives)` — the same one |
| filter | `include_deleted=False` | the same |
| order | commits descending, then path | the same |
| rows | rank number, path, commits, `+/-` lines | path, commits, `+/-` lines |
| `--json` | `build_ranking_json(...)` | the same function, byte for byte |
| `--limit` / `--all` | yes | yes |

Only the terminal drawing differed, plus the closing sentence `hotspots` prints.
A test pinned the byte-identical JSON
(`test_files_and_hotspots_json_are_the_same_bytes`) and the README stated it
("`files --json` prints exactly the same bytes").

Two consequences, both measured on the fixtures:

* **Deleted files were invisible in the CLI.** `rank_hotspots` takes an
  `include_deleted` argument that brings them back — `tests/test_hotspots.py`
  uses it to prove the fixture's busiest file is a deleted one — but no command
  ever passed it. The sample fixture's ranking showed 5 of its 6 files;
  the lifecycle fixture's showed 5 of 7, dropping `src/core/app.py` (4 commits,
  the busiest in the repository) and `heavy.py`.
* **A user had to be told which of two identical commands to use.** The README
  spent a paragraph on it.

---

## 2. The decision

**The two commands answer different questions.**

* **`hotspots` asks "which files are the busiest".** A hotspot is a *place*, and
  a file that is gone is no longer a place. It ranks living files by how many
  commits touched them, and it keeps its warning that frequency is not
  importance.
* **`files` asks "what files does this repository contain".** An inventory is a
  *list of what exists and what existed*, so it includes the deleted files and
  says which is which. It is ordered by path, the way a directory listing is,
  and it carries the same numbers per row so a reader can still see which
  entries were busy.

The rest of this document freezes each one.

---

## 3. `hotspots` — unchanged

Its definition does not move, and neither does its output:

```text
$ archaeology hotspots ~/projects/sample-project
Most Active Files

1. core/app.py
   3 commits
   +19 / -0
...
Frequent change is not importance: the reason each of these files is busy is not something this tool can see.
```

* Living files only. **No `--deleted` option is added** — the user's decision.
  If both commands could bring the dead back they would drift into being the
  same thing again, which is what this unit exists to end.
* Order: commits descending, then path. The tie-break stays.
* `--limit` / `--all` / `--json` keep their meanings, and `--json` emits the
  same bytes it emits today.
* The closing sentence stays. It is the command's whole epistemic position.

---

## 4. `files` — the inventory

### 4.1 Definition

> **`files` lists every file the stored history ever contained, alive or
> deleted, one row each, ordered by path.**

Three words carry the change:

* *every file* — the complete inventory, not a ranking. A file with one commit
  and a file with three hundred are both entries; neither is "more of a file".
* *alive or deleted* — the state is a column, not a filter. Nothing is hidden by
  default, because a list that silently drops part of what it lists is not an
  inventory.
* *ordered by path* — the order a person scans when they are asking "what is
  here", not "what is hot". The numbers ride along, but they do not sort.

### 4.2 The output

```text
$ archaeology files ~/projects/sample-project
 FILE                   STATE     COMMITS   +LINES   -LINES
 ──────────────────────────────────────────────────────────
 README.md              alive           1        3        0
 assets/logo.png        alive           1        0        0
 core/app.py            alive           3       19        0
 core/cache.py          alive           1       12        0
 legacy.py              deleted         2        5        5
 工具/文本.py           alive           1        5        0
```

* **`STATE` is the second column**, right after the path, because it is the
  fact that changes what the row means. Two values: `alive`, `deleted`.
* **`COMMITS`, `+LINES`, `-LINES` keep their current meaning** — the whole
  life's numbers, summed by `statistics.summarize`, exactly as `hotspots`
  counts them. The two commands must never disagree about a number they both
  print.
* **The path is the life's `current_path`** — the name the file has now, or the
  name it died under. That is what `file` already prints and what `hotspots`
  already ranks by; the inventory does not invent a third convention.
* **A renamed file is one row**, not one per name, and its row carries the whole
  history — `core/app.py` is the file that was born as `app.py`. The names are
  in `--json` (`path_history`) for a reader that needs them; the table keeps one
  row per file because "how many files are here" must have one answer.
* **The `hotspots` closing sentence is not printed.** It is about frequency and
  its reading; this command is a list. What `files` needs to say instead is the
  one thing a list of dead files invites a reader to get wrong, and §4.4 pins
  the sentence.

### 4.3 Ordering and slicing

Frozen, and the same rule the other listings use: **the same database and
parameters produce the same bytes.**

```text
1. current_path   ASC   (byte order, so it is stable across locales)
2. birth ordinal  ASC   (only reachable when two lives share a current path)
```

A name can belong to two lives — a file deleted and another created at the same
path later — and both are rows, because both are files the repository
contained. The birth ordinal breaks that tie and cannot be reached otherwise.

`--limit N` (default 20) and `--all` behave as they do everywhere else: the
first N rows of the frozen order are shown, and the count of hidden rows is
printed. **`--json` is not sliced** — it carries every row — which is the rule
the other JSON outputs already follow.

### 4.4 What the command must say

The table's `deleted` rows raise the question a reader will ask: *is this file
gone from the working tree, or gone from the history?* The command answers it in
one closing sentence, in the same register as `hotspots`' warning:

```text
Deleted files are in the list on purpose: this is what the history contains, not what the working tree contains.
```

That sentence is the whole reason the command is allowed to show dead files, so
it is part of the freeze rather than a rendering detail.

## 5. JSON

### 5.1 The contract splits, and only `files` moves

**`hotspots --json` keeps the bytes it emits today.** Its consumers must not
have to change because a different command changed meaning. The ranking's
schema — `repository`, `head_sha`, `files[]` with `path`, `commits`,
`additions`, `deletions`, `path_history` — is frozen as it stands.

**`files --json` gets its own shape**, because it answers its own question and
has one fact the ranking does not have. It carries `state` and it carries every
row, deleted ones included:

```json
{
  "repository": "/abs/path",
  "head_sha": "78c0647a…",
  "files": [
    {
      "path": "README.md",
      "state": "alive",
      "commits": 1,
      "additions": 3,
      "deletions": 0,
      "path_history": ["README.md"]
    },
    {
      "path": "legacy.py",
      "state": "deleted",
      "commits": 2,
      "additions": 5,
      "deletions": 5,
      "path_history": ["legacy.py"]
    }
  ]
}
```

* `state` is the word the table shows, so a program and a person read the same
  fact in the same vocabulary.
* `path_history` stays, for the reason the ranking already carries it: a row is
  counted by identity, and without the chain a renamed file and two unrelated
  ones cannot be told apart.
* The list is named for what it holds, and it holds one entry per file — the
  same key name as the ranking's, deliberately: both are lists of files, and a
  consumer that reads `files[].path` from either is reading the right thing.

The shared-schema test is replaced, not deleted: the new one asserts the two
commands' JSON **differs**, and that each differs only in the ways this section
says (`state` present in one, absent in the other; the row sets equal only when
no file is deleted).

### 5.2 What is deliberately not in the JSON

No `limit` echo, no counts of alive versus deleted, no directory rollups. The
question "how many files are alive" is a `len()` away for a program, and a
rollup by directory is a different feature — see §7.

## 6. The one open question, answered

**Question (the user's 4th): does the JSON contract split?**

**Answer: yes, and only `files` changes.** The reasoning:

* **The byte-identical contract was a consequence of the two commands being the
  same command.** It was decided when they were duplicates, and it is what the
  README had to apologise for. Once the semantics differ, identical bytes would
  mean the schema is hiding a difference the command line shows — the opposite
  of what this project's JSON rule is for ("JSON carries the same facts, not a
  summary of them").
* **Keeping `hotspots` byte-stable is the part that matters.** It has the longer
  history and the ranking is what other programs were pointed at; changing its
  output to add a `state` every row would be a breaking change for a fact that
  is always `alive` there. The inventory is the new thing, so the inventory
  carries the new field.
* **One schema for both was never really possible anyway.** After this change
  the two commands hold different row sets — the ranking cannot contain a
  deleted file, the inventory must — so "the same bytes" would have to mean
  "the same schema with different contents", and that is exactly what splitting
  the schema makes explicit.

## 7. Boundaries

What this unit does not do, so that the next session does not helpfully add it:

* **No `--deleted` / `--alive` / `--state` option on either command.** The
  inventory is complete and the ranking is living-only; a filter would be a
  third semantic on top of two that were just made to mean something. If a
  filter is ever wanted, it belongs to `files` and to a unit that argues for it.
* **No directory or module rollup.** Grouping by directory is a new dimension —
  a tree, a depth, a size per node — and it is not "a list of files".
* **No sorting option.** Path is the inventory's order and commits are the
  ranking's; a `--sort` flag would put both orders in both commands and undo
  §2. A user who wants the ranking has `hotspots`.
* **No change to `hotspots`' numbers, prose or options.** §3.
* **No new database column and no schema version move.** `state` is derived from
  the lifecycle the tool already builds; it is not stored, for the same reason
  `deleted` is not stored anywhere else.
* **No change to `file` or `cochange`.** `file` already answers for one file and
  already prints whether it is deleted; `cochange` is not a listing.

## 9. Impact

For whoever builds this, the files that change and the reason each one does:

* `src/codearchaeology/hotspots.py` — the module currently owns the ranking and
  the table renderer for it. The inventory needs its own builder (an
  `InventoryEntry`-style row carrying `state`, or a `state` field on `Hotspot`)
  and its own table; the ranking's `rank_hotspots` and `build_object` must not
  move. Where the inventory lives is the implementation's choice; the freeze
  only requires that `hotspots`' bytes do not change.
* `src/codearchaeology/cli.py` — the `files` command switches to the inventory
  and prints §4.4's sentence; `hotspots` is untouched.
* `tests/test_hotspots.py` — the `files` tests (table, limit, all, JSON) change;
  `test_files_and_hotspots_json_are_the_same_bytes` is replaced by case 13.
  The `hotspots` tests, including `test_the_busiest_file_can_be_one_that_is_gone`,
  stay as they are.
* `README.md` and `README.zh-CN.md` — the `files` section is rewritten (new
  table, the `state` column, the sentence, the new JSON) and the line "`files
  --json` prints exactly the same bytes" is deleted. The `hotspots` section
  keeps its text and gains nothing.
* `PROGRESS.md` — the decision goes in the decisions table with the user's four
  answers, and the "files and hotspots show the same ranking" item in *Next* is
  closed.

**Nothing here is built until the user confirms this freeze.**

## 10. Built, and what the building changed

**Written after the fact, so the document says what happened.** The user
confirmed the freeze, and the split is implemented:

* `src/codearchaeology/hotspots.py` — `InventoryEntry`, `build_inventory`,
  `build_inventory_table`, `build_inventory_object`, `build_inventory_json` and
  `DELETED_FILES_NOTE` were added. `rank_hotspots`, `Hotspot`, `build_table`,
  `build_object` and `build_json` were not touched, so the ranking's bytes are
  what they were; `build_json`'s docstring now says why it is no longer shared.
* `src/codearchaeology/cli.py` — `files` uses the inventory and prints the
  sentence; `hotspots` is unchanged.
* `tests/test_hotspots.py` — the `files` tests moved to the inventory's
  behaviour, and `test_files_and_hotspots_json_are_the_same_bytes` was replaced
  by `test_the_two_json_shapes_differ` plus
  `test_the_ranking_json_is_unchanged_by_the_split`, which is the stronger pair:
  one pins the difference, the other pins that `hotspots` did not move. Two
  further tests hold the inventory to the ranking's numbers where they overlap
  and pin the order.
* Both READMEs — the `files` section rewritten, the "same bytes" sentence gone,
  and every console block replayed against the fixtures (8 blocks, 0
  differences). The `hotspots` section keeps its text and gains the ranking's
  own JSON example, which it previously borrowed from `files`.

**Nothing in §1–§9 was changed to make the building fit**, with one exception
recorded rather than smoothed over: the freeze's §9 expected the inventory to
live wherever the implementation chose, and it lives in `hotspots.py` beside the
ranking. The module's docstring now states the two questions it answers, so the
file name is the only thing that still reads as ranking-only.

**Still not here, unchanged from §7**: no `--state` filter, no directory rollup,
no sorting option, no stored column.
