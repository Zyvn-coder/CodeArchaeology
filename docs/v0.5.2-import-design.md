# v0.5.2 — the minimal `memory import`, frozen

**What this is.** The design for the smallest `memory import` that makes a
`memory export` file usable again: restoring *this* repository's memories into
*this* repository's store. It is a **design**, not an implementation — nothing
below is built, no code, schema, CLI or test was changed by the unit that wrote
it, and §15 lists what a human must still approve or overrule before it is
built.

**What it is not.** It is not the Memory sharing system. It does not merge two
projects' memories, does not import a fork's memories into another repository,
does not rewrite a path, and does not re-resolve evidence. Those are named,
declared and deferred in §3 and §13 rather than half-built.

**The scope sentence this unit inherits, recorded in `PROGRESS.md` before this
document existed:**

> The minimal `memory import` is scoped to **this repository into a store that
> holds nothing for it**, and refusing a file made about another repository; it
> needs no conflict rules, no identity rewrite and no fork preview. What it
> closes is the one acceptance criterion `docs/v0.5.1-portability-design.md` §6
> records as unmet — **the reader half of the count guard**, which no command can
> hold until something reads a file.

**Where this document departs from that sentence, and why.** The review that
produced the final state of this design widened it in exactly two places, each
with its reason where it lives: **case B is supported behind `--from <path>`**
(§4.4) rather than refused, because the sentence's own scenario — a checkout
restored somewhere else — has no other way through; and **the duplicate rule is
per-row** (§6.2) rather than "a store that holds nothing for it", because two
exports of one store taken months apart are what a backup habit produces. Both
were put to the user with their reasons and **decided on 2026-10-11**; §16 is
the decision record and §13's table is the state after it. Everything else in
the sentence stands: no merge, no fork preview, no conflict rules beyond the
duplicate rules listed, and no path change that a human did not type.

**What is still not decided.** The four decisions §16 records are frozen; a
short list of reader tolerances the format's own freeze is silent about is not
(§5.4, §15.2). Those are this design's choices, listed so they can be
overruled, and none of them changes the deliverable's shape.

**How claims are marked.** **CONFIRMED** = read out of the current source, the
current tests, or an actual run of the shipped CLI (the runs are quoted, with the
temporary directory they ran in). **INFERRED** = reasoned from that evidence.
**UNKNOWN** = the evidence cannot settle it. **Where behaviour is described:
[existing]** is what the tool does today, **[proposed]** is this design's
decision, **[not implemented]** is what the implementation unit will build.

**One fact about the project's state that this document must not overstate.** The
understanding experiment is prepared and **not run** — there are no participants
and no results — so the project has **no evidence that anyone values this tool**,
and nothing in this unit creates any. `memory export` exists because a backup
that cannot be restored is not a backup; that is an argument about a missing
half of a feature, not about demand.

## 2. The export format and the memory schema, as they are

### 2.1 The bytes

Written by `memory_export.py`; re-confirmed by running the shipped command in a
scratch repository on 2026-10-11 (`D:\tmp\import-design`, quoted in full in §2.4).

```text
line 1   the header, one JSON object
line 2+  one memory per line, ascending by memory_id
```

- Encoding UTF-8 **without a BOM**; the line ending is `\n` on every platform,
  including after the last line (the file is opened with `newline=""`).
- `json.dumps(value, ensure_ascii=False)` with the **default separators** — a
  space after `:` and after `,` (CONFIRMED in the bytes below). The freeze's
  §3.2 example shows the compact spelling without spaces; the code and its
  docstring are the contract, and the example is illustrative — recorded here
  because the task asks for historical-document/implementation conflicts to be
  named rather than silently resolved.
- The header, exactly four fields:

```json
{"memory_export_version": "1", "repository": "D:\\tmp\\import-design\\repo", "count": 3, "exported_at": "2026-10-11T15:19:26.010616+08:00"}
```

- **The header's `repository` is the store's identity string, written verbatim.**
  The command passes `memory.repository_identity(repository_root)` and
  `memory_export.header_line` writes it as given (CONFIRMED: `cli.py`'s export
  command and `memory_export.py`), so the file carries a resolved path string —
  which is why §4's comparison is exact string equality against the same
  expression and nothing is re-derived from the file.

- A memory line, exactly twelve fields, this key order:

```json
{"memory_id": "7a1e5562-…", "repository": "D:\\tmp\\import-design\\repo", "statement": "…", "author": {"name": "Dev", "email": "dev@example.com"}, "admitted_at": "2026-10-11T15:19:16.867908+08:00", "state": "active", "subject": {"kind": "repository"}, "since": null, "ended_at": null, "end_reason": null, "superseded_by": null, "citations": []}
```

- `subject` is one of four shapes: `{"kind":"repository"}`, `{"kind":"path","path":…}`,
  `{"kind":"definition","path":…,"qualname":…}`, `{"kind":"commit","commit":…}`.
- `since` is `null` or `{"commit":…}` or `{"date":…}` — never both (the schema's
  CHECK makes both impossible).
- `citations` is a list of `{"kind":…,"ref":…}`, in the store's canonical order
  (`position`), empty meaning "none attached".
- **The four deliberate absences** — `subject.resolution`, `citations[].resolution`,
  `since.commit_date`, `supersedes` — are exactly the fields that need the
  evidence tables, which is why export reads no evidence at all.

### 2.2 The schema the file has to fit into

`memories` (18 columns): `memory_id` TEXT PRIMARY KEY, `repository_path` NOT
NULL, `statement` NOT NULL with `length(trim(statement)) > 0`, `author_name`/
`author_email` nullable with non-empty-when-present CHECKs, `admitted_at` TEXT
NOT NULL, **`admitted_epoch` INTEGER NOT NULL**, `subject_kind` IN the four
kinds, `subject_path`/`subject_qualname`/`subject_commit_sha`, `since_commit_sha`,
`since_date` (GLOB `YYYY-MM-DD` when present), `state` IN the three states,
`ended_at`, **`ended_epoch`**, `end_reason`, `superseded_by` **REFERENCES
memories(memory_id)**; plus the CHECKs: subject shape per kind, `since_commit_sha`
and `since_date` not both, non-active rows carry an end, active rows carry no
end/no reason/no successor, superseded rows name a successor, invalidated rows
carry a reason, and `superseded_by <> memory_id`.

`memory_citations` (4 columns): `memory_id` REFERENCES memories ON DELETE
CASCADE, `position`, `kind` IN the six evidence kinds, `ref` non-empty;
PRIMARY KEY `(memory_id, position)`, UNIQUE `(memory_id, kind, ref)`.

**Two consequences for import, both CONFIRMED by reading the schema:**

1. **The file is missing two NOT NULL columns** — `admitted_epoch` and
   `ended_epoch`. They are derived (`int(datetime.timestamp())`) and must be
   recomputed on import from the ISO strings. This is the *only* field the file
   does not carry that the table requires, and it is not information: the same
   instant, in another spelling.
2. `PRAGMA foreign_keys = ON` on every connection (`storage.connect`), so the
   `superseded_by` reference is enforced per statement unless the import defers
   it (§8).

**And the two the import act owns, not the file:** `repository_path` (the store's
identity, see §4) and nothing else. Every other column is a value the file
carries.

**The store the act writes into may have no memory tables at all, and that is
the ordinary case A.** `analyze` creates the evidence schema and nothing of
memory's; the memory tables appear with the first write act, through
`memory.prepare_memory`, and a store with neither the tables nor the stamp is
`memory._state`'s `_ABSENT` — a store with no memories, not an error
(CONFIRMED in the code). Import must therefore be able to create them, and
§8.2 states where and how, because the obvious way to do it — calling
`prepare_memory` — would break the idempotence contract of §6.4 (measured:
re-stamping writes, §8.2).

### 2.3 What the file deliberately does not carry

No resolution states, no derived counts, no evidence rows, no `exported_by`, no
tool version, no `memory_schema_version`, no `head_sha` (`docs/v0.5.1-portability-design.md`
§3.2, §3.6 — CONFIRMED in the code: `memory_export.header_line` and
`memory_line` build exactly the fields above).

Four more behaviours were re-confirmed in the same scratch store, because the
import rules in §6 and §7 rest on them:

| Behaviour | Observation | Marker |

The documented recovery is the README's sentence: `analyze --db <old file>` and
then `memory adopt --from <old path>`. **This unit does not change that
behaviour** — it inherits it, and §12 says what import must do about it (nothing
beyond refusing to write into a foreign store).

## 3. The minimal import: goal, non-goals, and the four cases

### 3.1 The goal, in one sentence

**[proposed]** `archaeology memory import <file>` restores a file that was
exported from **this** project — in place, or after a move the person asserts with
`--from` — into this repository's memory store, in one
transaction, writing every field exactly as the file carries it — except the
row's `repository_path`, which is always this store's own identity (§4.2) — and
nothing else, and refusing any file that is not one this tool could have written
about this repository.

### 3.2 The four operations the task names, each declared

| | Operation | v0.5.2 | Why |
|---|---|---|---|
| **A** | restore a backup to the original project | **SUPPORTED** | This is the whole point of export; the identity rule makes it exact and the round trip is testable byte for byte. |
| **B** | restore after the project moved to a new path | **SUPPORTED — behind `--from <path>`, the adopt device** (**decided 2026-10-11**, §16) | The file names `/old`, the store's identity is `/new`, and only a human can say the two are one project — which is what `adopt --from` already asks, in the same words ("the path must be given in full: typing it is the confirmation"). Refusing B would leave the feature's own scenario — *my machine died and I cloned the checkout somewhere else* — with no way through at all, including no way to fix it by hand short of renaming the checkout to the old path. `--from` costs one flag, one equality (`resolve(--from)` must equal the file's header), and writes the rows as **this** repository's. §4.4 argues it in full. |
| **C** | a fork's memories into another repository | **NOT SUPPORTED as a feature; reachable only by the same explicit assertion `adopt` already accepts** | With `--from` present, case C stops being impossible-by-construction and becomes possible-by-assertion: a person who names the fork's path gets the fork's memories, exactly as they can today by pointing `adopt` at the fork's database. What is *not* here is the mechanism that would make it reviewable — the citation re-resolution preview the freeze recorded (`docs/v0.5.1-portability-design.md` §5.2: "of 12 memories, 9 cite commits this repository does not have"). It stays deferred, and until it lands the signal after a mistaken assertion is the one the reader already gives: citations that no longer resolve are marked `no longer in this history` by `memory list`/`show`. |
| **D** | merging two different memory sets | **NOT SUPPORTED — refused** | The store's own law: "a database holds memories for one repository" (`docs/v0.5-storage-design.md` §8.1), and `adopt` already refuses to merge two repositories' memories. A merge would need the identity rule, the conflict semantics and the fork preview that the audit listed before v0.6 — not this unit. |

### 3.3 Non-goals, as a list a reviewer can check

**[not implemented]** in v0.5.2: merging two memory sets; importing into another
repository's database; re-resolving citations and reporting what would not
resolve; filtering or narrowing the set; producing a preview of a fork; writing
anything to the evidence tables; touching existing memory rows; creating
lifecycle relations between imported and local memories; leaving rows that name
another repository (every row written names this store's repository, whether or
not `--from` was given); deleting or replacing a row; any interactive prompt (the
tool has none, `docs/v0.5-cli-design.md` §6.6).

**The one phrase that used to be on this list and is now a rule instead:**
"rewriting `repository_path`". With `--from`, the act *does* write this
repository's path onto rows whose file names another one — that is what makes B
work at all. The non-goal that remains, and is absolute, is **rewriting it
without a human naming the source path**: no code path changes a path
implicitly, and the value written is always the store's own identity.

## 4. Project identity, and how the target is chosen

### 4.1 The rules, all of them already in force [existing]

1. **Target = the store of the repository you are in.** `memory import <file>
   [path] [--db]` resolves the repository the way every command does
   (`find_repository_root`, then `database_path` unless `--db` is given).
2. **The store's identity is compared before anything happens.** `open_analysis`
   refuses a database whose `meta.repository_root` is not this repository's
   resolved path — for reads and writes alike (§2.4, CONFIRMED).
3. **The store holds one repository's memories.** A write is refused when any row
   names another path; a read filters and reports.
4. Identity is **exact string equality after `resolve()`** — no case-folding, no
   trailing-separator tolerance, no symlink games beyond what `resolve()` does
   (`memory.repository_identity`).

### 4.2 What import adds [proposed]

**Two equalities before any write, both refused by name when they fail:**

- **the file against the target**: either the header's `repository` equals this
  store's identity byte for byte (mode **A**), or the path the human named with
  `--from`, resolved, equals it (mode **B**, §4.4);
- **the file against itself**: every row's `repository` must equal the header's
  (the freeze already states the reader refuses a row that disagrees).

**How the comparison is made, exactly** (decided 2026-10-11, §16):

- **The file's value is compared as written.** It is not resolved again, not
  case-folded, not trimmed, not expanded — the writer wrote
  `repository_identity`, and the reader compares that string. Re-deriving a path
  from the file would be inventing an identity the file did not carry.
- **The only value that goes through `resolve()` is the one a human typed.**
  `--from` is resolved the way `adopt --from` resolves it
  (`str(Path(...).resolve())`, the same public expression), so a trailing
  separator or a `.`/`..` in what someone typed is normalized by the rule that
  already defines every other repository identity — and a typo still matches
  nothing.
- **Same-path import needs no `--from`.** Mode A is the default and the flag is
  optional; a `--from` that resolves to the target's own identity is mode A with
  a redundant flag, allowed rather than special-cased.
- **A header with no `repository` is not this format's header** and is refused by
  §5.1 before any identity question is asked — so `--from` cannot supply an
  identity the file is missing.

**What is written into `repository_path` is always the store's own identity.** In
mode A that is the same string the file carries, so the row is byte-for-byte the
file's; in mode B it is the one value that differs from the file, and it is the
store's — never the file's, never `--from`'s text, never a third value. Either
way **no row can end up naming a path this store does not own**, which is the
property the one-store law rests on.

### 4.3 The cases this rule decides, and the one it cannot

| Situation | What happens | Marker |
|---|---|---|
| Same checkout, same path; the store lost and re-created (fresh `analyze`, or a new machine with the same layout) | **A** — imports; this is the case the reader half of the count guard was written for | [proposed] |
| The checkout was moved, renamed, or re-created at a different path (including a **case-only** rename) | **B** — refused without `--from`, and imported with it: `--from <the path the file names>` asserts the two are one project, and the rows are written as this repository's (§4.4) | [proposed] |
| `--db` names a file that belongs to another repository | refused by `open_analysis` before import reads a byte | [existing], CONFIRMED |
| `--db` names a file that *was* another repository's but was re-labelled by `analyze --db` | the store is now this repository's, and the old rows are foreign: import refuses (the store holds rows for another path) | [proposed] |
| The file was exported from this same path by an older tool whose format version is not `"1"` | refused by name (§5) | [proposed] |

**The case-only rename is worth stating on its own, because it was measured, not
reasoned.** In a scratch repository, `analyze` at `…\Case\Repo`, one memory
created, then `ren … \Repo repo`:

```console
$ uv run archaeology memory list 'D:\tmp\import-design\Case\repo'
Error: D:\tmp\import-design\cache\91feeefa82c2dc99.db holds D:\tmp\import-design\Case\Repo,
       not D:\tmp\import-design\Case\repo; run 'archaeology analyze D:\tmp\import-design\Case\repo' to replace it
$ git -C 'D:\tmp\import-design\Case\repo' rev-parse --show-toplevel
D:/tmp/import-design/Case/repo
```

So Windows' case-folding means the **file** is the same one (`cache.database_path`
casefolds, so both spellings map to `91feeefa82c2dc99.db`), while the **identity**
compares exactly and refuses. The rows are not lost — the same database holds
them, and the documented two-step recovery (`analyze` at the new spelling, then
`adopt --from` the old one) repairs it **without a file at all** (CONFIRMED:
`docs/v0.5-storage-design.md` §13.1 names this asymmetry as open; this unit does
not close it and does not depend on it).

### 4.4 `--from`: adopt's device, not a new rule [decided 2026-10-11, §16]

```text
archaeology memory import memories.jsonl ~/projects/sample --from ~/old/sample
```

**The contract, as decided** (§16 records the decision and what it changed):

1. `memory import` takes an optional `--from <path>`.
2. Without it, the same-path rules of §4.2 apply unchanged.
3. When the header's `repository` differs from the target store's identity, the
   file is refused **unless** `--from`, resolved, equals the header's
   `repository` exactly — the two strings, byte for byte.
4. `--from` is the person's assertion about where the file came from. It is not
   proof of repository identity and nothing treats it as one.
5. The `repository_path` written on the rows is the target store's own identity,
   always — never the file's path, never `--from`'s text (§4.2). No path is
   rewritten to get around the one-store law.
6. There is no implicit path rewrite, no fuzzy or case-insensitive matching, and
   no fork detection anywhere in the act. The only path change is one a human
   typed and the file's own header agrees with.
7. **The risk, recorded as it is**: an explicit assertion cannot tell a moved
   original repository from a fork. The citation re-resolution preview that would
   warn before the write is **not in this unit** (§3.2, case C), and nothing here
   may claim the risk is eliminated.

**Why it is `adopt`'s device and not a new rule:**

- **Its words are `adopt`'s, deliberately**: "the path the memories were made
  about, in full. Typing it is the confirmation." The act it describes is the
  same act — *these rows are this project's, at a new path* — applied to rows
  arriving from a file instead of rows already in the store.
- **Two sources must agree**: `repository_identity(--from)` must equal the file's
  header `repository`. A typo therefore matches nothing, and a file whose header
  was hand-edited to a path the person does not name is refused. `adopt` has only
  one source (the rows); import has the file *and* the person, which makes it the
  stricter of the two.
- **The path does not have to exist.** The moved case is exactly a path that is
  gone; `--from` is compared as a resolved string and nothing on disk is read —
  the same behaviour `adopt --from` has today (CONFIRMED: `repository_identity`
  is `str(Path(path).resolve())`, which does not require the path to exist).
- **What it does not do**: it does not change the file; it does not touch a
  statement, an author, a time, a citation or a state (adopt's frozen sentence);
  it does not create a lifecycle link; it does not merge two sets; it does not
  make the store hold rows for two paths; and it does not license an existing
  store row that belongs to another path — a foreign row with the same id is
  still refused (§6.1).
- **The honest consequence, stated because it is a real widening**: a person can
  now import a *fork's* memories into this repository by naming the fork's path —
  the same thing they can already do by pointing `adopt` at the fork's database,
  so it is not a new class of exposure, but it is a shorter path to it and the
  preview that would warn them (the freeze's §5.2 re-resolution count) is not
  built. What they will see, after the fact, is exactly what the reader always
  shows: citations that do not resolve are marked `no longer in this history`.
  Nothing is silent; it is just later than it should be.
- **What it costs to get wrong**: if the human asserts wrongly, the rows are
  written as this repository's and their statements are indistinguishable from
  local ones afterwards. There is no undo, and no act removes a memory (that is
  deliberate: nothing deletes knowledge). The mitigation is that the assertion is
  typed in full and that the file's own header must match it — and the honest
  limit, recorded in §10, is that no check can tell a moved project from a fork.

**Refusal, exactly** (§9.3 is the sentence): a `--from` that resolves to
something other than the header's path is refused before any write, naming both
paths; a header that names another repository with no `--from` is refused with
the same sentence plus the way to assert the move.

## 5. Format validation, and version compatibility

**All of this runs before a single row is written.** Validation is a pure
function of the file's text and this store's identity; it can be tested without a
database (§11).

### 5.1 The file as a whole

| Rule | Refusal (a sentence naming the file, the line, and what was found) | Marker |
|---|---|---|
| The file is readable and decodes as UTF-8 | `… is not UTF-8 (byte 0x… )` | [proposed] |
| It does not begin with a BOM | `… begins with a byte-order mark; this format is UTF-8 without one` | [proposed] |
| It is not empty | `… is empty; a file this format writes always has a header line` | [proposed] |
| The first line parses as a JSON object carrying `memory_export_version` and **no** `memory_id` | `line 1 is not this format's header` | [proposed] (the freeze's shape rule, §3.2) |
| The header's extra keys are none | `line 1 carries an unknown field 'x'` | [proposed] |
| The header carries all four of its fields | `line 1 is missing 'repository'` | [proposed] — a header without a source identity is not this format's header (§4.2) |
| `repository` is a non-empty string | `line 1: repository must be the path the memories were made about` | [proposed] |
| `memory_export_version` is exactly `"1"` | `… was written in format version '2'; this tool reads '1'` | [proposed] — **closes the freeze's §6.2 second half** |
| `count` is an integer ≥ 0 | `line 1: count must be a whole number of memories` | [proposed] |
| `count` equals the number of memory lines | `… says 12 memories and carries 9; the file is truncated or was edited` | [proposed] — **closes §6.2's first half** |
| Every line after the first is a memory line: a JSON object with `memory_id` and no `memory_export_version` | `line 7 is neither the header nor a memory` | [proposed] |
| No blank or whitespace-only line anywhere | the same sentence as above, naming the line | [proposed] |
| `exported_at` is a string that parses as a datetime | `line 1: exported_at is not a timestamp` | [proposed]; its *value* is never used — the freeze says nothing reads it, and a shape check is not a read |

**The header's `repository` is never re-derived.** It is compared as written, to
the target's identity or to what `--from` resolved to (§4.2); the reader does not
resolve it, case-fold it, or look at the disk. A file whose header carries a
relative path, or another machine's spelling, therefore matches nothing and is
refused by the identity sentence rather than being "fixed up" — no normalization
rule is invented here that the identity mechanism does not already have.

**Tolerated on read, and stated so the writer's contract is not weakened:**
trailing whitespace at the end of a line, and a missing final newline (the writer
always emits one; a reader that refused a hand-copied file over the last byte
would be refusing a difference that means nothing). A `\r\n` file therefore
parses, because the `\r` is trailing whitespace — but no line's *content* may be
empty.

### 5.2 One memory line

Each rule mirrors either the schema's CHECK or the acts' own `_checked`, so that
**a file can never smuggle in a row the acts would have refused**:

| Field | Rule | Refusal names |
|---|---|---|
| `memory_id` | a 36-character lowercase hex-and-dash UUID; unique within the file | the id and the line |
| `repository` | equals the header's — and the header either equals the store's identity or is the path `--from` named (§4.2) | the row's path and the header's |
| `statement` | non-empty after stripping; ≤ 4000 characters (`memory.STATEMENT_CHARACTERS`) | the length, or "empty" |
| `author` | `null`, or an object with exactly `name`/`email`, each a non-empty string or `null`, at least one not `null` | which key is wrong |
| `admitted_at` | parses as a datetime **and round-trips** (`fromisoformat(s).isoformat() == s`) | the spelling |
| `ended_at` | `null`, or the same round-trip rule | the spelling |
| `state` | one of `active`, `superseded`, `invalidated` | the value |
| `subject` | one of the four shapes, exactly the fields its kind carries (a definition needs both parts; a commit subject carries `commit`) | the kind and the missing/extra key |
| `since` | `null`, or exactly one of `{"commit":…}` / `{"date":…}`, the date round-tripping as `YYYY-MM-DD` | which of the two |
| `ended_at`/`end_reason`/`superseded_by` versus `state` | active ⇒ all three null; superseded ⇒ `ended_at` and `superseded_by` present and `end_reason` null; invalidated ⇒ `ended_at` and a non-empty `end_reason` present and `superseded_by` null | the contradiction |
| `superseded_by` | not the row's own id; and it must name a row **in the file or already in the store** (§7.3) | the dangling id |
| `citations[]` | each `{"kind","ref"}` with a kind from v0.4's six and a non-empty ref; no duplicate `(kind, ref)`; order preserved | the entry |
| unknown keys | none, in the header or in a row | the key |

**The round-trip rule for time strings is the same device the store already uses
for `since_date`** ("the parse refuses a day that does not exist, and the round
trip refuses a spelling the column's own GLOB would not keep",
`memory._checked_date`) — applied here because `admitted_at` and `ended_at` have
no CHECK, and a row whose `admitted_at` does not parse would make every later
`memory list` raise. Import is the last place that can refuse it cheaply
(CONFIRMED: `memory._memory` calls `datetime.fromisoformat(row["admitted_at"])` on
every read).

### 5.3 What import does *not* check, deliberately

- **Citations are not resolved against the evidence.** The store's rule is
  "checked twice, repaired never" (`docs/v0.5-storage-design.md` §4.3) and a
  citation that no longer resolves is *kept and reported* — refusing one at
  import time would be a stricter rule than the acts themselves have (the CLI
  refuses an unresolvable citation at *creation*, because the author is naming
  evidence they just looked at; a file is a record of what was admitted then).
  Import writes `kind`/`ref` verbatim; `memory list`/`show` report resolution as
  they always do.
- **A superseded row's `ended_at` is not required to equal its successor's
  `admitted_at`.** The acts share one moment, but the storage design's temporal
  rules are for reading, and a differing pair is diagnosable rather than corrupt.
  Stated so the omission is visibly deliberate.
- **`count` is not a cap on anything else** — no file-size limit, no memory-count
  limit. The file is the user's own; the per-row caps above bound the work.

### 5.4 What the freeze settles, and what this design settles on its own

Decision 4's rule is "check every reading rule against the existing exporter and
the format's definition before assuming it". Done, item by item:

| Reading rule | What the format's freeze says | Where this design's rule comes from |
|---|---|---|
| Blank or whitespace-only lines | **Settled: refused.** "No blank lines, no comments, no trailing content" (`docs/v0.5.1-portability-design.md` §3.1) | the freeze |
| A missing final newline | **Not settled.** The freeze fixes the *writer's* bytes ("every line ends with `\n`, including the last", §3.5) and says nothing about a reader's tolerance | this design tolerates it (§5.1), listed as pending in §15.2 |
| Trailing whitespace, a `\r\n` file | **Not settled**, same paragraph | this design tolerates it (§5.1), listed as pending in §15.2 |
| Unknown keys in the header or a row | Settled by the freeze's rule that a field nobody reads is a claim nobody verified (§3.2, §3.6, quoting `docs/v0.4-explanation-schema.md` §6) | the freeze's rule, applied by refusal |
| A format version that is not `"1"` | **Settled: refused by name** — "anything else is refused by name rather than guessed at" (§3.2) | the freeze |
| A row whose `repository` differs from the header's | **Settled: refused** (§3.3) | the freeze |
| The header identified by position and shape | **Settled** (§3.2) | the freeze |
| Missing required fields, wrong types, bad times, bad kinds | Not stated for a reader; the *store's* rules are the schema's CHECKs and the acts' `_checked` | this design mirrors them (§5.2), so a file cannot smuggle in a row the acts would refuse |
| Optional fields | There are none: the writer emits every key of a row, and `null` is a value it emits | the freeze's shape (§3.3) |
| A cap on file size or record count | **Not settled, and not proposed**: stated as a deliberate non-defence (§5.3, §10) | this design, listed as pending in §15.2 |

The three "not settled" rows are the honest boundary of this document's
authority: they are the reader's tolerances, they cannot change what a file
means, and they are listed in §15.2 so the user can tighten them.

## 6. Repeated imports and conflicts

### 6.1 The unit of the decision is the row, and the unit of the act is the file

**[proposed]** Import reads the file, reads the store's rows for the ids the file
names, and builds a plan: **insert**, **skip**, or **refuse**. The plan is
computed entirely before the write transaction opens; the transaction then either
does the whole plan or none of it.

| The file's row versus the store's row with the same `memory_id` | Plan | Why |
|---|---|---|
| No row with that id anywhere in the store | **insert** | the ordinary case |
| A row with that id, for this repository, **every comparable field equal** (the full field set and the comparison method are in the table below) | **skip**, and count it | re-running an import, or importing a newer export of the same store, must be a no-op. This is idempotence, and it is what makes the command safe in a script. |
| A row with that id and **any field different** | **refuse the whole file**, naming the id and the first field that differs | the alternative — replace, or insert beside it — would mean the tool choosing between two versions of what a person said. It cannot know which is newer (the file's `admitted_at` is the original, not the export time), and "the last import wins" is not a rule this project can defend. The person resolves it by hand, and what they need in that sentence is *which memory* and *which field*. |
| A row with that id belonging to **another repository** (a foreign row, reachable only in a store repaired by hand or re-labelled by `analyze --db`) | **refuse**, naming the path it belongs to | the primary key is global to the file; importing would either collide or move a row between repositories, and moving is `adopt`'s act |
| Two rows in **the file** with the same id | **refuse** | a file the writer cannot produce |

**The five cases, as decided on 2026-10-11, kept apart on purpose** (§16):

1. **Two rows in the file with the same id** — refuse the whole file, no writes.
   It is a file the writer cannot produce. This is a *different* thing from an id
   the store already holds, and the two rules must not be read as one: the first
   is about the file disagreeing with itself, the second about the file meeting a
   store.
2. **The store holds that id and every comparable field is equal** — treat it as
   already present; do not insert it again, and write nothing for that row.
3. **The store holds that id and any comparable field differs** — refuse the
   whole file. Not "skip it and import the rest": a file whose content disagrees
   with the store is never partially applied.
4. **The store does not hold that id** — insert it, after every check in §5 has
   passed for the whole file.
5. **The id belongs to a repository that is not this store's** — refuse by the
   identity rules (§4), and `--from` does not change this: it licenses the
   *file's* header path, never an existing store row's path.

**The comparable fields, exactly** — the field set behind cases 2 and 3, read
out of the schema and the export's serialisation, with the comparison method
each one uses. `repository_path` is deliberately absent (it is the act's value,
§4.2), and so are the two derived epochs (below).

| Column | Compared how | `null` means | Where the file's value comes from |
|---|---|---|---|
| `memory_id` | the key itself, exact string | — (never null) | the file, verbatim |
| `statement` | exact string equality | — (never null) | the file, verbatim |
| `author_name`, `author_email` | each exact, as a pair | the column is NULL | `author: null` ⇒ both NULL; otherwise each key verbatim, `null` allowed |
| `admitted_at` | exact string equality | — (never null) | the file, verbatim |
| `subject_kind`, `subject_path`, `subject_qualname`, `subject_commit_sha` | the four columns as one tuple | the kind's unused columns are NULL | the file's `subject`, per kind |
| `since_commit_sha`, `since_date` | the two columns as one tuple | `since: null` ⇒ both NULL | the file's `since` |
| `state` | exact string | — | the file, verbatim |
| `ended_at` | exact string equality | the column is NULL | the file, verbatim |
| `end_reason` | exact string equality | the column is NULL | the file, verbatim |
| `superseded_by` | exact string equality | the column is NULL | the file, verbatim |
| `memory_citations` | the list of `(kind, ref)` **in `position` order**, element by element | an empty list means "no rows" | the file's `citations` array, whose order *is* the position |
| `admitted_epoch`, `ended_epoch` | **not compared, and not carried** | — | rebuilt on insert from the same strings (below) |

**The derived epochs, verified and rebuilt.** `admitted_epoch` and `ended_epoch`
are `int(fromisoformat(s).timestamp())` — the expression `memory._epoch` applies
to the same value (CONFIRMED: `memory.py`'s `_epoch`, and `_write` stores
`when.isoformat()` beside `_epoch(when)`). The file carries the strings and not
the integers, so import recomputes them with that expression and the comparison
is on the strings. **Two spellings of one instant are never assumed equal**: the
round-trip rule (§5.2) refuses every spelling the writer would not have produced,
so the question cannot arise — and a store row whose derived column was
hand-edited to disagree with its own string is invisible to the file. That is
stated rather than papered over: import compares what the file carries, never
repairs the store, and only ever inserts or refuses.

**The two "duplicate" rules are never merged:** the file's own duplicate (case 1)
is a corrupt file; a store's existing id (cases 2–3) is a meeting between two
sets, decided by the comparison above.

**"Existing memories stay as they are" is enforced by construction**: the plan
has exactly two write shapes (insert a row that is absent; write nothing for a row
that is identical). There is no `UPDATE` against `memories` in the import path at
all, and no delete. That is checkable by reading the code, and by a test that
compares every pre-existing row before and after (§11).

**`repository_path` is not one of the compared fields**, and the omission is
deliberate: it is the act's value, not knowledge, and the row-level check above
already refuses an id that belongs to another path. Comparing it would make the
`--from` case refuse its own file on every re-import.

### 6.2 What this means for the recorded scope sentence

The recorded scope says "a store that holds nothing for it". **[decided
2026-10-11, §16]** The
stricter reading — refuse unless the store holds *no memories at all* — is
rejected, with the reason: two exports of one store taken months apart (`file1`
with 3 memories, `file2` with those 3 plus 7) are exactly what a backup habit
produces, and refusing the second file would make the tool's own habit
unusable. The plan above is idempotent, deterministic and never edits a row, so
layering backups works while the *danger* the scope was guarding against — a
merge between two divergent sets — remains refused: divergence in the same id is
refused, not merged, and a file about another repository is refused unless the
person names that path with `--from` and asserts the identity (§4.4).

**This is the one place this document reads its inherited scope more narrowly than
the words allow**, so it was put to the user as a decision rather than taken —
and decided on 2026-10-11 (§16). §13's row records it; the strictest reading
remains available as the overruling option if the scope sentence is to be read
literally.

### 6.3 Partial success

There is none: **the file is the unit of success.** A single conflicting row, a
single malformed line, a single dangling lifecycle link refuses the file and
writes nothing. The report says what would have been imported and what stopped
it. This is the same posture as the freeze's "a refusal is a sentence on stderr,
exit 1, and nothing on stdout", and it is what makes the command re-runnable
after the person fixes the one thing the sentence named.

**No conflict is ever handled by skipping it and importing the rest** — that
alternative (the one §13 records and this design rejects) would leave a store
that is part file and part store with no record of which is which. And when the
plan inserts nothing, **no write transaction is opened at all**: the checks read
the store, and reading is not writing (§8.1).

### 6.4 Strict idempotence, exactly, and the three defences against overwriting

**The contract, stated so it can be tested — and stated at both levels, because
they are not the same claim:**

- **The rows**: after a second successful import of the same file, every row of
  `memories`, `memory_citations` and `meta` is identical to what it was. This is
  the level the test device compares (`_store_state`, §11) and the level every
  other guarantee in this document lives at.
- **The bytes of the database file**: unchanged too, and this is achievable
  rather than assumed — *provided* the no-op path opens no write transaction at
  all. Measured on the scratch store of §2.4 (2026-10-11): `memory list` and
  `memory export` leave the file's sha256 identical, while a single
  identical-value `INSERT OR REPLACE` into `meta` — the statement
  `storage.set_meta` runs — changes it. So the byte-level promise holds only if
  the import path never re-stamps and never calls `prepare_memory`/`set_meta`
  when nothing is inserted (§8.2), and the test asserts the file's digest to hold
  the implementation to it. The one honest caveat: SQLite's own recovery of a hot
  journal left by a crashed process writes on open, which is a pre-existing
  condition of the store and not this act.

It follows that **an import which inserts nothing writes nothing at all** — no
rows, no `meta` keys (§7.2), no memory tables and no stamp, no write transaction.
A run that changed no knowledge is not an act that happened, and recording a
timestamp for it would make the command non-idempotent in the only sense a test
can check. This corrects an earlier draft of this document, which had the keys
written on every run.

**"A conflict never overwrites" has three independent defences, in this order —
and each has a stated limit:**

1. **Structural** — the import module contains no `UPDATE`/`DELETE` against
   `memories` or `memory_citations`, and calls none of the acts
   (`admit`/`supersede`/`invalidate`/`adopt`). Checkable by a test that scans the
   module's SQL, in the shape `tests/test_memory_boundaries.py` already uses for
   the writing acts — not by reading it once and remembering. **Its limit: it
   proves the shape of the code, not the behaviour of a transaction.** Atomicity
   is proved by the failure tests (#23, #24), never by this scan.
2. **Policy** — a differing row refuses the whole file (§6.1), so nothing partial
   is ever applied to a store whose content disagrees with the file.
3. **The primary key, as the last line of defence** — *even if* the comparison
   were wrong about "absent", the `INSERT` would violate
   `memories.memory_id PRIMARY KEY` and the transaction would roll back. There is
   no code path that can turn a collision into an overwrite: the worst case is a
   refused file, never a changed row. **Its limit: it covers the rows the primary
   key covers.** `memory_citations` is protected by its own key and by the
   all-or-nothing transaction, not by the collision check.

**What strictness costs, named because it is the alternative in §13:** the same
id with different content *also* refuses the benign-looking case of importing an
old backup into a store where that memory has since been superseded. That is not
an accident of the rule — two sets that disagree about one memory's state *are*
divergent, and merging divergent sets is case D, which this unit excludes. A
person who wants the missing memories and not the refusal has one move: import a
file that does not contain the conflicting row (export the current store, or edit
the file down) — and it should be the *tool* that offers that move if this
strictness ever bites, not the person doing it by hand.

schema, and nothing in it is invented.

### 7.2 What the act records about itself

**[proposed]** Two `meta` keys, mirroring `adopt`'s pair exactly:

- `memory_imported_from` — the resolved path of the file;
- `memory_imported_at` — the moment of the act, `datetime.now().astimezone().isoformat()`.

**And they are written only when the import inserted at least one row** — an
import that skipped everything writes nothing at all, so that re-running it
leaves the store identical at both levels, rows and bytes (§6.4). The trade,
stated: a no-op run leaves no
trace in the store. The alternative — a timestamp on every run — would make the
command non-idempotent in the only sense a test can check, and it would record an
act that changed nothing.

They record **the last import act, not a log** — the same semantics as
`memory_adopted_from/at`, and the reason there is no import table: a per-act
history is a new table, and a new table is a schema change this unit does not
need. They survive an evidence rebuild for free, because `storage._foreign_meta`
carries every key that is not `schema_version`/`repository_root`/`head_sha`
across a rebuild (CONFIRMED by reading `_foreign_meta`).

**They must be written inside the import transaction, not through
`storage.set_meta`.** `set_meta` calls `connection.commit()` itself — so calling
it in the middle of an import would commit a partial write if a later statement
failed. (CONFIRMED by reading `storage.set_meta`. `adopt` today ends with two
`set_meta` calls inside its `with connection:` block; the window is latent and
this unit does not touch it — recorded in §12 as an observation.) Import writes
the two rows with a plain `INSERT OR REPLACE` inside its own transaction.

### 7.3 The four questions the task asks, answered

- **Does import fake a human confirmation?** No: it never writes an `author` of
  its own, never attributes the imported statement to the person running the
  command, never calls an act (`admit`/`supersede`/`invalidate`), and never writes
  a memory in a `state` the file does not carry. The local git identity, which
  `memory create` reads from the repository, is **not** consulted on the import
  path at all.
- **Can the import time be mistaken for the original creation time?** Not in the
  store: `admitted_at` is the file's, and the import moment lives only in `meta`.
  The rendering keeps them apart the way it always has — `memory list`'s state
  line prints `admitted …` for a memory, which for an imported row is the
  original admission (CONFIRMED: that is what `_state_line` prints, and it is the
  truth about the memory).
- **Is the original source kept?** The file's path is kept in `meta`
  (`memory_imported_from`). The file's *contents* are kept where they matter —
  in the rows themselves. Nothing else about the source (a machine, a user) is in
  the format, and inventing one on import would be inventing provenance.
- **Lifecycle links that point outside the file?** Refused by name before any
  write, unless the target already exists in the store — a real case, since a
  file may carry a row whose `superseded_by` names a successor imported in an
  earlier run. The rule is closure: **every `superseded_by` must resolve to a row
  that will exist when the transaction commits** (the file's rows together with
  the store's). A link that does not is refused with the sentence naming both
  ids. This is the sentence that replaces what would otherwise be a raw
  `FOREIGN KEY constraint failed` at commit time.

### 7.4 What import must never do (the architecture boundaries, restated as rules)

No evidence table is written; no evidence module learns that memory exists; no
model is involved; no statement, author, time, citation or state of an existing
row is edited; no lifecycle relation is created between an imported row and a
local one (the links come only from the file); no row is deleted; the export
contract is untouched. §11's tests are written to hold each of these, and the
existing boundary suite (`tests/test_memory_boundaries.py`,
`tests/test_memory_provenance.py`) is the pattern.

## 8. Transaction atomicity, and failure recovery

### 8.1 The shape [proposed]

```text
1. parse + validate the whole file            (no database write)
2. read the store's rows for the file's ids   (a read: the database is opened
                                               and SELECTed, nothing more)
3. build the plan: inserts / skips / refuse   (no database write)
4. if the plan inserts nothing: stop here, having written nothing  (§6.4)
   otherwise, one write transaction —
       open it explicitly (BEGIN), not through `with connection:` alone
       CREATE the memory tables and write the memory stamp, when the store
         has neither yet
       INSERT the rows that are absent, in the file's order
       INSERT OR REPLACE the two meta keys
   COMMIT
```

**"No database write" is not the same as "no database operation".** Steps 2 and
3 open the database and read it: that is a read at most, it takes no lock that
outlives the statement, and — measured (§6.4) — it does not modify the file. The
distinction is stated because a document that said "no database operation" would
be making a claim about SQLite's internals that this design does not need and
cannot prove.

The validation and planning steps are pure functions of the file's text, the
store's identity and the store's rows. That has two payoffs: `--dry-run` is the
same code with step 4 skipped, and the dangerous part (the transaction) has no
decisions left in it.

### 8.2 The constraints that shape step 4

- **The `superseded_by` foreign key is immediate** (`PRAGMA foreign_keys = ON`,
  and SQLite checks FKs per statement by default). Rows sorted by `memory_id` do
  not have a dependency order — a successor's id is random — so inserting in file
  order can hit a row whose successor is not in yet.
  **[proposed]** Set `PRAGMA defer_foreign_keys = ON` inside the import's
  transaction, after `BEGIN`, and rely on the closure check in step 3 for the
  sentence. The PRAGMA is per-connection and SQLite resets it at every
  `COMMIT`/`ROLLBACK` (measured: on inside the transaction, off after the
  commit), and the CLI opens one connection per command — so it cannot leak into
  another command, and setting it after `BEGIN` keeps it in force for exactly
  the statements it must cover.
  The alternative — inserting in dependency order — is rejected because the
  transient states a two-pass insert creates violate the per-row CHECKs
  (`state = 'superseded'` requires `superseded_by IS NOT NULL` at every moment).
- **The store's state decides the DDL, and the DDL is inside the transaction.**
  The memory tables and their stamp may be absent (`memory._state`'s `_ABSENT`,
  §2.2) — that is the ordinary case A — so the write transaction creates them,
  using `memory.MEMORY_SCHEMA` and a plain stamp write. Three rules, each resting
  on a measurement (2026-10-11, Python 3.13.5 / SQLite 3.49.1, in the scratch
  store of §2.4):

  1. **The transaction is opened explicitly** — `BEGIN` (or `BEGIN IMMEDIATE`),
     not by relying on `with connection:` alone. Python's `sqlite3` starts its
     implicit transaction only at the first DML statement, so a `CREATE TABLE`
     executed before one is **committed outside the transaction**: measured — a
     `with connection:` block that created a table and then raised left the table
     behind; with an explicit `BEGIN` first, the same failure left nothing.
     Without this rule, a failed import into a fresh store would leave empty
     tables and no stamp — and `memory._state` reads that as `_UNSTAMPED`, which
     refuses every later memory read ("Copy the file before changing it"). That
     is the trap this rule closes.
  2. **`executescript` is never used inside the transaction.** It commits the
     open transaction first — measured: a row written before `executescript` was
     still there after a rollback. The DDL statements are executed one by one, as
     `memory.prepare_memory` already does.
  3. **`prepare_memory` and `storage.set_meta` are not called on the import
     path.** `set_meta` commits, and it re-stamps on every call; when the store
     was already current that is an identical-value `INSERT OR REPLACE`, which
     **changes the file's bytes** (measured, §6.4). Import writes the stamp and
     the two `meta` keys with plain statements inside its own transaction, and
     only when the plan inserts rows.

  When the store is `_CURRENT` the DDL is skipped — the statements are
  `CREATE ... IF NOT EXISTS`, so running them would be harmless, but it would
  also be a write this design does not need. When the store is `_UNSTAMPED`,
  `_UNREADABLE` or `_MISSING_TABLES`, the act refuses with the existing sentence
  (§9.3) before anything is written.
- **The per-row CHECKs are evaluated on insert** and are the safety net under the
  validation: if a rule in §5.2 was mis-implemented, SQLite refuses the row rather
  than storing a shape the acts could not produce.
- **No batching.** The whole file is one transaction, per the task's instruction
  to prefer the shape that is easy to prove correct. A hundred thousand memories
  in one transaction is a long write, not a wrong one, and the store's own read
  path is already batched for other reasons (`memory.CHILD_BATCH`).

### 8.3 What "provably unchanged on failure" means here

- **Validation failure**: nothing is written, because no write transaction is
  opened at all — and step 2 does not even run for a file that failed validation,
  because §8.1's order parses first. The database file is not modified.
- **A constraint failure inside step 4**: the transaction rolls back on the
  exception — the rows, the two `meta` keys, and (when the store had none) the
  memory tables and the stamp, because the DDL is inside the transaction too
  (§8.2). The test device already exists and needs no invention:
  `tests/test_memory_hardening.py`'s `_refuse_updates` creates a SQLite
  `BEFORE UPDATE … RAISE(FAIL, …)` trigger — for import, the equivalent trigger
  is on `INSERT INTO memory_citations` of the *second* memory, so the failure
  lands mid-file with the first memory already inserted. That test runs twice:
  against a store that already has memory tables, and against one that has none,
  where the tables and the stamp must be gone afterwards too (#24).
- **A `KeyboardInterrupt` or a process kill** mid-transaction: SQLite's journal
  leaves the store as it was; the next command sees the pre-import state. Stated
  as INFERRED from SQLite's own guarantee, and testable only by killing a process
  — not part of the must-pass matrix.
- **`--dry-run`** writes nothing by construction (step 4 skipped), and the test
  asserts the store's rows, `meta` *and* the database file's digest are identical
  after it (#25).

## 9. The CLI contract

### 9.1 The command [proposed]

```text
archaeology memory import <file> [path] [--db PATH] [--from PATH] [--dry-run] [--json]
```

- **`<file>` is required and positional**, named the way `memory create` names
  its statement: the first positional, with the repository path second
  (`create <statement> [path]`), so the group's shape is consistent.
- **`[path]` defaults to `.`** and `--db` behaviour is unchanged: the target is
  the current repository's store, and a `--db` that belongs to another repository
  is refused by `open_analysis` before anything else happens.
- **`--from <path>`** is the moved-repository device (§4.4): the path the file's
  memories were made about, in full. Absent, the file must name this repository.
  Present, the file must name the path given, and the rows are written as this
  repository's. It is optional, and a same-path import never needs it (§4.2). Its
  help text is `adopt`'s sentence, verbatim — "The path the memories were made
  about, in full. Typing it is the confirmation." — so the two commands ask the
  same thing in the same words (CONFIRMED: that is the string `cli.py`'s `adopt`
  declares for its own `--from`).
- **`--dry-run`** validates, plans and reports, and writes nothing. It is the
  flag that makes a big or unfamiliar file safe to try — and with `--from` it is
  the way to see, before committing to the assertion, that the file's path and
  the named path agree — and it is also the seed of the fork preview a later unit
  would grow (§3.2, case C).
- **`--json`** prints one object instead of the block, and the block is the only
  thing on stdout either way (notes about the database go to stderr, as `list`
  and `export` already do).
- **No `--force`, no overwrite switch, no prompt.** There is nothing destructive
  to confirm: the plan never edits or deletes.

### 9.2 Output

The block, on success (`--dry-run` says so in the first line; `Made about` appears
only when `--from` was given):

```text
Imported    9 memories
Skipped     3 already here, unchanged
From        D:\backup\memories.jsonl
Made about  D:\old\sample
Repository  D:\projects\sample
Database    C:\Users\you\AppData\Local\codearchaeology\1a2b3c4d5e6f7a8b.db
```

and, on a refresh where everything was already present:

```text
Imported    0 memories
Skipped     12 already here, unchanged
…
```

The JSON object, whose shape is the stable contract:

```json
{
  "file": "D:\\backup\\memories.jsonl",
  "file_repository": "D:\\old\\sample",
  "repository": "D:\\projects\\sample",
  "format_version": "1",
  "count_in_file": 12,
  "imported": 9,
  "skipped": 3,
  "dry_run": false
}
```

Eight fields, no list of ids (a program that wants the ids asks `memory list
--json`), no timestamps (they are in `meta`, and a JSON field nobody reads is the
field the freeze refused in the header). `file_repository` is what the file says
about itself — equal to `repository` in mode A, and the thing `--from` had to
match in mode B — so a dry run can be checked by a script before anything is
written. The block's first line and the JSON's `dry_run` are the only differences
a dry run produces.

### 9.3 Failures

| Failure | Where | Exit |
|---|---|---|
| the file does not exist, is a directory, or cannot be read | a sentence naming the path and the OS error | 1 |
| `--from` does not resolve to the file's header path | `Error: <file> names <path in file>, and --from names <resolved>; they must be the same path` | 1 |
| any validation refusal (§5) | `Error: <file>: <line>: <what was found>` on stderr; stdout empty | 1 |
| the file's header has no `repository`, or lacks any of its four fields | a validation refusal (§5.1) naming the field | 1 |
| identity refusal (§4) | `Error: <file> names <path in file>, and this repository is <this path>` — and when the two differ, the same sentence names `--from` as the way to assert they are one project | 1 |
| a conflicting id (§6) | `Error: <file>: memory <id> is already here and differs in <field>` | 1 |
| a dangling lifecycle link | `Error: <file>: memory <id> names successor <id2>, which is in neither the file nor this store` | 1 |
| the store holds another repository's memories | the existing sentence, naming the path and `memory adopt --from` | 1 |
| the store's memory tables are unstamped, or carry a newer stamp, or the stamp says tables that are gone (`_UNSTAMPED`, `_UNREADABLE`, `_MISSING_TABLES`) | the existing sentences (`memory._unreadable`) | 1 |
| the store has no memory tables and no stamp (`_ABSENT`) | **not a refusal** — a store nobody has written a memory in yet, which is the ordinary case A; the tables and the stamp are created inside the import's transaction (§8.2) | 0 |
| a missing or unreadable argument (`--db` twice, an unknown flag) | Typer's usage error | 2 |
| the analysis is behind HEAD | the existing note on stderr, and the import proceeds — the same `_warn_if_behind` every other memory command calls | 0 |

The import does not need the analysis to be current (it reads no evidence), and
it does need one to exist, because the store lives beside it — so the note is
kept for consistency and because a person importing is about to read citations
that resolve against that analysis.

## 10. The safety boundary

Only what this feature needs; nothing is generalised.

| Threat | The guard | Marker |
|---|---|---|
| a malformed or hostile JSONL file | every line is `json.loads`-parsed into a dict and validated field by field before any write; nothing is `eval`'d, no expression is interpreted; the file never names a path the tool writes to | [proposed] |
| a truncated file read as complete | the header's `count` is compared against the lines actually present | [proposed] — the freeze's §6.2 |
| a file whose shape is not this format's | version, header-by-position, unknown keys, and per-line shape are all refused by name | [proposed] |
| an enormous statement | the store's own cap (4000 characters) is enforced on import, so a file cannot introduce a row the acts would refuse | [proposed] |
| an enormous file | no cap. It is the user's own file; per-row caps bound each row, and one transaction bounds the memory a partial write needs. Stated as a deliberate non-defence. | [proposed] |
| a huge or nested `citations` list | each entry is validated; the count is not capped (the store does not cap it either) | [proposed] |
| path/identity confusion (the wrong store) | `open_analysis`'s identity check, then the file-to-store equality, then the row-to-header equality; nothing in the import path constructs a database path or a repository path of its own | [proposed] |
| a forged provenance | `author` is imported verbatim or absent; the import never writes the local git identity, never marks anything as confirmed by anyone, and records its own act in `meta` only | [proposed] |
| a duplicate id inside the file, or a self-supersede | refused, per §5.2 and the schema | [proposed] |
| a lifecycle link pointing outside the set, or a cycle | outside: refused by name (closure). A cycle: **[proposed]** refused — a supersede chain that closes on itself is a shape the acts cannot produce (`docs/v0.5-storage-design.md` §5.2 says the acts enforce acyclicity because SQL cannot), and this tool refuses shapes it did not write. (The read side would survive one — `tests/test_memory_hardening.py::test_a_cycle_a_hand_wrote_reads_without_hanging` — so a reader could accept it; that is the alternative in §13.) | [proposed] |
| a file exported from another repository, offered as this one's | the identity rule, and the row-level check as a second line of defence | [proposed] |
| SQLite errors (locked, full disk, corrupt file) | propagate as sentences through the CLI's existing `except` arms; a corrupt database is already refused with advice to copy it first (`memory._unreadable`, `analysis._unreadable`) | [existing] |
| an interrupted run | one transaction, no partial state (§8.3) | [proposed] |
| a person asserts, with `--from`, that another project's memories are this one's (the fork case, or a plain mistake) | **Nothing can tell a moved project from a fork** — the histories may be identical and in both cases the paths differ. The guards are the ones `adopt` already accepts: the path typed in full, the file's own header required to agree with it, and the reader marking citations that no longer resolve (`no longer in this history`). The preview that would warn *before* the write is deferred (§4.4), and this row is the honest statement that the deferral leaves the assertion unverified at write time — the decision of 2026-10-11 keeps the deferral and forbids describing the risk as closed (§16). | [proposed], decided |

**What a refusal says, and what it does not.** Every refusal names the file, the
line number and the field path, and quotes only the offending value (decision 4,
§16). It does not print another memory's statement, another row's content, a
database path the file did not carry, or anything else about the machine — a
refusal is about the file the person handed the tool, and the tool's own paths
are printed by the commands whose job that is.

**Not defended, deliberately:** a person who hand-edits a file to change a
statement and then imports it into an empty store — the tool has no way to know,
and the honest place that shows up is that the row is a memory whose author is
whatever the file says; a person who imports a stale file over a newer store —
every id in the stale file that the newer store kept unchanged is skipped, and
the store's newer rows are untouched, because import never deletes; a store whose
identity was itself re-labelled by `analyze --db` — a pre-existing hazard (§2.4)
that this unit does not add to.

**The migration path that does not exist — checked, not assumed.** CONFIRMED on
2026-10-11:

- **No migration code anywhere in `src/`**: no `ALTER TABLE`, no
  `PRAGMA user_version`, no function or branch named for migrating. The only
  occurrence of the word is `storage.prepare_database`'s docstring saying a
  database "is thrown away rather than migrated".
- **The evidence side rebuilds instead of migrating** — and it can, because every
  evidence row is derived from git.
- **The memory side has no rebuild and no upgrade**: `memory.prepare_memory`
  creates the tables and stamps the version when they are absent, and
  `memory._state`/`_unreadable` refuse a stamp that is not the current one
  ("written with memory schema version X, and this version of archaeology reads
  Y"), with no branch that could carry rows forward.
- **The consequence, stated plainly**: bumping `MEMORY_SCHEMA_VERSION` — or
  changing the DDL under the same stamp — would make every existing store refuse
  memory reads, and the tool's own advice for a store it cannot read is "copy the
  file before changing it". There is no way back through the tool. That is why
  the bar for touching this schema is a feature that cannot be built without it,
  and this one can.

## 14. Implementation order, and the acceptance criteria

### 14.1 Order (each step ends with its own test run)

1. **The reader as a pure function** — `read_document(text) -> header + rows`, or
   a refusal carrying `(line, field, sentence)`. No database, no CLI. Tests: the
   whole of §11.1's format half (#9–#19).
2. **The plan as a pure function** — `plan(file_rows, store_rows, identity) ->
   inserts + skips, or a refusal`. Tests: #5–#8, #20–#22.
3. **The writer** — one explicitly opened transaction (`BEGIN` before any
   statement), the DDL and the stamp when the store has none,
   `defer_foreign_keys` set inside it, the rows in file order, then the two
   `meta` keys. No `prepare_memory`, no `set_meta`, no `executescript`. Tests:
   #1–#4, #3c, #23, #24, #27.
4. **The command** — the Typer command, the block, `--json`, `--dry-run`, the
   `except` arms. Tests: #25, #34, and the CLI-shaped versions of the refusals.
5. **The guards and the paperwork** — `MEMORY_SIDE`, the writing-act scan, both
   READMEs, the CHANGELOG section, the version in its five places, and the
   acceptance run of the whole suite.

### 14.2 Acceptance criteria (the unit is done when all of these are demonstrable)

1. A file exported by this tool imports into an empty store, and a second export
   of that store reproduces the file's memory lines **byte for byte**, header
   aside.
2. The reader half of the freeze's §6.2: a wrong `count` and a wrong version are
   each **refused by name**, with exit 1 and nothing on stdout.
3. Every refusal in §5 and §6 is a sentence naming the file, the line, and the
   field, quoting only the offending value — never a Python traceback, never a
   raw `sqlite3` message, and nothing about the machine or another row (§10).
   (The project already holds this standard:
   `test_a_database_that_is_not_a_database_is_a_sentence_for_memory_too`.)
4. An import that fails at any point leaves `memories`, `memory_citations` and
   `meta` row-for-row identical to their pre-import state — demonstrated with a
   failure injected mid-file, not by inspection.
5. An import that inserts nothing opens no write transaction: every row of
   `memories`, `memory_citations` and `meta` is identical **and** the database
   file's sha256 is unchanged — including when the store had no memory tables,
   which must still have none afterwards.
6. An import that fails mid-file into a store with **no memory tables** leaves
   no tables and no stamp behind: the DDL is inside the transaction, so a later
   `memory list` reads an empty store rather than an `_UNSTAMPED` refusal.
7. `--dry-run` writes nothing on any input, valid or refused, and says so.
8. No evidence table changes; the boundary suite passes with the new module on
   `MEMORY_SIDE`; no module outside `MEMORY_SIDE` imports it.
9. An existing memory is never edited: a test compares every pre-existing row
   (statement, author, times, subject, state, citations) before and after an
   import that skipped it.
10. The local git identity is never written as an author by the import path.
11. `memory export`'s bytes and `memory adopt`'s behaviour are unchanged, and
    their suites pass untouched.
12. The command is documented in both READMEs, replayed by
    `tests/test_readme.py`, and the version agrees in the five places the suite
    compares — the release obligations the freeze's §6.8–§6.10 already fix.
13. The whole suite passes on 3.11 and 3.13, locally, before anything is tagged
    — the release order this project uses.

Three reader tolerances are not settled by it, and they are listed here rather
than assumed:

6. **A missing final newline** — tolerated (§5.1). The writer always emits one;
   the choice only affects a hand-copied file. To tighten it, refuse the file
   with a sentence naming the last line.
7. **Trailing whitespace and `\r\n`** — tolerated (§5.1). A `\r\n` file is a
   file copied through a Windows tool, and the `\r` is trailing whitespace. To
   tighten it, refuse any line whose raw bytes end in `\r`.
8. **No cap on file size or record count** — stated as a deliberate non-defence
   (§5.3, §10). To tighten it, add a limit with a sentence naming the number.

None of the three changes what a valid file means; each is listed so that
tightening it later is a decision someone makes, not a bug someone reports.

### Decision 1 — a moved repository is restored behind `--from <path>`

**Decided: support it, with the explicit assertion as the only mechanism.** The
seven-point contract is §4.4's list; the short form: the flag is optional; the
header must equal the target's identity or, when the two differ, exactly what
`--from` resolved to; `--from` is an assertion and not proof; the rows written
carry the *target's* identity and never the source path; there is no implicit
rewrite, no fuzzy matching, no fork detection; and the risk — an assertion cannot
tell a moved project from a fork — is recorded rather than claimed closed, with
the citation preview still deferred.

### Decision 2 — strict idempotence, never an overwrite, a conflict refuses the file

**Decided: yes, in the form §6.1/§6.4 state it.** Nothing is written when

refused; an absent id is inserted; and an id that belongs to another repository

the primary key under one transaction — are recorded with their limits, and the
