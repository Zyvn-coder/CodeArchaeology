# v0.5 design freeze — Developer Memory

## Status

**Design freeze. Nothing here is implemented, and nothing here changes the tree
it was written in.** This is Unit 1 of v0.5: the definitions, the boundaries and
the scope, fixed before any code. It was written on 2026-10-06 against `f27ebbf`
(version 0.4.0, schema 4, ten commands, 660 tests, `main` level with
`origin/main`), and every claim it makes about the current tool was checked
against that tree rather than recalled.

What it decides is frozen for v0.5.0 unless the user overrides it. What it does
not decide — the schema, the command names and flags, the rendering, the prompt
wording, the JSON key names — is listed in *What this unit does not decide*.

Two findings worth stating, because they shape the rest of this document:

- **`Developer Memory` has never been designed or built.** The only statement

  There is no prior decision to inherit, and no partial implementation to
  accommodate.

  "The database is a cache over a repository, not the system of record: every row
  here can be rebuilt by reading git again", and `prepare_database` throws the
  tables away when the schema version differs. Memory is the first thing in this
  project that **cannot** be rebuilt from git, and the storage decision below
  has to say so rather than quietly break that sentence.

## 1. Problem definition — why Developer Memory

### 1.1 What v0.4 is, exactly

v0.4 explains one commit from evidence the tool already holds. Its own evidence
contract fixes the boundary in a table called *Never*: the author's reason,
motive or intent; whether the change worked; the issue, the review, the
discussion; anything outside the repository. The rule underneath is the one hard
rule: **the model may use only what the bundle holds, and a claim that cannot
point at a stored fact is not printed.**

That boundary is right. It is also a ceiling, and it is a ceiling by design: git
stores what happened and not why, and no amount of history recovers a reason that
was never written down.

### 1.2 The gap this leaves

The project's own README says what it is for: git tells you what changed, when
and who — "What it cannot tell you is **why** the code looks the way it does
today", and "CodeArchaeology tries to put the story back."

Part of that story is in the repository and v0.1–v0.4 reconstruct it. Part of it
is not in the repository and never will be: the decision that was made in a
meeting, the constraint that came from an incident, the approach that was tried
and abandoned, the rule a team agreed on. Today the tool has exactly three ways
to handle such knowledge, and all three are wrong:

- **Let the model invent it** — forbidden, and the whole of v0.4 exists to
  prevent it.
- **Read it out of history** — a statistic read as a reason; the evidence
  contract already forbids causation from correlation.
- **Say nothing** — correct, and unhelpful: the reader who knows the reason gets
  nothing from the tool that they could not get from `git show`.

### 1.3 The new problem, in one sentence

> **v0.4's honesty is bounded by the repository, and some of the knowledge a
> project needs to explain itself is not in the repository. v0.5 adds a place for
> what people know, without ever letting it become evidence.**

So v0.5 does not make explanations better by giving the model more to guess
from. It gives the *project* a place to say what it knows — a place that is
authored rather than derived, labelled rather than laundered, and stored apart
from the facts so that no evidence query can ever read it.

### 1.4 What this problem is not

The brief that started this unit listed candidate directions — design decisions,
recurring engineering patterns, long-term developer preferences, problems solved
before, why a constraint exists, how an architecture formed, whether historical
experience should affect future explanations. Those are *content*, not the
problem, and none of them is adopted here by default. What survives is the
definition in §3: a memory is whatever a person states about this project that
the tool cannot derive. A decision, a constraint, a lesson and a preference are
all the same kind of thing to the tool — a statement — and §14 says why the tool
does not classify them.

### 1.5 The roadmap row, re-read

The README's roadmap says `v0.5 | Developer memory — your own technical usage
over time`. That row was written before v0.4 and it is a label, not a definition.
It is compatible with this freeze read one way: the memory belongs to the person
running the tool ("your own"), and it accumulates over time. It is *not*
compatible read as "a log of what the developer did" — that would be a usage
tracker, which is a different product, and §16 rules it out. The definition that
governs v0.5 is this document's, and the README row should be tightened to it by
the unit that ships v0.5 (recorded in *Open Questions*).

## 2. Terminology

Every word below has one meaning in this document and in the units that follow
it. Where a word already exists in the project, the existing meaning wins.

| Word | What it means here |
|---|---|
| **Evidence** | What the tool derives from the repository: commits, diffs, file versions, definitions, co-change counts, absences. Reproducible, checkable, stored in the evidence tables. v0.1–v0.3. |
| **Historical fact** | One item of evidence, with the test that fails when it stops being true. |
| **Interpretation** | What a model writes from the evidence in one run. Not stored, not reproducible, not evidence. v0.4. |
| **Proposal** | An interpretation offered as a *draft memory*. Not stored, not memory, no authority. Does not exist in v0.5.0 (§6, §15). |
| **Confirmation** | The explicit act by which a person admits a statement into the memory store. The only edge from a proposal (or a draft) to memory. |
| **Memory / Developer Memory** | A statement a person made about this project, admitted by that person's explicit act, stored apart from the evidence (§3). |
| **Curated knowledge** | The kind memory belongs to: authored, admitted, provenance-carrying, time-scoped, revocable — and never derived (§4). |
| **Subject** | What a memory is about: a path, a definition, a commit, or the repository as a whole. Required (§7). |
| **Citation** | A pointer from a memory to an item of evidence, in the same vocabulary v0.4 already uses: commit, file, definition, range, cochange, absence. Optional, and their absence is recorded (§7). |
| **Admission** | The moment a memory enters the store. `admitted_at` is a fact about the store, set by the tool. |
| **In force** | A memory is in force at a commit when its time span provably covers that commit. Otherwise it is *related, not provably in force* (§9). |
| **Supersede** | An explicit act that replaces a memory with a successor. The old memory stays, with its span closed (§8). |
| **Invalidate** | An explicit act that ends a memory without a successor, with a required reason (§8). |
| **Evidence layer / memory store** | The two parts of the database: the evidence tables (a rebuildable cache) and the memory table (not rebuildable). They are never the same thing (§12, §13). |

## 3. Memory definition

### 3.1 The definition

> **A Developer Memory is a statement a person made about this project, admitted
> by that person's explicit act, kept with the subject it is about and the
> evidence it was made from (which may be none), and stored apart from the
> evidence layer — knowledge the tool cannot derive from the repository, cannot
> verify, and must never present as derived.**

### 3.2 The four properties, each of which is load-bearing

1. **Authored, not derived.** Its origin is a person's assertion. The tool did
   not compute it and cannot recompute it.
2. **Admitted, not accumulated.** It exists in the store because a person made
   an explicit act of confirmation. Nothing enters the store by existing in the
   history, by repeating, or by a model writing it.
3. **Durable and scoped.** It is kept across runs, across `analyze` re-runs and
   across a schema rebuild, and it is about something identifiable — a path, a
   definition, a commit, or the repository.
4. **Grounded or explicitly ungrounded.** It names whatever evidence it was made
   from, and when there is none it says so. The tool never fabricates a citation
   to make a memory look supported.

### 3.3 The test that separates memory from everything else

> **If the tool can derive it, it is not memory.**

A statement the tool can compute belongs in the evidence layer, where it is
reproducible and testable. Storing a derivable statement as memory would be
storing a derivation as knowledge — the same mistake the AST tables refuse to
make when they keep no `function_id` and no `renamed_from`. This test is what
makes the definition operational rather than rhetorical: it is the question to
ask of every candidate memory, and it has one answer.

Its corollary, stated so it cannot be quietly dropped:

> **Evidence does not become memory by accumulating.** A file that changed two
> hundred times is a fact about two hundred commits, not a memory. Frequency is
> not knowledge, and repetition is not authorship.

### 3.4 The definition applied, in examples

| Statement | Is it memory? | Why |
|---|---|---|
| "`auth.py` was renamed from `login.py` in `1edec27`." | **No** — evidence | The tool derives it from the stored history. |
| "This file has changed 214 times." | **No** — evidence | A statistic; derivable, reproducible. |
| "This commit is consistent with fixing a refresh-token bug." | **No** — interpretation | A model's reading of the evidence, per run, not stored. |
| "We keep authentication in one module because the state machine was split across two files once and it caused an incident." | **Yes** | Not derivable, not in git; a person's statement about why a rule exists. |
| "Do not add a network call to `auth.py`; it must stay usable offline." | **Yes** | A constraint the tool cannot read out of the code. |
| "The retry wrapper exists because the upstream API used to return 503 under load." | **Yes** | History that was never committed. |

## 4. Fact / Interpretation / Memory — the boundary

### 4.1 The three kinds side by side

| | Historical fact | Model interpretation | Developer memory |
|---|---|---|---|
| Who produces it | the tool, from git or an AST | a model, per run | a person |
| Derivable again | yes, byte for byte | no | no |
| Checkable by the tool | it *is* the check | its citations only | its citations only, never the statement |
| Stored | yes — the evidence tables | no | yes — the memory table |
| Reproducible | yes | no | the row is; the claim is not |
| Usable as evidence | it is evidence | never | **never** |
| What "wrong" means | a defect in the tool | a sentence that overstates its citation | a statement a person corrects |
| How it ends | it does not; it is history | discarded at the end of the run | superseded or invalidated |

### 4.2 The boundary against a historical fact

A fact is derived and reproducible; a memory is asserted and not. The tool can
attest to a fact ("this row says so") and can only attest to a memory that *a
person said it* ("this row says someone stated it at this time"). The two are
stored in different tables, read by different code, and printed under different
headings, because a reader who confuses them has been misled by the tool.

### 4.3 The boundary against an interpretation

An interpretation is written by a model for one run and thrown away; a memory is
owned by a person and kept. The boundary is crossed in exactly one direction and
in exactly one way:

> **An interpretation becomes memory only when a person reads it and confirms it,
> and the memory records that this happened.** The model's text is not the
> memory's authority; the person's confirmation is. An unconfirmed interpretation
> is not stored at all, in any form, and memory is never evidence.

**Who owns the promotion.** The person using the tool — and only that person,
through an explicit act. Not the model, not the tool, not a rule about how often
something happened, and not a default. In v0.5.0 there is no proposal route at
all (§15), so the question is answered twice over: nothing is promoted, because
nothing is proposed.

### 4.4 What memory may never become

- **Never evidence.** No evidence query, derivation or bundle section may read
  the memory table (§13, and the structural test in §20).
- **Never a source of another memory's support.** A memory may cite evidence; it
  may not cite another memory as what it rests on. Lifecycle links
  (`supersedes` / `superseded_by`) are history, not support, and are the only
  memory-to-memory edges allowed.
- **Never a fact by repetition.** Confirming a memory twice, or confirming
  twenty, does not make it checkable.
- **Never a model's statement.** A memory's author is a person; when the tool
  cannot determine who that was, it records `unknown` rather than inventing an
  author.

## 5. Sources

Each candidate source, examined one by one. The question is never "can this
support a memory" — almost anything can — but "can this *be* memory".

| Source | Can it become memory directly? | Why |
|---|---|---|
| **Git history** | **No** | It is evidence: derived, reproducible, checkable. It can be *cited* by a memory; it cannot be one. Repetition does not promote it (§3.3). |
| **Diff** | **No** | Same. A diff is what git printed; it says what moved, never why. |
| **AST** | **No** | Same. A definition's creation, modification and deletion are facts with tests behind them. |
| **Co-change** | **No** | A statistic over a file's life. The evidence contract already forbids reading it as a reason; storing it as one would launder the same mistake into a durable row. |
| **v0.4 interpretation** | **Not directly** | It may be the *draft* a person confirms, and then what is stored is the person's statement, with the interpretation's origin recorded. Unconfirmed, it is not stored. In v0.5.0 this route does not exist (§15). |
| **Documentation** (README, docs, comments) | **Not directly** | A document is a file in the repository: that it said something at a commit is evidence, and the tool does not read prose today. If a person wants a documented statement to be memory, they write the memory and cite the file. The tool must never scrape prose and call the result memory — a sentence lifted out of context and given a row would be exactly the laundering this design forbids. |
| **Developer explicit input** | **Yes** | The only direct source, and the definition of the feature. The person is the source; the memory is what they stated. |
| **Future sources** (issues, review, chat, incident trackers) | **Not directly** | They can become memory only through the same act of confirmation, and adding a source is a unit with its own argument. A memory may *carry* knowledge whose origin is outside the repository — that is the point — but the tool never claims to have read the outside thing. |

**Evidence is not memory.** The table above is one long restatement of that
sentence, and it is the sentence a later unit is most likely to erode: it is
always tempting to "just derive" a memory from a pattern. The definition's test
(§3.3) is what refuses it.

## 6. Ownership — who writes memory

Three options were compared, and the comparison is the decision.

| | A: fully automatic | B: AI proposes, person confirms | C: person writes |
|---|---|---|---|
| Who authors | a model, from history | a model drafts, a person owns | a person |
| Reliability | unknown and unknowable — nothing checks the result | high: a person is the filter | high |
| Automation | total | good: the model does the typing | none |
| Hallucination risk | **unbounded**: a wrong reading becomes durable knowledge | contained: nothing unconfirmed is stored | none from the tool |
| Traceability | to a pattern in history — not to a person | to a confirmation, plus the citations the proposal carried | to a person, plus whatever citations they attached |
| UX | no work for the user | the natural way to accumulate | the user must think of it |
| Engineering | the whole loop plus a memory writer | the proposal path plus a confirmation surface | one command group |
| Core First | **violates it** — memory would need a model | fine, if C exists | it *is* the floor |
| Definition (§3) | **violates it** — memory must be authored, not derived | compatible | compatible |

**Decision: B and C, with C as the floor.** A person's explicit act is the only
thing that creates a memory, ever. A proposal route may exist later; a proposal
is never stored, never authoritative, and never memory. Route A is rejected
outright, and the reason is not that models are unreliable — it is that a
memory's definition is *a statement a person made*, and an automatically
extracted row is not that, whatever its quality.

**v0.5.0 ships C only** (§15). That is not a retreat from B; it is the order the
project already follows everywhere else: the floor first, the layer on top after
the floor has tests.

**Identity is metadata, not authority.** A memory records the author the tool can
determine (the git identity of the environment it runs in), falling back to
`unknown`. There is no login, no permissions and no ownership model in v0.5.0:
the store is local, the person running the command is the one whose act it is,
and the tool must not invent an authority structure the environment does not
have.

## 7. Provenance

### 7.1 The rules

1. **A subject is required.** A memory is about a path, a definition (path and
   qualified name), a commit, or the repository. A memory with no subject could
   never be surfaced by relevance, which would make it invisible — so "no
   subject" is refused rather than stored.
2. **Citations are optional, and their absence is recorded.** A memory may carry
   zero or more citations in the vocabulary v0.4 already uses — `commit`, `file`,
   `definition`, `range`, `cochange`, `absence` — so that the whole tool has one
   way to point at evidence. When there are none, the record says so, and the
   reader is told; the tool never manufactures one.
3. **A memory with no Git evidence is allowed.** That is the feature, not an
   edge case: the knowledge this phase exists for is precisely the knowledge
   that is not in the repository. What is forbidden is a memory that *looks*
   grounded and is not.
4. **A memory may hold knowledge from outside the repository.** The incident,
   the discussion, the vendor's behaviour — the tool cannot check any of them,
   and that is exactly why a memory is not evidence. The memory is the carrier
   of a person's account, and it is labelled as one.
5. **Citations are checked twice.** At admission, the tool checks that each
   citation names something the store holds (reusing the shape of v0.4's
   semantic pass: a commit sha that exists, a path the history contains, a
   definition that appears, a co-change direction the analysis produces). At
   read time, it re-checks and **reports** a citation that can no longer be
   resolved rather than silently dropping it.
6. **A citation is a historical reference, not a live link.** A sha names a
   commit as of the moment the memory was written. History can be rewritten; the
   tool never edits the memory to match.

### 7.2 When the evidence changes underneath a memory

- **A cited commit is gone from the history** (rebase, force-push, a shallower
  clone): the memory stays, and the read says the citation can no longer be
  resolved. Deleting the memory would be the tool destroying knowledge because
  the repository moved.
- **A cited path is gone from the tree**: the same — the memory is kept and the
  reader is told the subject no longer appears.
- **The memory's subject is a definition that no longer exists**: the memory is
  shown under the file that held it, marked as no longer present. A definition
  that was renamed is a different definition (the v0.3 identity rule), so this
  is the ordinary case and not an error.
- **The tool never "updates" a memory.** Only a person changes a memory, and
  only by superseding or invalidating it (§8).

## 8. Lifecycle

### 8.1 The states

| State | Entered by | What it means | Shown as |
|---|---|---|---|
| *(candidate)* | a draft, in the session where it is being written | **Not a stored state.** An unconfirmed draft exists only in the command that is confirming it. | nowhere — it is not in the store |
| **active** | admission | The statement holds now, as far as anyone has said. | a current memory |
| **superseded** | an explicit act naming a successor | A later statement replaced it. Its span is closed; it is kept. | history: "in force until …" |
| **invalidated** | an explicit act with a required reason | It is no longer true, or was never true. No successor. | history, with the reason |

**`archived` is rejected for v0.5.0.** It is a visibility preference ("stop
showing me this"), not a truth status, and the two would be confused the moment
both exist: a reader cannot tell "we stopped caring" from "it stopped being
true". Filtering belongs to a view, and when a view needs it, it will be a flag
on the read commands, not a state a memory can be in.

**There is no `candidate` state in the store**, which is the same decision seen
from the other side: nothing unconfirmed is persisted, so nothing unconfirmed
can be read, counted or mistaken for knowledge.

### 8.2 The acts, and the rules they obey

- **Admission** creates an `active` memory. It requires a statement and a
  subject; citations are optional; the author and the admission time are set by
  the tool.
- **Supersede** requires a successor. The old memory's span closes at the act,
  the successor link is recorded in both directions, and the old memory is never
  shown as current again — but it is never deleted, because the end of a rule's
  life is exactly what a reader of an old commit wants to find.
- **Invalidate** requires a reason (short text). "It was wrong" and "it stopped
  applying" are both invalidation, and the reason is what tells them apart.
- **No in-place edit.** The statement, the subject, the author, `since` and the
  citations are fixed at admission. A correction is a new memory that supersedes
  the old one — including a typo fix, which costs one command. The reason is the
  one this project applies everywhere: a record that can be edited in place is
  not a record of what was said, it is a record of what it was last edited to,
  and nothing tells the reader which part moved.
- **No delete.** A wrong memory is invalidated, which keeps the honest fact that
  it was once believed. The whole database can still be deleted by deleting the
  cache file — and the documentation must say that doing so destroys memory,
  because memory is the one thing in it that cannot be rebuilt (§12).

### 8.3 The worked example from the brief

> Today: "the project uses SQLite because we did not want to run a database
> service." Two years later: the project moves to PostgreSQL.

- The first memory is `active` from its admission (or from its `since`).
- When the move happens, a person writes the second memory and **supersedes** the
  first with it. The first one's span closes; it stays in the store; the second
  becomes `active`.
- Reading a commit from before the move shows the first memory as in force and
  the second as related but not yet in force — which is the truthful account of
  what the project believed when that code was written.
- If instead nobody ever writes the second memory, the first one stays active
  and the tool reports the conflicts it can see (the subject may be gone, a
  citation may no longer resolve) — but it never rewrites the statement. §10.

## 9. Temporal semantics

CodeArchaeology is a project about evolution, so a memory that only described
"now" would be out of place in it.

### 9.1 Three timestamps, three meanings

| Field | Who sets it | What it is a fact about |
|---|---|---|
| `admitted_at` | the tool | **the store** — when the statement entered it. Always known. |
| `since` | the author, optional | **the project** — the commit or date from which the statement held. When absent, the start is *unknown*, and the tool says unknown. |
| `ended_at` (+ reason) | the tool, on supersede or invalidate | **the store** — when the statement stopped being current. |

The first and third are facts about the database; the second is an
author-attested claim about the project. They are never conflated, and the
rendering prints them under different labels.

### 9.2 In force, and the reading of an old commit

> **A memory is *in force* at a commit when its span provably covers that
> commit** — `since` is known and at or before the commit, and the memory has not
> ended before it.

When a commit is read (`explain`, and any later command that shows memory), the
memories related to it are shown in **two groups**, each row stating its span:

- **In force at this commit** — the statements that provably held when the code
  was written.
- **Related, not provably in force** — a memory whose start is unknown, or whose
  span lies outside this commit. It is shown rather than hidden, because hiding
  knowledge is worse than labelling it, and labelled rather than merged, because
  a reader must not read a rule from 2026 as the reason for a commit from 2023.

A superseded memory is shown as history — "in force until commit F" — never as a
current rule. Its successor is named.

### 9.3 Why a memory's time range is closed by an act and not predicted

The tool cannot know when a statement stops being true; only a person can say
so. So a span is *opened* by an author (`since`, or unknown) and *closed* by an
act (supersede or invalidate), and there is no third mechanism — no expiry, no
automatic end when the subject changes. A memory that has outlived its subject
stays in force until someone says otherwise, and the tool reports what it can see
about that (§10).

## 10. Conflict semantics

### 10.1 Memory versus evidence

> **Evidence wins, always, and the tool never resolves the conflict.**

Concretely, when a memory says "this project never calls a network service" and
the commit under the reader's eyes adds an HTTP call:

- the evidence is built, printed and cited exactly as v0.4 built it — memory
  cannot filter, hide, reorder or reinterpret a single row of it;
- the memory is printed beside it, as what a person stated, with its span;
- the tool does not decide which is right, does not amend the memory, and does
  not annotate the evidence with the memory's claim;
- what the tool *does* report is what it can see: the subject no longer being
  present, a citation that no longer resolves, the memory's span not covering
  this commit, its state.

### 10.2 Memory versus memory

Two active memories can contradict each other, and **the tool cannot detect
it**: it does not read sentences, and a program that claimed to compare two
statements' meanings would be making exactly the kind of inference this project
refuses. What the tool does instead:

- memories that share a subject are shown together, so a reader sees both;
- supersede is the human act that resolves a contradiction, and it is recorded
  as what it is — one statement replacing another, not a proof that the first
  was wrong;
- the tool never deletes one because another exists, and never picks a winner.

### 10.3 What the check can see, and what it cannot

Written down in the same spirit as `docs/v0.4-explanation-schema.md` §6, because
the honest limit belongs next to the check:

**The tool can see:** a missing subject; an unresolvable citation; a span that
does not cover the commit; a superseded or invalidated state; a citation that
names this commit while the memory's span starts after it.

**The tool cannot see:** whether a statement is true; whether two statements
contradict; whether the code violates a stated constraint; whether a memory is
out of date in any way that is not one of the visible ones above. Every one of
those is a reader's judgement or a model's *proposal*, never a finding the tool
prints as checked.

## 11. Memory and the AI

### 11.1 The directions, and the one that is forbidden

```
git / AST  ──►  evidence  ──►  interpretation  ──►  printed, never stored
                    ▲                                    │
                    │ citations only                       │ a person reads it
                    │                                    ▼
                 memory  ◄──────────  confirmation  ◄──  draft / proposal
                    │                 (a person)         (a model; not stored)
                    └──►  shown to the reader and to the model, labelled
```

- **Memory is an input to the model** (v0.5.0): the prompt carries it in a
  section of its own, labelled for what it is.
- **Memory may later be drafted by a model** (not v0.5.0): a proposal, never
  stored, never authoritative.
- **Memory is never authored, edited, superseded, invalidated or deleted by a
  model or by the tool acting alone.** The confirmation act is the only edge
  from a draft to the store, and it requires a person.

### 11.2 The loop, and where it is broken

The failure this design exists to prevent:

```
AI interpretation → memory → future AI → new interpretation → memory → …
```

with no human in the loop, each generation treating the last one's output as
knowledge. It is broken **structurally, at the confirmation edge**: there is no
edge from a model's output to the store that does not pass through a person's
explicit act, and no edge from memory back into evidence. A model can influence
what a person writes; that is the residual risk, it cannot be engineered away,
and it is named here rather than papered over. What *can* be engineered away has
been: nothing a model writes is ever stored on its own authority.

### 11.3 How memory reaches the model, and what the model may do with it

- **In the prompt, in its own section.** The section states what it is in as many
  words: statements people made about this project, kept by the tool, not derived
  by it, not checkable by it.
- **It is not the evidence bundle.** The bundle stays exactly what v0.4 froze:
  evidence, built deterministically, printed offline byte for byte. Memory is a
  second, separately-labelled input (§12.4, §13).
- **The model may use it; the model may not launder it.** The rule added to the
  instructions: never present a memory as something observed, never cite one as
  evidence, never invent one. A memory can inform a *reading* — a candidate
  reason — and it can never become an observation.
- **Attribution is allowed and is checkable.** The answer may relate itself to a
  memory through a field of its own: the memory's id, plus the model's sentence
  about the relation. The id is checked against the memory section the model was
  shown (the same shape as v0.4's citation check), and the rendering prints the
  **stored statement verbatim** — the tool's own bytes — with the model's
  sentence beside it, marked as the reading. A model never paraphrases a memory
  into the record.
- **A memory is never citable as evidence.** v0.4's semantic pass checks every
  `evidence[]` ref against the bundle; since memory is not in the bundle, a
  memory citation fails that check unchanged. This costs nothing to enforce,
  which is why the design chose it.

### 11.4 The one amendment to v0.4's rule

`docs/v0.4-problem-definition.md` §11 says the model may use only what the
bundle holds. v0.5 amends it narrowly, and the amendment is written here so it
cannot be discovered later as a contradiction:

> The model may use the evidence in the bundle **and** the curated knowledge it
> is shown beside it, and it must keep them apart: memory may inform a reading
> and may never become an observation.

Everything else in §11 stands. The bundle is still the only source of facts, the
citations are still the facts, and the sentences around them are still the
reading.

## 12. Storage decision

### 12.1 The options

| | A: derive every time | B: SQLite table | C: SQLite table + provenance | D: external store |
|---|---|---|---|---|
| Is it memory? | **No** — derivable knowledge is evidence by definition (§3.3) | yes | yes | yes |
| Reproducible | n/a | yes, as a record | yes, as a record | depends on the service |
| Consistency with the evidence | n/a | one file, one transaction | one file, one transaction | two systems that can disagree |
| Lifecycle | n/a | full | full | full, if the service has it |
| Migration | n/a | one schema version, one exception (§12.2) | same | a second versioning problem |
| Backup | n/a | the one file the user already knows | same | a second thing to back up |
| User editing | n/a | via the CLI only | via the CLI only | two editors for one record |
| Version control | n/a | not in the repository | not in the repository | same |
| Pollutes the evidence layer? | no — it does not exist | **only if the boundary is not enforced** (§13) | same | same |

**Option A is rejected by the definition itself**, and it is worth saying why
plainly: a v0.5 that recomputed its answers from history every time would not be
a weaker version of this feature — it would be a different feature, an evidence
view, and it would violate "authored, not derived" on its first line.

**Option D is rejected for v0.5.0** by Local First and SQLite-only: a remote
store would make the tool need a service to read its own knowledge, and it would
introduce a second system of record. It is not rejected forever as a *sharing*
mechanism — export and import are the honest way to share memory, and that is a
later unit.

**Decision: C — the same SQLite file, its own table, with provenance.** One file
per repository, as today; one thing to back up; memory and evidence joinable in
one query when a commit is read; and the provenance rows are what make the
lifecycle and the conflict reporting possible at all.

### 12.2 The cache exception, stated out loud

This is the one architectural sentence v0.5 changes:

> The evidence tables are a cache over the repository — every row in them can be
> rebuilt by reading git again. **The memory table is not a cache**: no row in it
> can be rebuilt from anything, and every path that rebuilds or discards the
> evidence must preserve it.

Consequences the implementing unit must honour, named here so none of them is
discovered by a user losing their notes:

- `analyze` and `ast` never write, delete or touch memory;
- `clear_history` clears the history and nothing else;
- a schema rebuild — today, `prepare_database` dropping every table when the
  version differs — must **preserve** memory, which makes it the first table the
  drop list does not contain;
- the schema version that adds the table is therefore the first bump that has to
  carry something across, and the storage unit must say how (the table is
  created outside the drop set; a rebuild recreates the evidence tables around
  it);
- both READMEs and `PROGRESS.md` must stop saying "every row can be rebuilt"
  without the exception, and must say that deleting the cache file destroys
  memory.

### 12.3 Two hazards, named

- **Moving the repository.** The database is named after a digest of the
  repository's absolute path, so moving the checkout makes the tool look for a
  new, empty database and the memory *appears* to vanish. The old file is still
  in the cache directory, but the tool will not find it. The fixes are an
  export/import path or a repository-identity key; neither is v0.5.0's, and the
  hazard is recorded rather than engineered around in this unit.
- **`--db` shared across repositories.** A user can already point two
  repositories at one database. Evidence tolerates it; memory would mix two
  projects' knowledge. So a memory row names the repository it was made about,
  and reading a memory under a different repository reports the mismatch instead
  of pretending it applies.

## 13. Architecture boundary

### 13.1 The dependency direction, drawn once

```
        git / AST
            │
            ▼
      evidence layer            (v0.1–v0.3; a rebuildable cache)
            │
            ├──────────────►  interpretation (v0.4)  ──►  printed, never stored
            │                        ▲
            │                        │ the model reads the evidence it is shown
            │                        │
            │                   [ prompt: evidence + memory, separately labelled ]
            │                        ▲
            │                        │
            ▼                        │
        citations only ──────►  memory store   ◄── confirmation ◄── a person
            (memory → evidence)  (not a cache)                     (a model's draft,
            │                                                       never stored)
            │
            └──────────────►  shown to the reader and to the model, labelled
```

### 13.2 The five hard rules

1. **Evidence never depends on memory.** No evidence table, query, derivation,
   bundle section or selection may read the memory table. Held later by a
   structural test in the shape `tests/test_offline.py` already uses: the
   evidence modules may not import the memory module.
2. **Memory never enters the evidence tables.** It is not a fact, not a row in
   `commits`, `commit_files`, `file_versions` or `definition_versions`, and not
   a new column on any of them.
3. **Memory is never evidence for a memory.** A memory cites evidence; it never
   cites another memory as support. The only memory-to-memory edges are the
   lifecycle links.
4. **The model never writes memory, and the tool never writes memory on its
   own.** Only a person's explicit act does.
5. **Memory never overrides evidence.** Conflicts are reported; they are never
   resolved by the tool (§10).

The direction is the whole point of the phase. Written as the failure it
forbids:

```
AI memory  ──►  Git facts        (never)
Memory     ──►  presented as a historical fact   (never)
```

## 14. Minimal memory types

The brief listed six candidates — Decision, Constraint, Pattern, Preference,
Lesson, Context — and asked which survive. Examined against the definition and
against the behaviours the tool actually has:

| Candidate | Survives as a type in v0.5.0? | Why |
|---|---|---|
| **Decision** | **No** | "Why this is so" is content, not a kind. Nothing in the tool branches on it. |
| **Constraint** | **No** | The tempting one, and it fails the same test: the tool cannot check whether code violates a constraint (§10.3), so the type would buy a label and no behaviour. |
| **Pattern** | **No** | A recurring pattern in the code is *derivable* — which makes it evidence at best (§3.3), not memory. A person's statement about why the pattern is kept is a memory whose words carry the meaning. |
| **Preference** | **No** | Same as Decision. A preference is a statement; its content is its type. |
| **Lesson** | **No** | Same. |
| **Context** | **No** | The vaguest of the six, and the one most likely to become a junk drawer. |

**Decision: v0.5.0 has no memory-type field.** The test applied is the project's
own, from `docs/v0.4-explanation-schema.md` §6: *a rule with no case is a rule
that could be deleted without anything going red.* No mechanical behaviour in
this design — storage, provenance, lifecycle, temporal scope, conflict
reporting, selection, rendering, validation — branches on a type. The statement's
own words carry its force ("must", "we decided", "this failed once"), and a
reader gets more from those words than from a label the tool chose.

**What would bring a type back, and how:** a unit that gives a type a
*behaviour* — for example, a check that a constraint's subject was touched by
this commit, or a rendering that separates normative statements from narrative
ones, or a read command that filters by type. Adding one later is a nullable
column with a default, so nothing in this decision forecloses it, and the
candidate list above is kept here so the argument is made again with reasons
rather than re-invented.

## 15. v0.5.0 scope — the minimal vertical slice

### 15.1 The slice

```
a person writes a memory about a subject, with whatever evidence they attach
        │
        ▼
it is stored, apart from the evidence, with its author, its times, its state
        │
        ▼
a reading command shows it — with no model anywhere near it
        │
        ▼
`explain` shows the memories related to the commit, offline and to the model,
and the model may relate its answer to one, attributed and checked
```

Four edges, and each one is Core First: with no model configured, the first
three work completely and the fourth degrades to "the reader sees the memory
beside the evidence", which is the whole feature minus the prose.

### 15.2 The acts, and the read side

| Act | Kind | What it does |
|---|---|---|
| create | write | Admit a statement with a subject and optional citations. The act *is* the confirmation. |
| list | read | The memories the store holds, with their state and their spans. `--json`, like every other reading command. |
| show | read | One memory in full: statement, author, times, state, citations, lifecycle links. `--json`. |
| supersede | write | Replace a memory with a successor; closes the old span; records the link both ways. |
| invalidate | write | End a memory with a required reason. |

The command's name, its flags, the `--json` key names and the block's rendering
are the interface unit's to fix — the same division v0.4's architecture freeze
used. What is frozen here is the *set of acts* and the *semantics* above.

### 15.3 What `explain` does with memory in v0.5.0

- selects the memories related to the commit — subject is a path the commit
  touched (including the file's earlier names), a definition the commit's AST
  changes name, the commit itself, or the repository; plus any memory whose
  citations name this commit;
- orders them deterministically (the most specific subject first, then the most
  recent admission), caps them, and **states every count it dropped** — the
  v0.4 selection discipline, unchanged, because a model reading a truncated list
  as complete is the failure that rule exists for;
- prints them to the reader in both paths: the offline block and the model's
  prompt carry the same memory section, so the two cannot drift;
- labels them for what they are, in the section heading and in the instructions;
- lets the model relate its answer to one, by id, checked against what it was
  shown; the stored statement is printed verbatim, never the model's paraphrase.

### 15.4 Deliberately not in v0.5.0

| Not in v0.5.0 | Why |
|---|---|
| AI proposals of memories | The floor first; the proposal route is where the self-reinforcement risk lives, and it needs its own unit and its own UX decisions (§6, §11). |
| Memory types | §14. |
| Editing or deleting a memory | §8.2. |
| Export, import, sharing, sync | A later unit; the hazards in §12.3 are the argument that it will be needed. |
| Memory in any command's output other than `explain` (beyond the memory commands themselves) | Every other command is about the evidence, and none of them should start reading curated knowledge. |
| Semantic search over memories | SQLite-only, no embeddings (§16); retrieval is by subject and citation, which is deterministic and checkable. |
| Memory for a repository other than the one being read | The store is per repository (§12.3). |

## 16. Non-goals

The brief's list, classified, with the reason. "Never" means this project does
not do it at all, not that it is waiting for a version.

| Non-goal | Classification | Why |
|---|---|---|
| Whole-repository chat | **Not v0.5** (and not v0.4's successor either) | The unit of every answer is a commit. Memory does not change that; it is knowledge about the project, surfaced where the project is read. |
| An automatic agent | **Never in v0.x** | Nothing is executed, nothing is written, nothing is fixed. |
| Automatic code modification | **Never** | The tool reads repositories; it does not write to them. |
| Automatic generation of permanent knowledge | **Never** | This is route A (§6), and it is the definition's opposite. |
| Vector databases, embedding-first retrieval | **Not v0.x** | SQLite-only is a hard constraint; retrieval by subject and citation is deterministic, and "similar meaning" is exactly the kind of inference this project refuses. If it is ever wanted, it has to argue against the constraint first. |
| RAG over the repository | **Not v0.5** | The bundle is built, not retrieved; v0.4's context budget is the retrieval story. |
| Languages other than Python | **Roadmap, not v0.5** | Python-only is the v0.x range. |
| A web UI | **Not v0.x** | CLI before web. |
| Rewriting Git history | **Never** | The tool never writes to the repository; a memory's citations are historical references (§7.1). |
| Modifying the evidence layer | **Never** | §13. |
| Auto-promoting AI output to fact | **Never** | The interpretation contract, `docs/v0.4-problem-definition.md` §12. |

One more, not on the brief's list but implied by the definition:

| Not a memory | Why |
|---|---|
| A task list, a TODO tracker, an issue tracker, a chat log | Those are different tools with different lifecycles. Memory is knowledge about the code, and a store that accepts anything becomes a store nobody trusts. |
| A place for secrets | A memory is plain text in a local database and is printed. The tool has no secret-detection and will not pretend to; the documentation says a memory must not hold credentials. |

## 17. The fifteen questions, answered

The brief required these answered explicitly. Each answer is one line and a
pointer, so nothing has to be reconstructed.

1. **The formal definition** — §3.1: a statement a person made about this
   project, admitted by their explicit act, kept with subject and evidence,
   stored apart from the evidence.
2. **Memory vs historical fact** — §4.2: derived and reproducible versus
   asserted and not; different tables, different headings.
3. **Memory vs AI interpretation** — §4.3: one is stored and owned by a person,
   the other is per-run and discarded; the crossing is a person's confirmation.
4. **The sources** — §5: developer input directly; interpretation only through
   confirmation; everything else (git, diff, AST, co-change, documentation)
   never directly.
5. **Who may create memory** — §6: a person, by explicit act. Only.
6. **Can AI create memory directly** — §6, §11: no. It may draft a proposal
   (later unit), which is not stored and not memory.
7. **Must a memory have provenance** — §7: a subject always; citations optional
   with their absence recorded; citations checked at admission and re-checked at
   read.
8. **Does it have a time range** — §9: yes. `since` (author, optional, unknown
   when absent), `ended_at` (tool, on an act), `admitted_at` (tool, always).
9. **How it is invalidated** — §8.2: an explicit act with a required reason; the
   row is kept.
10. **How it is superseded** — §8.2: an explicit act naming a successor; the old
    span closes; both directions of the link are recorded; the old memory is
    kept and shown as history.
11. **Memory conflicts** — §10.2: not detectable in general, never resolved by
    the tool; co-subject memories are shown together; supersede is the human act.
12. **Memory vs evidence** — §10.1: evidence wins, always; conflicts are
    reported, never resolved; the memory is never auto-updated.
13. **Is memory persisted** — §12: yes, the same SQLite file, its own table,
    with provenance; the first thing in it that is not a cache.
14. **How memory enters `explain`** — §15.3, §11.3: a labelled section shown to
    the reader and the model, selected and counted, attributable by id, never
    citable as evidence, stored statements printed verbatim.
15. **The v0.5.0 minimum** — §15: create / list / show / supersede / invalidate,
    plus `explain` showing related memories; no proposals, no types, no delete.

## 18. Counterexample review

The brief's ten cases, each run against the frozen rules. The verdicts are what
the design does, not what it hopes.

| # | Case | Verdict |
|---|---|---|
| 1 | **A model misunderstands a commit — can it pollute memory?** | Not by itself: in v0.5.0 no model creates memory at all, and later a proposal is not stored until a person confirms it. Pollution requires a human act, and the record then says a person stated it. Residual risk: a person can be persuaded by a wrong draft — named, not engineered away (§11.2). |
| 2 | **A developer writes a memory with no Git evidence** | Allowed, and it is the feature (§7.1.3). The record says it has no citations; the reader is told; the tool never fabricates one. |
| 3 | **An old memory conflicts with new code** | The evidence is printed untouched; the memory is printed beside it with its span; the tool reports what it can see and resolves nothing (§10.1). The human supersedes or invalidates. |
| 4 | **Two memories contradict each other** | Not detectable, and not resolved (§10.2). Both stay active, shown together under their shared subject; supersede is the human's act. |
| 5 | **A memory describes a rule that has since died** | Its span is closed by invalidate (or it stays in force until someone says otherwise). The row is kept and shown as history, with its reason (§8). |
| 6 | **The project changes developers — whose memory is it?** | Content: the project's. Custody: the person running the tool, locally, in v0.5.0 (§6, §12). Each memory names its author; the documentation must not present the store as a shared team record. |
| 7 | **The project is forked** | Memory does not follow automatically: it lives in the local database, and a fork is a different checkout. Its citations may or may not resolve in the fork's history. Export/import is the later, explicit answer (§12.3). |
| 8 | **History is deleted (rebase, force-push, a shallow clone)** | The memory is kept — it is not a cache — and the read reports the citation that no longer resolves (§7.2). The tool never edits or drops it to match the repository. |
| 9 | **A model reads memory and produces a new wrong reading, and it accumulates** | The loop is broken at the confirmation edge: no model output reaches the store without a person, and memory never becomes evidence, so a wrong reading cannot corrupt facts (§11.2). |
| 10 | **"Tell me why this project is designed this way" — can the answer tell facts, confirmed memory and speculation apart?** | Yes, structurally: evidence under its citations, memory as its own labelled section with the stored statement printed verbatim, the model's relation marked as a reading, and speculation having no field to live in (§11.3, §4.1). |

## 19. What this unit does not decide

Left to the units that implement v0.5, in the same division v0.4 used:

- **The schema** — the table's columns, its indexes, the schema version bump,
  and the exact mechanism that preserves memory across a rebuild.
- **The command names and flags**, and whether memory is a command group.
- **The rendering** — headings, order, colour, what the block says about itself.
- **The prompt wording** — the memory section's instructions and their exact
  phrasing; and whether the prompt now deserves a unit of its own (it is bigger
  than it was, and that question was already open in v0.4).
- **The JSON key names**, in `explain --json` and in the memory commands' own
  output.
- **The citation-check implementation** — reusing `validation.py`'s shape without
  importing its evidence-only assumptions.
- **Export / import**, repository identity, and the move hazard of §12.3.
- **The proposal route**, which is a unit of its own.
- **The README roadmap row's wording** (§1.5), to be tightened by the unit that
  ships v0.5.

Also still open from v0.4, and unchanged by this freeze: whether the evidence
alone can be read in block form once a model is configured; and whether the
prompt gets a unit. One v0.4 open question **is** answered here: an explanation
is still never stored. What a person confirms becomes memory, and memory is not
an explanation — it is the person's statement, with the interpretation's origin
recorded beside it.

## 20. Acceptance criteria

What the units that build v0.5.0 must be able to show. Written as tests would be,
because that is how this project holds every other rule it has.

1. **The evidence layer is unchanged by memory.** For a fixed database, the
   bundle's bytes for a commit are identical with and without memories stored,
   and the v0.4 determinism test still passes.
2. **Evidence never reads memory.** Held structurally: the evidence modules
   (`context.py` and everything below it) do not import the memory module —
   the shape `tests/test_offline.py` uses for the provider boundary.
3. **Only a person writes memory.** No code path from `analyze`, `ast`,
   `explain`, the provider or the validator writes, updates or deletes a memory
   row; the memory acts are the only writers.
4. **Memory survives a rebuild.** After a second `analyze`, after an `ast` run,
   and after a schema rebuild, every memory is still there, unchanged, with its
   citations and its lifecycle.
5. **Core First holds.** With no model configured, the memory commands and
   `explain` (which prints the evidence and the memory section) all work and
   exit 0.
6. **The three kinds stay apart.** In the rendered output and in the JSON, the
   evidence, the stored memory and the model's reading are distinguishable
   without reading the prose; the stored statement is printed verbatim.
7. **A memory is not citable as evidence.** An answer whose `evidence[]` names a
   memory is refused by the unchanged semantic pass, and a test says so.
8. **Provenance is honest.** Every memory has a subject; a memory with no
   citations says so; an unresolvable citation is reported, never dropped; no
   citation is ever fabricated.
9. **The lifecycle is recorded, not rewritten.** Supersede closes the old span
   and links both ways; invalidate requires a reason; the old row is never
   deleted or edited.
10. **The conflict rules hold.** Memory cannot filter, reorder or annotate the
    evidence; a conflict is reported and never resolved; a memory is never
    auto-updated.
11. **Selection is stated.** The memory section `explain` sends is capped and
    every dropped count is printed, in the v0.4 discipline.
12. **The documentation contract holds.** Both READMEs document the new commands
    and their blocks are replayed by the test suite, as every command's are
    today; the cache exception is stated wherever the database is described.
13. **No new dependency and no new network.** `typer` and `rich` stay the only
    runtime dependencies, and the memory path never reaches a network.

## 21. Open questions

Recorded rather than answered, because answering them here would be designing
units that have not started.

1. **Export / import, and repository identity.** The move hazard (§12.3) is real
   and the fix is not obvious: an export path, a repository-identity key, or
   both. The freeze decides only that memory must not be silently lost, and that
   whatever is chosen must keep the evidence cache's rebuildability intact.
2. **Whether `--db` should refuse a second repository's memory** or merely
   report it (§12.3).
3. **Whether a memory should be able to cite prose** — a README's lines, a
   comment — which today's `range` citation cannot express (it names a diff
   hunk). Not v0.5.0; a new citation kind is a decision with its own argument.
4. **What the tool should do when a memory's subject disappears from the
   history**: report it (decided), but where, and how loudly, is open.
5. **Whether the memory section should be printed by `explain` when the model
   path is used but the memory list is empty** — an empty section is a statement
   too, and the v0.4 rule for empty fields (`possible_reasons: []`) is the
   precedent to follow.
6. **The prompt unit.** v0.5 makes the prompt carry a second kind of input; the
   question of whether it deserves a unit of its own is now more pressing than
   it was in v0.4, and still unanswered.
7. **How the evidence alone is read in block form once a model is configured** —
   unchanged from v0.4.
8. **The README roadmap row's wording** (§1.5), and whether the phase's name
   stays "Developer Memory" once the definition is this one.
