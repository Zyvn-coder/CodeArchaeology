**Status: the design freeze the problem definition defers to.** It turns the
five rulings of 2026-10-24 (`docs/v0.6-problem-definition.md` §11) into a
design: the bundle's shape for a revision range, the diff's read mechanism and
its stated bound, the selector, the selection rule for a set, the run record
(option E), and the amendments to two frozen documents. **No code accompanies
it** — implementation starts only after the user reviews this freeze, in the
units §11 sketches.

**Date:** 2026-10-24. **Tree read:** `338b362` — working tree clean, `main`
level with `origin/main`, the last release `v0.5.3` an annotated tag at
`90b2c8a`. CI is green on `338b362` itself (all four jobs, run 40066909584),
so the standing precondition — tree clean, last release's CI green — holds on
both halves today.

**What this freeze stands on.** The user ruled: the unit is B, a revision
range, with A (one commit) kept as the floor and C demoted to a selector over

execution of those rulings. Where this freeze decides something they did not
name, §9 marks it so the user can veto it at review rather than discover it in

## 2. The diff: one object per unit, computed by git, bounded per path

### 2.1 The rule that keeps it single

> **The bundle carries the diff of the unit — the two endpoints git itself
> would diff — and nothing else.**

For one commit: its parent and it. For a range: the resolved base and the
resolved tip. Per-commit diffs inside a range are **never carried**: they are
recomputable from stored facts, they would multiply the bundle's largest
section by the commit count, and the net diff is the honest object for the
unit a reviewer holds — a pull request shows the net diff too. What the
intermediate commits did is already in the bundle as facts: paths, change
types, line counts, definition events, per-commit rows.

This rule is what dissolves the merge question. A merge commit **as the unit**
has no two endpoints git would unambiguously diff, and it keeps today's answer:
the `merge_no_diff` absence, parents stored, nothing recomputed, no parent
chosen. A merge commit **inside a range** needs no diff of its own at all,
because the unit's diff is base-to-tip and exists regardless of what the range
contains. `docs/v0.4-problem-definition.md` §3.3 feared "the diff of a merge is
not well-defined until a parent is chosen"; under this rule the question never
arises, which is a better answer than choosing a parent would be.

### 2.2 The read mechanism, and the honest correction it makes

**Git computes every diff the bundle carries.** The reader invokes git with
pinned flags, per unit:

```console
git diff --no-color --no-ext-diff --no-textconv --unified=3 \
         --find-renames=50% <base> <tip>
```

with the base side replaced by git's well-known empty tree object
(`4b825dc642cb6eb9a060e54bf8d69288fbee4904`) when the unit is a root commit.
The flags mirror the ones `context.py` already pins for `git show`
(`SHOW_ARGUMENTS`): `--no-color`, `--no-ext-diff`, `--no-textconv` keep user
configuration from changing the bytes, and `--unified=3` is git's own default
context — the diff is what `git diff` prints, nothing less. Rename detection
is pinned explicitly (`--find-renames=50%`) for the same reason: left to
configuration, two machines could print different bytes for the same unit, and
the bundle's whole design is that they cannot.

**This corrects an assumption the evidence contract made, and the amendment
says so.** The contract's §5 assumed the diff would come through
`objects.py`'s blob reader — two blobs, differenced by the tool. That shape is
rejected here, with the reason: the standard library's `difflib` is not git's
diff algorithm, and the same two blobs can produce different hunks under it
than under git's. `docs/v0.4-problem-definition.md` §12 already fixes what a
diff **is** in this project — "what git printed" — so a diff the tool computed
would be a new kind of thing wearing an old name. Reading git's output costs a
subprocess the tool already pays for the line ranges; computing diffs in
Python would buy nothing and cost the fact layer its meaning.

### 2.3 Where the diff rides, and what each row says

The diff is **per path, riding the file row** — the same row that already
carries the change type, the counts and the hunk line spans. One place per
fact, and the file row is the place a citation already means. Every touched
path gets its diff whatever the file type: the Python-only boundary governs
definition evidence, not patch text, and a range that renames a `.md` file has
that fact in its diff. The special rows, each a stated sentence and never a
silence:

| Case | What the row carries |
|---|---|
| Binary path | The existing binary fact (counts are null), plus `binary_no_text` — a named absence, **never an empty diff string** |
| Pure rename, no line changes | The rename line git prints (old path, similarity); no hunks — visible as the event it is, not as "nothing happened" |
| Root commit | The whole file as an addition, bounded like any other text and stated as whole-file |
| Merge commit as the unit | `merge_no_diff`, unchanged from today |
| Path absent from the unit's net diff | One of two named absences (§3.5): `gone_within_range` or `net_unchanged` — the partition is mechanical and both halves are facts |

### 2.4 The bound: shape here, value in the implementation unit

**One per-path character cap.** No whole-diff cap, no summary tier: the
whole-diff ceiling is this cap composed with the file cap the selection
already holds, and a summary would be a derived reading — the tool summarising
a diff is exactly the inference the contract makes the model's, not the
bundle's.

Each diff row states what it did, in the precedents' own shapes: the text it
carries (`characters`), the whole size (`characters_total`), and whether it was
cut (`truncated`) — the `ranges_total` pattern, one row saying its own bound.
The omission the selection reports is the count of rows whose text was cut, in
the `selection` block where every other dropped thing is counted. The cap is a
named constant (`DIFF_CHARACTERS`) beside the six in `selection.py`, and its
value is **not fixed here** — the user's ruling keeps it open, and it is to be
set in the implementation unit against the same benchmark harness extended to
range shapes, quoted then, exactly as `docs/v0.4-context-budget.md` §3 set the
first six.

The frozen rule that makes the bound honest rather than cosmetic: a bounded
diff is never presented as the whole one (contract §9), and the offline path
prints exactly what the model is shown — so the bound appears in both places
or in neither, and the reader can always see what was cut.

## 3. The bundle for a range

The contract's §3 tables were written for one commit. The amendment (§9 of
this document) extends them; this section is the semantics. Throughout, "the
set" means the commits `git rev-list` returns for the resolved range.

### 3.1 The selector

`explain <rev>`, where `<rev>` is either a single revision — today's unit A,
prefix accepted as now — or `X..Y`, two revisions git can resolve, each side a
sha, a branch, a tag or `HEAD`. **Both sides are resolved to full shas at
invocation and those shas are what the bundle records.** A ref is a moving
name; a bundle built on a name would be a bundle built on a moment pretending
to be a permanent thing. Same resolved pair plus same database, same bytes —
that is the determinism claim, and §11 pins it with a test. Re-running the
same ref names after the refs move is a different set, honestly so.

C (a branch, a pull request) stays what the ruling made it, a selector over B:
`main..feature` is a range, computed locally by git, and nothing about it
needs the network or a hosting-platform object. **A bare branch name is not
accepted as a range** — it would need an implicit base (the default branch?
the tracking branch?), and an implicit base is an assumption about someone
else's repository layout wearing the clothes of a convenience.

Two failures, each a named error and never a guess: a side that does not
resolve (git's own message, the rev named), and a range that resolves to no
commits (stated as such — "the range is empty", with the two shas, rather than
an empty bundle printed as though it were evidence).

### 3.2 The ordering

```console
git rev-list --topo-order --reverse <base>..<tip>
```

Oldest first, parents before children, and the order is a function of the
commit graph alone — not of timestamps, which can lie about sequence, and not
of the machine. This order is the bundle's spine: the commit list, the
per-path occurrence lists and the definition event lists all cite it, so
"first", "then" and "last" in any answer mean the same thing every run.

### 3.3 The bundle, item by item

Mirror of the contract's tables, extended to the set:

**The unit.** The resolved base and tip shas; the commit count; the distinct
authors; the first and last authored timestamps in the bundle's order; and
that this is a range, not a commit — the header says which unit it holds, in
the place a reader looks first.

**The commits.** One entry per commit in the §3.2 order: sha, author name and
email, authored and committed timestamps, the message in full (the bundle
never caps; the view caps per commit as today), the parents, and whether it is
a merge. A commit in the range that the database holds no analysis for is
**not skipped and not faked**: it appears, marked `not_analyzed` — a named
absence (§3.5), because "the analysis does not cover this commit" is a fact a
reader must have, and a range over a `--since`-analyzed repository will
contain such commits routinely.

**The paths.** One row per path the set touched, carrying: the net change type
git reports for the endpoints (`git diff --name-status`, with the rename line
for a rename); the occurrence list — which commits touched it, in the bundle's
order, each with its own change type and counts; `old_path` and `similarity`
where git reported them; the aggregated added and deleted lines (a sum, stated
as a sum); the hunk line spans of the **net** diff (new side), where the
single-commit bundle's spans already sit; and the bounded diff text (§2). A
path touched by five commits is one row with five occurrences, not five rows —
the file is one thing that happened to several times.

**The definitions.** One row per (path, definition) the set's commits changed,
aggregated: each event inside the range, by commit and in the bundle's order
(`created`, `modified`, `unchanged` against the nearest earlier readable
version, exactly as the AST pass computes them today); the event count; and
the definition's presence at each endpoint — present, absent, or no readable
version to tell — derived lifecycle-style from the nearest readable versions
at base and tip. **No identity inference is added:** a definition renamed
inside the range is still one ending and another beginning, the
`tests/test_ast_storage.py` rule, and the aggregation groups by (path,
qualname) without joining across a rename.

**The file's life.** Per path, the lifecycle as today, with the events of the
set's commits merged in by the bundle's order — no order invented, because the
order is git's.

**The earlier-commit window.** Per path, the path's commits **before the
oldest in-range commit that touched it** — its life up to the moment this
change first touched it, which is the set-level reading of what the window
means for one commit today. Capped as now: five in the bundle, two in the
view.

**Statistics.** Hotspots and co-change per path, semantics unchanged, the
correlation labelling unchanged — they are facts about a file's whole life and
say nothing about why this range touched it.

**Memory.** The sibling section, unchanged in shape and rules (row 5: the
layer is not touched). It is what people stated; it is not evidence; the model
may use it only where the frozen rules already allow.

### 3.4 What stays out of the set bundle

Per-commit diffs (§2.1). Anything outside the repository (the *Never* table,
which the range does not relax — a range has no more access to the issue
tracker than a commit does). Any ordering of the set's commits by "importance"
— the order is topological or it is nothing. Any claim that the set is *one*
change: ten commits in a range are ten commits that arrived between two
points; whether they form one change is a reading the model may offer as a
candidate and the bundle may not assert.

### 3.5 The absences, four become eight

The contract's §7 discipline — each absence a different sentence, never
collapsed — extends to eight. The four that exist, unchanged:
`merge_no_diff`, `parse_failed`, `no_version_stored`, `not_in_this_commit`.
The four this phase adds, each with the mechanical test that detects it:

| Absence | Means | Detected by |
|---|---|---|
| `binary_no_text` | The path's blobs are binary; there is no diff text — not an empty diff | git reports no text for the path pair |
| `not_analyzed` | This commit of the range has no row in the database's analysis | the commit sha is absent from `commits` |
| `gone_within_range` | The path was created inside the range and deleted before the tip; it is in the occurrence rows and **not in the net diff** | in neither endpoint's tree, but the set's commits hold rows for it |
| `net_unchanged` | The path was touched inside the range and ends where it began — same blob at both endpoints — so the net diff prints nothing | in both endpoint trees with the same blob, and the set's commits hold rows for it |

The last two are a partition of "touched in the range, absent from the net
diff", and they must never be merged: a file that lived and died inside a
change and a file that was changed and changed back are different facts, and
each is the kind of thing a fluent paragraph would slide over.

## 4. The selection for a set

The view's architecture is unchanged — deterministic constants, largest-rows
rules, a refusal past the window, never a truncation — and every rule is
re-stated for the set rather than inherited by silence.

**The new dimension is commits.** The set's commit list is itself a list the
model may be shown too little of, so it gets what every list gets: a cap
(`COMMITS`, value set against the benchmark, not fixed here), a largest-rows
rule — largest by the added and deleted lines the commit's rows sum to, ties
by sha, which is a fact about the rows and not a claim about importance — and
a `selection` entry: `{"shown": 25, "omitted": 180}` in the block every other
dropped thing is counted in.

**The existing lists go set-wide.** The file list is the set's paths, largest
by the summed added and deleted lines across the set's rows for that path,
ties by path. The definition list is the set's definitions under the existing
rule — largest by the lines the definition spans, ties by path and name —
because size is a fact about the definition and event count is a fact about
the set, and the view orders by the thing that does not change meaning when
the unit changes; the event count rides the row as a number, uncapped in the
bundle. The message cap stays per commit (`MESSAGE_CHARACTERS`), and how many
messages there are is the commits cap's business, not the message cap's. The
absence cap, the history window and the co-change caps are unchanged in name
and value domain.

**The constants stay constants.** Six names carry over (`FILE_CHANGES`,
`RANGES_PER_FILE`, `DEFINITIONS`, `ABSENCES`, `HISTORY_WINDOW`,
`MESSAGE_CHARACTERS`); two are added (`COMMITS`, `DIFF_CHARACTERS`). No
configuration, for the reason `selection.py` already gives: a selection that
moved with a setting would make the model's input depend on the machine.

**A list that lost rows is never silent** — the property the problem
definition named as load-bearing (§3.3 item 4) holds per list: commits, paths,
definitions, spans, absences, and now diff characters per row and cut-diff
rows in the selection block. The note the reader sees (`LARGE_COMMIT_NOTE`
generalised: it names the unit, not the commit) still says where the whole of
it can be read: the same command, no model.

## 5. The command line

### 5.1 `explain <rev>` — one command, two units

The command gains nothing but the range reading of the argument it already
has. `explain <sha>` is today's behaviour byte for byte; `explain X..Y` is the
set bundle through the same three paths — offline print, `--json`, model —
because the frozen rule ("what the offline path prints is exactly what the
model is shown") does not permit a fourth path to appear for the new unit.

### 5.2 `--no-model`

Added, for both units. Today a configured model means the evidence alone can
be read only by unsetting environment variables, which is a hoop nobody jumps
twice. The flag forces the offline path — the bundle is printed, the note says
why, nothing reaches a provider, **no run row is written** (§6.4). It is the
flag the problem definition's §12 named, taken with its stated purpose: a
person with a model configured can still read the evidence alone.

### 5.3 `runs` — the read half of option E

Option E's question — "was this explanation produced from the bundle I have
now?" — needs both halves: the row that records a past run, and a way to see
it. The table is ruled (row 3); a table nothing reads is half a feature, so
this freeze designs the smallest surface that completes it:

`archaeology runs` — the model runs this database recorded, newest first,
default the last twenty, one line each: when, the unit (a sha or `base..tip`),
the model, and the bundle hash. `--json` for the same rows as objects. No
filters, no lifecycle, no export — a run is history and history is not
managed; `memory export` is memory's, and this is not memory.

**This is the one surface in the freeze beyond what the rulings named**, and
it is marked so at review: §9 lists it as the user's to cut, and cutting it
costs only the reading of the table — the write side stands on the ruling
either way.

### 5.4 The envelope

`explain --json` keeps its shape — `state`, `explanation`, `evidence`,
`selection` when something was dropped, `memory` when there is one — and gains
one key: `bundle_sha256`, the hash of the evidence object the same command
carries (§6.3). A program holding an answer can then compare its input against
a stored run row without a second command, which is the whole of what the key
is for. Nothing else in any command's JSON moves; `commit --json` is untouched.

## 6. The run record

### 6.1 Placement and name

The table is `explain_runs`, and the name is chosen against a collision the
tree already contains: **"provenance" in this project means memory's
subject-and-citation re-checking** (v0.5 Unit 7), and a second thing wearing
the word would blur the first. The run record follows the memory layer's
placement precedent exactly — its own version stamp
(`explain_runs_schema_version`, starting `"1"`, in `meta`), its own create
path, **deliberately outside `storage.TABLES`**, because it is not evidence
and must never be reachable as though it were. The evidence stamp
`schema_version` stays `"4"`; this is the only schema change v0.6 commits
itself to (`PROGRESS.md`, the rulings section).

### 6.2 The columns

Exactly the ruled five, plus the unit a row cannot mean anything without:

| Column | Holds |
|---|---|
| `unit_kind` | `commit` or `range` |
| `unit_spec` | the sha, or `base..tip` with both shas resolved |
| `bundle_sha256` | §6.3 |
| `provider` | the configured base URL |
| `model` | the configured model id |
| `prompt_sha256` | §6.5 |
| `created_at` | UTC, the moment the explanation was printed |

No text. No sentence a model wrote, nowhere, in any column — row 3's first
half, and the boundary tests extend to hold it (§11).

### 6.3 `bundle_sha256` — the hash of the evidence, not the view

sha256 over the bundle object's canonical JSON serialisation — `sort_keys`,
compact separators, the same object `explain --json` carries as `evidence`.
Not the view: the view is derived from the bundle deterministically, so the
bundle names the run, and the selection that happened is a function of the
bundle and the constants. Same resolved unit plus same database gives the same
hash, run after run; a different hash means the evidence moved, which is the
one fact "replay" can honestly check.

### 6.4 When a row is written

**Exactly when an explanation is printed** — the validator has accepted the
answer and the command is emitting it, online path only. A provider failure
writes nothing (no answer existed). A model failure, retried once and failed
again, writes nothing (nothing was shown, and a row would claim a run whose
output nobody can see). The offline path and `--no-model` write nothing (no
model was reached; there is no run). One printed explanation, one row,
append-only, forever — a run is history, and the record is the record.

### 6.5 `prompt_sha256` — a version that cannot forget to bump

The prompt has no version identifier today (`INSTRUCTIONS` is a bare constant
in `explanation.py`), and option E needs one. The design hashes the
instructions text itself — sha256 over the exact `INSTRUCTIONS` string the
prompt was built from — rather than a version constant a human must remember
to raise: a forgotten bump is a silent lie about what the model was told, and
a hash cannot lie. The alternative is recorded as rejected for that reason
alone, not for cost.

### 6.6 The boundary, restated for this table

The run record is not evidence: the evidence layer never reads it, no command
treats a row as a fact about a commit, and nothing in it can enter a bundle.
It is a fact about a **run**, the way a shell's exit status is — history about
the tool, not history about the repository. The five memory boundary rules are
untouched (row 5), and the test suite that holds them gains the parallel
cases for this table (§11).

## 7. The prompt

### 7.1 What `INSTRUCTIONS` gains

Two rules, in the register of the existing ten:

**The unit rule.** The evidence is for one commit or for a range of commits,
and it says which. In a range: the commits are listed oldest first; a path may
appear under several commits, and its row is the whole of what the set did to
it; the diff is **the net diff of the range** — what the whole change did
between its two endpoints — and a path that does not appear in it carries one
of the named absences saying why; never read the range as one commit, and
never present "these commits form one change" as anything but a candidate.

**The bounded-diff rule.** A diff row carrying `truncated` holds part of its
text, and `characters_total` says the whole size — read it as the
`ranges_total` rule's sibling: never treat a bounded diff as the whole one,
and never make a claim about the lines that were cut.

### 7.2 What the citation vocabulary gains

One evidence kind: `changeset`, ref form `{base_sha}..{tip_sha}` — the unit
itself, for the claims that are about the whole ("ten commits arrived between
these two points"). **It is not called `range` because `range` is taken**: the
citation kind for a changed span (`<path>:<start>-<end>`) has held the word
since v0.4, and a second meaning on one word is the kind of ambiguity the
validator exists to refuse. The `range` kind generalises to the net diff's
spans unchanged. The commit kind accepts any commit in the set; the
uncertainty kinds gain the four new absences. The schema amendment (§9) lists
all three extensions.

### 7.3 No prompt unit

The wording changes in place, inside the unit that builds the set bundle, and
the dedicated prompt unit stays deferred as it has been since
`docs/v0.4-context-budget.md` §8 left it open. The reason is the same one
that doc gave: nothing here needs a unit of its own, and a freeze that spawns
a unit per edit is a freeze that will be argued with by process rather than by
reasons.

## 8. What the provider layer notices: nothing

The provider receives a string (`provider.explain(context: str)`) and returns
text or raises. The range changes what is **in** the string — a set bundle
under a prompt with two new rules — and nothing about how it is reached, keyed
for, retried or refused. No provider code, setting, error path or test of the
provider layer moves in v0.6, and that is by design: the unit and the evidence
are this phase's work, and the network was finished in v0.4.

## 10. What this freeze does not do

- **No code, no schema, no CLI.** Nothing here is implemented; §11 sketches
  the units that would build it, and they start only on the user's word.
- **No Memory change** (row 5): no new read, no new write, no semantics. The
  sibling section rides along exactly as it is.
- **No pilot, no second experiment, no macOS job** — each shelved or optional
  on its own record, none moved by this document.
- **No prediction, scoring or judgement anywhere** — §2.5's rule of the
  problem definition, restated because a range invites it: "what this change
  may do next" is as unavailable for ten commits as for one.
- **No new runtime dependency** — a git subprocess and the standard library.
- **No per-section configuration, no relevance ordering, no summaries of
  diffs, no identity inference across renames** — each rejected above with its

## 11. The test matrix, designed

The units that build this hold it; the matrix is fixed here so the tests are
written to a design rather than to what the code happened to do.

**The diff.** The bound states itself (`truncated`, `characters_total`, the
cut count in `selection`); a bounded diff never prints unbounded; binary is
`binary_no_text` and never an empty string; a pure rename is visible; a root
commit's whole-file reading is stated; a merge as the unit is `merge_no_diff`;
the same unit gives the same bytes twice (the determinism pin).

**The set.** A path touched twice is one row with two occurrences; created and
deleted inside is `gone_within_range`; changed and changed back is
`net_unchanged`; the two are never merged; an un-analyzed commit in the range
is `not_analyzed`; the order is the graph's (parents before children, stable
across runs); the window is "before the range first touched the path";
definitions aggregate without joining across a rename.

**The selection.** Every list that lost rows says so — commits, paths,
definitions, spans, absences, cut diffs; the refusal past the window names the
size and says the evidence was already reduced.

**The paths' parity.** The offline print for a range is the set bundle whole;
`--json` carries the whole evidence and the selection; the two never drift on
anything the model was given whole.

**The run record.** A row exactly when an explanation is printed; offline and
`--no-model` write none; a failed call writes none; the stored hash equals the
envelope's `bundle_sha256`; the same unit re-explained gives the same hash;
the evidence layer never reads the table (boundary case, parallel to the
memory five).

**The validator.** A `changeset` ref resolves against the unit header and
nothing else; the new uncertainty kinds are accepted and their spellings only;
a citation of a commit not in the set is refused as today's sha checks refuse.

**And the harness trap, carried forward:** the README replay tests pass only
under `uv run pytest` (`PROGRESS.md`, the v0.6 problem-definition section) —
the invocation is part of the command, and a red that means nothing is the
worst kind.
