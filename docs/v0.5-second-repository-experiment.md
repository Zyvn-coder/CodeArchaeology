# The second repository: `python-tqdm/tqdm`, and six calibrated questions

**What this is.** The second half of the understanding experiment's materials: a
second repository, chosen by measurement, with a six-question set built the way
`docs/v0.5-understanding-experiment.md` §4.1 prescribes, so that the pilot can
run the same within-subject crossover on a repository that is *not* attrs.

**What this is not.** It is not a change to the frozen protocol. The levels, the
rubric, the control and treatment conditions, the `explain` exclusion and the
pre-registered decision rule stay exactly as
`docs/v0.5-understanding-experiment.md` §4, §6, §7 and §10 define them. This
document adds materials; it does not edit the agreement.

**Status: prepared, not run.** Date: 2026-10-09. No production code, schema, CLI
or dependency was changed by the unit that wrote this, and — per the task's own
rules — nothing was committed. **Review pass 2026-10-09:** every claim this
document rests on was re-measured against the clone; the corrections are the
clone's HEAD line (§5, §9.6), the date columns in §10, several blame/event lists
in §5's calibration records, and the two instrument facts in the method note. The
review, its startup conditions and its verdict are in
`docs/v0.5-second-repository-review.md`.

**How each claim is marked.** **CONFIRMED** = the repository or the tool shows it
directly (a command was run, and its output is quoted or counted). **INFERRED** =
reasoned from evidence that exists but does not state it. **UNKNOWN** = the
evidence in the repository cannot settle it. Estimates are labelled as estimates
and never presented as measurements.

**One methodological note worth reading first.** Every candidate question
below was derived with the tool's own views (`structure --history`, `commit`,
`file`) and verified with `git blame`, `git log -S` and `git log --grep`
against the checkout. Where a claim rests on the tool's database, the command
that produces it is named. Two conventions bit the derivation and are recorded
because they will bite a facilitator: **the tool reports *commit* dates, while
`git log --date=short` prints *author* dates**, and tqdm has rebased commits
where the two differ by months (`48b90f6`: authored 2016-12-28, committed
2017-09-23 — CONFIRMED); and **definition lifecycles are not queryable by path in
the raw tables**, because the tool unions each file's rename chain
(`tqdm.py -> tqdm/_tqdm.py -> tqdm/std.py` — CONFIRMED), so a per-path query
silently truncates a definition's life at the rename.

**Two instrument facts re-measured while reviewing this document (2026-10-09),
recorded because a facilitator will meet both.** `ast` reports **11 of 2,214 file
versions unparseable** (0.5%); one of them is a `tqdm/std.py` version, `59f457a8`
(2019-10-29), which is genuinely broken Python (`except Import Error:` — the
syntax-error commit `b3589f6` two days later fixes it), and the tool marks it
`unavailable / parse failed` rather than pretending it parsed; that commit
touches only the pandas integration, and **none of the six definitions' event
lists carries a blind spot or an unresolved event**. And a second full
measurement reproduced the preparation costs within 15% of §3.1's numbers
(`analyze` 0.84 s, `ast` 26.2 s cold, database 19.5 MB).

## 1. Task background and goal

The first repository is `python-attrs/attrs`: 1,845 commits over 11.7 years, one
maintainer, a meticulously maintained changelog, and a question set of six
(Q-A…Q-F) whose levels are two L1, two L2 and two L3. Deriving those six also
produced three procedural rules (experiment document §2.6), and the sharpest of
them is a warning about repositories like attrs: **a densely documented project
saturates L1** — most candidate "why" questions are answered in the working tree,
so the questions that discriminate had to be hunted in changes the changelog
never recorded.

That is why the second repository had to be chosen on a property attrs does not
have. The goal of this unit is therefore twofold, and the second part is the one
that matters:

1. **External validity.** Show that the tool is useful in a project with a
   different shape, a different history and different maintainers, so a positive
   result cannot be read as "the tool works on attrs".
2. **A harder test, deliberately.** Per the task's instruction, the second
   repository was *not* chosen because the tool performs well on it. It was
   chosen because it is a repository where the tool's central claim — that a
   definition's *life* answers questions its current text cannot — is testable
   and not pre-answered by a changelog.

**What a facilitator gets:** six complete questions (T-1…T-6) with ground truth,
evidence chains, three scoring anchors each, what the tool can and cannot do for
each one, and a verification procedure for a second scorer; plus the
correspondence to the attrs set, the validity risks, and the execution plan.

**What a facilitator does not get:** participants. Nothing in this document was
measured on a human. Every level below is a property of the repository and the
question, not of a person's performance.

## 4. The choice: `python-tqdm/tqdm`

**Chosen for the one property attrs lacks and the experiment needs: it keeps no
changelog in the tree.** tqdm's history has to explain itself through commit
messages, diffs and code comments, which is precisely the material L2 and L3
questions are made of — and it means no question in the set can be answered by
grepping a maintained user-facing document.

**CONFIRMED** for the choice:

- **2,132 commits over 12.9 years, 147 authors** — above every floor, and a
  *different* social shape from attrs: contributor-fed, merge-centred
  ("bump version, merge pull requests #1781, #1773…"), release-per-merge, with no
  single owner rewriting whole modules.
- **No changelog in the tree.** The probe's only hit is a GitHub Actions
  workflow. Release notes live in GitHub Releases, i.e. outside the repository,
  so they cannot smuggle answers into either arm. This is the property that makes
  the second set *harder* than the first, deliberately.
- **15% of messages explain themselves** — the highest rate measured, and the
  raw material for L2 questions. Examples read while deriving: "fix
  multiprocessing lock creation leak — fixes #982", "Avoid global multiprocessing
  locks — Moving locks to class properties", "Assign to `_instances` and monitor
  under the class lock" with a two-paragraph body naming two races.
- **A different *kind* of "why".** attrs' questions are about API design and
  interpreter workarounds. tqdm's are about the outside world: terminal width and
  ANSI codes, broken pipes and closed streams, multiprocessing start methods,
  threads that outlive the interpreter, and the arithmetic of rate estimation.
  If the tool only works on attrs' kind, this set will show it.
- **Affordable.** `analyze` 0.95 s, `ast` 30.1 s, database 19.5 MB (measured);
  the clone is 8 MB. A facilitator can prepare a session in under a minute, which
  matters because §6.2's crossover needs two prepared repositories.
- **`hotspots` has a clear top file** — `tqdm/std.py`, 496 commits,
  +6,254/−4,699 (the tool's own view) — so the derivation and the participants
  both land on the same 1,532-line module rather than wandering.

**The costs and constraints, stated now rather than discovered later:**

- **The file was split, twice.** `tqdm.py` → `tqdm/_tqdm.py` (2015) →
  `tqdm/std.py` (2019-08-26). The tool unions the rename chain for definitions
  (CONFIRMED: `format_interval` reports a 2013-10-26 creation, and `file
  tqdm/std.py` prints the chain), but the raw tables keep one path per version.
  A facilitator who queries the database by path will truncate lives at 2019;
  nobody using the CLI will.
- **Definitions created before 2019 are still usable**, because the chain is
  unioned; but a question whose answer *requires* walking back through the split
  is riskier than one anchored after it. All six questions below are anchored on
  constructs whose lives the tool reports completely (verified per question).
- **tqdm's README is its manual** and embeds docstrings verbatim
  (CONFIRMED: `README.rst:613` repeats `tqdm.std`'s `write()` docstring). It is
  therefore an L1 source in the same way attrs' changelog is, and each question's
  calibration record below states what the README does and does not say.
- **Author dates and commit dates differ** on rebased commits (one example
  named above; the tool reports commit dates). A facilitator reading a date aloud
  from the tool and from `git log` can see two different years for one commit.
- **UNKNOWN:** whether tqdm's merge-commit style makes the tool's `commit`
  command *less* useful than in attrs, where every change was a squashed PR
  commit. This is a real possibility and is listed in §9.

### T-1 — which bars move when a nested bar finishes (`_decr_instances`) — **L1, an instrument control**

**The site**, `tqdm/std.py:687-715`:

```python
    @classmethod
    def _decr_instances(cls, instance):
        """
        Remove from list and reposition another unfixed bar
        to fill the new gap.

        This means that by default (where all nested bars are unfixed),
        order is not maintained but screen flicker/blank space is minimised.
        (tqdm<=4.44.1 moved ALL subsequent unfixed bars up.)
        """
```

**The question, as a participant would read it:** *"When a bar nested inside
another bar finishes, which bars move? The code moves exactly one bar and its own
docstring admits that display order is not maintained as a result. Why is that
the trade, and has it always been this way?"*

**Learning goal.** That a library's user-visible behaviour can be a deliberate
trade between two kinds of ugliness, and that the trade is *recorded* — including
the version it changed in.

**Ground truth.**

| | |
|---|---|
| The rule | on completion, `close()` calls `self._decr_instances(self)`; that method finds the unfixed bars whose `pos` is at or past `last = (nrows or 20) - 1` (the ones that overflowed the screen) and moves **the one with the smallest `pos`** into the vacated row: `inst.clear(nolock=True); inst.pos = abs(instance.pos)` (`std.py:705-715`) |
| Why one and not all | moving every subsequent bar up is what tqdm did up to 4.44.1; it repaints more of the screen, and the docstring states the goal as minimising "screen flicker/blank space" at the cost of ordering |
| When it changed | `bee52fa1 rework decr_instances()`, authored 2020-03-30, first release **v4.45.0**; its message body: "Reduces screen flicker/blank space at the cost of ordering. — don't move displaying (non-overflow) bars upwards — move the first unfixed (`pos >= 0`) overflow (`pos >= nrows`) bar to the current `pos`" |
| The `pos` arithmetic | `pos` is the bar's row; `_get_free_pos` (`std.py:680-685`) returns the lowest row not in use (`min(set(range(len(positions) + 1)).difference(positions))`), and a `position=` passed by the user is stored negated (`std.py:1097`) — the `abs()` calls are how the two conventions are kept apart |

**Evidence chain.** `tqdm/std.py:687-715` (the docstring and the three statements
that implement it); `bee52fa1` (full diff: the single-bar move replaces the loop);
`git tag --contains bee52fa` → `v4.45.0` (CONFIRMED); the tool:
`archaeology structure tqdm/std.py <repo> --history` lists `tqdm._decr_instances`
as 28 events from 2016-01-10 to 2020-10-06, with `bee52fa1` and `6943da2e` on
2020-03-30 (CONFIRMED from the JSON view).

**External corroboration.** No PR or issue is needed; the docstring, the commit
body and the release tag carry the whole answer. This is deliberate for an
instrument control.

**Common wrong answers.** (1) "All bars below shift up by one" — the pre-4.44.1
behaviour, and the single most likely answer from someone reading only the loop
without the docstring. (2) "Order is maintained because `pos` is renumbered" — the
opposite of what the docstring says. (3) "The bar is removed and the next refresh
repaints everything" — plausible, contradicts `close()`'s explicit call.

**Scoring anchors.**

- **Correct (2):** one bar is moved — the unfixed *overflow* bar with the smallest
  `pos`, into the vacated row — and the reason is flicker/blank-space reduction at
  the cost of ordering; evidenced by the docstring, the code, or `bee52fa1`.
- **Partially correct (1):** the flicker trade-off without the "one bar, and which
  one" half, or the rule without any evidence.
- **Correctly uncertain:** not applicable — the repository states the answer.
- **Wrong (0):** "all subsequent bars move up", or a claim that the behaviour is
  accidental.

**What the tool uniquely adds: nothing.** This is the point of an instrument
control: `hotspots` sends a reader to `std.py`, `structure --history` names the
2020 commit, and `commit bee52fa1` prints the body — but so does `git blame`,
which lands on `bee52fa1` for twelve of the method's lines (CONFIRMED, §5.7's
calibration record). If the tool arm does *worse* here, the tool is actively
misleading, which is the outcome §10 cares most about.

**What the tool cannot do.** It cannot tell a participant *what* the right answer
is; it only names the commit. The reading is theirs.

**Verification by a second scorer.** Open `tqdm/std.py:687-715`; confirm the
docstring's claim against lines 705-715; run
`git show bee52fa1 --stat` and read the message body; check
`git tag --contains bee52fa` contains `v4.45.0`. Scoring is mechanical from
there: the answer either names the single-bar move and the flicker trade, or it
does not.

**Calibration (§4.2's three tests, run on the clone).**

### T-2 — why the library owns a write path (`write` / `external_write_mode`) — **L1, an instrument control**

**The site**, `tqdm/std.py:717-759`. The public method and the context manager it
delegates to:

```python
    @classmethod
    def write(cls, s, file=None, end="\n", nolock=False):
        """Print a message via tqdm (without overlap with bars)."""
        fp = file if file is not None else sys.stdout
        if fp is None:
            return
        with cls.external_write_mode(file=file, nolock=nolock):
            # Write the message
            fp.write(s)
            fp.write(end)
```

**The question, as a participant would read it:** *"A progress-bar library ships
its own `write()`. Why does that exist, and what exactly does it do to the bars on
screen before and after the message?"*

**Learning goal.** That output interleaving is a real problem with a designed
solution, and that the solution has an condition in it that looks arbitrary until
you know why (`fp == inst.fp`, or both streams being stdout/stderr).

**Ground truth.**

| | |
|---|---|
| What it does | it enters `external_write_mode`, which acquires the write lock (unless `nolock`), **clears every live bar that writes to the same file** — where "same file" includes the case that both the message's stream and the bar's stream are among `sys.stdout`/`sys.stderr`, because terminals interleave the two — writes the message, and **refreshes the bars it cleared**, releasing the lock in a `finally` |
| Why | so that a message appears on its own line instead of being overwritten by the next bar refresh; the method's docstring says "without overlap with bars" and the context manager's says "Disable tqdm within context and refresh tqdm when exits" |
| The odd condition | `inst.fp == fp or all(f in (sys.stdout, sys.stderr) for f in (fp, inst.fp))`, commented in the tree as "because both are mixed in terminal" (`std.py:746-750`) |
| Where it came from | `9c2a524 Added contextmanager to disable tqdm and allow smooth write to stdout` (authored 2017-08-25, first release **v4.17.0**); `write()` itself dates from `d3c3ad2` (2016-04-25) and gained `nolock` in `da46cd43` (2017-09-23) |
| The safety net nearby | `DisableOnWriteError` (`tqdm/utils.py:166-206`) wraps a stream so that a write failing with `errno 5` or a "closed" `ValueError` quietly sets `miniters = inf` instead of crashing the program — the same problem one layer down |

**Evidence chain.** `tqdm/std.py:717-759` (code and both docstrings);
`tqdm/utils.py:166-206`; `README.rst:613` (the README embeds the same docstring);
`9c2a524` and `git tag --contains 9c2a524` → `v4.17.0` (CONFIRMED); the tool's
lifecycle for `tqdm.write` (13 events, 2016-04-25 → 2026-07-07) and
`tqdm.external_write_mode` (10 events, 2017-09-09 → 2026-07-07) — CONFIRMED.

**External corroboration.** `74e6eba Fix overlap of nested progressbar`
(the related older problem, found by `--grep="overlap"`); the README's

### T-4 — the divisor in the EMA (`EMA.__call__`) — **L2**

**The site**, `tqdm/std.py:211-239`:

```python
class EMA:
    """
    Exponential moving average: smoothing to give progressively lower
    weights to older values.
    ...
    """
    def __init__(self, smoothing=0.3):
        self.alpha = smoothing
        self.last = 0
        self.calls = 0

    def __call__(self, x=None):
        """..."""
        beta = 1 - self.alpha
        if x is not None:
```

### T-5 — the write lock's three lives (`TqdmDefaultWriteLock.__init__`) — **L3, discriminating**

**The site**, `tqdm/std.py:74-98`. The class's own comment, then the constructor:

```python
class TqdmDefaultWriteLock:
    """
    Provide a default write lock for thread and multiprocessing safety.
    Works only on platforms supporting `fork` (so Windows is excluded).
    ...
    """
    # global thread lock so no setup required for multithreading.
    # NB: Do not create multiprocessing lock as it sets the multiprocessing
    # context, disallowing `spawn()`/`forkserver()`
    th_lock = TRLock()

    def __init__(self):

        # bars works only if fork available (Linux/MacOSX, but not Windows)
        cls = type(self)
        root_lock = cls.th_lock
        if root_lock is not None:
            root_lock.acquire()
        cls.create_mp_lock()

        if root_lock is not None:
            root_lock.release()
```

**What is *not* comparable, and must not be reported as if it were.**

- **Topic overlap.** The two repositories share almost no subject matter (attrs:
  class construction, exception semantics, interpreter versions; tqdm: terminals,
  processes, rate estimation). That is the point, but it means a difference in
  results cannot be attributed to a single "difficulty of the repository".
- **Question count per subsystem.** attrs concentrated four of its six in one file
  with one maintainer; tqdm spreads them across four subsystems written by
  different people. A participant's prior experience (e.g. with terminal
  libraries) therefore matters more in tqdm than in attrs. **This is the largest
  single threat to comparability** and the reason §7 asks for prior-familiarity to
  be recorded per repository.

  measurement here that says one is harder; what matters is that the *crossover

  repository effect and not as a tool effect. **If only one repository is run per
  participant per arm — as §6.2's one-repository fallback allows — the repository's

- **Level composition is identical**, which is the one thing deliberately kept
  equal (2/2/2). That is what makes the per-level breakdown in §7.3 of the
  experiment document meaningful across the two sets.

## 7. Validity risks, answered against the task's checklist

**Does the set lean on one historical pattern? No — CONFIRMED.** The six
questions rest on: a documented behaviour rule (T-1), a documented protocol
(T-2), a concurrency race (T-3), a mathematical correction (T-4), a
process-safety incident series (T-5), and a set of positional guards (T-6). Four
different *kinds* of reason across four subsystems.

**Can any question be answered from the README alone? Two, and that is by
design.** T-1 and T-2 are the L1 instrument controls; the frozen protocol requires
two L1s precisely so that a tool which *misleads* is detectable. No L2 or L3
question is answerable from the README (CONFIRMED by the L1 greps in §5; the only
README hits are the `write()` docstring and a `position=n` sentence that does not
state the `leave` rule).

**Is any question unscoreable for lack of ground truth? No — CONFIRMED by
construction.** Every question's answer was reconstructed from at least two
independent artefacts (a message plus a diff, or a docstring plus the code), and
each has a written correct / partial / correctly-uncertain form. Three
*sub*-claims are marked UNKNOWN in the ground truths (why `__new__` rather than
`__init__`; the physical mechanism of the lock leak; why the EMA correction is a
post-division) — and in each case the scoring anchors say so, so a participant is
not punished for stopping where the evidence stops.

**Could "detailed" be mistaken for "correct"?** The rubric already handles it: a
score of 2 requires an artefact that exists and supports the claim, and 1 is
"right conclusion, no usable evidence". The risk is real for T-5 and T-6, where a
plausible narrative can be spun from the code alone; the mitigation is in the
anchors ("require the origin for a 2") and in the fact that the ground truths name
the SHAs a scorer can check.

**Could confidence be mistaken for understanding?** That is measured, not
mitigated: confidence minus correctness is a declared endpoint (§7.3), and it is
the one that catches a tool that makes people confidently wrong.

**Does the tool arm get information the control arm lacks?** **Yes, by
construction, and the frozen protocol owns that decision.** The treatment adds the
nine reading commands; the control has git, the source and the repository's own
documents, with the internet off. What this document had to ensure is that the
*ground truth* is reachable by the control too — otherwise the question is unfair
rather than discriminating. Each question's reachability check does that: every
non-L1 answer is reachable by `git blame`/`-S`/`--grep` alone (CONFIRMED in §5),
and each L3 is a question where those commands produce a *misleading* answer
rather than none.

**Does any question hint at the answer the tool would give?** Checked one by one:
T-1's question names the trade without naming the rule's version; T-2 asks what the
method does, not which commit; T-3 names `__new__` and the lock (both visible in
the code) but not the races; T-4 names the divisor (visible) and does not mention
biasing; T-5 names the three constructs (visible) and asks why; T-6 states the
two phenomena a user would notice and asks where the rules came from. **No
question names a commit, a date, or a reason.**

**Can the tool's time saving be separated from its comprehension effect? The
primary endpoint already does this** — score 2 counts correctness with evidence,
time is reported separately and never blended (§7.1, §7.3). This set adds one
practical note: T-1 and T-2 are expected to be *fast* for both arms (the answer is
in the file being read), so a time difference there is not evidence of anything.
Report the per-level breakdown, as §7.3 requires.

**Can someone who does not know the repository finish in reasonable time?** The
frozen cap is ten minutes per question. Each answer here needs between one and
four artefacts to reach (measured: the reachability checks are 1–3 commands plus
reading); the two L3s need a lifecycle list to be *read*, not just produced. **The
facilitator's rehearsal is the only way to know** — and per §6.1 that run's data is
discarded. **UNKNOWN until run.**

## 8. What it costs to run, and how to score it

**Estimates, not measurements. Nothing here was run on a person.**

- **Time per participant.** The frozen protocol allows ten minutes per question,
  sixty for the set, ninety for the session. **Estimate: the tqdm set fits the
  same envelope — INFERRED** from the reachability checks (1–3 commands to the
  evidence, quoted per question in §5) and from the answers' size (each ground
  truth is 4–6 rows). A facilitator should expect T-1 and T-2 to finish early and
  T-5/T-6 to consume the cap. The rehearsal (§6.1) is what turns this into a
  measurement.
- **Preparation.** Clone tqdm in full (8 MB), then `analyze` and `ast`:
  **measured 0.95 s and 30.1 s**, database 19.5 MB. `git status` must be clean
  before the session, and `CODEARCHAEOLOGY_AI_*` must be unset for the treatment
  arm (the tool must run offline; `explain` is excluded anyway).
- **What participants must already know.** Python at a working level; that git
  exists and `blame`/`log` do. **Nothing about terminals, multiprocessing,
  progress bars or tqdm's API is required** — but prior familiarity with tqdm as a
  user is a *real* advantage on T-1 and T-2, so it must be recorded per
  participant (see the threat in §6).
- **The same grouping design works.** Six to eight participants, at least three
  who have never read either repository, at least two experienced Python
  developers, nobody who has read the tool's source or the experiment documents
  (experiment document §6.1). The counterbalanced crossover (§6.2) can now be run
  two ways: repository X versus Y (attrs versus tqdm) or, if only one repository
  is prepared, two matched halves of one set — with the learning-effect
  limitation the document already states.
- **Keeping participants away from the answers.** The questions and ground truths
  stay in the facilitator's copy (Appendix D shape, Appendix C for answers);
  participants get no repository history beyond what the arms allow; the tqdm
  clone must be the *participant's* checkout, not the derivation one (the
  derivation clone contains no extra artefacts — it is a clean `git clone` — but
  the rule is the rule). Anything a participant writes is collected before the
  debrief.
- **Blind second scoring.** Transcribe the paper answers into one file per
  participant, strip the arm label, and give the second scorer §5's ground truths
  plus the rubric. Each question's "verification by a second scorer" paragraph
  lists the commands that reproduce the ground truth, so the second scorer never
  has to trust the first. Where the two disagree, the experiment document's
  threats table already requires reporting it.
- **What gets recorded per answer.** The answer text, the evidence named, the
  minutes (capped at ten), a confidence 0–100, and — for the treatment arm — the
  command after which the answer arrived (a facilitator's note).
- **What cannot be concluded with too few participants.** With n≈6 and a
  within-subject crossover, no p-values, no significance claim, and in particular:
  no per-repository effect size (each participant contributes three questions per
  repository — too few), no claim about tqdm as a *class* of repository, and no
  claim about the AI layer (`explain` is excluded). §10 of the experiment document
  also stands: a null, harmful or merely convenient result is a finding, and the
  response is to change the plan, not to re-run with easier questions.
