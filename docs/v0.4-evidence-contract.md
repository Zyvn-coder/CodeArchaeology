# v0.4 evidence contract

This is Unit 2 of v0.4, and it is the unit the rest of the phase hangs on. It
decides **what the model is allowed to see**, item by item, and what each item
is. The problem definition (`docs/v0.4-problem-definition.md`) says what is being
asked; this says what may be used to answer it.

## 1. The principle

The user's words, and they are the whole of the rule:

> **AI 永远不能把 Evidence 和 Interpretation 混成一个东西。**

Three consequences, and each is structural rather than a matter of tone:

1. **The bundle is sectioned by kind.** A section holds one kind of thing, and
   nothing is in two sections.
2. **An inference names the facts it rests on.** An inference with no facts
   behind it is not offered.
3. **The split survives into the output.** A reader must be able to tell which
   sentence is a fact and which is a reading, without having to judge the
   model's confidence from its phrasing.

The failure this prevents is specific. A fluent paragraph that slides from "the
file was renamed twice" into "the team was restructuring the package" reads as
one continuous finding, and the second half is not in the data. Nothing about
the prose marks the seam, so the seam has to be put in the structure.

**The other half of this contract is `docs/v0.4-problem-definition.md` §12.**
This document's rule is that the two kinds must never be mixed; that one says
what the answer *is* — an interpretation of the evidence, not a historical fact —
and therefore why mixing them is not a stylistic failure but a false claim about
the output. Read together: the bundle holds facts, the answer is a reading of
them, and the reading has to show where it is reading.

## 2. The three kinds

**Fact** — a value that is stored, or read from git, and can be pointed at. "The
parent of this commit is `1edec27`." "The definition `Config.load` was modified."
Anyone with the database and the repository can check it.

**Inference** — a reading of facts. It may be offered. It must be marked as a
reading, and it must name the facts it rests on.

**Unknown** — not in the data and not derivable from it. Never offered, in any
phrasing, however hedged. "The author was under time pressure" is not a cautious
inference; it is a statement about a fact that does not exist.

The line between the last two is worth stating exactly, because it is thin:

- "This change is **consistent with** fixing a defect" — the code now guards a
  case that the previous version did not, and the guard is in the diff. That is
  an **inference**, and it may be offered with those facts named.
- "The author was fixing a bug they hit in production" — the defect, the
  production incident and the author's reason are all outside the repository.
  That is **Unknown**, and it is not offered.

## 3. The contract

Every item the model may see, where it comes from, and what it is.

### The commit

| Evidence | Source | To the model | Kind |
|---|---|---|---|
| The sha | `commits.sha` | yes | Fact |
| Author name and email | `commits` | yes | Fact |
| Authored and committed timestamps | `commits` | yes | Fact |
| The message, in full | `commits.message` | yes | Fact |
| The parents | `commit_parents` | yes | Fact |
| That this commit is a merge | derived: two or more parents | yes | Fact |

### What it touched

| Evidence | Source | To the model | Kind |
|---|---|---|---|
| The paths it touched | `commit_files.path` | yes | Fact |
| The change type, as git reported it | `commit_files.change_type` | yes | Fact |
| Added and deleted line counts | `commit_files` | yes | Fact |
| `old_path` and `similarity`, for a rename or a copy | `commit_files` | yes | Fact |
| That a file is binary — the counts are null, not zero | `commit_files` | yes | Fact |
| **The diff** | not stored; read from the repository | yes, bounded — see §5 | Fact |

### The file's life

| Evidence | Source | To the model | Kind |
|---|---|---|---|
| The names the file carried, in order | `lifecycle.py` | yes | Fact |
| When it appeared, when it was last changed | `lifecycle.py` | yes | Fact |
| Whether it is still there | `lifecycle.py` | yes | Fact |
| How many commits touched it, and what it cost in lines | `statistics.py` | yes | Fact |
| The other commits that touched it | `relationships.py` | yes | Fact |

### The AST layer

| Evidence | Source | To the model | Kind |
|---|---|---|---|
| Every definition at this version — kind, qualified name, lines, decorators, fingerprint | `definition_versions` | yes | Fact |
| Each definition's `created` / `modified` / `unchanged` against the nearest earlier readable version | `definition_versions` | yes | Fact |
| That a version did not parse, and the parser's reason | `file_versions` | yes | Fact |

### Repository statistics

| Evidence | Source | To the model | Kind |
|---|---|---|---|
| How often these files change, against the rest | `hotspots` | yes | Fact, as a count |
| Which files change alongside them, and the counts | `cochange` | yes | Fact, as a count |
| What those numbers mean for this commit | — | only as an inference, with the counts named | Inference |

### What a change was for

| Evidence | Source | To the model | Kind |
|---|---|---|---|
| "This is consistent with fixing a defect" | the facts above | only when they support it, and marked | Inference |
| "This is consistent with an API change" | the facts above | only when they support it, and marked | Inference |

### Never

| Evidence | Source | To the model | Kind |
|---|---|---|---|
| The author's reason, motive or intent | — | **no** | Unknown |
| Whether the change worked, or what happened after it | — | **no** | Unknown |
| The issue, the review, the discussion | — | **no** | Unknown |
| Anything outside the repository | — | **no** | Unknown |
| What will break, or what to do next | — | **no** | Not offered at all — a prediction, ruled out by the problem definition §6 |

## 4. One item can be a fact and an inference at once

The co-change row above is the case that matters, and it is the one most likely
to be got wrong.

**The counts are facts.** "This file and `app.py` appeared together in 7 of this
file's 9 analyzed commits, and 4 of those were shared" is arithmetic over stored
rows. It is checkable, and it is the same number every time it is computed.

**What the counts mean is not.** "These two files are related", "changing one
usually means changing the other", "this commit touched both because they belong
together" — each of those is a reading. Co-change is a correlation over a file's
whole life; it is not a fact about this commit, and it is not causation.

So the freeze is: **the bundle carries the value as a fact, with its denominator,
and any reading of it is the model's and must be marked as one.** The same rule
applies to the line counts, the change frequency and the definition counts. None
of them is evidence about *why*; all of them are evidence about *what*.

## 5. Where it comes from, and what it costs

Two sources, and the difference matters for the design freeze:

- **The database** — everything except one row of the table. Already computed by
  `analyze` and `ast`, read straight out of SQLite.
- **The repository** — the diff, and nothing else. Blob reads through the one
  `git cat-file --batch` process `objects.py` already keeps open.

**The diff is the one item that does not exist yet.** Nothing in the tool
produces a diff today: `commit_files` holds counts, not text, and no module calls
`difflib` or `git diff`. It is obtainable — the reader resolves `<commit>:<path>`
and returns the bytes — but it is new work, and it is the only row of this
contract that is.

**It is also the only item whose size is unbounded.** A generated file, a vendored
copy or a lockfile can produce a diff of hundreds of thousands of lines in a
commit that is otherwise three lines of real change. So the contract says the
diff is available **and bounded**, and that the bound is stated in the bundle
rather than applied silently: a model reasoning over a quietly truncated diff
believes it has seen the whole change, which is the mixing failure of §1 in its
most dangerous form. What the bound is — a line count, a per-file count, a
summary for large files — is the design freeze's to set.

## 6. The merge hole

Measured on a purpose-built repository rather than taken from a comment: a merge
commit is stored with its message, its author, its date and **both parents**, and
with **zero rows in `commit_files`**. `git log` prints no diff for a merge, so
there is nothing to store.

Two things follow, and both belong in the contract:

- **An empty changed-file list has two meanings** — "git reports no diff for a
  merge" and "this commit changed nothing" — and they are not the same. The
  bundle must say which one it is, the way the structure view already refuses to
  print an empty listing for a version nobody could read.
- **The diff of a merge is recomputable, and only because the parents are
  stored.** That is a capability the contract names rather than assumes: it is
  work the freeze may choose to do, not something the bundle has for free.

## 7. Absences are evidence, and each is labelled

v0.3 already treats absence as evidence. The bundle inherits that, and the four
absences must stay four different sentences:

| The absence | What it means |
|---|---|
| A definition has no row | The definition is gone. Absence is the evidence for the deletion; nothing is written to spell it out. |
| A version has a parse failure and no definition rows | **Nothing could be read.** Not "nothing was there". |
| A path has no version row at this commit | The file was not part of this commit's recorded events. |
| A merge has no rows in `commit_files` | Git reports no diff for a merge. Not "nothing changed". |

The bundle reports all four. An explanation that runs any two of them together is
wrong in a way a reader cannot see, which is why the distinction is a contract
item and not a nicety.

## 8. What the separation looks like

The bundle is sectioned, and the section is the kind:

```
FACTS            the commit, what it touched, the definitions, the file's life
STATISTICS       counts over the file's history — facts about the history,
                 not about this commit
ABSENCES         what is not there, and which of the four it is
UNKNOWABLE       named, so the model can see the edge of what it was given
```

The output carries the same split. Every sentence is attributable to a section;
an inference names the facts it rests on; and a sentence that fits no section is
not printed. The `UNKNOWABLE` section is not padding — it is how the model is
told where the data stops, instead of being left to discover it by guessing.

## 9. What this contract forbids

- Stating an inference as a fact, however hedged the wording.
- Offering anything in the *Never* table, in any phrasing.
- Reading a statistic as a fact about this commit.
- Treating an absence as emptiness, or one of the four absences as another.
- Presenting a bounded or truncated diff as the whole diff.
- Predicting, scoring or judging.
- A sentence that cannot be attributed to a section.

## 10. What this unit does not decide

- **The diff's bound**, and how a bounded diff is presented.
- **Whether the diff is in the bundle at all** in the first version. It is
  contract-available, but it is new work and it is the largest thing in the
  bundle; the freeze may choose to ship without it and say so.

Everything Unit 1 §10 left open stays open: how the model is reached, the command
and its arguments, the no-AI path, the bundle's serialisation, how a networked
feature is tested, the shape of the output, and whether an explanation is ever
stored.
