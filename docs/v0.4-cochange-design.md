**Unit 10.** Written 2026-09-30, the day after v0.3.0 was released. This unit
writes no production code: this file is the deliverable, and it is what Unit 11
is checked against.

Everything marked *measured* was run on this machine on 2026-09-30 under CPython
3.13.5 against real databases built from the fixtures in `tests/sample_repo.py`
and from a generated fifty-thousand-commit history. The traps recorded in §16
were hit for real while writing this, not imagined.

A number nobody can explain is worse than no number.

## 1. Definition

> **Co-change is the observed frequency with which another file changed in the
> same commits as the file you asked about.**

One sentence, and every word in it is doing work:

* *observed* — counted from stored commits, never inferred.
* *frequency* — a ratio, with a denominator that §6 pins down.
* *another file* — never the file itself (§11).
* *in the same commits as the file you asked about* — the sample is the file's
  commits, not the repository's (§6).
* *changed* — the commit has a `commit_files` row for it, whatever the letter
  (§2).

It is a description of the past, not a claim about the future or about meaning:
"these two files moved together" is what the data says; "these two files belong
together" is not.

---

## 2. Observation model

The unit of observation is already stored and needs no new reading of git:

```text
commit → file occurrence   ==   one row of commit_files
```

A commit's *occurrence set* is the set of files that have a row for it. The
naive statistic "how many times did A and B appear together" is then

```text
|commits(A) ∩ commits(B)|
```

and it is identical whether computed from the rows or from pairs generated
within each commit — `commit_files` has `PRIMARY KEY (commit_sha, path)`, so a
file cannot contribute twice to one commit even when git reports several
records for it (a rename, a copy). The deduplication the rule asks for is
already a property of the schema, not a step the algorithm must remember.

**Every letter counts as an occurrence**, `A`, `M`, `R`, `D` alike, and so do
the letters that never occur in practice (`C`, `T`, `U`, `X`, `B`). A file being
created, edited, renamed, or deleted is the file's life being touched by that
commit, and the co-change question is "was this file part of what that commit
did". An `R` row is one occurrence, not two, even though it names two paths —
the row is keyed on the new path and the old path is a column on it.

Two consequences of the storage model are worth stating because they shape the
numbers:

* **Merge commits contribute nothing, for free.** `git log --raw --numstat`
  prints no diff for a merge, so those commits were stored with zero rows and
  they can only ever have an empty occurrence set. They are in `commits`, they
  are in the denominator of nothing, and no rule is needed to exclude them.
  This is not a co-change decision; it is how `history.py` reads history, and
  §8 confirms it is the right behaviour for this statistic too.
* **A commit git found no changes for is also empty** — the same handling, for
  the same reason.

## 3. Identity: life, not name

**A co-change pair is a pair of file identities, where a file identity is the
lifecycle identity `lifecycle.py` already builds.** This is the answer to
"Co-change 是按 path 统计还是按 file lifecycle 统计": it is lifecycle-level, and
the word *path* appears in the design only as a way to name a life.

The rule was applied by construction and then checked by hand, because the
intuitive implementation is subtly wrong in a way that only shows up in
fixtures that reuse a name:

* The identity walk is the same walk `build_lifecycles` does — `A` starts a
  new life, `M` extends the one holding the path, `R` moves it, `D` ends it,
  with the same "unoccupied path falls back to the last life that held it"
  rule for interleaved branches.
* Each commit is reduced to a **set of identities**. A rename commit therefore
  contains one identity, not two: the `R` row's old and new path are the same
  file, and if a naive implementation resolved both paths it would count a file
  as co-changing with itself.
* If a file is deleted and re-created at the same path, the re-creation is a
  **new life** (an `A` row always starts one), and co-change does not bridge the
  two. Reusing a path is not the same file coming back.
* If git failed to recognise a rename — the lifecycle fixture's
  `heavy.py` → `renamed.py`, reported as `D` + `A` because too little content
  survived — the two are two lives, and the pair between them is not invented.
  The tool reports what git observed, including the limit of git's rename
  detection; `statistics.py` already states that consequence for line counts,
  and co-change inherits it.

**The user-facing consequence is the one the rule was chosen for.** Querying
`core/app.py` answers for the file that was born as `app.py` and was renamed
twice — the pre-rename history is included, because it is the same file. This
matches the single-file command: `file core/app.py` already prints
`History: app.py -> src/app.py -> src/core/app.py`, and co-change is the same
file seen from the other side. A name can belong to more than one life, so a
query answers for **every life that ever carried the name**, oldest first,
exactly as `file.py` does. Answering for one and hiding the others would be the
mistake the lifecycle model exists to avoid.

## 4. Formula

The default, and the only metric Unit 11 implements:

```text
commits(A)   = { c : c has a commit_files row for a path of A's life }
analyzed(A)  = { c ∈ commits(A) : |occurrence set of c| ≤ large_commit_limit }
shared(A,B)  = |analyzed(A) ∩ analyzed(B)|

co_change_score(A → B) = shared(A,B) / |analyzed(A)|
co_change_count(A,B)   = shared(A,B)                    (a fact, see §5)
```

`co_change_score` is **directional**: `score(A → B)` is the share of A's
analyzed commits that also touched B, which is the question a developer asks —
*"when I change this file, what else tends to move with it?"* — and it is the
only one of the three candidates whose denominator is small enough to carry
signal (§6).

The score is a property of a *pair and a direction*, so the natural key of a
result row is `(A, B)` with A fixed by the query; `score(B → A)` is not shown
unless B is queried. That asymmetry is a feature, and the fixture shows it
plainly: in the sample repository `score(app.py → README.md) = 1/3` while
`score(README.md → app.py) = 1/1` — README has been touched exactly once, and
that one commit also touched app.py.

### Rejected metrics, and why

* **Jaccard** `|∩| / |∪|` is symmetric and stable, but it answers "how alike
  are these two files' commit sets", which is not the question. It also
  punishes a file for having a long life: a busy file and a quiet file that
  always move together still score low because the union is large.
* **Global share** `|∩| / |all commits|` is rejected outright. *Measured* on the
  50,000-commit history: the strongest pair in it shares 51 commits, which is
  `0.1%` of the repository — a number that looks like noise and is in fact the
  strongest signal in the data. This metric would make the tool report
  "nothing co-changes" on a repository full of co-change.

Unit 11 implements only the directional metric. A second metric is not
forbidden forever, but adding one means adding a second number with a second
meaning, and that is a decision for its own unit, not a convenience.

## 5. Count and score are two fields, never one

The freeze keeps the two apart on purpose, and the JSON shows both:

```text
shared_commits   17        a fact: seventeen stored commits hold both
score            0.72      derived: 17 / 24 analyzed commits of the queried file
```

The count can be read out of git by hand; the score depends on the definition
in §4 and would change if the definition did. Storing the second would freeze a
derivation — the same rule that keeps `deleted` out of `definition_versions` and
the word "renamed" out of `commit_files.change_type`. §13 draws the storage
conclusion.

---

## 6. The denominator

The denominator is **A's analyzed commits**: the commits that touched A and
whose occurrence set is not a large commit. Three notes on why it is this and
not something else:

1. **The sample is A, not the repository.** The question is conditional —
   "given that A changed, what else changed" — and the conditional's sample
   space is A's commits. This is also what makes the score readable: `0.33`
   means one in three of this file's changes dragged the other along.
2. **The numerator and the denominator must be over the same commits.** If a
   commit is excluded from the analysis (a large commit, §9), it must leave both
   the numerator and the denominator, or the score is no longer a ratio of the
   same sample and the percentages stop meaning anything. The implementation
   must therefore build `analyzed(A)` once and count the numerator inside it.
3. **A's commit set is life-wide, not name-wide.** A commit from before a
   rename counts in the denominator, because it touched the same file. The
   fixture's `core/app.py` has four commits for this reason, not the three it
   had under its final name.

The count of commits left out — `large_commits_excluded` — is reported beside
the score rather than hidden in it, so a reader can see the sample the ratio was
taken over. On the lifecycle fixture it is `0`; on the generated 50,000-commit
history it is `4` for one queried file and `0` for another (§9).

---

## 7. Directionality

Directional (`A → B`), as §4's formula says. The freeze records the consequence
explicitly because it is visible in the output: **there is no `--reverse`
option in Unit 11.** Asking about the other direction is asking about the other
file, and `archaeology cochange B` answers it. A reverse flag would double every
result list for a question the user can ask directly, and it would make the
output harder to explain ("the score shown is for the other file"). If the
demand appears later it can be added then; it is not in this freeze.

## 8. Merge commits

**A merge commit contributes nothing, and that is correct rather than a
limitation to work around.**

*Measured*: the sample fixture's merge (`bbed4c4`, two parents) has `0` rows in
`commit_files`, because `git log --raw --numstat` prints no diff for a merge.
Every merge in every database this tool can build behaves the same way, so the
rule "merges are excluded" is enforced by the storage model itself and cannot
be violated by a future change to the query layer.

Is excluding them the right semantics? Yes, for this statistic. A merge commit's
diff would say "these two branches' changes landed together", which is a
statement about the merge, not about the changes: the files it would report were
already counted, as separate commits, on the branches that made them. Counting
them again at the merge would multiply every pair that crossed the merge — the
exact over-counting the hotspot module already documents ("work that was merged
is counted on the branch that made it and not again on the merge"). So the
freeze's merge rule is: **merges are not counted, and no code has to say so**,
because they have no occurrences to count. Unit 11 needs no merge branch and
must not add one.

---

## 9. Large commits

A commit that touches five hundred files is not five hundred pairwise facts. It
is one bulk change — a reformat, a dependency bump, a license header, a vendor
drop — and if it were treated as pairwise facts it would claim every pair in it
co-changes, dominate the counts, and drown the signal. *Measured*: one
500-file commit generates `124,750` pairs on its own, and on the generated
50,000-commit history the ten biggest commits (of 49,996 non-empty ones)
account for most of the pair volume.

**The rule, frozen:**

* A commit whose occurrence set holds **more than 100 files** is excluded from
  the analysis: it contributes to no numerator and to no denominator (§6).
* The cap is a **parameter**, not a constant buried in code:
  `--large-commit-limit`, default `100`. A repository of generated code can
  raise it; a repository of vendored dumps can lower it.
* The number of excluded commits is reported (`large_commits_excluded`), so the
  exclusion is visible rather than silent.

Why 100, and why a cap at all rather than only a report:

* *Measured* on the 50,000-commit history: cap 100 keeps `49,731` of `49,996`
  non-empty commits — `99.5%` of the history stays in the analysis — while
  cutting generated pairs from `7,609,547` to `2,117,167`. The exclusion is
  aimed at the tail and hits almost nothing else.
* *Measured* on the same history: the ten largest commits hold 463–493 files.
  A cap of 50 would have cut the 40–150-file band too, which is a band real
  refactors live in; 100 sits above it.
* The threshold is deliberately a round, explainable number. The design
  question is "is a 100-file commit a pairwise observation", and the answer
  should not depend on a fitted constant.

**What a 500-file commit means statistically, stated plainly:** it is a single
observation that the repository changed in a sweeping way, and a statistic about
*which files move together* cannot use it. This is a definition, not a
performance trick: §13's measurements show performance never required the cap
(the per-file algorithm costs milliseconds either way). The cap exists because
the statistic is wrong without it, and Unit 11 must not "optimize" by applying
it somewhere the definition doesn't say.

## 10. Rename and delete

Both are occurrences of the file's life, and the identity model settles the rest:

* **Delete (`D`)** — the commit touched the file by ending it. A commit that
  deletes A and edits B is a co-change of A and B, because both lives were
  touched by that commit. *Measured* on the sample fixture: `legacy.py` is
  deleted in `78c0647` alongside `assets/logo.png` and `工具/文本.py`, and the
  pair `legacy.py ↔ assets/logo.png` therefore scores `1/2` from legacy's side
  — its two commits are its birth and its death.
* **Rename (`R`)** — one occurrence, for the identity that moved. A commit that
  renames A and edits B co-changes A with B (the lifecycle fixture's `657e78e`:
  `plain.py` is edited in the same commit that moves `src/app.py` to
  `src/core/app.py`, so `plain.py` and the app life share it). A rename is not
  two occurrences of A and never a pair with itself.
* **A rename git did not recognise** is a `D` + `A`, hence two lives and no
  invented pair (§3). The fixture contains exactly this case (`5c87edb`) and
  the test matrix pins it.
* **A name reused after a delete or a rename** starts a new life, and the two
  lives are separate subjects of the statistic. Querying the shared name returns
  both, each with its own denominator — the behaviour `file.py` already has.

---

## 11. Self-pairs, canonicalisation, and duplicates

* **A file never pairs with itself.** The occurrence set of a commit is a set
  of identities, so `A ↔ A` cannot arise; it is not filtered, it is impossible.
  (It *would* arise from a naive implementation that resolved both paths of an
  `R` row — §16's trap.)
* **The pair key is ordered** `(A, B)` with A the queried file. No
  canonicalisation is needed or wanted: the metric is directional (§7), so
  `(A, B)` and `(B, A)` are two different rows with two different scores. The
  JSON names the two ends separately (`file`, `co_changes_with`) rather than as
  a pair, so nothing invites reading it as symmetric.
* **One commit, one occurrence per identity.** Guaranteed by the schema's
  primary key and by the set reduction in §3.

---

## 12. Threshold and ordering

### Minimum shared commits

**Default `--min-shared 2`: a pair must share at least two commits to be
shown.**

The reason is arithmetic, not taste. A pair with `shared_commits = 1` and
`score = 1.0` is the strongest possible reading of the weakest possible
evidence: the file has one analyzed commit, that commit touched one other file,
and the output says "100% co-change". *Measured*: this is not hypothetical —
on the generated history, `pkg29/mod2900.py` has 48 analyzed commits and 712
co-changing files, almost all of them at `shared = 1`; they are the pairs of a
file that has simply been touched often, and they carry no information about
those files. Requiring a second shared commit is the smallest support that can
distinguish "these two moved together" from "these two were both in the room
once".

It is a **display filter, not part of the definition**: the denominator (§6) is
not recomputed and the score of a shown pair is unaffected. `--min-shared 1`
shows everything, and the count of hidden pairs is not silently swallowed — the
command reports how many pairs the threshold hid, the way the other commands
report hidden rows. (If a repository is small enough that `2` hides everything,
the report says so; that is more honest than lowering the default.)

### Ordering

Frozen, so that the same database and parameters produce the same bytes:

```text
1. score            DESC
2. shared_commits   DESC
3. co_changes_with  ASC   (the other file's current path)
4. identity ordinal ASC   (only reachable if two lives share a current path)
```

`co_changes_with` is the life's `current_path` — what the file is called now,
not the name it had in the commits. Ties beyond step 3 need two lives with the
same current path, which the lifecycle model allows (a name reused after a
delete), and step 4 makes even that deterministic. The sort is done in the
query layer over materialised rows; nothing relies on dict iteration or on
SQLite's unspecified order.

## 13. Storage: query-time, derived, never a table

**Co-change is computed when asked. Unit 11 adds no table, no cache, and no
schema version.**

The reasoning, with the measurements that settled it:

* **The naive cost is real but avoidable.** Generating every pair of every
  commit is `7,609,547` pairs on the 50,000-commit history (`3,526,390`
  distinct, `456 MB` peak) and takes `31 s`; even capped at 100 it is
  `2,117,167` pairs and `8.3 s`. That is a cache candidate on its face.
* **A per-file query does not pay it.** *Measured* on the same database: the
  busiest file (265 commits) answers in `17.9 ms` with a `0.2 MB` peak; a
  typical file answers in `4–11 ms`. The trick is that the pair explosion only
  happens if you enumerate all pairs; a query for one file counts occurrences
  inside that file's commits and never materialises the rest. The query layer
  is where the design wins, not a table.
* **The identity walk is cheap and reusable.** *Measured*: loading 297,602
  rows takes `0.21 s` and mapping them to identities takes `0.36 s` on top —
  less than one second to have the whole history in the shape the query needs,
  against the minutes the AST pass spends on the same repository.
* **A table would freeze a derivation.** The rows would be `score`-bearing
  derived values, exactly what the storage docstring forbids: they depend on
  rules (`large_commit_limit`, `min_shared`, the identity model) that may
  change, and a stored score cannot be recomputed, only invalidated. It would
  also need cache-invalidation machinery tied to `analyze` and `ast`, and at
  the measured scale it would hold millions of rows to save milliseconds.

So: **query-time derived analysis**, living in a module of its own
(`cochange.py`), reading only `commits` / `commit_parents` / `commit_files`
through the existing readers. The only fact the database needs to hold for
co-change is the one it already holds.

## 14. CLI shape (designed, not implemented)

```text
archaeology cochange <file> [PATH] [--db PATH]
                             [--limit N | --all]
                             [--min-shared N]
                             [--large-commit-limit N]
                             [--json]
```

* `<file>` is the file to ask about, in the same form the `file` and `structure`
  commands take, normalised by `file.normalise`.
* `--limit` / `-n`, default `20`, and `--all` are the convention every list
  command already uses; the report says how many rows were hidden, as the
  others do.
* `--min-shared`, default `2` (§12), and `--large-commit-limit`, default `100`
  (§9), are the two parameters the definition exposes. Nothing else is a knob.
* `--json` follows the existing contract: JSON only, nothing else on stdout,
  the stale-analysis note on stderr. The object:

```json
{
  "repository": "/abs/path",
  "head_sha": "…",
  "file": "core/app.py",
  "path_history": ["app.py", "src/app.py", "src/core/app.py"],
  "analyzed_commits": 4,
  "large_commits_excluded": 0,
  "co_changes": [
    {
      "path": "plain.py",
      "shared_commits": 2,
      "score": 0.5
    }
  ]
}
```

  The list is named for what it holds, the way `hotspots` names its `files` and
  the timeline names its `commits`. `analyzed_commits` is the denominator, shown
  so a reader can verify any score by division; `large_commits_excluded` is the
  sample that left the analysis.
* Text output: a header block like `file`'s (current path, history line when the
  file was renamed), then one row per co-changing file — its current path, the
  shared count, and the score — and a closing note stating what the number is
  not ("co-change is what the history shows, not what it means: two files moving
  together is not a dependency"), the way `hotspots` closes with its own
  warning. A file with no partners prints "no file changed alongside it" and
  exits 0; a file not in the stored history exits 1 with the same message shape
  as `file`.
* Two lives carrying the queried name are printed oldest first, as `file` does,
  each with its own header — and this includes deleted files: asking about a
  file that no longer exists is a legitimate historical question, so there is no
  `--alive-only` filter in Unit 11.

## 16. Traps

Two were hit for real while writing this freeze. They are recorded because Unit
11 will walk the same path.

1. **Identity ordinals must be counted, not derived from `len(seen)`.** The
   first draft of the measurement script numbered each new identity as
   `("life", len(seen))`, where `seen` maps *paths* to identities. The lifecycle
   fixture re-creates a path after a delete (`907ef3e`), and the reused name
   gave the new life the same ordinal as an unrelated one — two lives merged,
   `kept.py` appeared to pair with `renamed.py`, and the fixture's co-change
   table was quietly wrong. `build_lifecycles` avoids this by numbering lives
   with a separate counter (`len(lives)`), and the co-change module must derive
   identities the same way — or, better, reuse `build_lifecycles` itself and map
   `(commit_sha, path)` → life ordinal from its events, so there is one identity
   implementation, not two.
2. **A merge is invisible in `commit_files`, not marked.** The sample fixture's
   merge has no rows, so a query "did this commit touch anything" and a rule
   "skip merges" are indistinguishable in the data. Anyone writing the test for
   case 8 must assert the merge's *absence from the counts* (the denominator),
   because asserting "the code skips merges" would pass on code that does
   nothing of the kind.

A third, smaller one: the design's measurements live in throwaway scripts under
`D:/tmp/coh/`, and the numbers quoted here are the reason they were run. If
Unit 11's implementation disagrees with any of them, the implementation is
wrong until proven otherwise.

---

## 17. What this freeze does not do

* No production code, no schema change, no CLI command, no benchmark (Unit 10's
  charter forbids all of them).
* No AI, no semantic inference, no AST, no import or call graph. Co-change
  stays a statement about commits and files. Future work may combine the two
  layers; that is a different analysis and a different unit.
* No Jaccard, no global-share metric, no `--reverse`, no cache table — each is
  rejected above with its reason, and a future unit may revisit any of them by
  arguing with the reason, not by adding it quietly.

**Unit 11 starts only after the user reviews this freeze.**

## 18. Built, and what the building changed

**Written after the fact, so the document says what happened rather than what
was planned.** Units 11 and 12 built this freeze: the analysis is
``src/codearchaeology/cochange.py``, the command is ``archaeology cochange``,
and the tests are ``tests/test_cochange.py`` and ``tests/test_cochange_cli.py``.
Nothing in §1–§17 was changed to make them fit, and that is the point of the
section: a freeze that gets quietly edited during implementation is not a
freeze.

**One deviation, recorded rather than smoothed over.** §14's JSON example is a
single object; the command emits an object holding a ``files`` list, one entry
per life that carried the queried name. The reason is the one ``file --json``
already documents: a name can belong to several lives, and the shape must not
depend on which repository was asked. ``path`` at the top is what was queried,
each entry's ``path`` is what that life is called now, and the entry carries
§14's ``path_history``, ``analyzed_commits``, ``large_commits_excluded`` and
``co_changes`` exactly as written — plus ``hidden_pairs``, so a reader can tell
"none found" from "none shown".

**What the measurements said.** The implementation was checked against §13's
numbers on the 50,000-commit history and agrees with them exactly
(``pkg0/mod0.py``: 228 analyzed, 20 excluded, top pair ``pkg0/mod1.py`` shared
45 at 0.197). One figure moved: the whole pass costs about 1.4 s, not the ~0.6 s
§13's separate measurements suggested, because ``build_lifecycles`` builds every
event object for every file rather than only the path-to-identity mapping the
measurement script kept. The query itself is still milliseconds; the walk is the
cost. ``benchmarks/cochange_benchmark.py`` holds the curve, and its numbers are
the ones to quote from now on.

**What is still not here**, unchanged from §17: no storage, no ``--reverse``, no
``--alive-only``, no Jaccard. The two READMEs do not describe the command — that
is release work, and v0.4 has no release unit yet.
