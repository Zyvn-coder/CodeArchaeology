# v0.3 design freeze

**Unit 0.** Written 2026-09-29. This unit writes no production code: this file is
the deliverable, and it is what every unit after it is checked against.

Everything marked *measured* was run on this machine on 2026-09-29 under CPython
3.11.16 and 3.13.5, the two interpreters CI runs. The traps recorded here were
hit for real while writing this, not imagined.

The rule that governs the whole version, in the user's words: **v0.3 途中不要
增加功能**. An idea that arrives mid-flight goes into §7 and waits.

## 1. The freeze

| # | 项目 | Decision | Why, in one line |
|---|---|---|---|
| 1 | 支持语言 | Python, `.py` paths only | Python-only is the v0.x range. `.pyi` is written down in §7, not built. |
| 2 | 分析对象 | `FunctionDef`, `AsyncFunctionDef`, `ClassDef` | Every named definition Python has. A lambda has no name, so there is nothing to follow across versions. |
| 3 | 身份 | A definition is identified by **file version + qualified name** | No rename inference. A renamed function is a death and a birth, and the tool says exactly that. |
| 4 | 内容读取 | `git cat-file --batch` | *Measured:* about 5,900 objects/s through the interactive protocol, 15 MB/s on 2 KB files — one process for the whole run, which is the point. Its header carries the blob sha, and a path that is not in that commit answers `missing` instead of failing. The protocol's traps are in `objects.py`'s docstring. |
| 5 | AST | Python's stdlib `ast` | No new dependency, so Core First and Local First stay intact. |
| 6 | 失败 | A `ParseFailure` record; never a silently missing row | Every visited file version gets a row, and the row says whether it parsed. |
| 7 | 解释器 | The interpreter that produced the facts is recorded per file version | The fingerprint is *measured* to be version-independent; a measurement is not a proof, and this is what makes a surprise explainable. |
| 8 | schema | version 2 → 3, dropped and rebuilt | `storage.py` already calls the database a cache; there is nothing worth writing migration code to keep. |
| 9 | AST 流程 | Its own command, never inside `analyze` | *Measured:* `analyze` is 45.6s at 200,000 commits; extraction runs at 664 files/s, so the same repository costs roughly 25 minutes of AST work. A user who wants the git facts must not pay for that. |
| 10 | 内容 sha | Taken from `cat-file --batch`, never from the log | *Measured:* `git log --raw` prints **abbreviated** shas (`9e822a6`, not 40 characters), so they cannot be used as identities. |

## 2. The three commands

| Command | Reads | Writes | Cost |
|---|---|---|---|
| `archaeology analyze` | git history | `commits`, `commit_parents`, `commit_files` | seconds |
| `archaeology ast` | `commit_files`, then file contents from git | `file_versions`, `definition_versions` | minutes |
| `archaeology structure` | `file_versions`, `definition_versions` | nothing | instant |

`analyze` does not change. It keeps doing what v0.2 did, and the AST pass does
not touch its tables — it only reads `commit_files` to learn which file versions
exist. That is the point of the split: `analyze` stays cheap enough to run
whenever the user wants, and the expensive pass is something they ask for.

A database that has been analyzed but not AST-scanned is a normal state, not an
error. `structure` says which command to run, the same way every read command in
v0.2 names `analyze` when the database is missing.

## 3. Question 1: what is a Python file's structure at a commit?

It is a **file version** and the definitions that version contained.

A file version is one `(commit_sha, path)` pair where the file exists at that
commit — that is, one row of `commit_files` whose change type is not `D`, whose
path ends in `.py`. Each gets exactly one row in `file_versions`, and one row in
`definition_versions` per definition that version contained. Nothing is stored for
a `D` row: there is no content to parse, and the deletion is already the evidence
that the definitions ended there.

The answer for `src/codearchaeology/statistics.py` at the commit that last
touched it (a real file in this repository, measured):

| position | kind | name | qualname | lineno | end_lineno | col_offset | decorators |
|---|---|---|---|---|---|---|---|
| 0 | class | `FileStatistics` | `FileStatistics` | 19 | 43 | 0 | `["dataclass"]` |
| 1 | function | `net_change` | `FileStatistics.net_change` | 35 | 43 | 4 | `["property"]` |
| 2 | function | `summarize` | `summarize` | 46 | 63 | 0 | `[]` |
| 3 | function | `_changed_content` | `_changed_content` | 66 | 79 | 0 | `[]` |

That is the *structure* — what `definitions_of` reads out of the bytes. The row
that reaches the database keeps less of it: `name` is not stored because it is the
last segment of `qualname`, and `col_offset` is not stored because the line range
and the path already say where the definition is. §6 lists what is kept.

Five facts about that table, each of which was measured or is a direct
consequence of one:

- **`lineno` is the `def` line, not the decorator's.** `net_change` starts at 35,
  where `def` is written; `@property` on line 34 is not part of the range. That is
  `FunctionDef.lineno`'s own behaviour since 3.8, and the decorator is recorded in
  its own column, so nothing is lost.
- **`qualname` follows Python's own convention**, including `<locals>` for a
  function inside a function: `handler.<locals>.helper`, `Service.fetch`. It is
  the same string `__qualname__` would hold at runtime, so the tool is not
  inventing a second naming scheme.
- **`decorators` holds the dotted name** (`property`, `app.route`), not the source
  text: a rendering of the source can change between interpreters, a name cannot.
  The arguments of a decorator are still part of the fingerprint (§5), so changing
  `@app.route("/a")` to `@app.route("/b")` is a modification even though the
  dotted name is unchanged.
- **`position` is the order the definitions appear in the file**, a parent before
  the definitions inside it. It is what makes the primary key unique: two
  definitions in one file can share a qualified name — a name defined again under
  an `if`, or a fallback in an `except` — and a key on `(commit, path, qualname)`
  would silently keep only one of them. Unit 1 covers this case with a fixture.
- **A version is parsed once, and a re-run parses nothing it already has.** Reuse
  is keyed on the version itself — the same commit, path, content and interpreter
  — because the row that has to be written is per version. A pure rename carries
  the same bytes under a new name and is parsed again; that is the accepted cost
  of keying the cache on the thing being written.

The last version of a file before it is deleted is a normal version and gets a
row; the deletion itself gets none. Merge commits have no rows in `commit_files`
(v0.2 records no diff for a merge), so they have no file versions either — the
structure at a merge commit is not recorded, and that limitation is inherited,
not new.

## 4. Question 2: what happens when parsing fails?

The failure is a stored fact, attached to the file version it happened to.

```
file_versions
  commit_sha        = 3f2a1bc…          the version this is about
  path              = "src/legacy.py"
  content_sha       = d477bab…          the exact content that was parsed
  parsed_at_version = "3.13.5"          which interpreter did the parsing
  parse_error       = "SyntaxError: Missing parentheses in call to 'print'. …"
  error_lineno      = 4
  error_offset      = 1
```

and no `definition_versions` rows for it. A file version with `parse_error IS NULL`
has definitions; a file version with a `parse_error` has none. There is no third
state, so a query can never mistake "could not be parsed" for "contained nothing".

What the user sees:

```console
$ archaeology structure src/legacy.py
src/legacy.py at 3f2a1bc could not be parsed:
    SyntaxError: Missing parentheses in call to 'print'. Did you mean print(...)?
    line 4, column 1
```

`error_offset` is 1-based, because it is `SyntaxError.offset` verbatim, while
`col_offset` on a definition is 0-based, because it is `ast`'s. The two are
deliberately not renamed to match: each keeps the base of the thing that produced
it, and this sentence is the only place the difference is written down.

What can fail was measured, not guessed. `ast.parse` given **bytes** raises:

| Input | Outcome |
|---|---|
| Python 2 `print 'x'` | `SyntaxError` |
| Merge-conflict markers | `SyntaxError` |
| A NUL byte | `SyntaxError: source code string cannot contain null bytes` |
| Non-UTF-8 bytes with no coding cookie | `SyntaxError` (a unicode error inside it) |
| A file with a `# -*- coding: latin-1 -*-` cookie | **parses** — but only from bytes |
| 100 levels of indentation | `IndentationError`, which is a `SyntaxError` |
| 500 nested parentheses | `SyntaxError: too many nested parentheses` |
| A deeply nested attribute chain | **`RecursionError`**, "maximum recursion depth exceeded during ast construction" — at 5,000 on Windows, and above 5,000 on the Ubuntu runner; see below |

So the recorded set is `SyntaxError` and `RecursionError`. The first is a fact
about the content. The second is a fact about the content *and the machine*: the
parser stops when the C stack runs out, so where that line falls is a property of
the interpreter that read the file. Measured after this table was written: the
Windows interpreter gives up at about 3,000 nested attributes and Ubuntu reads
5,000 without complaint, and `sys.setrecursionlimit` does not move the line (the
same 3,000 at a limit of 100 and of 1,000). It is still recorded rather than
propagated, because a file the parser cannot build a tree for is something a
reader has to be told about; what is *not* claimed is the depth, and a test that
asserted one would be testing the platform instead of the tool — which is how CI
found this. Anything else — a `MemoryError`, an interrupted read — is a fact
about the machine alone, and it is allowed to propagate and stop the run rather
than be filed as a property of somebody's file.

Two consequences of that table, both of which are requirements on Unit 1:

- **`ast.parse` must be handed bytes, never a decoded string.** The latin-1 file
  above parses as bytes and raises `UnicodeDecodeError` as a utf-8 `str`, so
  decoding first would turn a parseable file into a crash.
- **Warnings must be suppressed while parsing.** *Measured:* an invalid escape
  sequence makes 3.11 emit a `DeprecationWarning` and 3.13 a `SyntaxWarning`. A
  scan over a large repository would print one per occurrence; `catch_warnings`
  with `simplefilter("ignore")` silences both.

## 5. What the fingerprint is, exactly

A definition's fingerprint is the sha256 of a **canonical rendering** of
everything about it except its name and where it sits:

```
the kind ("function" / "async function" / "class")
each decorator
for a function: its arguments, and its return annotation
for a class:    its bases, and its keywords
every statement of its body
```

The rendering is written by the tool, not taken from `ast.dump`, and the reason
is measured:

> **`ast.dump` is not portable between interpreters.** On 3.11 it prints every
> field — `decorator_list=[]`, `keywords=[]`, `posonlyargs=[]`, `type_ignores=[]`.
> On 3.13 it omits the empty ones. The same source therefore produces two
> different dumps, and a fingerprint built on one would mark every definition in
> a repository as modified the first time it was analyzed by another Python.

The canonical rendering instead walks the fields and **omits empty and absent
ones**, which is exactly the difference between the two. *Measured:* over a
42-sample corpus — every form of f-string, `match`, walrus, `except*`, async
comprehensions, decorators with arguments, unicode identifiers, type comments —
the rendering is byte-identical on 3.11.16 and 3.13.5. Unit 1's tests pin the
resulting digests as constants, so the four CI jobs verify that claim on every
run rather than trusting this paragraph.

What the fingerprint ignores, and what that costs:

| Change | Fingerprint | Note |
|---|---|---|
| `def login` → `def authenticate`, same body | unchanged | This is the whole point: it is how a rename can be *seen* without being inferred. |
| The definition moves down the file | unchanged | Positions are not part of it. |
| A comment is added inside the body | unchanged | Comments are not in the AST. The git layer still counts the lines. |
| A default value, an annotation, a decorator argument, or any statement changes | changed | |

A fingerprint that is unchanged between two versions is evidence the *structure*
did not change; it is not evidence the file did not change. Both facts are
available, and the tool reports each as what it is.

## 6. Schema version 3

**Raised to version 4 in §18.** The tables below are unchanged — the version
moved because `commit_files.change_type` gained a constraint.

Two tables, added to the four that exist. `storage.py`'s docstring already says
the database holds "only facts git reported" — these two hold what the parse
produced, and **not** the identities a later unit derives from them.

```sql
CREATE TABLE IF NOT EXISTS file_versions (
    commit_sha        TEXT NOT NULL REFERENCES commits(sha),
    path              TEXT NOT NULL,
    content_sha       TEXT NOT NULL,
    parsed_at_version TEXT NOT NULL,
    parse_error       TEXT,
    error_lineno      INTEGER,
    error_offset      INTEGER,
    PRIMARY KEY (commit_sha, path)
);

CREATE TABLE IF NOT EXISTS definition_versions (
    commit_sha  TEXT    NOT NULL,
    path        TEXT    NOT NULL,
    position    INTEGER NOT NULL,
    kind        TEXT    NOT NULL
                        CHECK (kind IN ('function', 'async function', 'class')),
    qualname    TEXT    NOT NULL,
    change_type TEXT    NOT NULL
                        CHECK (change_type IN ('created', 'modified', 'unchanged')),
    fingerprint TEXT    NOT NULL,
    lineno      INTEGER NOT NULL,
    end_lineno  INTEGER NOT NULL,
    decorators  TEXT    NOT NULL,
    PRIMARY KEY (commit_sha, path, position),
    FOREIGN KEY (commit_sha, path) REFERENCES file_versions(commit_sha, path)
        ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS file_versions_path ON file_versions (path);
CREATE INDEX IF NOT EXISTS definition_versions_qualname
    ON definition_versions (path, qualname);
```

Five notes on what is not obvious in that DDL:

- **It is a snapshot, not a change log.** Every definition the version contained
  has a row, whether or not it changed; `change_type` says which of the three it
  was, and the row count is roughly twice what a change log would cost — measured
  in the audit at 869 rows against 404. What that buys is that "what did this file
  look like at this commit" is one query instead of a replay of every change the
  file ever had, and that a single wrong row cannot make every later version of
  the structure wrong.
- **A definition that is gone gets no row, and `change_type` may not say
  `deleted`.** Absence is the evidence, and the constraint keeps the two ways of
  expressing it from both existing. `lineno` and `end_lineno` are therefore always
  known: a row only exists for a definition that is there.
- **A version that could not be parsed is not an empty version.** It has a
  `file_versions` row with a `parse_error` and no definitions at all, which is
  what keeps "read it, nothing was there" apart from "could not read it". A
  later unit that reads absence as deletion has to check that column first, and
  the alternative — no row at all for a failed version — would have made the two
  indistinguishable.
- **`position`, and not the qualified name, is in the key**, because two
  definitions in one file can share a name — a name defined again under an `if`,
  a fallback in an `except`. A key on `(commit, path, kind, qualname)` would keep
  one of them and silently drop the other, which is the same failure as losing a
  parse error quietly.
- **No `function_id`, `lifetime_id`, `same_as_previous`, `renamed_from` or
  `moved_from`.** Those are what a later unit derives; a table of facts must not
  be where a derivation gets frozen, because a row that cannot be recomputed is a
  row that cannot be corrected. A test holds both column lists to that.

`decorators` is a JSON array. A separator character would be ambiguous the moment
a decorator's rendering contains it, and JSON escapes instead.

The version bumps to 3, so the existing tables are dropped and rebuilt on the
next `analyze` — which means a re-analysis is required before `ast` can run. That
is the intended cost of the schema change and there is nothing to migrate: every
row in the database can be read out of git again.

## 9. Unit 1, as frozen

`src/codearchaeology/definitions.py`, and nothing else:

- `Definition` — a frozen dataclass: `kind`, `name`, `qualname`, `lineno`,
  `end_lineno`, `col_offset`, `decorators`, `fingerprint`, `parsed_at_version`.
- `ParseFailure` — `reason`, `lineno`, `offset`, `parsed_at_version`. The reason
  carries the exception's own name (`SyntaxError: …`, `IndentationError: …`,
  `RecursionError: …`), so a reader never has to guess which one it was from the
  wording of the message.
- `definitions_of(source: bytes) -> tuple[Definition, ...] | ParseFailure` — the
  pure function. No git, no database, no file system.

The tuple is in the order the definitions appear in the file, and that order is
the `position` §6 stores: a definition can share its qualified name with another
one in the same version, so the index is what identifies it, and a field holding
the index would be a second copy of the same fact.

Verified by `tests/test_definitions.py` over source strings: every construct in
§5's corpus, the duplicate-qualname case from §3, the failure table from §4, and
the golden fingerprints that make the four CI jobs check the cross-interpreter
claim. The module's independence is a test too — it reads the module's own
source and refuses an import that is not in the allowed set.

## 10. Unit 2, as frozen

`src/codearchaeology/objects.py`, and nothing else:

- `GitObject` — `sha`, `kind`, `size`, `content`: one object exactly as git
  reported it.
- `ObjectReader` — one `git cat-file --batch` process, a context manager, with
  `read(object_id) -> GitObject | None` and `read_many(object_ids)`.
- `read_blob(repository_root, blob_sha) -> bytes | None` — one object's content,
  with a process of its own, for a caller that wants a single answer.
- `read_objects(repository_root, object_ids)` — many objects over one process,
  lazily, so a caller that stops early ends the process too.
- `file_version_id(commit_sha, path)` — the way to name a file version, so that
  "which blob did this version hold" is one read with one answer.

**The identity is part of the answer.** Asking for `<commit>:<path>` returns the
blob's own object id beside its bytes, because git puts the id it resolved the
request to in the header. That is what Unit 3's `content_sha` needs: the AST pass
stores a content identity for every version it parses without re-reading the
history, without a second `--batch-check` pass, and without hashing anything
itself. `kind` comes back too, so a caller can tell a file from a directory —
a path naming a directory resolves to a `tree`.

A missing object is `None`, not an exception: git answers `missing` and carries
on. A process that died is a `GitError`, raised whether it is met at the write of
the next request or at the read of its answer. An object id holding a newline is
refused, because git would read it as two requests and every answer afterwards
would belong to somebody else's question. The protocol's other traps — the answer
is a length rather than a set of lines, an empty object still ends with the
separator newline, and requests cannot be written ahead of the answers — are in
the module's docstring.

Verified by `tests/test_objects.py`: a normal, empty, binary, 5 MB and
header-shaped blob; a missing object; a name that resolves to a sha; the id of a
file version checked against `git rev-parse` rather than trusted, and its content
against the file on disk; a directory coming back as a tree; the process ending
with its block and closing twice; a killed process being reported; and — the
performance requirement — that fifty objects start **one** process, with a second
test proving the counter would have seen three.

## 11. Unit 3, as frozen

`storage.py`: `SCHEMA_VERSION = "3"`, the two tables of §6, and the shape of what
goes in them.

- `FileVersion` — `commit_sha`, `path`, `content_sha`, `parsed_at_version`,
  `parse_error`, `error_lineno`, `error_offset`.
- `DefinitionVersion` — `commit_sha`, `path`, `position`, `kind`, `qualname`,
  `change_type`, `fingerprint`, `decorators`, `lineno`, `end_lineno`.
- `write_file_versions` and `write_definition_versions` — replacing whatever is
  already stored for the versions they are given, so that a pass re-run over the
  same commits ends in the same state instead of failing on its own earlier work.
- `CREATED`, `MODIFIED`, `UNCHANGED` — the words `change_type` may hold, and the
  schema's `CHECK` says the same three. `deleted` is not among them, and the
  database refuses it.

**The two questions the user settled** (both were open when this unit started,
and both changed what was here before):

1. **The table is a snapshot with a change marker.** Every definition a version
   contained has a row; `change_type` says whether that version created it,
   modified it, or left it alone; a definition that is gone has no row at all.
   The earlier draft stored only the definitions that changed — a change log —
   which made "what did this file look like at this commit" a replay of the
   file's whole history, and let one missing row corrupt every later answer.
2. **A rescan keeps the AST rows that are still true.** `write_commits` now means
   "the stored history is exactly these commits": it writes them, and removes the
   commits git no longer has together with their file versions and definitions.
   The earlier draft cleared the AST layer on every `analyze`, which threw away
   minutes of parsing — and, worse, did it quietly: `structure` would start
   saying the repository had never been scanned.

Two things about that second decision are worth carrying forward:

- **The commit row is updated, not replaced.** A file version names its commit,
  so the foreign key refuses to let the commit's row go while those rows exist.
  `INSERT ... ON CONFLICT(sha) DO UPDATE` keeps the row in place; a delete and an
  insert would have taken the AST rows with it.
- **The pruning happens inside the same transaction as the write**, in
  `write_commits`'s own `with connection:` block, so a failure leaves either the
  old history or the new one and never a new commit table beside half an old AST
  layer.

A database written by version 2 is dropped and rebuilt on the next `analyze` or
`ast`, as asked. There is no migration code, and `test_ast_storage.py` proves the
old rows are gone rather than carried across.

Verified by `tests/test_ast_storage.py`, read back with plain SQL rather than
through a reader of ours — a writer and a reader wrong in the same way would agree
with each other. It covers both round trips; a failed version keeping its reason
and having no definitions; the three-version case where a file parses, fails and
parses again, which is the test that keeps a syntax error from reading as a
deleted function; two definitions sharing a qualified name; a definition refused
without its file version; a version replaced taking its definitions with it; the
three `change_type` words being accepted and `deleted` being refused; the four
`analyze` scenarios (unchanged history, a commit added, commits removed, and
`analyze` never writing AST rows at all); and the column lists themselves, which
is what holds the tables to "facts here, identities later".

## 12. Unit 4, as frozen

`ast_pass.py` — the pass — and the `ast` command that runs it. The pipeline, in
the order it happens:

    the stored history
      -> the file versions it contains, in the order each file lived them
      -> read the blob (its identity and its bytes in one read)
      -> parse it, or reuse what is already stored for this exact version
      -> compare with the last version of the same file that could be read
      -> write the version and its definitions, one transaction per batch

Four rules, all of them the user's:

- **A definition is identified by its kind and its qualified name**, and by
  nothing else. A renamed function is one definition gone and another appearing;
  no identity is invented for it, and nothing is followed across files.
- **`change_type` compares against the nearest version that could be read.** A
  version that fails to parse is a recorded failure with no definition rows —
  never a set of deletions — and the next readable version is compared against
  the last readable one, so an `unchanged` can span a failure. It is a cached
  comparison, not a claim that nothing happened in between, and the history layer
  must not read it as an unbroken chain.
- **The predecessor is resolved through the file lifecycle**, not through the
  path, so a renamed file continues rather than restarts: after the sample
  fixture's pure rename, everything in the file is `unchanged`.
- **A re-run reuses what it has already worked out.** Reuse is keyed on the
  version — same commit, same path, same content, same interpreter — so a second
  run reads and compares but parses nothing. The rows are written again either
  way, which is what makes re-running the way a change in the tool takes effect.

Nothing is cleared up front. The pass replaces the versions it visits, and a
version's own row and its definitions go in together, so an interrupted run
leaves whole versions behind rather than half of one — the batches exist so that
committing is not the cost of the run, not so that a version can be split. Rows
for commits git no longer has are `analyze`'s to remove, and it removes them.

Two smaller things worth writing down: a version whose path is not in that commit
or names a directory is counted as skipped and gets no row, because a version
nobody could read is not a version that was empty; and two definitions sharing an
identity are compared in the order they appear — the *n*-th against the *n*-th —
which is the only comparison available when the name is not enough to tell them
apart.

Verified by `tests/test_ast_pass.py` over real repositories: every version of the
definition fixture stored; created, modified and unchanged each asserted on the
version that should show it; a renamed function as one gone and one created; a
version that does not parse recorded with a reason and no definitions, and the
next version compared *across* it rather than read as a fresh start; a second run
parsing nothing and leaving the rows identical; a changed file parsed again while
the rest are reused; a file of nothing but comments stored with no definitions;
two definitions sharing a name compared in order; only `.py` paths visited; a
pure rename keeping its definitions unchanged and a later edit showing as
modified; a deleted file leaving no deletion row; `analyze` keeping what the pass
stored; and the command filling the database, and telling a repository with no
analysis to run `analyze` first.

## 13. Unit 5, as frozen

`definition_history.py` — the derivation — plus the two `storage.py` readers it
needs. Nothing is written: a history is derived on the spot from rows that can
always be rebuilt, so a rule that changes takes effect on the next read rather
than needing a migration.

    the stored snapshots (file_versions, definition_versions)
      -> one file life, its versions in the order they happened
      -> each version: read (a Snapshot), or a BlindSpot with the reason
      -> each definition's life, comparing every readable version against the
         nearest earlier version of the same file that was readable
      -> created / modified for what is there, deleted for what is gone, and on
         each event the blind spots it was derived across

Five rules, all of them the user's:

- **Identity is the file's life plus the kind and the qualified name**, and
  nothing else. No semantic identity, no rename inference, no move inference: a
  function renamed is one definition ending and another beginning, and a
  definition that moves to another file is one ending here and another beginning
  there. A *file* that was renamed carries its definitions, because the identity
  is scoped to the life and the life follows the rename.
- **A deletion is only ever read from a version that was read.** It comes from a
  snapshot that did not hold the definition, or from the file's own deletion —
  never from a missing row, because a missing row is exactly what a version
  nobody could read produces.
- **`unchanged` is a fact, not an event.** A definition that never changed has
  one event, its creation. That it was there in the versions between is what the
  life says, and no event repeats it.
- **A change derived across a gap carries the gap.** The comparison is against
  the nearest *readable* version, so a deletion can be derived across a version
  that failed to parse — and then the event names the versions it was derived
  across, because it cannot say *when* inside that span it happened. This is
  §5.7 exactly: `A: foo exists, B: parse failure, C: foo absent` is neither
  "deleted at B" nor a deletion at C presented as an unbroken history.
- **A definition whose file's latest versions are unreadable has no ending.** No
  deletion is emitted, and the life carries `unresolved` — the versions after the
  last readable one, which it may or may not have survived. A life that was
  *seen* to end is not reopened by them.

The records:

| Record | What it is |
|---|---|
| `BlindSpot` | One version nobody could read, with the reason: the parser's words, `NOT_STORED` when no version was stored for that commit at all, or `NOT_IN_TREE` when the file was not in that commit |
| `Snapshot` | One version that was read, and the definitions it held |
| `DefinitionEvent` | One thing that happened to one definition, with the version it was compared against and the blind spots in between |
| `DefinitionLife` | One definition in one file's life: its events, its `unresolved` tail, and which occurrence of that name it is |
| `FileHistory` | One file's life: every name it carried, every version of it in order, and the lives in it |

Four decisions inside the unit worth writing down:

- **`FileHistory.versions` holds the blind spots too**, in the order they
  happened, so a reader can see where the file went dark and for how long rather
  than only that something did. The commit that ends a file's life joined them in
  §15, where the reason for it is written down.
- **The derivation repeats the comparison the pass cached** instead of reading
  `change_type`. The cache is keyed on the pass's identity rule, and this layer
  has to be able to say what *it* derived; a test walks every stored row and
  holds the two to each other in both directions.
- **The *n*-th definition of a name continues the *n*-th life**, which is the
  same rule the pass compares by, and the only one available when a file defines
  one name twice. `occurrence` on the life is that index: 0 for nearly every
  name.
- **The blind spots of one step are one shared tuple**, handed to every event of
  that step. A file with a long gap and many definitions would otherwise hold one
  copy of the gap per definition.

`tests/test_definition_history.py` (20 tests) verifies it over real repositories:
creation, modification, the rename as one death and one birth, `unchanged` never
an event, a deletion read from the version that was read rather than from the
failure before it, a deletion derived across a gap naming that gap, a definition
whose file never parses again left with no ending, a file deleted after a gap
closing its definitions, a file absent from one commit being a gap rather than an
ending, a rename carrying its definitions across two names, a name used again
being a second history, two definitions sharing a name keeping two lives, a
version with no stored row being a gap rather than an empty file, a repository
that was analyzed but never scanned saying so, and a file of nothing but comments
having a history with no definitions in it. `build_gap_repo` and
`build_interleaved_repo` were added to the fixtures for it: the first puts one
parse failure in front of three different endings, the second produces a
mid-life absence of the file from a delete on one branch and an edit on another.

**The command is not part of this unit.** `archaeology structure --history` is
its own row in the plan, and §8 leaves its shape open — a flag on `structure` or
a command of its own. This unit is what that command will read.

## 14. Unit 6, as frozen

`structure.py` — the lines — and the `archaeology structure <path> --history`
command. **The user settled the shape §8 left open**: a flag on `structure`, not
a fourth command. The other half of that command, a file's structure at one
commit, is the next unit; until it exists, `structure` without `--history` says
so and exits 1 rather than printing something that reads like an answer.

Unit 6's own responsibility, in the user's words: **turn the snapshot facts into
a user-facing evolution model** — not recompute the change types, which are
already a cache on the stored rows. The rules of §6.1–6.4 were satisfied by Unit
5's derivation, and the mapping is worth keeping in one place:

| The rule | Where it lives |
|---|---|
| 6.1 the lifecycle is created / modified / deleted, never unchanged | `DefinitionLife.events`: `_step` drops the unchanged rows instead of making events of them |
| 6.2 `unchanged` stays in the database and is ignored when reading evolution | the rows keep it (8 of the definition fixture's 13 rows); the derivation never looks at it |
| 6.3 `modified` is not taken on trust | the derivation compares fingerprints itself and reads no `change_type`; the order comes from the lifecycle walk; `blind_spots` and `unresolved` carry the parse status |
| 6.4 `deleted` is derived from absence, never stored | a deletion needs a snapshot that was read without the definition, or the file's own end |

What this unit adds is the saying of it:

- **The header counts the versions and lists the ones nobody could read**, with
  the reason each gave. Without that list, a gap that no event happened to span
  would leave no trace in the output at all.
- **A change derived across a gap says so on the line under it** — "at some point
  after 296267d7; 2a5a6fec could not be read, so when it went is not known". The
  event line above can only claim the change had happened *by* the version that
  showed it.
- **A creation whose earlier versions were never read says "first seen here"**
  rather than repeating "created": with nothing readable before it, the first
  version that showed the definition is not proof that it was born there.
- **A definition whose file was never read again is given no ending**, only a
  line naming the versions that could not be read. No deletion is printed for it.
- **Two definitions of one name are told apart in the heading** ("2nd of that
  name"), because the *n*-th life is the identity and the name alone is not.

Exit codes follow the rest of the tool: a path that is not Python, a path the
stored history never carried, and a file no version of which could be read all
fail with a message on stderr and exit 1 — the command cannot answer the question
asked, so it says why. A file that *was* read and holds no definitions is not an
error: it has an answer, and the block prints it.

Not built here, and next: the plain `structure <path>` — a file's structure at
one commit, with `--json` — and `--json` for `--history` itself, which the
project's CLI → JSON principle will want.

Verified by `tests/test_structure.py` (17 tests): the block for the definition
fixture line by line with `unchanged` never appearing in it; the header's counts
and its list of unreadable versions; a rename shown once; a deletion across a
gap; a definition left without an ending; a creation across a leading gap; a
mid-life absence of the file; two definitions of one name told apart; a file with
no definitions; a name used twice printing both histories; and the command's six
outcomes — the block, the half that is not built, a non-Python path, a path the
history never carried, a repository that was only analyzed, and a file no version
of which could be read.

## 15. Unit 7, as frozen

The other half of `structure`, and the JSON for both halves. The user's rules:

- **The query model is `definition_versions`**, the snapshot table. There is no
  `definition_changes` and there will not be one: `change_type` is a cached
  comparison stored on a snapshot row, and a deletion is derived by the query
  layer from two snapshots. The history JSON makes that visible — an event
  carries the `change` the layer derived, and beside it the two versions it was
  derived from (`previous_commit_sha`, `blind_spots`).
- **`structure <path>` shows one file version** — kind, qualname, lines,
  decorators, change type — and `--commit <prefix>` picks which version. The
  default is the file's latest stored version, which is what the stored data can
  answer and does not refuse a file that has since been deleted.
- **A version nobody could read does not print a listing.** It prints `AST
  analysis unavailable` and why: `parse failed` with the parser's own words, `no
  version was stored for this commit`, or `the file was not in this commit`.
  "Nothing was there" and "nothing could be read" must not look alike, in the
  block or in the JSON.
- **JSON**: stdout is the JSON and nothing else, notices go to stderr, and a
  parse failure is fields — `state`, `reason`, `parse_error`, `error_lineno`,
  `error_offset` — rather than a sentence. `state` is `read` or `unavailable`, so
  no reader has to infer "could not be read" from an empty list.

Two things about the rendering worth writing down:

- **`compared_with` and `blind_spots` are printed and carried.** `change_type` is
  the pass's cached comparison against the nearest version that could be read, so
  a version that was compared across unreadable ones says which version it was
  compared against. Without that line, an `unchanged` on a version whose file went
  dark in between reads as "nothing happened".
- **The kind column shows the stored word**, and the counts line names the
  methods: a method is a function whose enclosing scope is a class in the same
  file, which the qualified name already shows. No second naming scheme is
  invented in the table, and the JSON carries `kind` and `qualname` as stored.

One change to the model came out of this unit, and it is a correction rather than
a feature: **the commit that ends a file's life is now one of its versions**, as a
blind spot whose reason is `the file was not in this commit`. Until then the
deletion commit was reachable from no query at all, so `structure app.py` on a
deleted file answered about the last version before it and said nothing about the
file being gone. Now the default answer is "the file was not in this commit", the
history's header lists that commit with its reason, and
`--commit <the last version that had it>` still shows what it held.

The two faces now cover the whole read side: `structure <path>`, `--commit`,
`--history`, and `--json` on both.

Verified by `tests/test_structure.py` (32 tests), which now also covers the
listing's columns and counts on a file with a class, a method, an async method, a
decorated function and a function inside a function; the parse-failure block and
its JSON fields; a version that was never stored; a file that is gone; a version
that was read and held nothing; the line that says what the change types were
compared against; `--commit` picking a version and refusing a commit that did not
change the file; `--history` with `--commit`; and the JSON of both faces, with the
notice on stderr rather than in stdout.

## 16. Unit 8, as measured

No production code changed: this unit measures the AST layer and hardens the
regression surface around it. Two things changed, and both are the fixtures:

- **`build_large_repo`'s files are valid Python now** — a class with two methods,
  three functions, twenty-two lines, one function's operator flipped per edit.
  They used to be lines no parser accepts, so the AST layer had nothing to measure
  on the only large fixture in the suite.
- **The benchmark generates the same shape**, plus one thing the test fixture does
  not need: one file in ten cannot be parsed, so the pass has a failure rate to
  report rather than a sentence claiming everything worked.

### The scale fixture, in the test suite

`tests/test_scale.py` asserts the AST layer's arithmetic rather than its timing.
At a thousand commits and five thousand versions: every version is stored, every
version holds exactly the six definitions the fixture gave it, exactly sixty
versions create their definitions and the rest hold nought, one or two modified,
the created rows are `LARGE_FILES * LARGE_DEFINITIONS` and no others, and every
row carries the interpreter that read it. The query layer is checked at the same
scale — one file's history reads back with its versions, its six lives, and
exactly as many events as the store called changes.

### The benchmark, in phases

`benchmarks/benchmark.py` measures the pass by wrapping the names it calls its
phases through — `ast.parse`, `definitions_of`, `_change_types`,
`write_ast_batch`, `ObjectReader.read` — and **counts the calls**, so a wrapper
that stopped being called reports zero calls instead of a phase that got
infinitely fast. Measured on this machine, 2026-09-29, Python 3.13.5:

| commits | versions | definitions | db git | db +ast | read | parse | extract | compare | insert | total |
|---|---|---|---|---|---|---|---|---|---|---|
| 1,000 | 5,000 | 27,000 | 1.3M | 10.1M | 0.86s | 0.31s | 1.12s | 0.02s | 0.52s | 3.02s |
| 10,000 | 50,000 | 270,000 | 12.4M | 100.4M | 8.29s | 3.16s | 11.11s | 0.24s | 11.11s | 35.63s |
| 20,000 | 100,000 | 540,000 | 24.9M | 202.4M | 13.93s | 5.24s | 19.13s | 0.38s | 27.42s | 69.09s |
| 100,000 | 500,000 | 2,700,000 | 124.9M | 1008.0M | 67.91s | 25.52s | 100.40s | 2.07s | 192.18s | 405.27s |

Six facts from it, each of which is a measurement rather than a prediction:

- **Every phase is linear in the number of versions except the insert.** Ten times
  the history costs ten times the reading, parsing, walking and comparing.
- **The insert falls from about 52,000 rows/s to about 20,000** as the database
  goes from ten megabytes to two hundred. The transition happens as the file
  stops fitting in the page cache, and the rate flattens after it — which is a
  hypothesis about the cause, not a measurement of one. What is measured is the
  rate at each size, and the fact that the total stays linear anyway.
- **The walk over the tree costs more than the parse it does first**: `extract` is
  about three and a half times `parse` at every scale, because the canonical rendering and
  the fingerprint are per definition and the parser is per file.
- **A snapshot stores 2.78–2.99 rows for every row a change log would keep** on
  this fixture, and the ratio is a property of the churn rather than a constant:
  the audit's 2.15× was this repository's history, this is the fixture's. The
  report prints both counts so the ratio can be recomputed for any history.
- **The AST layer costs about eight times the git facts to store** for a version
  that holds six definitions. That is the number to use instead of v0.2's
  database size, and it moves with the number of definitions per file: a hundred
  thousand commits of git facts are 125 MB, and the same history with its AST
  layer is a one-gigabyte database.
- **A second pass costs almost as much as the first** — 374s against 405s at a
  hundred thousand commits — even though it parses nothing and reuses all 500,000
  versions. It saves the parse and the walk (126s) and pays for it with one query
  per version to read back what it is reusing. The docstring's claim, "a read and
  no parsing", is true; what the read costs had not been measured until now.

The pass reports its own success rate — `parsed 90000, failed 10000` at twenty
thousand commits, a 10.0% failure rate, which is the fixture's one-file-in-ten —
and every row carries the interpreter that read it, which is what keeps two
interpreters' rows from being read as one another's.

### The regression surface

`tests/test_ast_pass.py` adds the three cases the user asked for, end to end
against real git: the whole cycle run again (analyze, pass, analyze, pass — the
second pass parses nothing and every row is unchanged), a history rewritten with
`git commit --amend` (the five commits git kept keep their versions and
definitions; the rewritten one has neither until the pass runs again, and then it
gets its own), and a row whose `parsed_at_version` names another interpreter
(every version is read again rather than reused, and the stored version is the one
that read it).

## 18. Unit 10: the change-type constraint

One line of DDL, and the decision that came with it. `commit_files.change_type`
held git's letter from the `--raw` status field with nothing stopping a writer
from putting a word there instead; it now carries a `CHECK`, and the schema
version moved 3 → 4 with it.

- **The letters are git's, not the view's.** The constraint allows the nine
  letters git documents for that field — `A C D M R T U X B` — including the two
  this command line cannot produce (`C` needs `-C`, `B` needs `-B`). A constraint
  narrower than git's alphabet would reject a real observation, and its failure
  mode is a repository that cannot be analyzed at all; the failure mode of the
  wider one is a letter with no word of its own, which `commit.py` already
  handles by printing the letter (`CHANGE_NAMES.get(letter, letter)`).
- **The version moved with the DDL.** `open_analysis` refuses a database whose
  schema version differs, and `prepare_database` rebuilds it on the next
  `analyze`. Measured on the fixture: every reading command refuses a version-3
  database with the message that names the command to run, `analyze` rebuilds it,
  the structure layer comes back empty and says so, and `ast` re-reads all six
  versions. That is the documented path, and no database of version 3 exists
  outside this machine — v0.3.0 has not been pushed.
- **It changes no row.** The constraint describes what the writer was already
  doing. The only state that differs is which writes are refused, which is why
  the two tests for it are about refusals rather than about data.

The rule it enforces is the one the whole version follows, stated in §6: the
storage holds what git and the parser observed. `D` is an observation; "deleted"
is the tool's reading of it, and a reading belongs to the layer that can be
changed and re-derived.

## 19. The dependency chain, and what each unit owns

The spine of v0.3, written down after the fact so a later session can see the
whole of it in one place. Each unit is built on the ones above it, and nothing
below a unit is reachable from it.

```text
Unit 1  Definition Extraction      definitions.py
   ↓
Unit 2  Git Content Reader         objects.py
   ↓
Unit 3  Schema v3                  storage.py
   ↓
Unit 4  AST Analyze + Comparison   ast_pass.py
   ↓
Unit 5  Definition History         definition_history.py
   ↓
Unit 6  Definition Evolution       structure.py, the --history face
   ↓
Unit 7  Structure / CLI / JSON     structure.py, the version face; cli.py
   ↓
Unit 8  Scale / Hardening          tests/test_scale.py, benchmarks/
   ↓
Unit 9  Release                    both READMEs, the version, the roadmap row
```

**The responsibility split, in the user's words**, and the code that owns each:

| Unit | 职责 | Where it lives |
|---|---|---|
| 3 | 怎么存 — how a fact is stored: tables, keys, constraints, the rescan | `storage.py` |
| 4 | 当前版本里有什么，以及和上一可比较版本有什么差异 — the snapshot, and the comparison cache on it | `ast_pass.py` |
| 5 | 这些 snapshot 串起来以后，definition 的历史是什么 — the events, the gaps, the endings | `definition_history.py` |
| 6 | 把历史转成 evolution model — what a reader is shown as the evolution | `structure.build_history` and the helpers under it |
| 7 | 把结果展示给用户 — the version face, the JSON of both faces, the command | `structure.build_version*`, `cli.py` |

Four things the table cannot show, each of which is a decision rather than a
description:

- **The chain is a build order, not an import graph.** `storage.py` imports
  nothing but the `Commit` and `FileChange` dataclasses; it does not know that
  `objects.py` exists. The first module that ties Units 1, 2 and 3 together is
  Unit 4. "3 cannot be built before 2, because there would be nothing to store
  yet" is the true reading; "3 imports 2" is not.
- **Unit 5 reads the pass's rows, never the pass.** `definition_history` imports
  `storage`, `lifecycle` and `analysis`, and not `ast_pass`. A history is derived
  from what is stored, so the pass can be rewritten without touching the
  derivation — and the derivation cannot borrow a rule from the layer whose
  cached comparison it has to be able to disagree with.
- **Units 6 and 7 share one module on purpose.** They are the two faces of one
  command, and the line between them is the question each answers rather than the
  file each lives in: 6 answers "how did these definitions evolve", 7 answers
  "what was in this file at this version" and gives both faces a JSON form.
  `structure.py` imports no database — every fact it renders arrives as the
  history model, and the one thing it takes from the extraction layer is
  `FUNCTION_SCOPE`, the marker Python puts in a nested function's qualified name.
- **The 5/6 line is facts against words.** Unit 5 decides *what happened*: that
  `unchanged` is not an event at all, that a deletion needs two snapshots that
  were read, that a life whose file never parsed again has no ending, and that a
  gap is carried on the events it spans. Unit 6 decides *what a reader is shown*:
  the header counting the versions that could not be read, the "first seen here"
  and "at some point after X" wordings, the "no ending" note. The words are
  Unit 6's; every one of them is traceable to a fact Unit 5 put on the event. The
  omission of `unchanged` is not Unit 6's decision — it cannot print one, because
  `structure.py` imports `CREATED`, `MODIFIED` and `DELETED` from the history
  layer and there is no fourth word to import.

Unit 8 changed no production code (it measured, and hardened the fixtures), Unit 9
changed no production code (it documented and released), and Unit 10 — the `CHECK`
on `commit_files.change_type` — sits beside Unit 3 rather than in the chain: it
constrains how a fact may be stored and added no step.
