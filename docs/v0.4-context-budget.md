# v0.4 context budget

Unit 12 of v0.4. It measures what the evidence bundle costs, decides what a model
may be shown of it, and implements that as `selection.py`. The one rule it is
built around is the user's:

> **不能为了省 token 而改变事实层。只能改变送给模型的 context。**

Nothing in the bundle changes. What changes is what is sent to a model.

## 1. The measurement, before anything was decided

`benchmarks/context_benchmark.py`, run by hand like the other benchmarks. Six
shapes, each isolating one axis a commit can be large along, over generated
histories with real Python files and a real history behind the target commit —
every earlier commit writes different bytes, so the earlier-commit window and the
co-change statistics are built from something rather than from nothing.

`bytes` is the section's own JSON, `tokens` is the tool's estimator (four
characters per token, stated as the estimate it is), and the share is of the whole
bundle:

| Shape | Whole bundle | Largest section | Second |
|---|---|---|---|
| five files, two hunks each | 18,182 B / 4,545 | history 31% | ast_changes 16% |
| two hundred files | 495,954 B / 123,988 | history 45% | lifecycle 21% |
| a thousand files | 1,492,002 B / 373,000 | lifecycle 32% | history 22% |
| one file, five hundred hunks | 36,130 B / 9,032 | file_changes 82% | history 3% |
| one file, three hundred definitions | 118,645 B / 29,661 | ast_changes 75% | file_changes 15% |
| two hundred files, twenty hunks and ten definitions each | 1,431,464 B / 357,866 | ast_changes 41% | file_changes 27% |

Four things to carry forward:

- **The bundle is linear in the commit and has no ceiling at all.** The three
  sections that scale with the commit — `file_changes`, `lifecycle`,
  `ast_changes` — are exactly the ones the context builder deliberately does not
  cap, and `history` scales with both the commit and the depth of the repository.
- **The two sections the bundle does cap stay small.** Co-change never exceeded
  3.3 KB (five files, five partners) and the commit header is 335 bytes. The
  bundle's own `bounds` mechanism works; what it did not cover is the rest.
- **`lifecycle` outweighs `file_changes` on a wide commit** — 471 KB against
  296 KB at a thousand files — which is worth knowing because it is *context
  about* the files rather than the files themselves, and a reader would guess the
  other way round.
- **The earlier-commit window is the fattest section per file** (about 1,100 bytes
  for a file with five of them). That is what made it the one thing the view
  re-cuts rather than merely filtering rows out of.

## 2. The pipeline

```text
the bundle  ──────────────►  printed offline, carried by --json, unchanged
     │
     └──► selection ──► the budget check ──► the model
          (deterministic)   (a refusal)
```

Three steps, and each has a rule:

**The selection is deterministic and is not configuration.** The caps are
constants in `selection.py`. A selection that moved with a setting would make the
model's input depend on the machine it ran on, and the bundle's whole design is
that the same commit and the same database produce the same bytes.

This is also the half of the contract in `docs/v0.4-problem-definition.md` §12
that this unit is responsible for: the evidence is reproducible and the answer is
not, so what a reader can check is the bundle. Reducing it for the model without
reducing it for the reader is what keeps that true when a commit is too large to
send — otherwise the one artifact that is checkable would have been the one
artifact that was quietly cut.

**The budget check is a refusal, not a truncation.** This is the architecture
freeze's §8 rule, unchanged: the provider refuses a context over
`CODEARCHAEOLOGY_AI_MAX_CONTEXT_TOKENS` and names the size. What the selection
changes is that the refusal is now rare, and its message says the evidence was
already reduced — because past that point the limit is too low for the model
rather than the commit being too large.

**When nothing has to be dropped, nothing is.** `build_view` returns the bundle
itself, `selection` is `None`, and `view.json` is `build_json(context)` byte for
byte. Units 5 to 11 built "one bundle, two paths" and it still holds for every
commit that was never too large; the test that pins it is
`test_a_commit_that_fits_is_shown_whole`.

## 3. What is kept

| Section | Cap | Rule |
|---|---|---|
| `file_changes` | 20 | the largest by `added_lines + deleted_lines`, ties by path |
| `ranges` (per file) | 5 | the first spans, and the row carries `ranges_total` |
| `ast_changes` | 20 | the largest by the lines the definition spans, ties by path and name |
| `lifecycle` | follows the kept files | — |
| `history` | follows the kept files | and its window is re-cut from 5 to 2 |
| `cochange` | unchanged | the bundle already caps it at 5 × 5 |
| `absences` | 20 | the first, in the bundle's order |
| `message` | 4,000 characters | counted in characters, not bytes |

**Size is not importance, and the module says so rather than implying it.** The
rule is "the largest", which is a fact about the rows; the prompt is told the rule,
the counts are printed, and nothing claims that what was kept matters more than
what was left out. The bias is real and is written down in both READMEs: a pure
rename moves no lines, so on a commit large enough to be reduced it sorts last and
is the first thing left out.

**Why these numbers.** The widest shape the benchmark builds comes to about 11,000
estimated tokens at these values, against 357,866 for the bundle it was cut from.
They were chosen against that ceiling rather than by taste, and the ceiling is what
the README quotes. The earlier-commit window is the one that was re-cut rather
than row-capped: two commits say what five do about whether a file is hot, at a
third of the cost, and the window is a dimension the bundle already had a concept
for.

## 4. A selection is stated, in the place that already means it

Two mechanisms, and the split is deliberate:

- **`selection`**, inside the object the model is shown, carries a count for every
  list: `{"shown": 20, "omitted": 180}`. A list that lost rows is never silent,
  and a file whose spans were cut says so on its own row with `ranges_total` — a
  file showing five spans and one that has exactly five look alike otherwise.
- **`bounds`** carries the window, because that is where the bundle already says
  what it capped. The view's `bounds` is recomputed for the rows the view holds
  (`history_commits: 2`, and an omitted count summed over the view's own entries),
  so it cannot describe a set the view does not have.

The alternative — one block restating the other — was rejected because two places
saying the same thing are two places that can disagree.

**The model is told how to read it.** `INSTRUCTIONS` gained a seventh rule:
a `selection` means the commit was too large to send whole, never read a list as
complete when one is present, and never make a claim about what is not shown. The
prompt carries the block and the rule together, which is what the test
`test_the_prompt_carries_the_selection_and_the_rule_for_reading_it` holds.

## 5. The answer is checked against what the model saw

`validate(text, view.context)` — the view, not the bundle. A citation of a row the
model never saw is refused even though the bundle holds it.

This is the tighter of the two checks and the honest one: an answer has to rest on
what it was given, not on something that happens to be true elsewhere. It is also
free — `View.context` is a `CommitContext`, so `validation._known` and every other
pass work on it unchanged.

## 6. What a program is told

`explain --json` keeps the evidence whole and gains one key, `selection`, when the
model's view was reduced. A program checking an answer against its input can then
tell the two apart without a second call, which is the same reason `state` exists:
a reader that had to work out which of two things it got is a reader that can be
wrong.

The key is absent when nothing was dropped, which is not the same as an empty
block — its absence is the statement that the view and the evidence are the same
bytes.

## 7. The fact layer, checked

Three tests hold the user's rule rather than describing it:

- `test_the_evidence_is_not_reduced_by_being_selected` builds the view and then
  checks that the bundle is the same bytes it was before, and that the view really
  is smaller.
- `test_the_offline_path_prints_the_whole_evidence` runs the command with no model
  over a thirty-file commit and asserts stdout is the bundle, all thirty rows of
  it.
- `test_the_json_carries_the_whole_evidence_and_says_what_the_model_saw` asserts
  the envelope's `evidence` still holds every row and that `selection` is what
  reports the reduction.

## 8. What this unit does not decide

- **No per-section configuration.** The caps are constants. A user who wants
  different ones is asking for a different model's window, which is what
  `MAX_CONTEXT_TOKENS` is for.
- **No relevance beyond size.** Nothing here ranks by what a change *meant* —
  Evidence First forbids it — so "largest" is the only order the view uses, and
  the section that cannot be ordered that way (`cochange`) is left as the bundle
  wrote it.
- **No prompt unit.** The wording the model reads is still Unit 4's, plus the
  seventh rule; whether the prompt deserves its own unit is still open.
- **Nothing is stored.** An explanation is still not written anywhere, and a
  selection is not either — both are derived per run, which is what keeps a rule
  change from leaving rows nobody can correct.
