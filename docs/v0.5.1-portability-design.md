# The v0.5.1 memory portability design freeze

**What this is.** The frozen design for `memory export` — the first command that
takes a memory out of the database it lives in. It fixes the file format, what
the command writes and refuses to write, and the constraints the format must
satisfy so that `memory import` can be designed on top of it in a later unit.

**Why it exists.** `docs/v0.5-product-audit.md` §3 found three independent
scenarios — a newcomer arriving, a checkout being backed up, a repository being
moved — that all end in the same place: a memory exists in exactly one file, in
an operating-system cache directory, under a name derived from a path digest, and
nothing the tool offers can get it out. It also found the reason this is a
*completion* rather than a new direction: `docs/v0.5-storage-design.md` §1 chose
UUID memory ids **specifically so that an export and a re-import would not have
to renumber them and rewrite every lifecycle link**. The data model paid for this
feature in advance and the feature was deferred.

**Status: frozen, not built.** No code exists for this document yet.
`memory import` is *not* designed here — §5 records what the format must
guarantee for it, and its own unit designs it.

**Date:** 2026-10-08. **Tree:** `1c2bebd` plus the audit document; no source,
schema, CLI, test or README was changed by the unit that wrote this file.

---

## 1. What this unit is for

### 1.1 The three scenarios, and which half of them this unit answers

The audit separated the portability question into two halves that are easy to
confuse and must not be:

| | The scenario | What it needs | Is it gated by the understanding pilot? |
|---|---|---|---|
| **Data protection** | A backup that does not include the cache; a checkout that moves and looks empty forever | A way to get the memories out of the file, and a way to say where they belong | **No.** Losing what a person already stated is a defect whether or not the tool improves anyone's understanding. |
| **Sharing** | A newcomer who cannot see what a colleague stated; a fork that inherits a history but not the knowledge about it | A way to get them *in*, with a preview of what no longer resolves | **Yes.** If the tool does not help a person understand a codebase, knowledge about that codebase is not worth carrying. |

**This unit freezes export, which is the first half.** Export is the half that is
justified without the pilot, export is the cheap half, and export is the half
that must exist before import can be designed at all — a format has to be frozen
before something reads it.

### 1.2 Export first and import second, stated as a rule

`docs/v0.5-product-audit.md` §3.3 makes the enforcement point: **the whole cost
of every portability option is in import, not in export.** Export is a query and
a serialisation. Import needs conflict rules, an identity rewrite, an answer for
"the file and the store disagree", and a policy for two divergent sets of
lifecycle edges. Splitting them is therefore not a scheduling preference; it is
where the risk is.

**Rule for this unit:** design the format so that import is *possible*, freeze
only what export *does*, and leave every import decision to the unit that has to
argue for it.

## 2. The decision, and the options it beat

### 2.1 The decision

**A memory can be written to a text file that is a faithful copy of it, by an
explicit act, on demand. The store remains the only system of record. The file is
an artifact the person places; the tool never writes into a repository on its
own.**

This is Option D of the audit's §3.3 — repository-local with explicit
export/import — frozen for the export half.

### 2.2 What it beat, and why

| Option | What it would mean | Why it lost |
|---|---|---|
| **A copy of the `.db` file** | Tell the user to copy the SQLite file | It is already possible and already documented, and the audit found it insufficient: the file's name is a 16-hex digest of a path, and the documented advice ("copy the file before replacing it") is a ritual, not a workflow. A `.db` cannot be read, diffed, reviewed or hand-carried into a repository. |
| **Export into the repository by default** | `memory export` writes `.archaeology/memories.jsonl` into the working tree | It reverses a rule that is currently true and stated — "The tool never writes to the repository" (`docs/v0.5-storage-design.md` §2.2) — and it makes the tool a writer of the user's source tree, with dirty-tree and branch-switch questions nobody has argued. **It remains possible for a person to put the exported file in the repository**; the tool does not do it for them. |
| **Memory lives in the repository as the system of record** | Audit Option C: a tracked file is the truth and the database is a cache over it | Audit §3.3: it makes "in force at this commit" exact and retires the `not_provably_in_force` category — a real attraction — and it also makes **a memory written today invisible when reading a commit from last year**, which is the opposite of what the feature is for. That trade has not been argued and is not this unit's. |
| **A shared or remote store** | Audit Option E | Local First and SQLite-only for v0.x. The format frozen here is line-oriented text, so it does not foreclose one later. |
| **Nothing; document the file location better** | Leave the architecture alone | The audit's Scenario D is the answer: the file sits in a directory every operating system calls disposable, and documentation does not survive a disk-cleanup utility. |

## 3. The format

### 3.1 The shape, whole

A file is **JSON Lines**: one JSON value per line, terminated by `\n`. The first
line is a **header**; every line after it is **one memory**. No blank lines, no
comments, no trailing content.

The name of the format version lives in the header, so a reader can tell a file
it can read from one it cannot *before* reading a single memory.

### 3.2 The header

```json
{"memory_export_version":"1","repository":"/home/you/projects/sample","count":2,"exported_at":"2026-10-08T13:04:22.918273+08:00"}
```

Four fields, and each has a stated job — the project's rule that "a field nobody
reads is a claim nobody verified" (`docs/v0.4-explanation-schema.md` §6, where an
unknown field in a model's answer is refused) applied to a file:

| Field | Its job |
|---|---|
| `memory_export_version` | The reader's check. `"1"` is the only value this tool reads; anything else is refused by name rather than guessed at. |
| `repository` | What the import act names, so it can say "these were made about *that* path" without parsing every row — the same requirement `adopt --from` has. |
| `count` | The integrity check. A reader counts the memory lines and **refuses a file whose count disagrees**, so a truncated file is loud rather than silent. |
| `exported_at` | A person's provenance: when this copy was made. Nothing reads it. |

**A reader identifies the header by position and by shape**, and refuses any
first line that is neither: the header carries `memory_export_version` and no
`memory_id`, a memory line carries `memory_id` and no `memory_export_version`,
and a line that is both or neither is a corrupt file.

**Deliberately not in the header:**

- **No tool version.** The *format* version is the compatibility contract; the
  tool version is not, and the reader would ignore it — which is the field
  nobody verified, refused one paragraph up.
- **No `memory_schema_version`.** A file format and a table shape are two
  different contracts, which is the same reason the store keeps its own stamp
  separate from the evidence schema's (`docs/v0.5-storage-design.md` §7.2).
- **No `head_sha`.** It would be a fact about the *exporting repository* that the
  importing side can check for itself by resolving the citations, and it would
  make export read git for a field nothing uses.

### 3.3 One memory, and the rule that defines it

**A memory line carries exactly the fields the store holds, and nothing the store
works out.** Every field is a column of `memories`, a value the author gave, or a
citation the author gave. This is one sentence, and it decides four exclusions:

| Excluded field | What answers it | Why it cannot be in the file |
|---|---|---|
| `subject.resolution` | The evidence layer | It is answered against **this** repository's stored history. The same field read in another repository would be a different answer, so a file carrying it carries an answer that is wrong where the file is going. |
| `citations[].resolution` | The evidence layer | The same, and the check is re-run on every read by design (`docs/v0.5-storage-design.md` §4.3, "checked twice, repaired never"). |
| `since.commit_date` | The evidence layer | It is the cited commit's recorded date, read out of `commits`; the importing repository re-reads it, or cannot and says so. |
| `supersedes` | The rest of the memory set | It is the reverse of `superseded_by`. The store keeps **one** direction so that two rows cannot disagree about it (`memory.py`, the `Memory` docstring), and a file is storage. |

**A consequence worth stating because it is a feature:** the four exclusions are
exactly the fields that need the evidence tables. So **`memory export` reads no
evidence table at all** — it cannot be affected by a stale analysis, it performs
no citation check, and its cost is a scan of the memory tables and nothing else.

**What is included, in full.** Every field of the `Memory` object as the store
holds it, in the shape the tool already uses for a memory everywhere else
(`memory_view.memory_object`):

```json
{"memory_id":"6f1c0a6e-2b31-4a97-9e2c-9b7f0a1d3e55","repository":"/home/you/projects/sample","statement":"We keep the login helper in one module: the split state machine caused an incident.","author":{"name":"You","email":"you@example.com"},"admitted_at":"2026-10-08T12:40:01.123456+08:00","subject":{"kind":"path","path":"core/app.py"},"since":{"commit":"1edec2712ab34cd56ef7890123456789abcdef01"},"state":"active","ended_at":null,"end_reason":null,"superseded_by":null,"citations":[{"kind":"commit","ref":"1edec2712ab34cd56ef7890123456789abcdef01"}]}
```

and a second memory, superseded, to show the lifecycle in the file:

```json
{"memory_id":"ab7d13f0-9c44-4b1e-8a55-02de6c7f9a10","repository":"/home/you/projects/sample","statement":"The retry wrapper exists because the payment provider returns 200 with an error body.","author":null,"admitted_at":"2026-10-08T12:41:55.004321+08:00","subject":{"kind":"definition","path":"core/payments.py","qualname":"Client.send"},"since":null,"state":"superseded","ended_at":"2026-10-08T12:43:02.778899+08:00","end_reason":null,"superseded_by":"6f1c0a6e-2b31-4a97-9e2c-9b7f0a1d3e55","citations":[{"kind":"file","ref":"core/payments.py"},{"kind":"absence","ref":"core/payments.py:retry budget"}]}
```

**The row is not the object `memory show --json` prints, and that is deliberate.**
Four readings of a store — the block, the JSON, the model's prompt, and the
envelope — share one shape because they are all readings of the same store, and
the project says so where that shape is defined (`memory_section.section_object`:
"One object for all four paths"). **A file is not a fifth reading.** It is
storage that has to be true in another repository and after a round trip, and the
four fields it drops are exactly the ones that would not be. The difference is
stated here so that a reader who finds it does not have to guess whether it was
an oversight.

**`since` appears only when the author gave one.** `{"commit": …}` when they gave
a commit, `{"date": …}` when they gave a date, `null` when they gave neither —
and `null` means unknown, never "from the beginning", which is the rule the store
already holds (`memory.py`, the `Memory` docstring). The schema's `CHECK
(since_commit_sha IS NULL OR since_date IS NULL)` means a file can never carry
both.

**`repository` appears on every row**, as well as in the header. Both have a job:
the header's is what an import act names, and the row's is that the row is a
faithful copy of the object and that a file which disagrees with itself can be
detected. A reader refuses a row whose `repository` differs from the header's.

### 3.4 Order

**Ascending by `memory_id`.** One total order, chosen so that the file is a
function of the set and not of the order things were written in:

- Admission order is not available as a total order — two memories can share a
  timestamp, which is the trap the store's own microsecond precision exists to
  narrow and does not close (`_now`, and trap 10's "Commits can share a
  timestamp").
- A UUID is unique by construction, so sorting on it is total, stable and
  reproducible.
- The consequence is that **two exports of an unchanged store are byte-identical
  in their memory lines** (§4.7), and a diff between two exports of the same
  store at different times shows only what changed.

`position` on a citation is **not** a field of the file: the array's order *is*
the position, which is how the store encodes it (`memory_citations`'s primary key
is `(memory_id, position)` and `Memory.citations` is a tuple in that order).

### 3.5 The bytes

| Property | Value | Why |
|---|---|---|
| Encoding | UTF-8, no BOM | The tool already writes UTF-8 to a stream that is not a terminal (trap 35), and a memory's statement is a person's own words — including in whatever language they wrote it. |
| `ensure_ascii` | `false` | The same reason the rest of the tool's JSON uses it: a statement is meant to be read. |
| Line ending | **`\n` on every platform, written explicitly** | A file whose bytes depend on the platform is a file whose diffs are noise. The project has already paid for this lesson once (the READMEs are CRLF and `docs/` is LF, and `git diff` warns about it). |
| One line per memory | Guaranteed by JSON | A statement containing a newline is escaped by the serialiser, so "one memory per line" cannot be broken by a statement's content. This is the property the whole format rests on and §6 tests it. |
| Trailing newline | Every line ends with `\n`, including the last | So `wc -l` counts memories plus the header, and appending to a file cannot corrupt the last record. |

### 3.6 What is deliberately not in the file

- **No resolution states** (§3.3) — and therefore **no evidence is needed to
  write it or to read it**.
- **No count per state, no summary, no statistics.** A file that carries a
  derived total is a file that can disagree with its own rows.
- **No evidence rows, no diff, no commit data.** A memory cites evidence; it does
  not carry it. The file is not a backup of the repository.
- **No metadata about the act** — no `exported_by`, no command line. `exported_at`
  is the one fact about the act that a person needs, and the act is not written
  to the store either (§4.4).

## 4. `memory export`

### 4.1 The command

```console
$ archaeology memory export [PATH] [--db PATH] [--output PATH] [--force]
```

`[PATH]` and `--db` are the two arguments every command in the tool takes, and
this one resolves them the same way (`_repository_and_database`). There is no
`--json`: **the output *is* JSON**, and a JSON envelope wrapped around a JSON
document would be a second shape for the same facts.

### 4.2 Where the bytes go

- **With `--output PATH`**: the file is written, and the block (§4.5) is printed.
- **Without it**: the JSON Lines document goes to **stdout** and nothing else
  does, so it composes:

```console
$ archaeology memory export ~/projects/sample > memories.jsonl
$ archaeology memory export ~/projects/sample --output backup/memories.jsonl
```

Notes and refusals go to stderr, per the exit contract
(`tests/test_contract.py`: "A refusal is `Error: <sentence>` on stderr, exit 1,
and nothing on stdout"), which is what keeps a redirected export parseable.

### 4.3 It refuses to replace a file it did not write

**When `--output` names an existing file, the command refuses**, unless `--force`
is given. The refusal names the path and says both ways out:

```console
Error: /home/you/backup/memories.jsonl exists; this command does not replace a
file it did not write. Give another path, or pass --force to replace it.
```

**This is the first command in the tool that writes a file at a path a person
named and would replace one that is already there.** The precise version of the
claim, because the loose version is not true: `analyze` and `ast` write the
database and create its parent directory (`analysis.py`, `database.parent.mkdir`),
which `--db` lets a person place anywhere — including inside a working tree. What
no command does is **replace** a file: a database that exists is opened and
written *into*, table by table, and the tool never deletes or recreates the file;
nothing outside the database is written at all. The tool does destroy data — a
schema rebuild drops the evidence tables and `clear_history` clears the history —
but only inside a file it wrote itself. So `--output` pointing at an existing file
is a genuinely new kind of act: **the first one that can destroy something the
tool did not write.** There is no precedent to follow, and the choice is made
here.

The reasons it refuses rather than replacing, in the order they weigh:

1. **The tool has no interactive prompt anywhere**, deliberately ("**No
   interactive prompt.** The tool has none anywhere… the exact-path requirement
   is the safety", `docs/v0.5-cli-design.md` §6.6). So the safety cannot be a
   question; it has to be a refusal and an explicit flag.
2. **The destructive case is a typo, and it is cheap to catch.** `--output
   README.md` in a project root should not delete a README. `--outpt` would be a
   usage error; `--output` pointed one directory wrong is not.
3. **A refused export costs one flag; a destroyed file costs a file.** The
   asymmetry is the same one `adopt` uses when it refuses a destination that
   already holds memories.

**`--force` is the explicit act**, in the same family as `adopt --from`'s full
path: the tool does not ask, and the person says what they mean.

### 4.4 What it reads, and what it does not

| | |
|---|---|
| **Reads** | The two memory tables, and the `meta` row that says they are this tool's shape. |
| **Does not read** | Any evidence table. No commit, no file version, no definition, no co-change. Consequently: no citation is checked, no resolution is computed, and the analysis being stale cannot affect the output. |
| **Does not write** | Anything, anywhere, except the output file. **The store is not touched.** `adopt` records its act in `meta` because it changes the *rows'* identity; export changes nothing, so it records nothing. `exported_at` is a fact about the file and lives in the file. |

**Because it reads no evidence, it takes no `_warn_if_behind` note.** The note
exists to say that a reading built from the evidence may be behind the
repository; export builds nothing from the evidence. (`memory list` does take it,
because the list re-checks each memory's cheap citations.)

**One requirement it does inherit:** `open_analysis` must accept the database,
which means the database has to be an analysis of *this* repository. A database
whose `meta.repository_root` names another path is refused with the sentence the
tool already gives, and the way through is unchanged: `analyze --db <file>` first,
then the memory command. Export does not weaken that rule and cannot be used to
read another repository's store by pointing `--db` at it.

**Zero memories is a success, not an error.** A project nobody has written a
memory about exports a header and no memory lines, and the block says `0
memories`. "None found" and "none shown" are two different answers
(`memory.py`, `foreign_memories`), and a user who pointed `--db` at the wrong file
can see which database was read in the block.

**Another repository's memories are not exported, and are reported.** The file is
about one repository — the same rule the read side already follows — so the
export filters to this repository and, when the database holds others, says so on
stderr with the count and the paths, exactly as `memory list` does. They are never
silently included in the file.

### 4.5 The block

Aligned label and value, the shape `adopt` uses:

```console
$ archaeology memory export ~/projects/sample --output backup/memories.jsonl
Wrote       12 memories
To          /home/you/backup/memories.jsonl
Repository  /home/you/projects/sample
Database    /home/you/.cache/codearchaeology/82d48b376fde.db
```

Four rows, each with a job: what was written, where it went, which repository the
file is about, and which database it was read from. The last two are the ones a
user needs when the answer surprises them, and they are the same two rows
`adopt` prints.

The block is deterministic — no timestamps, no elapsed times — so that both
READMEs can replay it (`tests/test_readme.py`), which is a contract every command
in the tool is held to.

### 4.6 What the file is, in one sentence, for the reader

The block is followed, in both READMEs and in `--help`, by the sentence that
prevents the one misreading this feature invites: **the file is a copy, not a
second copy of record.** Editing it changes nothing until something imports it,
and the store is what every other command reads. The tool says so where the
misreading would happen — the rule the v0.4 contract already follows for its
block ("the tool says so where the misreading would happen").

### 4.7 Determinism, as a stated contract

**Two exports of an unchanged store differ in exactly one byte range: the
`exported_at` value in the header.** Every memory line is byte-identical, because
the order is a function of the set (§3.4) and no field in a row is derived.

This is narrowed deliberately rather than dropped. The project's habit is a
byte-identity claim ("the bundle is byte-identical with and without memories"),
and the honest version of the claim here is that the *rows* are identical and the
header's timestamp is not — a person asking "is this the same set I exported
yesterday?" compares rows, and a test can too.

## 5. What `memory import` will require of this format

Recorded, not designed. Each is a constraint this format either satisfies or
does not, so that the import unit inherits a short list rather than a
re-investigation.

1. **The file must name the repository it was made about.** It does — in the
   header and on every row — so an import act can require the source path to be
   named, exactly as `adopt --from` does, and can refuse a typo by matching
   nothing.
2. **Every citation must be re-resolvable against the target repository, and the
   resolution states must be recomputed there.** The format carries `kind` and
   `ref` only, in v0.4's form, so the importing side runs the checks the tool
   already runs (`memory_checks.py`) and can show a preview — "of 12 memories, 9
   cite commits this repository does not have" — **before anything is written**.
   This is the mechanism that makes a fork import reviewable rather than
   automatic.
3. **The lifecycle links are closed under the set.** `superseded_by` is a
   foreign key into `memories` and `PRAGMA foreign_keys = ON` is set on every
   connection (`storage.connect`), so a partial import cannot leave a dangling
   link — the insert would fail. An import therefore takes a *closed* set, or a
   subset it can close. Two divergent sets still have no defined merge, which is
   the open question this format does not answer.
4. **Ids are stable, so a re-import is identifiable.** A `memory_id` is a UUID4
   chosen so that "a lifecycle link survives the copy"
   (`docs/v0.5-storage-design.md` §1). An import meets a memory id that is already
   present, which is what makes idempotence *possible* to define; whether to skip,
   refuse or compare is the import unit's decision.
5. **Nothing but `repository_path` may change on import.** The `adopt` rule —
   "It never touches a statement, an author, a time, a citation or a state" —
   is the standard. An import that reworded, re-dated or dropped anything would
   be the tool editing knowledge.

**What the format does *not* settle, and must not be read as settling:** whether
an import merges, replaces, or refuses; what happens when a memory id exists with
different content; whether an import may narrow the set; and whether an import is
available when the store holds another repository's memories already. All four are
the import unit's, and the audit's §11 lists them among the decisions needed before
v0.6.

## 6. Acceptance criteria

The unit that builds this is done when all of these are demonstrable:

1. **A round trip of the file's own quality.** Two exports of the same unchanged
   store are byte-identical but for `exported_at` (§4.7), and that is asserted by
   comparing bytes, not by comparing parsed objects.
2. **The count guard works in both directions.** A file whose header `count` does
   not match its memory lines is refused by name; a file whose version is not
   `"1"` is refused by name.
3. **One memory per line, whatever the statement contains.** A statement holding
   a newline, a `\n` inside a JSON string that must stay escaped, a quote, a
   backslash and a non-ASCII character all survive to a file whose line count is
   memories plus one.
4. **The four exclusions hold.** No memory line carries `resolution`,
   `commit_date` or `supersedes`, asserted as a key-set comparison against the
   canonical object rather than by spot-checking.
5. **Export reads no evidence.** Held the way this project holds such things: run
   `memory export` against a database whose evidence tables have been emptied,
   and get the same bytes. This is the structural test in the shape
   `tests/test_memory_boundaries.py` already uses (`analyze → memory`, `ast →
   memory`).
6. **The store is not written to.** Every `meta` row and both memory tables are
   compared byte for byte before and after an export.
7. **A refusal is a sentence on stderr, exit 1, and nothing on stdout** — the
   existing exit contract, with the two new refusals (the target exists, the
   database is not this repository's) as cases.
8. **Both READMEs carry the command**, because
   `tests/test_readme.py::test_every_registered_command_is_documented_in_both_readmes`
   walks every registered command *including a group's* (`_registered_commands`
   has a second loop for exactly this), and every `console` block a README shows
   is replayed.
9. **The version agrees in five places** — `pyproject.toml`, `__version__`, both
   READMEs and the CHANGELOG's newest section, which
   `tests/test_cli.py::test_every_copy_of_the_version_agrees` compares. Adding a
   command therefore forces the release unit to bump the version *and* write the
   CHANGELOG entry; the two cannot drift.
10. **The narrowed determinism contract is stated in both READMEs**, not only in
    this document, so that a user comparing two exports knows which bytes to
    compare.

## 7. What this unit does not decide

Open for the user. The first two are the ones that change the deliverable; the
rest have a recommendation recorded and will be built as recommended unless
they are overruled.

1. **Does the export filter anything?** — *Recommendation: no.* A copy is whole,
   and a filter is a view, which is what `memory list --json` already is. If a
   filter is wanted later (`--active-only`, `--subject`), it is a later unit with
   its own argument, and it should not ride in on this one.
2. **The file's default name and extension.** — *Recommendation: none imposed.*
   The tool takes a path and writes it; the READMEs use `.jsonl`. Enforcing an
   extension would refuse a name for a reason that does not matter.
3. **Does the header keep `count`?** — *Recommendation: yes, with a refusal on
   mismatch.* The trade is honest both ways: the count catches a truncated file,
   and it is the one derived value in the header. It is kept because a truncated
   *backup* is the failure this feature exists to prevent, and a refusal is loud
   while a short file is silent.
4. **`--force`, or always replace?** — *Recommendation: refuse without it.* §4.3
   gives the reasons; this is the decision most likely to be overruled, because
   it is the first file the tool writes to a user-named path and the user may
   want the Unix `>` behaviour instead.
5. **Does export write to stdout by default, or require `--output`?** —
   *Recommendation: stdout by default.* It composes, and the shell's own `>` is
   **the person's** act of replacing a file rather than the tool's, which keeps
   §4.3's refusal from blocking the everyday case.

**Not open, and recorded so it is not re-litigated:** the format is JSON Lines
(one line per memory; a diff must be readable and a hundred thousand memories must
not have to be parsed to be counted); the order is `memory_id` ascending; the
line ending is `\n`; the encoding is UTF-8 without a BOM; the file carries no
evidence and no derived field; and the store is never written to.

## 8. Amendments

Six, each recorded with its reason. The pattern is v0.5's own: a freeze is worth
having precisely so that the places it was wrong are visible rather than
rediscovered.

**1. The row is built by sharing `memory_view`'s builders, not by restating
them.** §3.3 said the four exclusions would be held "as a key-set comparison
against the canonical object". That comparison is in the tests, but the *stronger*
form was available: `author_object`, `subject_object` and `since_object` became
public in `memory_view`, the object composes them, and so does the export. The
three fields that are excluded from a row are now added *beside* the rendering
rather than held in the memory — so a fifth field added to the object cannot go
missing from a file, which a key-set test would only catch if someone remembered
to update it. Key order and every existing byte are unchanged, which the memory
and contract suites hold.

**2. `memory.repository_identity` is public.** The freeze said the header must
name the repository the rows name, byte for byte (§3.2), and did not say where
that string comes from. It is one expression, `str(Path(path).resolve())`, and a
second copy of it in the command line is exactly how the two would drift, so what
was `_resolved` was renamed rather than duplicated.

**3. A target that cannot be written is refused with a sentence, and its parent
directory is not created.** The freeze gave the refusal for an existing file
(§4.3) and said nothing about a path whose directory is missing. Creating it would
be the tool guessing on a path a person typed — every other path it writes to is
one it chose itself — so the `OSError` is caught and refused by name. This is the
reading §4.3's own reasoning gives, made explicit.

**4. The replayed README block is the `--output` form, and the file's shape is
shown as a tree rather than as a line of JSON.** §6 criterion 8 asks both READMEs
to carry the command, and the checker replays every `console` block — which the
*standard-output* form cannot satisfy, for two reasons the freeze could not see:
the lines are ordered by a generated id, so which memory appears where changes
every session, and a single memory line runs to about four hundred characters
where the longest line in `README.md` is 235. So the block that is replayed is the
`--output` summary — four short deterministic lines — and the format itself is
shown in the tree form `docs/v0.4-explanation-schema.md` §3 already uses for a
JSON shape. Two blocks per README: one replayed, one illustrative.

**5. The README checker gained two pieces of machinery.** `Scenario.restore()`
now removes the file the export block wrote, because copying the database back is
not enough for a file and *both* READMEs carry the same block — the second one
would otherwise be shown a refusal instead of what its own text says. And
`_normalise` now collapses the separator a documented path is joined with, after
the path substitutions: a path the tool prints by joining the repository to a name
carries the machine's separator, so a block written with `/` failed on Windows and
one written with `\` would have failed on Linux. Found by running it, not by
thinking about it.

**6. The boundary suite caught the new module, which is what it is for.**
`tests/test_memory_provenance.py::test_the_evidence_layer_never_reads_memory`
scans every module in the package for an import of the memory side, and
`memory_export.py` reached for two of them without being on `MEMORY_SIDE`. The
fix is one line on that list — the module *is* the memory side — and the failure
is worth recording because it is the guard doing exactly the job it was written
for on the first module to be added since.

**One criterion is not met by this unit, and it is the import unit's.**
§6's criterion 2 — "a file whose header `count` does not match its memory lines is
refused by name" — describes a *reader*, and there is no reader until there is an
import. What this unit holds is the writer's half: the count it writes always
matches the lines it wrote (`test_the_header_counts_the_memories_and_names_the_format`).
The refusal is the import unit's to build and to test.
