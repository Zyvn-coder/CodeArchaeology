# v0.3.x Final State

The deterministic evidence layer, frozen. This file is the record of what v0.3.x
is: what it contains, what holds it in place, what it costs, and what it does not
do. Everything in it is a fact about the tree it was written in, and the numbers
are measurements taken on 2026-09-30 on one machine, with the commands that took
them named so they can be taken again.

## What it is

Git tells you what changed, when, and who did it. This tool answers the other
question: **what was the code, and how did it get this way.** Every answer it
gives is traceable to a commit, a diff or an AST node — the file that was touched,
the definition that was there, the commit that moved it. It never says why.

That boundary is the freeze. v0.3.x proves what happened; it does not interpret
it.

## The five rules of the model

These are the frozen decisions, and each one has a test that fails if it stops
being true. They are what "the deterministic evidence layer" means concretely.

1. **A snapshot is a fact.** `definition_versions` holds every definition that
   every readable version of every file contained — not a change log, so no
   answer depends on replaying a file's history.
   *Held by:* `tests/test_ast_storage.py::test_a_fresh_database_has_both_tables`.
2. **A deletion is derived, never stored.** There is no `deleted` row anywhere;
   a definition that is gone is an absence, and `change_type` is not allowed to
   hold the word.
   *Held by:* `tests/test_ast_storage.py::test_the_three_change_types_are_the_only_ones`,
   `tests/test_ast_pass.py::test_a_deleted_file_gets_no_deletion_row`.
3. **A parse failure is uncertainty.** A version that could not be read is
   recorded with the parser's own words and no definitions, and never as a file
   that held nothing — so a syntax error can never be read as a deleted function.
   *Held by:* `tests/test_ast_storage.py::test_a_version_that_could_not_be_parsed_is_not_an_empty_version`,
   `tests/test_definition_history.py::test_a_deletion_across_a_gap_names_the_gap`.
4. **`change_type` is a cached comparison.** `created`, `modified` and
   `unchanged` say what one snapshot looks like next to the last readable one.
   The history layer re-derives it rather than trusting it, and a test holds the
   two to each other in both directions.
   *Held by:* `tests/test_definition_history.py::test_the_derived_events_agree_with_the_stored_comparison`.
5. **Identity is derived.** There is no `function_id`, no `lifetime_id`, no
   `renamed_from` in the schema: a definition is its kind and qualified name
   within one version, and a file is a chain of commits, both rebuilt on demand.
   *Held by:* `tests/test_ast_storage.py::test_the_tables_hold_no_derived_identity`.

## Evidence First

Verified on 2026-10-01 against the whole of `src/`:

- **No AI, no LLM, no prompt, no embedding.** No import of `openai`,
  `anthropic`, `langchain`, `transformers` or anything like them.
- **No network.** No `urllib`, `requests`, `httpx`, `socket` or `http`. The only
  subprocess this tool runs is `git`.
- **No semantic inference.** No reading of commit messages, no guessing at
  intent, no similarity scoring of our own — rename detection is git's, and the
  score it reported is stored rather than recomputed.

The two runtime dependencies are `typer` and `rich`. Anything that would break
one of these three lines is v0.4 work at the earliest, and needs the user's
decision first.

## What it costs

From `benchmarks/benchmark.py` over a generated history — 200 files, five edited
per commit, uniform commit sizes. Read the curve, not the numbers.

| Commits | Git facts | Database (Git) | `analyze` | `timeline` | `hotspots` | `cochange` | AST: cold | warm | after 100 new |
|---|---|---|---|---|---|---|---|---|---|
| 10,000 | 8.5 MB | 12.4 MB | 1.4s | 0.24s | 0.36s | 0.40s | 33.0s | 10.0s | 9.0s |
| 50,000 | 42 MB | 62.6 MB | 7.8s | 1.7s | 2.3s | 3.0s | 186.9s | 46.3s | 46.8s |
| 100,000 | 84 MB | 125 MB | 17.1s | 3.5s | 5.6s | 6.3s | 395.3s | 109.6s | 134.5s |
| 200,000 | 168 MB | 250 MB | 41.0s | 8.6s | 13.6s | 15.5s | 809.9s | 304.0s | 333.7s |

- The AST layer is about **8× the Git facts** to store and about **3 rows per row
  a change log would keep**: at 200,000 commits, 250 MB becomes 2.0 GB and 5.4
  million definition rows.
- The pass holds the stored versions and definitions whole, so a
  200,000-commit history wants about **4.3 GB of memory** to run it.
- **Nothing is quadratic**, and nothing is incremental: `analyze` rewrites every
  commit row it already has (85% of its time at 200,000 commits), and the pass
  reads every blob back to learn it is the one that was stored.
- A warm pass **parses nothing and writes nothing**; a pass after a hundred new
  commits **writes those hundred and nothing else**.

`benchmarks/index_benchmark.py` audits the schema's four indexes against the same
three questions — what a read loses without it, what the file saves, what a write
pays. Two of the four are in no query plan at all (`commit_parents_parent`,
`commit_files_path`), and they cost 8.1 MB between them; the other two
(`file_versions_path`, `definition_versions_qualname`) are what `structure` reads
through. The index set is unchanged, and the audit table in `PROGRESS.md` has the
numbers and the reasoning.

## Known limitations

The full list is in both READMEs, kept there because it is what a user reads
before deciding whether the tool is for them. The load-bearing ones:

- **Python only.** The structure layer reads `.py` files; the git side reads any
  repository. Other languages are a roadmap item, not a bug.
- **The parser is part of the evidence.** Every stored row names the interpreter
  and the analyzer that produced it, so a database written by 3.11 and read by
  3.13 re-reads those versions instead of mixing two producers' answers. The
  practical cost is a re-parse after an upgrade; the benefit is that no answer is
  ever attributed to the wrong reader. Deeply nested source that exhausts the
  parser's own C stack is recorded as a failure, and the depth at which that
  happens belongs to the machine, not to the source.
- **A parse failure is not a deletion.** A version that cannot be read leaves its
  definitions unknown, and the tool says so instead of inferring.
- **Large repositories cost real time and memory** — about thirteen minutes and
  four gigabytes for the first pass over two hundred thousand commits.
- **The database is about eight times the Git facts** it comes from, because it
  is a snapshot rather than a change log.
- **A co-change score is a statistic about commits.** It is a conditional rate
  over one file's commits, it is not symmetric, and it is not a statement about
  the code. Commits over `--large-commit-limit` files are excluded and pairs under
  `--min-shared` are hidden; both counts are reported so neither reads as "none
  found".
- **`commit` has no JSON form.** The six other reading commands do, and the block
  is the only way to read one commit's facts from a program. It is a gap rather
  than a decision: the shape would be the block's own facts under the names the
  other JSON outputs use, and it is recorded in `PROGRESS.md`'s *Next* rather than
  invented during a freeze.
- **Rename detection is git's**, at its default 50%: a rename that changed too
  much is a deletion plus an addition, which splits that file's life.
- **A shallow clone is a differently shaped history**, not a shorter one, and
  `analyze` says so on stderr.

## What is not here

- **AI in any form.** No provider, no prompt, no explanation. That is v0.4, and
  it starts from a new design freeze rather than from this layer's assumptions.
- **A web UI.** v0.1–v0.3 are a CLI. The JSON output is what a UI would read, and
  it exists; the UI does not.
- **Inferring why something changed** — "this file changes often, so it has
  bugs". There is no evidence for that in the data, and inventing it is not the
  plan.
- **Complexity scores, call graphs, dependency analysis.** Those are different
  features, not evolution.
- **Languages other than Python**, and **AST similarity used to re-link files**
  git reported as a delete and an add — that would change file identity, which
  v0.2 settled on git's evidence alone.

## The release

The v0.3.0 tag points at `a2a4565`, and its CI run is green. Everything built
since — co-change, the `files`/`hotspots` split, the README contract checker, the
AST reuse path and the write the pass no longer makes — is in this commit, which
is where the tree calls itself 0.3.1.

The release of v0.3.1 is a sequence, and the order is the point: a tag must name a
commit that passed CI on every job, not a commit that was fixed afterwards.

1. Commit the tree with the release date written into `CHANGELOG.md`'s 0.3.1
   section. **Done — `c9359b6`, dated 2026-10-01.**
2. Push `main` and wait for all four CI jobs to pass **on that commit**.
3. Tag `v0.3.1` at that commit and push the tag.
4. Create the GitHub Release from the tag.

Step 2 is what the order is for: the two Windows jobs failed on `c9359b6`, and
what they found was a real defect in the tool rather than in the blocks — the
README checker's first Windows run, recorded as trap 35 in `PROGRESS.md`. The fix
is `c2d5b97`, its run is green on all four jobs, and **the tag is on it**: `v0.3.1`
points at `c2d5b97`, not at the release commit that failed. The failed run stays in
the Actions log, so the sequence is visible rather than erased — the same shape as
v0.3.0, whose tag also moved onto the commit that fixed its red run.
