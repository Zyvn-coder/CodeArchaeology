# v0.6 problem definition

**Status: a problem definition, not a plan and not a change.** No production
code, schema, CLI, provider, evidence bundle, memory semantics, test or README
contract was touched by the unit that produced this file. It is one document. It
fixes the question v0.6 would answer, the evidence it may use, what it must not
do, and which decisions belong to the user — and it decides nothing that is the
user's to decide.

**Date:** 2026-10-24. **Tree read:** `b2fd3d8` — working tree clean, `main` one
documentation commit ahead of `origin/main` (`fdc6198`), the last release `v0.5.3`
an annotated tag at `90b2c8a` whose own CI is green. The one unpushed commit is
documentation; §10.3 records the state rather than fixing it.

**What this is not:** it is not the v0.6 design freeze (that document does not
exist), it is not a commitment to ship v0.6, and it is not a change to any frozen
document. Where it recommends something, the recommendation is marked
**PROPOSED** and is the user's to rule on.

---

## How to read the markers

Every substantive claim carries one of five words. The first three come from
`docs/v0.5-product-audit.md`; the last two were added here because a problem
definition makes recommendations as well as claims.

| Marker | Means | How a reader checks it |
|---|---|---|
| **CONFIRMED** | A file, a test, a measurement or a command output in this tree proves it. | Re-read the file or re-run the command named beside it. |
| **INFERRED** | It follows from confirmed facts by argument. No experiment supports it. | Attack the argument. If it holds, it is still only an argument. |
| **UNKNOWN** | This tree cannot settle it. It needs an experiment, a measurement, or a decision by the user. | Nothing to check — that is what the word means. |
| **FROZEN** | An earlier freeze records the decision, with a source named beside it. This document may not change it. | Read the source. Changing it is a formal amendment, not an edit here. |
| **PROPOSED** | A recommendation of this document. **The user has not ruled on it.** | Nothing to check; §11 lists it as an open decision. |

Two consequences of the split are worth stating where they apply: a **FROZEN**
item is a boundary and not a backlog, and a **PROPOSED** item is not a decision —
anything in this document that looks like a design and is marked PROPOSED is
still open.

## 1. The question, and who it is for

### 1.1 The user, and the moment

The user this project has always written for is **a developer who did not write
the code and needs to understand it** — someone joining a repository, or the
author of it six months later. `README.md` states the motivation in those terms
("Git already tells you what changed, when, and who changed it. What it cannot
tell you is why the code looks the way it does today"), and the audit named the
shape of the tool: not a productivity tool and not a quality tool, but a
**comprehension** tool (`docs/v0.5-product-audit.md` §2, **INFERRED** as a
product category, **CONFIRMED** as the project's stated intent).

The experiment narrowed the same user further, and the narrowing matters here:
it measured **one code site and one question about it**, answered by a person who
does not know the repository, against git alone
(`docs/v0.5-understanding-experiment.md` §1, **CONFIRMED**).

**And the honest limit, restated because every question below depends on it.**
Three things are kept apart here, because only the first is a measurement:

- **Observed, and re-checked 2026-10-24** (`gh repo view`, `gh issue list`): the
  repository is public, with **2 stars, 0 forks, and 0 issues of any state, open
  or closed**. Those are counts of what the hosting platform displays, and they
  are all the tree can see.
- **Not found in the sources reviewed for this document** — the repository's own
  records and the audit: no external user feedback, no issue, no review and no
  independent validation from anyone who did not write the tool.
  `docs/v0.5-product-audit.md` §1 finding 1 records the same absence, and
  `PROGRESS.md`'s head restates it ("the value claim unverified (no user, no
  experiment, 0 forks and 0 issues on a public repository)").
- **Not derivable from either**, and the audit says so itself: whether anyone has
  used the tool and said nothing; whether the two stars and zero issues mean
  nobody has tried it or that people tried it and had nothing to say
  (`docs/v0.5-product-audit.md` §12 item 9); and anything about the tool's value
  or the demand for it. **Stars, forks and issue counts are not evidence of
  either, and are not treated as any below.**

Every statement below about what a user needs is therefore the project's
argument, not a measurement.

### 1.2 What the moment looks like, and what git alone answers

A person looking at a change they did not make has four different questions
available to them, and git answers the first one well:

- **What changed.** `git show`, `git diff`, `git log -p` — line by line, exactly,
  and better than any model will (`docs/v0.4-problem-definition.md` §2 says so in
  as many words, **CONFIRMED**).
- **When, who, which files, how many lines.** `git log`, `git blame`,
  `git log -S`, `git log --grep`, `--follow`. The experiment's control arm is
  precisely this list plus the repository's own documentation, with the internet
  off (`docs/v0.5-understanding-experiment.md` §6.3, **CONFIRMED**).
- **Whether this change is part of something larger.** Git answers this only if
  the commits happen to be adjacent in the log — which is what a rebase, a
  squash-merge or a long branch destroys.
- **Why.** Git stores no intent. The reason is in the code's shape, in the
  history of the files involved, and — when someone wrote it down — in a memory.

### 1.3 What v0.5.3 already answers

The tree has eighteen commands: ten reading the evidence
(`analyze`, `ast`, `timeline`, `hotspots`, `files`, `file`, `commit`,
`structure`, `cochange`, `explain`) and eight for Developer Memory (`create`,
`list`, `show`, `supersede`, `invalidate`, `adopt`, `export`, `import`)
(**CONFIRMED**, `src/codearchaeology/cli.py`). For **one commit**, the tool
already assembles a deterministic evidence bundle: the commit and its parents,
the files it touched with change types and line counts, each file's life across
renames, every Python definition that changed, an earlier-commit window, co-change
statistics, and four named kinds of absence
(`src/codearchaeology/context.py` `build_object`, **CONFIRMED**). `explain` puts
that bundle in front of a model under a validator that refuses any citation the
bundle does not hold; with no model configured it prints the bundle itself and
exits 0 (`cli.py:760-772`, **CONFIRMED**).

That is a real capability, and it is aimed at the third question in §1.2 — the
"why" — with the project's own discipline about what may be said.

### 1.4 The gap this phase would consider

Three gaps are visible in the tree, and they are different sizes:

| Gap | Evidence | Marker |
|---|---|---|
| **The unit is one commit.** "Whether this commit is part of a larger series" is named as *not available* — "A refactor split over ten commits looks like ten commits" | `docs/v0.4-problem-definition.md` §4.6 | **CONFIRMED** |
| **The diff is not in the tool at all.** The contract lists it as available evidence, and §10 of the same document leaves its inclusion open; the implementation reads only the new-side **line ranges** of hunks and no patch text. Both READMEs say so under *Known limitations* | `docs/v0.4-evidence-contract.md` §5, §10; `context.py` `_ranges_by_path` | **CONFIRMED** |
| **Nothing an explanation says is stored**, so no reading can be revisited, compared or checked after the fact — including by the person who wrote the tool | `docs/v0.4-problem-definition.md` §12; audit §7.1 | **CONFIRMED** |

**Why the first two are worth considering at all** — and this is an argument, not
a measurement: the unit a person actually holds in their hands when they ask
"why" is rarely a commit. It is a change: a branch, a pull request, a range of
commits that arrived together for one reason. And the thing they look at first is
the patch. Neither of those is in the tool. **INFERRED.**

**Why the third is different in kind:** §7 shows it is not a feature but a rule
the project has never argued, only restated.

### 1.5 What is established, and what is assumed

| Claim | Standing |

| **The tool helps anyone understand anything** | **UNKNOWN.** No human-subject result exists in the tree or in the sources reviewed, and the experiment has not run. This is the claim the experiment exists to test |

### 1.6 This document does not presume that v0.6 ships

Stated first so no later section can be read as a commitment. The experiment's

## 2. The problem, split into four different questions

The candidate goal as it has been written down is "AI-assisted change analysis
and replay" — one row of the README roadmap, defined nowhere else in the tree
(**CONFIRMED**, audit §2). It is four questions wearing one name, and they have
different evidence, different costs and different standing.

### 2.1 Presenting what actually changed

*"This commit renamed `load` to `load_config`, rewrote its body, and dropped two
call sites."*

- **Who answers it today:** git, better than this tool
  (`docs/v0.4-problem-definition.md` §2, **CONFIRMED**). The tool shows the paths,
  the change types, the line counts and the line ranges — never the patch text.
- **Evidence it would need:** the diff (§4.3).
- **Standing:** this is an **input**, not a goal. On its own it is explicitly not
  an explanation: "A restatement of the message or the diff. If the answer could
  have been written by reading `git show`, the tool added nothing"
  (`docs/v0.4-problem-definition.md` §6, **FROZEN**).

### 2.2 Relating the historical evidence

*"This is the fourteenth change to a file that has been renamed twice; those two
files have moved together in 45 of this file's 228 analyzed commits; this
function has been rewritten eleven times."*

- **Who answers it today:** v0.1–v0.3 — lifecycles, hotspots, `definition_history`,
  co-change — and for one commit, the v0.4 bundle. This is the layer
  `docs/v0.4-problem-definition.md` §2 calls "the only thing the AI layer has to
  offer that a diff does not" (**CONFIRMED**, and it is shipped).
- **Standing:** **implemented**. What is missing is not this capability but the
  unit it is asked about (§3).

### 2.3 Explaining what the change was for

*"The evidence is consistent with a fix for a case the previous version did not
guard."*

- **Standing:** **FROZEN as a candidate reading, never a finding.** Intent, motive
  and the author's reason are in the evidence contract's *Never* table
  (`docs/v0.4-evidence-contract.md` §3); a candidate reason must rest on named
  facts and is refused if it rests on nothing (`validation.py`). The unit of
  knowledge is a statement a person makes (Developer Memory), and it may inform a
  reading and never become one.
- **What is genuinely open:** whether the unit (§3) and the diff (§4.3) change
  *how much* of this question is answerable — not whether the ground rules move.

### 2.4 What the change may do next

*"This will break the plugin API", "this is risky", "this should be reverted".*

- **Standing: FROZEN — not a candidate at all.** Three separate prohibitions
  forbid it: the problem definition rules out a prediction and a verdict (§6);
  the evidence contract forbids "predicting, scoring or judging" (§9); impact,
  the issue, the review, the discussion and anything outside the repository are
  in the *Never* table (§3). The audit found no argument anywhere in the tree for
  relaxing any of them, and this document does not make one.
- **Consequence for "replay":** one of the plausible readings of the roadmap's
  word is *simulating what a change would do*. That reading is **ruled out by the
  frozen contract**, not deferred. §3.4 and §12 keep the remaining readings open.

### 2.5 The rule that keeps the four apart

> **Explaining a change must never be expanded into predicting its impact.**

This is the same separation the project already enforces between evidence and
interpretation, applied one step further out: a reading of the past may be
offered as a candidate; a statement about the future is not offered in any
phrasing (**FROZEN**, `docs/v0.4-evidence-contract.md` §9). Any v0.6 that ships
must be describable without the fourth question.

## 3. The unit of a change

This is the phase's central open decision, and the one the user must take
(§11 row 1). Four candidates, each with what it is, what it answers and what it
costs. **None of them is adopted here.**

### 3.1 The candidates

**A — one commit.** What the tool does today, unchanged. `explain <sha>` builds
the bundle for a single commit; the whole validator, selection discipline and
offline path are built around it. Answers §2.1–§2.3 for one commit. Answers
nothing about a series. **Cost: zero.** Already shipped and tested.

**B — a span of commits.** A set of commits named explicitly — in git's own
terms, a revision range. Answers: "these ten commits arrived together; what is
the shape of that change, what did it touch, what does the history say about
those files, and what candidate reasons does the evidence support for the whole
of it?" It is the unit a reviewer actually holds (a branch, a squash, a series
pushed for review), and the missing capability §1.4 names.
**Cost:** the bundle is currently built for one commit and is **linear in the
commit with no ceiling at all** — measured at 1.49 MB / 373,000 estimated tokens
for a thousand-file commit (`docs/v0.4-context-budget.md` §1, **CONFIRMED**). A
range multiplies that, so the selection discipline (`selection.py`, whose caps are
constants, lines 82–87) must be extended to a shape it was not designed for, and
every semantic question below has to be answered for a set rather than a commit.

**C — a branch or a pull request.** In practice this is B plus a *selector*: a
base ref, a merge-base, a tip. It is presented as its own candidate because it is
where the ambiguity lives, and because one of its readings is not local at all:
a "pull request" is a hosting-platform object, reachable only over the network,
and this project's Local First rule and the experiment's control arm both assume
the repository itself is the world
(`docs/v0.4-problem-definition.md` §9; experiment §6.3, **FROZEN**). A local
equivalent exists — "commits reachable from `tip` and not from `base`" — and it
is exactly B with a computed rather than typed-in set.

**D — another unit with a basis in the tree.** Two were checked and are **not**
candidates, with the reason recorded so the check is not repeated:

- **A file's whole life.** Evidence exists (`lifecycle.py`, and the `file`
  command already shows it), but it is a *history of a path*, not a change: it
  answers §2.2 directly and would be a second way to say what `file` says.
- **A definition's whole life.** Evidence exists (`definition_history.py`, and
  `structure` shows it, following file renames). Same argument.

A third reading of D is worth naming because it is the honest general form:
**a selector over commits** — a range, a date window, a path filter. If the user
chooses B, the selector is the interface question §12 leaves to the design freeze.

### 3.2 What each candidate changes, and what it risks

| | A — one commit | B — a span (range) | C — branch / PR | D — a life |
|---|---|---|---|---|
| Answers §2.1–§2.3 for | one commit | a set of commits | a set, chosen by a ref | one path or definition across all history |
| Evidence it needs | nothing new | the same evidence, N times, plus what is new about a set (§3.3) | B, plus ref resolution and merge-base | nothing new |
| Input the user gives | a sha | two revs (or a selector) | a ref name | a path or a definition |
| Architecture impact | none — shipped | bundle shape, selection caps, validator's known set, prompt rules | as B, plus a resolution step and its failure modes | none, but a new view rather than a new unit |
| Implementation / test complexity | none | **high** — every boundary becomes a set question | higher, and partly unresolvable locally | low |
| New ambiguity it creates | none | "the same file touched twice", "created and deleted inside the range", which commit's lifecycle window, ordering | which base, which merge-base, a rebase that rewrote the set after review, a PR with no local object | none |
| What it still cannot answer | §2.4, and never intent | §2.4, and never intent | §2.4 | §2.1 for a single change |

### 3.3 What a span makes hard, stated before it is chosen

Not a reason to refuse B; a list of the things the design freeze must answer if B
is chosen, because each one is a place where a plausible implementation is wrong:

1. **The bundle's shape.** Today's bundle is *about* one commit: one author, one
   message, one set of parents, one "is_merge". A span has many of each, and the
   contract (`docs/v0.4-evidence-contract.md` §3) fixes the bundle item by item,
   so a span bundle is a **formal amendment** to a frozen document, not an
   addition to it.
2. **The same path touched more than once**, including created and deleted inside
   the range, and renamed twice. Lifecycle events have to be merged across the
   set without inventing an order the repository does not have.
3. **Merges inside the range.** A merge has no diff (contract §6) and its parents
   are stored, so the diff is recomputable — but "the diff of a merge" is not
   well-defined until a parent is chosen (first parent? each? combined?). Today's
   answer is the absence `merge_no_diff`, which does not generalize silently.
4. **Selection.** The current rule keeps the largest rows and says so
   (`docs/v0.4-context-budget.md` §3). Over a span, "largest" is a different
   question, and the omissions multiply. Whatever rule is chosen must keep the
   existing property: **a list that lost rows is never silent.**
5. **The offline path.** "What the offline path prints is exactly what the model
   is shown" (`docs/v0.4-ai-architecture-freeze.md` §3, **FROZEN**) — so the span
   bundle must be printable whole, or `--json` must carry it whole, or the two
   paths drift.
6. **Cost.** Bundle size is unbounded by design; a span is N bundles' worth of
   material. The refusal-not-truncation rule stays, so the practical ceiling is
   the model's window, which makes the selection the load-bearing part.

### 3.4 Recommendation, and it is a recommendation only

**PROPOSED, for the user to rule on: keep A as the floor and add B as a second
unit, defined as an explicit revision range; treat C as a selector over B rather
than a unit of its own; reject D.**

Three arguments, and one honest counter-argument:

1. **The gap is already written down.** The problem definition names "part of a
   larger series" as unavailable (§4.6). B closes exactly that, and nothing else.
2. **C is B with a computation.** A branch is a ref; a PR is a remote object the
   tool cannot see without violating Local First. Defining C as a selector keeps
   the evidence shape single, which keeps the validator, the selection and the
   offline path single.
3. **D adds views, not units.** The two candidates checked already have commands,
   and the `file`/`structure` outputs are the right place for them.

**The counter-argument, which is serious:** nothing in this tree shows that a
span is *more valuable* than a commit. The argument for B is that it matches the
unit a reviewer holds and that the project itself names the gap — and that is
all. Complexity is a cost, not evidence of value, and the pattern this project
has correctly refused four times is building the bigger thing because it is
bigger. If the user rules for A alone, that is coherent: the tool then has one
unit, one bundle shape, no amendment to the contract, and the diff question (§4)
becomes the whole of the phase's deterministic work.

## 4. The evidence available, and the diff's boundary

### 4.1 What the bundle holds today

Everything below is the frozen contract's list (`docs/v0.4-evidence-contract.md`
§3), with the tree's own status beside it. **Implemented** means stored or derived
today and carried by the bundle.

| Evidence | Source | Status |
|---|---|---|
| The sha, author, authored/committed timestamps, the full message | `commits` | **Implemented** |
| The parents; that this commit is a merge | `commit_parents`; two or more parents | **Implemented** |
| The paths touched, the change type as git reported it, added/deleted lines | `commit_files` | **Implemented** |
| `old_path` and `similarity` for a rename or copy | `commit_files` | **Implemented** |
| That a file is binary — the counts are null, not zero | `commit_files` | **Implemented** |
| The names a file carried, in order; when it appeared; whether it is still there; the commits that touched it; what it cost in lines | `lifecycle.py`, `statistics.py`, `relationships.py` | **Implemented**, derived per query, never stored |
| Every definition at this version — kind, qualified name, lines, decorators, fingerprint — and its `created`/`modified`/`unchanged` against the nearest earlier readable version | `definition_versions` | **Implemented**, written by `ast` |
| That a definition is gone — a missing row | — | **Implemented** as an absence, nothing written to spell it out |
| An earlier-commit window per touched path | derived | **Implemented**, capped at 5 in the bundle, 2 in the model's view |
| How often these files change against the rest | hotspots, derived | **Implemented** as counts |
| Which files change alongside them, with counts and the denominator | cochange, derived | **Implemented**, capped at 5 files × 5 partners |
| Two paths' line spans where the change landed (new side only) | read from git per run | **Implemented** — and this is the *only* thing read from git for the bundle besides commits |
| **The diff** | putatively the repository | **Not implemented** — see §4.3 |
| Developer Memory | `memories`, `memory_citations` | **Implemented, and deliberately not in the bundle** — a sibling section of the prompt and of the output (§4.2) |

### 4.2 Memory's place, restated because v0.6 must not move it

Memory is not evidence, in five separately tested ways: evidence never depends on
memory; memory never enters the evidence tables; memory is never evidence for a
memory; the model never writes memory and the tool never writes memory on its own;
memory never overrides evidence (`docs/v0.5-final-state.md`, "Memory is not
evidence — the five rules, each with its test", **CONFIRMED**). A v0.6 that adds a
unit or a diff must leave all five intact; nothing proposed in this document
requires touching them.

### 4.3 The diff: the one row of the contract the tree does not have

The contract lists the diff as evidence available to the model, **bounded** with
the bound stated rather than applied silently (§5), and §10 leaves "whether the
diff is in the bundle at all" to a design freeze. It was never built: the tool
reads patch text only to extract hunk line spans, and stores nothing.

**The items a decision has to cover, each with the tree's current answer:**

| Item | Today | What a change would have to decide |
|---|---|---|
| Whether the diff enters the bundle | It does not | §11 row 2 |
| How it is read | `git show --format= --unified=0 …` for ranges; a `git cat-file --batch` reader exists for blob content (`objects.py`) | Which mechanism; the contract's own §5 assumes the object reader. Two blobs are needed for a modification, one side for an add or a delete, two paths for a rename |
| How large it may get | Unbounded if added | A per-file cap, a whole-diff cap, or a summary for large files (the contract's own suggestion), and *where* the bound is stated |
| How omissions are expressed | Not applicable yet | The existing precedent: a count of what was dropped, and a per-row total — `selection`'s `{shown, omitted}` and `ranges_total` (`docs/v0.4-context-budget.md` §4) |
| Binary files | Counts are null; no text exists | "Binary — no text" as a fact, never as an empty diff |
| Pure rename | Zero lines moved; git prints no hunks | Must not read as "nothing happened" — the bundle already gives such a path an entry with no ranges for exactly this reason (`context.py` `_ranges_by_path`) |
| Empty diff | Two meanings, already distinguished: `merge_no_diff` versus a commit that changed nothing | Must stay two sentences |
| Root commit | `git show` prints the whole file as an addition | The bound matters most here, and the whole-file reading must be stated |
| Merge commit | No diff printed; parents stored, so recomputable | Whether it is recomputed, and against which parent — today the answer is the absence `merge_no_diff` |
| Partial diff presented as whole | Forbidden by the contract §9 | The rule is frozen; the mechanism that carries it is the design's |

**Two consequences worth stating plainly, because they are easy to get wrong:**

- **An unbounded diff cannot be added.** The bundle's whole design is the same
  bytes every time, and its size is already unbounded in the commit with no
  ceiling at all. Adding patch text without a bound would make the bundle's size
  depend on a lockfile.
- **The diff cannot exist for the model alone.** "What the offline path prints is
  exactly what the model is shown" is frozen (**FROZEN**,
  `docs/v0.4-ai-architecture-freeze.md` §3). A diff shown to a model but not
  printed by the offline path would be the one case that rule exists to prevent:
  the checkable artifact would be the one that was quietly cut.

### 4.4 What changing the contract would cost

Adding the diff — or a span bundle — is an amendment to
`docs/v0.4-evidence-contract.md`, a frozen document. The project's own precedent
for such an amendment is `docs/v0.4-cochange-design.md` §18, which records what
the building changed about the freeze. **No schema change is implied**: the diff
would be read from the repository per run, as the line ranges already are
(**INFERRED**, and it is the cheapest shape; storing diffs would be a schema
question and a much larger one). This document does not make the amendment and
does not decide it (§11 row 2).

## 6. When the evidence is thin

The project already refuses to round evidence off, in four places the contract
names and one the AST layer adds. v0.6 must inherit the distinctions rather than
re-derive them.

### 6.1 The five situations

| Situation | What it is | What happens today | Recommended behaviour |
|---|---|---|---|
| **No related evidence** | Nothing in the repository bears on the question — a three-line change to a file that has never been touched | The bundle carries the facts and no statistics; the answer's second part is short or absent, and that is "a correct answer, not a failure of one" (`docs/v0.4-problem-definition.md` §5, §7) | Unchanged. State thinness as thinness |
| **Evidence exists but is insufficient to answer** | There is material, and it does not settle the question | A candidate reason may be offered only if it names the facts it rests on; uncertainty is a first-class output kind (`uncertainty` in the schema), and the experiment scores "the history does not say" as **correct** where it is true | Unchanged. This is not a defect to engineer away |
| **Evidence cannot be read** | A file version that did not parse; a path with no stored version; a merge | Four distinct absence kinds are carried: `merge_no_diff`, `parse_failed`, `no_version_stored`, `not_in_this_commit` (`context.py`), and "nothing could be read" is never reported as "nothing was there" | Unchanged; if a diff is added, an unreadable or binary source becomes a **fifth stated absence**, not an empty diff |
| **Evidence outside the allowed scope** | Intent, the issue tracker, the review, anything after the commit | Never offered, in any phrasing (*Never* table) | Unchanged. A v0.6 that wants to reach outside the repository is asking to change the contract |
| **Evidence conflicts with other evidence** | Two stored facts that cannot both be true; a memory that no longer resolves; two memories that contradict each other | Resolutions are re-checked on read and reported (`resolved` / `unresolved` / `not_checked`); a memory's subject may no longer exist; **two active memories can contradict each other and the tool cannot detect it** — the design says so (`docs/v0.5-design.md` §10.2) | **Report, never resolve.** A conflict between two *stored facts* is a tool defect to fix, not something to explain around; a conflict between two *statements* is reported as the state it is |

### 6.2 The two rules that must not weaken

- **Nothing is filled in to make an output look complete.** The precedents are
  already in the tree: a deletion is evidenced by a missing row and nothing is
  written to spell it out; a failed parse is never a file that held nothing; a
  model's answer is never repaired, and a partial answer is never printed
  (`docs/v0.4-ai-architecture-freeze.md` §7, **FROZEN**).
- **A bound is stated, never silent.** Wherever a v0.6 caps anything, the count of
  what was dropped travels with it.

## 7. Whether an explanation is ever stored

This is the question the audit named "the one that is genuinely blocking"
(`docs/v0.5-product-audit.md` §8 concept debt 3, **INFERRED** there,
**CONFIRMED** here as the state). Today nothing is stored: there is no
explanation table and no code path that writes model text anywhere.

The five options below are the audit's own (§7.3, **CONFIRMED** as its
definitions), plus one the brief adds, marked as such so the two are not merged.
The audit's table and the brief's five are not the same list; the mapping is
stated rather than smoothed over.

| Option | Saves | Does not save | Architecture / database | Reproducibility and auditability | Cost | Relation to the current rule |
|---|---|---|---|---|---|---|
| **A — Never store** (today; the brief's "only for the current run") | nothing | everything | none | The evidence is reproducible, the answer is not — and that is the stated design (`docs/v0.4-problem-definition.md` §12) | zero | It **is** the current rule |
| **B — Store the raw output** | the model's text | nothing about how it was produced | a new table; a schema decision | Full auditability of what was said; zero reproducibility of it — "one input can produce two answers" | A durable class of text nobody can regenerate, and a stored answer is indistinguishable from a record | **Breaks** it at its weakest point |
| **C — Person confirms → Memory** (the audit's C) | the *person's* statement | the model's text, even then | already shipped in spirit | The memory machinery's own: citations checked, lifecycle, provenance | none new | **Not a persistence path for interpretations** — the audit says so explicitly, because it is easy to mistake for D |
| **C′ — An external file, explicitly managed by the user** *(added by the brief; not in the audit's five)* | the answer, as text, at a path the person chooses | nothing about provenance unless the file carries it | none in the database; a file the tool writes | Reviewable — the only option that can be read in a PR, or diffed between two runs, without a database | A format to freeze, a lifecycle for the file, and a question the project has already answered once for memory (`export` writes a file; it never writes into the tree) | Sits *outside* the rule rather than satisfying it: the text is still stored, just not in SQLite. It inherits B's honesty problem and adds a location question |
| **D — A separate Interpretation Artifact table** | the answer, labelled, never evidence, with its own lifecycle | — | a new table, its own version stamp, and an answer to "how long does an artifact live" | Two readings of one commit can be compared; a stored reading becomes a durable class the project has never had | The largest: a schema bump, a lifecycle, and it re-creates the "a wrong reading becomes durable" risk | Requires an explicit exception to it |
| **E — Store the run's provenance, not its text** | the bundle hash, provider, model id, prompt version, timestamp | every sentence | a new table or a new set of rows, small | Answers "was this explanation produced from the bundle I have now?" — which is the only *replay* capability that needs no stored prose, because the bundle is deterministic and byte-identical | Low; and it is a **fact**, so storing it is what this project does | Consistent with it — this is the option the audit called "the one that fits the project's existing principles rather than trading against them" |

**Two things to notice before choosing:**

1. **Option E is the only one that makes "replay" mean something checkable.**
   Re-running can produce a different answer; comparing the *bundle hash* under a
   stored answer's provenance is a comparison of facts. If the roadmap's word is
   to survive, E is what it most plausibly means.
2. **C′ is the only option that makes an answer reviewable by a second person**
   without a database — and it is the option the project has never argued. It
   should be treated as new, not as one of the audit's five.

**PROPOSED, for the user to rule on:** keep A (store nothing) for the answer's
text, and if anything is stored at all, store **E** — the run's provenance, never
the prose. If the user prefers any of B, C′ or D, the storage shape must be
decided **in the same document that chooses it**, and the reasoning must survive
the audit's objection to each: B and C′ store text that cannot be regenerated,
and D creates a durable class.

**What this document does not do, and may not:** add a table, a column, a
migration, or any persistence code (see §12 and the boundary at the head of this
file). The decision is cheapest now, before any such rows exist — that is the
audit's sequencing argument, and it is the reason this row is in §11 rather than
deferred to the implementation.

## 8. The understanding experiment's place

The experiment is the only instrument in the tree that can test the product
claim, and its rule was written before any data exists. Nothing below changes it.

### 8.1 What it tests

> Given a piece of code whose shape is not self-explanatory, a person who does not
> know this repository reaches a correct, evidence-backed reason for it faster, or
> more often, with CodeArchaeology than with git alone.
> — `docs/v0.5-understanding-experiment.md` §1, **FROZEN**

It tests the **deterministic** layer against git: control is git, the source and
the repository's own documentation with the internet off; treatment adds the nine
deterministic commands. **`explain` is excluded from the treatment by an explicit
design decision** — if it were included, a positive result could not be attributed
to this tool, "the same result would be obtained by pointing a model at a
`git show`" (§6.3, **FROZEN**). `explain`'s offline path may be used, because it
is deterministic and is not an AI feature.

### 8.2 The design and the scoring, in the terms the rule needs

- **Six to eight participants**, split by familiarity (at least three who have
  never read the target repository, at least two experienced Python developers);
  nobody who has read the tool's source or the experiment document. n≈6 is a
  pilot: per-participant results, **no p-values**.
- **Six questions, two at each calibration level** (L1 instrument controls, L2,
  L3 discriminating pair), each with its ground truth and its measured
  calibration record; ten minutes per question, capped.
- **Scored from the written answer alone**, by a scorer who did not run the
  session: 2 correct-and-evidenced, 1 correct-unevidenced, 0 wrong, **U correctly
  uncertain — scored 2 where uncertainty is the truth, 0 where it is not.**
- **The primary endpoint is score 2 per question.** Reported separately: time,
  **calibration** (stated confidence minus correctness — the metric that catches a
  tool that makes people confidently wrong), the per-level breakdown, the commands
  used, and a labelled-weak self-report.
- **Two repositories are prepared** (attrs and tqdm); a one-repository variant is
  allowed only with its stated learning-effect limitation (§6.2). Materials are
  printable (`docs/pilot-kit/`), pinned to specific commits, and the second
  repository's materials passed an independent review with disclosed limitations.

### 8.3 The pre-registered outcomes, unchanged

| Outcome | Condition | What it means for what gets built next |
|---|---|---|
| **Supported** | `ΔCE ≥ 0.20` and `ΔCal ≤ +0.10` | The value claim holds well enough to continue. **v0.6 gets its justification** |
| **Convenience only** | `ΔCE < 0.20` and `ΔT ≤ −30%` | The tool is a speed-up, not a comprehension aid. Narrow the README's claim to what was measured, and **reconsider v0.6**, because "AI-assisted change analysis" is sold as depth, not speed |
| **Harmful** | `ΔCal ≥ +0.15` without a correctness gain, or the tool arm is worse on the L1 questions | **Stop feature work** |
| **Null** | none of the above | The value claim is unsupported. **The next thing to build is not v0.6.** Re-answer the portability decision with this in hand |

**And the rule that overrides all four:** a null, harmful or merely convenient
result is a finding and not a failure; the correct response is to write it down
and change the plan, not to re-run with easier questions (**FROZEN**).

### 8.4 The AI question is a second experiment

Whether a model's answer adds anything *on top of* the evidence is a separate
experiment, with the same protocol and the treatment defined as `explain` versus
the evidence alone. It is not this one, and running them together would leave both
uninterpretable (§6.3, **FROZEN**). **Consequence for v0.6:** the phase's name
contains "AI-assisted", and the experiment as designed does not test the AI layer
at all. Nothing in the tree measures whether `explain` helps. That is
**UNKNOWN**, and it is a reason to sequence any AI work behind the deterministic
work rather than beside it — **INFERRED**.

### 8.5 Status, stated because nothing may be claimed about it

**The experiment has not been run.** It is prepared: the six questions for the
first repository and the six for the second exist with ground truth and
calibration records, the printable kit exists, the decision rule is declared. The
**Memory sub-experiment is deferred by the user's decision of 2026-10-09** and its
session block is annotated as not run. No participant has been recruited, no
session has been scored, no second scorer has been found. `PROGRESS.md` records
the same state, and no document in the tree claims a result (**CONFIRMED** by
reading all three).

The five things only the user can do are listed in the experiment's §12: recruit
six to eight people; choose the second repository or accept the one-repository
variant; decide who scores; fix the date; and decide the AI question separately.
**Recruitment is the whole blocker**, and it is not something this project — or an
agent — can do for itself.
