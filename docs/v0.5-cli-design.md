# v0.5 CLI design freeze — how a person operates a memory

## Status

**Design freeze. Nothing here is implemented.** This is Unit 3 of v0.5. Unit 1
(`docs/v0.5-design.md`) said what a memory is; Unit 2
(`docs/v0.5-storage-design.md`) said how it is kept; this says what a person
types, what they see, and what a program reads.

Written on 2026-10-06 against `f27ebbf` (version 0.4.0, ten commands, 660 tests).
The interface below is frozen; no command, option, block or JSON key is written
into any file by this unit.

## The interface conventions it was written against

Read from the real command line, because a new command that invents its own
conventions is a second interface in one tool:

| Read | Found | What it decides here |
|---|---|---|
| `cli.py` | every command takes the repository as a positional directory (default `.`) and `--db`; errors are `Error: <sentence>` on stderr with `typer.Exit(code=1)`; notes go to stderr so `--json` keeps stdout parseable | §2, §7: the memory commands take the same two, and obey the same split |
| `cli.py` | the two writers print a labelled summary; the reading commands take `--json`; listing commands take `--limit/-n` and `--all` | §3, §6, §7: writes print a summary, reads take `--json`, `list` follows the `--limit`/`--all` convention |
| `commit.py` | a sha prefix is accepted, and the three refusals are `'x' is not a commit sha; use one from 'archaeology timeline'`, `no stored commit starts with 'x'`, `'x' matches N commits: …; give more characters` | §5, §6: memory ids are addressed the same way, with the same three refusals |
| `explain`'s offline path, and its README block | with no model it prints **the evidence bundle's JSON**, not a prose block | §10: memory cannot be appended as prose there; it becomes one more key of the printed object |
| `tests/test_readme.py` | `_registered_commands()` walks `app.registered_commands` only, and five scenarios replay every console block | §12: a group is invisible to that test as it stands, so it must learn to walk groups — otherwise six commands would ship undocumented, which is the exact drift the test exists to catch |
| `hotspots.py`, `timeline.py`, `cochange.py` | read JSON carries `repository` and `head_sha` at the top level | §8: memory's read JSON carries the same two, in the same names |

## 1. The group, and the acts

One new command group, six acts. The names are Unit 1's five acts plus Unit 2's
`adopt`; nothing else is invented.

```console
$ archaeology memory --help
```

```text
Usage: archaeology memory [OPTIONS] COMMAND [ARGS]...

  Statements people made about this project, kept by the tool and never treated
  as evidence.

Options:
  --help  Show this message and exit.

Commands:
  create      Record something a person knows about this project.
  list        Show the memories kept for this project.
  show        Show one memory in full.
  supersede   Replace a memory with a new statement.
  invalidate  End a memory, with the reason.
  adopt       Take over the memories made about this project at another path.
```

**Why a group rather than six flat commands.** The tool's flat names are all one
word for one question (`file`, `commit`, `cochange`); six more verbs at the top
level (`remember`, `memories`, …) would either collide with that style or need
invented names for acts that already have names. A group makes the acts
discoverable in one place, and it is where a reader looks for them.

**The act names are the frozen ones.** `create`, `list`, `show`, `supersede`,
`invalidate` are Unit 1 §15.2's words, and `adopt` is Unit 2 §8.3's. The command
line is the fifth place they appear and the first place a person meets them, so
they are not paraphrased here.

## 2. What every memory command shares

| Shared | Form | Notes |
|---|---|---|
| The repository | a positional directory, default `.`, resolved | the same `REPOSITORY_ARGUMENT` object every existing command uses |
| The database | `--db PATH` | the same option object; defaults to the cache lookup |

Two consequences that are inherited rather than decided:

- **A memory command needs a stored analysis.** It opens the database the same
  way every reading command does, so an unanalyzed repository answers with the
  existing sentence (`no analysis of …; run 'archaeology analyze …' first`), and
  a database holding a different repository is refused by the same check. This is
  required, not incidental: a subject and a citation are resolved against the
  stored history, so there has to be one.
- **A stale analysis is a note, not an error.** The `Note: this analysis stops at
  …` line goes to stderr as it does everywhere else, and the command proceeds.

## 3. The statement

```text
memory create <STATEMENT> [PATH] [options]
```

**Positional, and required.** A memory is the statement; the flags are about it.
The shell quotes it, the way it quotes a commit message, and the two examples
below are the whole of what a user has to learn:

```console
$ archaeology memory create "We keep authentication in one module." --about-path auth.py
$ archaeology memory create "The retry wrapper exists because the API returned 503s." \
      --about-path api/client.py --about-definition request --cite-commit 8eaff71d
```

**`-` reads the statement from stdin**, whole, with the trailing newline stripped.
That is for the two cases the command line is bad at: a paragraph long enough to
be worth its own line breaks, and a Windows shell whose quoting rules make a
long sentence painful. It is the only stdin in the tool, and the README examples
deliberately do not use it, so the block checker stays as it is.

**The statement is checked, not trimmed.** Leading and trailing whitespace is
stripped; what is left must be between 1 and **4,000 characters** (Unit 2 §3.5).
An empty statement, and a statement over the cap, are refusals — the second names
the cap and the length it got.

## 4. The subject

Exactly one subject, given by flags. Four forms, and the flag names are the
subject kinds' own words:

| Form | Flags | `subject_kind` |
|---|---|---|
| The project | `--about-repository` | `repository` |
| A file | `--about-path PATH` | `path` |
| A definition | `--about-path PATH --about-definition QUALNAME` | `definition` |
| A commit | `--about-commit SHA` | `commit` |

Rules, each of which is an error when broken:

1. **Exactly one form.** No subject at all, and two forms at once, are both
   refusals — the message lists the four forms.
2. **A definition needs its path.** `--about-definition` without `--about-path`
   is refused: a qualified name alone does not name a definition (Unit 2 §3.3).
3. **The path is normalised** with the same function `file` and `structure` use,
   so `./auth.py` and `auth.py` are one subject.
4. **The subject must resolve against the stored history**, because a memory
   nothing can be found by is a memory nobody will read:
   - a path resolves if it appears in `commit_files` under any name it ever had
     — a deleted file resolves, which is the point of a memory about it;
   - a commit resolves like every sha in the tool (a unique prefix is enough);
   - a definition resolves if the stored definitions hold that qualified name
     **under that path** — which needs the AST pass, and the refusal says so
     (`run 'archaeology ast' first`), the way the structure commands already do;
   - the repository always resolves.
5. **The refusal for a path that resolves to nothing reuses the tool's existing
   sentence**, because it is the same situation `file` and `structure` already
   answer: `nothing in the stored history touched <path>; use 'archaeology files'
   to see what is there`.

**Why flags and not a `kind:value` string.** A Windows path can contain a colon
and a definition needs two strings; a prefixed form would need a parser and would
make `C:\src\auth.py` ambiguous. The flags are longer to type and impossible to
misread, and they mirror the storage's CHECK one for one.

**One word, two vocabularies, said out loud.** The subject kind is `path` and the
citation kind is `file` — Unit 2 §3.3 and v0.4's evidence vocabulary, each frozen
where it was defined. The flags follow their own vocabulary (`--about-path`,
`--cite-file`) rather than inventing a third word to smooth over the difference.

## 5. The evidence

Six repeatable flags, one per citation kind, with the forms v0.4 defined:

| Flag | Ref form | Example |
|---|---|---|
| `--cite-commit SHA` | a sha or a unique prefix | `--cite-commit 8eaff71d` |
| `--cite-file PATH` | a path | `--cite-file auth.py` |
| `--cite-definition QUALNAME` | a qualified name | `--cite-definition request` |
| `--cite-range PATH:START-END` | a changed span of a cited commit's diff | `--cite-range auth.py:12-20` |
| `--cite-cochange "PATH -> PARTNER"` | one direction of a pair | `--cite-cochange "auth.py -> core/app.py"` |
| `--cite-absence KIND` | one of the four absence kinds | `--cite-absence parse_failed` |

Rules:

1. **Every citation is resolved when the memory is admitted** (Unit 2 §4.3), and
   an unresolvable one is refused with a message naming it and what would make it
   resolvable. Nothing is stored that did not mean something when it was written.
2. **`--cite-range` requires a `--cite-commit` in the same act.** A range is a
   span of one commit's diff and has no meaning without it; the refusal says so
   (Unit 2 §4.2).
3. **A citation given twice is refused**, by the same rule the storage's
   `UNIQUE (memory_id, kind, ref)` enforces — the act refuses first, with a
   sentence, rather than letting the constraint raise.
4. **No citations is a valid memory.** It is stored with none, and every display
   says "no evidence attached" rather than showing an empty list.
5. **The stored order is deterministic**: by kind in the schema's order
   (`commit`, `file`, `definition`, `range`, `cochange`, `absence`), then by ref.
   The order flags appear on the command line is not preserved across different
   options, and rather than pretend otherwise the tool fixes a canonical order —
   the same rule `explanation._citations` already uses to print an answer's
   citations in a stable order.

**Why six flags and not one `--cite kind:ref`.** The ref forms already contain
the separators a prefixed form would need (a range is `path:start-end`, a
co-change is `path -> partner`), so the parser would have to know the kinds to
split on the first colon, and the flags would stop being discoverable in
`--help`. Six flags are longer and need no parser.

## 6. The six commands

### 6.1 `memory create`

```text
archaeology memory create <STATEMENT> [PATH] [--db PATH]
    [--about-repository | --about-path PATH [--about-definition QUALNAME] | --about-commit SHA]
    [--cite-commit SHA]... [--cite-file PATH]... [--cite-definition QUALNAME]...
    [--cite-range PATH:START-END]... [--cite-cochange "PATH -> PARTNER"]...
    [--cite-absence KIND]...
```

Writes one new memory with `state = active`. Prints:

```text
Memory      3f2a9c1e-8b47-4d6a-9f10-2c5e7a0b41d9
Subject     auth.py
Evidence    2 citations
Database    /home/you/.cache/codearchaeology/82d48b376e387fde.db
```

`Evidence` reads `none attached` when there are none. The id is the first line
because it is what the user needs next.

### 6.2 `memory list`

```text
archaeology memory list [PATH] [--db PATH] [--limit N|-n N] [--all]
    [--include-ended] [--json]
```

- **Default: what the project knows now** — `active` memories. `--include-ended`
  adds `superseded` and `invalidated` ones, which is the "what did it used to
  believe" question. One flag, one axis, and no second meaning of `--all`.
- **Newest admission first**, ties broken by `memory_id`, so the same store
  prints the same order on every machine.
- `--limit` defaults to 20, as it does on every listing command; the hidden count
  is printed as `<n> more memories. Use --all to see them.`
- **`--json` carries every memory of the current repository**, not the slice:
  `--limit` is a terminal convenience and a program that asked for the list asked
  for all of it — the rule `files --json` already follows.
- A database holding another repository's memories prints the count and the paths
  on **stderr**, never inside the block (Unit 2 §8.2), and the `--json` object
  carries them under `other_repositories`.

### 6.3 `memory show`

```text
archaeology memory show <MEMORY> [PATH] [--db PATH] [--json]
```

`<MEMORY>` is the id or any unique prefix, refused when it matches nothing or
more than one — the three refusals are `commit.py`'s, with "commit" replaced by
"memory". Works for a memory of any repository in the database, by id (Unit 2
§8.2), and the block names the repository it belongs to.

### 6.4 `memory supersede`

```text
archaeology memory supersede <MEMORY> <STATEMENT> [PATH] [--db PATH]
    [the subject and citation flags of `create`]
```

One act, two rows (Unit 2 §5.1): the successor is admitted, and the old memory is
closed with `state = superseded`, `ended_at`, and `superseded_by` naming it. The
flags are `create`'s, shared as objects rather than copied, so the two commands
cannot drift apart.

Refused when the old memory is not `active` — a terminal state stays terminal
(Unit 2 §5.1), and the message says a new memory can be created instead.

Prints the successor's id first, then what it replaced:

```text
Memory      8eaff71d-2c5e-7a0b-41d9-3f2a9c1e8b47
Supersedes  3f2a9c1e-8b47-4d6a-9f10-2c5e7a0b41d9
Subject     auth.py
Database    /home/you/.cache/codearchaeology/82d48b376e387fde.db
```

### 6.5 `memory invalidate`

```text
archaeology memory invalidate <MEMORY> --reason TEXT [PATH] [--db PATH]
```

`--reason` is required — Unit 2 §5.2 makes it a CHECK on the row, and "it was
wrong" and "it stopped applying" are different sentences a reader needs. Refused
when the memory is not `active`.

```text
Memory      3f2a9c1e-8b47-4d6a-9f10-2c5e7a0b41d9
State       invalidated
Reason      the module was split again in 4c1b2e
Database    /home/you/.cache/codearchaeology/82d48b376e387fde.db
```

### 6.6 `memory adopt`

```text
archaeology memory adopt --from PATH [PATH] [--db PATH]
```

Unit 2 §8.3's act. `--from` must be the full path the memories were made about —
typing it is the confirmation, and it is why a typo cannot match. Refused when it
matches nothing, and when the path is already this repository's.

```text
Adopted     3 memories
From        /old/path/to/sample-project
To          /home/you/projects/sample-project
Database    /home/you/.cache/codearchaeology/82d48b376e387fde.db
```

**No interactive prompt.** The tool has none anywhere, a prompt would break
scripting and the README block checker, and the exact-path requirement is the
safety. This refines Unit 2 §8.3's "says how many rows it would move before
moving them": the count is printed as part of the act's summary, and the
confirmation is the path.

## 7. stdout, stderr, exit codes

The rules are the tool's existing ones, applied without exception:

| Stream | Carries |
|---|---|
| **stdout** | the block, or the JSON. Nothing else, ever. |
| **stderr** | `Error: <sentence>` for a refusal; notes (stale analysis, foreign memories in the database, shallow clone) as sentences without the prefix. |

| Exit code | When |
|---|---|
| **0** | the act happened, or the read produced its output — including a list of zero memories, and including `explain` with no model configured |
| **1** | everything else: every refusal in §11 |

There is no third code. A refusal is not a crash and never prints a traceback: a
database that cannot be read, a stamp from a newer tool and an ambiguous prefix
are all sentences on stderr with status 1, the way `commit`'s three refusals
already are.

**`--json` writes only JSON to stdout**, so a note never lands inside the
document — which is why the foreign-repository count goes to stderr in the block
form and inside the object in the JSON form.

**No `--json` on the writing acts.** `analyze` and `ast` print a summary and have
no JSON form; a machine-readable *write* would be a change to the whole command
line's convention, not a memory decision, and the summary's first line carries
the id for anything that needs to grep it. Recorded as deferred, not forgotten.

## 8. The JSON

### 8.1 One memory object, one shape everywhere

The same object appears in `list`, in `show`, and in `explain`'s memory section —
one shape in three places, so a reader never has to work out which one it got.

```json
{
  "memory_id": "3f2a9c1e-8b47-4d6a-9f10-2c5e7a0b41d9",
  "repository": "/home/you/projects/sample-project",
  "statement": "We keep authentication in one module.",
  "author": {"name": "Zyvn Coder", "email": "zyvn@example.com"},
  "admitted_at": "2026-10-06T21:14:03+08:00",
  "state": "active",
  "subject": {"kind": "path", "path": "auth.py"},
  "since": {"commit": "1edec2712ab…", "date": "2024-03-06"},
  "ended_at": null,
  "end_reason": null,
  "superseded_by": null,
  "supersedes": null,
  "citations": [
    {"kind": "commit", "ref": "1edec2712ab…", "resolution": "resolved"},
    {"kind": "file", "ref": "auth.py", "resolution": "resolved"}
  ]
}
```

The rules behind the fields:

- **`author` is `null` when the tool could not determine one** — never an empty
  string and never a guess. Unit 2 §3.2 stores the two parts.
- **`subject` carries the columns its kind has**: `{"kind": "repository"}`,
  `{"kind": "path", "path": …}`, `{"kind": "definition", "path": …,
  "qualname": …}`, `{"kind": "commit", "commit": …}`.
- **`since` is `null` when the start is unknown** — the whole point of Unit 2
  §6. When it is known it carries `commit` and/or `date`, and the `date` is the
  commit's own recorded date so a reader can see where the comparison comes from.
- **`resolution` is one of three words**: `resolved`, `unresolved`,
  `not_checked` (the expensive kinds in a list view — Unit 2 §4.3). Three words
  because "not checked" and "checked and gone" are different, and the list must
  not imply the second by staying silent.
- **`supersedes` is derived** (Unit 2 §5.1) and is present in the same shape as
  `superseded_by`, so a chain reads the same in both directions.
- **The statement is always the whole statement.** No view truncates it — the
  list truncates for the terminal and says so (§9.1); JSON never does.

### 8.2 `memory list --json`

```json
{
  "repository": "/home/you/projects/sample-project",
  "head_sha": "f27ebbf…",
  "memories": [ <memory object>, … ],
  "other_repositories": {"count": 3, "paths": ["/old/path/to/sample-project"]}
}
```

`repository` and `head_sha` are the names the other read outputs already use.
`other_repositories` is **absent** when there is nothing to report, which is the
same rule `explain --json`'s `selection` follows: an absent key is a statement,
and its absence says "this database holds this repository's memories only".

### 8.3 `memory show --json`

The memory object alone, with `supersedes` filled in and every citation checked
(`resolution` never `not_checked`).

### 8.4 `explain`'s memory key

`explain --json`'s envelope gains one key, under the same absent-when-empty rule:

```json
{
  "commit": "8eaff71d…",
  "state": "explained",
  "explanation": { …, "related_memory": [ {"memory_id": "3f2a9c1e-…", "note": "…"} ] },
  "evidence": { …the bundle, unchanged… },
  "selection": { …unchanged… },
  "memory": {
    "in_force": [ <memory object>, … ],
    "not_provably_in_force": [ <memory object>, … ],
    "selection": {"shown": 5, "omitted": 12}
  }
}
```

- **The bundle under `evidence` is unchanged**, and memory is a sibling key. Unit
  1 §11.3's "it is not the evidence bundle" is enforced by the shape: a program
  reading `evidence` gets exactly what it got in v0.4.
- **Two groups, not one list**, because "in force at this commit" and "related,
  not provably in force" are different claims (Unit 1 §9.2), and merging them
  would be the one thing the temporal rule exists to prevent.
- **`selection` inside `memory`** is the v0.4 shape (`shown` / `omitted`), and it
  is present only when whole memories were dropped (Unit 2 §3.5 — never a cut
  statement).
- **`related_memory` is the model's field**, the one place an answer may point at
  a memory. Each `memory_id` is checked against the section the model was shown,
  so a relation to a memory it never saw is refused exactly as a citation of an
  unseen row is today. The field is optional and may be empty; the prompt's
  wording and the validator's message are the AI unit's (Unit 1 §11.3).

## 9. The renderings

### 9.1 `memory list`

```text
Memories (2)

1. auth.py
   We keep authentication in one module because the state machine was split
   across two files once and it caused an incident.
   3f2a9c1e  active  admitted 2026-10-06 21:14:03 +0800  since 1edec2712ab
   evidence: commit 1edec2712ab, file auth.py

2. core/app.py
   The retry wrapper exists because the API returned 503s under load.
   8eaff71d  active  admitted 2026-10-06 21:20:11 +0800

1 more memory. Use --all to see them.

A memory is what a person stated about this project: the tool did not derive it
and cannot check it. The citations are checked; the statements are not.
```

- **The short id** is the first eight characters, the form the tool already
  prints a sha in, and it is what `show` accepts. Collisions are possible in
  principle and harmless in practice: an ambiguous prefix is refused with `give
  more characters`, and the full id is always in the JSON.
- **A long statement is cut with an explicit marker**, naming the command that
  prints it whole (`… use 'archaeology memory show 3f2a9c1e' for the whole
  statement`). A silent cut would read as the whole claim, which is the failure
  the project refuses everywhere else; this is the timeline's message-cutting
  rule, with the cut stated.
- **Ended memories** (`--include-ended`) print their state and their end instead
  of `active … since …`: `superseded 2026-10-06, replaced by 8eaff71d` or
  `invalidated 2026-10-06: the module was split again in 4c1b2e`.
- **The closing sentence is the block's own device**, in the project's habit —
  `files` ends by saying what a deleted row means, `cochange` by saying what a
  score is not, and this ends by saying what a memory is not. It states three
  things and the implementing unit may polish the wording but not drop one: a
  person stated it, the tool did not derive it and cannot check it, and the
  citations are checked while the sentences are not.
- **Zero memories** prints `Memories (0)` and one sentence (`No memories are kept
  for this project.`), never an empty block.

### 9.2 `memory show`

```text
Memory      3f2a9c1e-8b47-4d6a-9f10-2c5e7a0b41d9
Repository  /home/you/projects/sample-project
Subject     auth.py
Author      Zyvn Coder <zyvn@example.com>
Admitted    2026-10-06 21:14:03 +0800
State       active
Since       1edec2712ab (2024-03-06 09:00:00 +0000)

We keep authentication in one module because the state machine was split across
two files once and it caused an incident.

Evidence (2)
  commit      1edec2712ab…   resolved
  file        auth.py        resolved

Lifecycle   nothing supersedes it

A memory is what a person stated about this project: the tool did not derive it
and cannot check it. The citations are checked; the statements are not.
```

- **`Author` is `unknown`** when the tool could not determine one — a word, not a
  blank.
- **`Since` is `unknown`** when the author gave none, and it prints the commit's
  own date beside the sha when it did.
- **`Evidence` shows the three states in words**: `none attached`; the citations
  with `resolved`; and `no longer in this history` for one that stopped
  resolving. A citation is never dropped from the display because it stopped
  resolving (Unit 2 §4.3).
- **`Lifecycle`** prints `nothing supersedes it`; or `supersedes <short id>`
  and/or `superseded by <short id>, admitted <date>`; or, for an ended memory,
  the end and its reason.

### 9.3 `explain`'s memory section

With a model configured, the block gains a section after the answer; with none,
the printed object gains the `memory` key (§10). The section:

```text
Memory (1 in force, 1 related)

  in force at this commit
    auth.py  3f2a9c1e  in force since 1edec2712ab
      We keep authentication in one module because the state machine was split
      across two files once and it caused an incident.
      stated by Zyvn Coder, admitted 2026-10-06
      evidence: commit 1edec2712ab (resolved), file auth.py (resolved)

  related, not provably in force
    core/app.py  8eaff71d  start unknown
      The retry wrapper exists because the API returned 503s under load.
      stated by Zyvn Coder, admitted 2026-10-06
      no evidence attached

  A memory is what a person stated about this project: the tool did not derive it
  and cannot check it. The citations are checked; the statements are not.
```

- **The two groups are the two headings**, and each row states its span, so a
  reader cannot take a rule from 2026 for the reason of a commit from 2023.
- **The statement is the stored text, verbatim** — the tool prints it, never the
  model. When the answer carries a `related_memory` entry, the model's sentence
  is printed under the statement and marked as the reading
  (`related by the model: …`), the way `render` already prints a candidate's
  citations under it.
- **The section's sentence** is the same statement `list` and `show` end with.
- **When there is nothing to show, there is no section** — no heading, no empty
  list. An absent section is the statement "this commit's files carry no stored
  memory", and it is the rule that keeps the offline output of a repository with
  no memories byte-identical to v0.4's (§10).

## 10. `explain`'s interface change, exactly

The offline path prints the evidence bundle's JSON today, and the model path
prints the prose block. Memory goes into each in that path's own form, and
neither form is replaced by the other:

| Path | Today | With memory |
|---|---|---|
| no model, no `--json` | the bundle object | the same object **with one added key `memory`**, absent when there is nothing to show |
| no model, `--json` | the envelope with `explanation: null` | the same envelope with the same `memory` key |
| model, block | the answer's prose | the same block with a memory section (§9.3) |
| model, `--json` | the envelope | the same envelope with the same `memory` key |

**Absent when empty, and that is a decision, not an accident.** It closes Unit 1
§21's open question, it follows `selection`'s existing rule (absent is not the
same as an empty block), and it has a property worth having: **the README's
`explain` block, which runs against a repository with no memories, keeps printing
exactly what it prints today**, so the change is additive where it can be and
visible only where there is something to see.

**The model is shown the same object, under a heading that says what it is.** The
section is not part of the evidence bundle, it is not citable as evidence (the
semantic pass checks citations against the bundle and memory is not in it, so a
memory citation is refused for free — Unit 1 §11.3), and the only way an answer
may point at one is `related_memory`.

## 11. Error cases

Every one of these is `Error: <sentence>` on stderr, exit 1, and no traceback.

| Case | The sentence says |
|---|---|
| Not a git repository | the existing one (`not a git repository: <path>`) |
| No stored analysis | the existing one, naming the command to run |
| A database holding a different repository | the existing `open_analysis` refusal |
| A database that cannot be read at all | that it could not be read, naming the file, and that the file should be copied before anything is done to it (Unit 2 §9) |
| The memory stamp is newer than the tool, or missing under existing tables | which of the two it is, naming the file; evidence still works |
| No subject | the four forms, in one sentence |
| Two subjects | the same, saying one is allowed |
| `--about-definition` without `--about-path` | that a definition is a path and a name |
| A path the history never touched | the existing `nothing in the stored history touched …` sentence |
| A commit prefix that names nothing or several | the existing three refusals, with "memory" for "commit" only where the id is the subject |
| A definition not in the stored definitions | that the AST pass has not read this path (`run 'archaeology ast' first`) |
| An empty statement | that a memory is a statement, and it is empty |
| A statement over 4,000 characters | the cap and the length it got |
| A citation that resolves to nothing | the citation, and what would make it resolvable |
| `--cite-range` without a `--cite-commit` | that a range is a span of one commit's diff |
| An unknown `--cite-absence` kind | the four kinds |
| The same citation twice | the citation, and that it is already there |
| A memory id that names nothing, or several | the three refusals, with "memory" for "commit" |
| `supersede`/`invalidate` on a memory that is not active | its state, and that a new memory can be created instead |
| A write when the database holds another repository's memories | the foreign path, and the two ways forward (drop `--db`, or `adopt --from`) |
| `adopt --from` that matches nothing | the path, and that nothing was made about it |
| `adopt --from` that is already this repository | that there is nothing to adopt |

## 12. The README contract

Both READMEs are the command line's contract: every console block is replayed
against the fixtures, and every registered command must have a section. Six new
commands therefore mean six new sections in each file, and three things the
implementing unit must do that are not prose:

1. **The command checker must learn about groups.** `_registered_commands()` in
   `tests/test_readme.py` walks `app.registered_commands`, which does not see a
   sub-app's commands — so as it stands it would pass while six commands shipped
   undocumented. It must walk `registered_groups` too and yield the full name
   (`memory create`), and the READMEs must carry each full command line.
2. **A new scenario is needed.** The five existing fixture states have no
   memories in them; a block that shows a memory needs a database that holds one,
   and the scenario's restore-before-each-block behaviour already handles writes.
   The new state should be built the way the blocks describe it — memories
   created through the tool, not inserted by hand — so the blocks and the state
   cannot disagree.
3. **The prose that counts things must be updated**: the number of commands in
   the introduction, the sentence about which commands take `--json`, the module
   tree (`memory.py`), the roadmap row for v0.5, and — required by Unit 2 §12.2 —
   the section about where the database lives, which must stop saying every row
   can be rebuilt and must say that deleting the file destroys memory.

The blocks to add, at least one per act: `create` (with a subject and a
citation), `list` (two memories, one with no evidence), `show` (the same memory,
in full), `supersede`, `invalidate`, `adopt`, and the `explain` memory section in
the new scenario. Both languages, replayed, exactly as every other block is.

## 13. What this unit does not decide

- **The prompt's wording** for the memory section — the sentence the model reads
  about what a memory is and what it may do with one. Unit 1 §19 left the prompt
  to a unit of its own, and that is still open.
- **The validator's messages** for `related_memory`, beyond the rule that an id
  the model was not shown is refused.
- **The rendering's exact spacing, widths and colours** — the implementing
  unit's, as every block's spacing is its own module's.
- **The module's internal split** (`memory.py` versus a view module beside it),
  and where the shared note's constant lives.
- **Whether `list` should filter by subject** (§15.1).
- **Whether the writing acts should take `--json`** (§7).

## 14. Acceptance criteria

1. **Six commands exist under one group**, with the help text above, and
   `archaeology memory` with no sub-command prints the group's help.
2. **Every act has a test for what it writes and a test for what it prints**, and
   every row of §11 has a test asserting the sentence and the exit code — the
   project's rule that a rule with no case is a rule that could be deleted.
3. **stdout carries only the block or the JSON**: a test runs each command with a
   note due (a stale analysis, a foreign memory) and asserts the note is on
   stderr and stdout parses.
4. **The JSON shapes are pinned**: the canonical memory object's keys, `list`'s
   envelope, `show`'s object, and `explain`'s `memory` key — the way
   `tests/test_explain.py` pins the explanation's shape today.
5. **Absent when empty is asserted**: a commit with no related memories produces
   an `explain` output byte-identical to v0.4's, in both forms.
6. **The README checker walks groups**, and both READMEs carry every act's full
   command line and at least one replayed block each.
7. **A memory never appears in `evidence`**, and a model's citation of one is
   refused — the check is the unchanged semantic pass, and a test says so.
8. **`--json` on `list` carries every memory** even when `--limit` was given.
9. **The subject and citation refusals are the tool's existing sentences** where
   §11 says so, asserted by their text, so the two places cannot drift.
10. **No new dependency, no network**, and `SCHEMA_VERSION` is still `"4"`.

## 15. Open questions

1. **Subject filtering on `list`.** "What do we know about this file?" is the
   most natural question a store like this gets, and `memory list --about-path
   auth.py` is the obvious way to answer it. It is not in v0.5.0 because the
   listing commands are listings and a filter is a query, and because one filter
   would immediately suggest the other three subject forms. Recommendation: the
   first thing added after v0.5.0, as its own unit.
2. **`--json` on the writing acts**, and whether the whole command line's
   writer convention should change to match.
3. **`--no-memory` on `explain`**, for a reader who wants the answer without the
   section.
4. **The short id's length** if a real store ever produces an ambiguous prefix —
   the refusal handles it, but the display could grow.
5. **Whether `show` should accept a *subject* as well as an id** (e.g.
   `memory show auth.py` meaning "the memories about this file"), which is
   question 1 wearing a different hat.
6. **The memory section's cost in the prompt**, and whether it needs a measured
   budget the way the evidence bundle has one.
