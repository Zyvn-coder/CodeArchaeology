# The understanding experiment

**What this is.** The design of the first test of CodeArchaeology's product claim:
that it helps a person understand a codebase they did not write. The audit
(`docs/v0.5-product-audit.md` §4) said this claim has no evidence of any kind —
921 tests measure the tool against its own design, the public repository has 0
forks and 0 issues, and no human who did not build it has ever said anything
about it.

**What this is not.** It is not the result. **The experiment has not been run**,
and it cannot be run by the agent that wrote this document: it needs six to eight
people and a facilitator, and the agent is neither. What is here is everything a
facilitator needs to run it — the repositories, the procedure, **six calibrated
questions** with their ground truth, the materials to print, the metrics, and the
decision rule written down **before** any data exists.

**What was done instead of guessing.** Preparing this document meant measuring
things the audit could only reason about, and **six of those measurements
changed the design** — including the rehearsal in §2.5, which invalidated the
level of a question already written, and §2.6, which derived the last four
questions and found three ways the derivation goes wrong. They are in §2 and §4,
and each says which part of the design it moved.

**Status: prepared, not run.** Date: 2026-10-08. No production code was changed
by the unit that wrote this.

---

## 1. What this phase can and cannot answer

```text
Correctness validation — what the 946 tests and five benchmarks do
    input → tool → expected output          the tool measured against its design

Product value validation — what this is for
    developer → tool → understanding → faster / more accurate / more confident
                                            the tool measured against a person
```

**This document tests the second line, and it tests one part of it.** The claim
under test is deliberately narrow:

> Given a piece of code whose shape is not self-explanatory, a person who does
> not know this repository reaches a correct, evidence-backed reason for it
> faster, or more often, with CodeArchaeology than with git alone.

**Narrow on purpose**, because the wide version ("does it help people understand
code") is not falsifiable in a day. Three things follow from the narrow form:

- The unit is **one code site and one question about it**, not a repo-wide task.
- **The answer has to exist and be checkable** — "why is this like this" is a
  question with a truth, and the truth is not the tool's opinion.
- **"The history does not say" is a correct answer** where that is true, and it
  is scored as correct. Without that escape a participant confabulates, and the
  experiment measures fluency instead of understanding.

**What this cannot answer, and no version of it can:** whether the tool helps
over months, whether it helps a team, and whether a memory is worth carrying
between people. Those are §8 and the audit's §3.

## 2. What was measured while preparing this

Six measurements, each of which changed something. The first three are about
feasibility, the fourth is about the instrument, the fifth produced the selection
rule the procedure now runs on, and the sixth is about the questions themselves.

### 2.1 The tool's first run on a codebase with real age

The audit recorded that CodeArchaeology **has never been run against a repository
with a real history — not by its author, not by anyone.** It has now been run
against one, and the numbers are the reason the rest of this document is
possible.

`python-attrs/attrs`, cloned in full, 2026-10-08:

| | |
|---|---|
| Commits | 1,845 |
| Span | 2015-01-27 to 2026-10-06 (11.7 years) |
| Repository size | 8.4 MB |
| Files the history contains | 463 |
| `analyze` | **1.0 s** |
| `ast` (cold) | **24.8 s** — 1,839 file versions, 88,512 definitions, 0 parse failures |
| Most-changed file | `src/attr/_make.py`, 342 commits, +8,657 / −5,195 |
| Definitions in that file | 122 |

**Every candidate question in §5 is reachable with the shipped commands** — that
is a requirement, not a convenience: if a question is only reachable through SQL,
then *neither* condition can answer it, and the question measures nothing. (The
first four were found by walking the tool's views by hand. The last four came from
the bulk scan in §2.6, and each accepted site was then re-checked the same way:
the tool's `structure --history` must name the commit the answer needs.)

### 2.2 Candidate repositories are much harder to find than the audit assumed

The criteria were "≥1,000 commits, ≥3 years, Python, not this project". Measured:

Budget it as its own session.

### 2.3 What the tool's own views actually look like on a real repository

`structure --history` on `src/attr/_make.py` gives, for each definition, every
moment it changed:

```text
_frozen_setattrs  function
  created  2016-08-20 18:45:15 +0200  cfa6d2e9  line 149
  modified 2020-11-04 11:02:15 +0100  f2dabeae  line 533
  modified 2023-01-08 18:34:28 +0100  a71fbbad  line 585
  modified 2024-08-16 07:23:14 +0200  ae734096  line 539
  modified 2024-10-26 11:20:44 +0000  1921da6e  line 538
```

**One command, five SHAs, five dates.** This is the view the experiment is
testing, and §5's second question is built on it.

Two things the output does that a facilitator should know before reading it
aloud: it reports a name that appears twice as `(2nd of that name)` — the parser
cannot tell two same-named functions apart inside one file version — and
definitions nested inside a function appear with `<locals>` in their qualified
name. **Both are real, documented behaviours and neither is a defect**; they are
mentioned here because a facilitator who notices them mid-session without knowing
will derail.

### 2.4 The instrument has a failure mode the audit did not predict

**The audit's strongest trigger — "a definition was deleted and later restored" —
almost never fires.** Measured over attrs' 1,845 commits: **four** definitions
have three or more `created` rows, and three of those four are nested functions
reported with `<locals>`, which is a parser artifact rather than a decision
anyone made. The trigger was reasoned from the design, not measured, and on a
real repository it is not a source of questions.

**And a meticulous changelog ruins a question.** The first candidate question was
the `linecache` loop in `_make.py` — a genuinely puzzling piece of code with a
real reason. The reason is **in the current tree**:

```console
$ grep -rn "cached more efficiently" .
CHANGELOG.md:447:- Generated source code is now cached more efficiently for identical classes.
```

A control participant who greps the changelog — an obvious move — is handed the
answer. The question is not *biased*, it is *flat*: both conditions answer it and
it separates nothing. **This is why §4 has calibration levels and why §3 has a
criterion the audit did not.**

### 2.5 The rehearsal, and the selection rule it produced

The design authorises one rehearsal run "for logistics, its data discarded"
(§6.1). **Its data is discarded here too** — the times below come from the person
who wrote the tool and who already knows the answers, so they are not an effect
size and must never be reported as one. What a rehearsal *can* do is invalidate a
question, and it did.

**The control's cheapest path was walked, and it gives a wrong answer.** `git
blame` is what any experienced developer reaches for on a puzzling construct, and
on Q-B's site it prints:

```console
$ git blame -L 561,575 --date=short src/attr/_make.py
a71fbbad (Julian Berman   2023-01-08 561) def _frozen_setattrs(self, name, value):
...
a71fbbad (Julian Berman   2023-01-08 572)         BaseException.__setattr__(self, name, value)
1921da6e (Thomas Grainger 2024-10-26 569)         "__suppress_context__",
1921da6e (Thomas Grainger 2024-10-26 570)         "__notes__",
```

Two commits, both real, both with explanatory messages — and **the origin is
missing**. `f2dabea` (2020) is invisible because `a71fbbad` (2023) rewrote those
lines when it removed the `if PYPY:` wrapper. A participant who stops at blame
produces a *plausible, well-evidenced, incomplete* answer.

**The rule this produces, and it is mechanical:**

> **A site is L3 when `git blame` on its current lines returns a commit that is
> not the origin of the construct** — because a later commit rewrote, generalized
> or moved it. Blame answers "which commit last touched this line"; a question
> about *why the code is shaped this way* is a question about the decisions, and
> a single intermediate rewrite hides all of them.

**This is the cheapest and sharpest test found, and it replaces guesswork.**
Running it costs one command per candidate site, and it produces the level
directly: blame lands on the decision → L1 or L2, never L3 (§4.2's tie-break
decides which); blame lands on a rewrite →
**L3, take it**. It is now step 5 of §4.1 and the L3 test in §4.2.

**It also says something about the tool that the audit could only assert.** For
"which commit last touched this line", `git blame` has been excellent for fifteen
years and the tool adds nothing. The tool's views answer a different question —
*every* moment a definition changed, across rewrites, renames and file moves —
and the sites where the two answers differ are exactly the sites worth asking
about. **A candidate question whose answer `git blame` gets right is not worth
asking**, because the control has it in one command.

### 2.6 Deriving the last four questions, and the three ways it goes wrong

The composition rule (§4.3) asks for two questions at each level, so four more
were derived. §4.1's procedure is one site at a time and that is its weakness: on
a repository with 88,512 definitions the first hour goes to sites that turn out to
be L1. So the blame test was turned into a bulk scan — for every definition in the
current tree, blame its line range, compare the commits blame reports with the
definition's lifecycle from the tool's database, and rank the ones whose **visible
lines do not include their origin**. Run over `src/attr/_make.py`, that ranks 30
definitions and 22 of them have an origin blame cannot reach; the list is short
enough to read, and every entry on it is an L2-or-L3 candidate by construction.
Each accepted question was then re-checked by hand, and **the tool must be able to
name the commit the answer needs** — this is §2.1's requirement, and the scan is
only a way of proposing candidates, not a shortcut past it. The scan is cheap to
write again (blame per definition, plus the lifecycle rows) and the modules worth
scanning are the ones whose reasons are not user-visible: `_make.py`, `_funcs.py`,
`_compat.py`, `_next_gen.py`, and the test files.

The scan produced three findings that changed the procedure. All three are
procedural, so they are written again where they are used: §4.1 (steps 4, 5 and
7), §4.2 (the tie-break) and §4.4 (failures 5, 6 and 7).

**1. A documented repository saturates L1.** attrs records its reasons twice over
— a maintained `CHANGELOG.md` *and* comments with `.. versionchanged::` markers
in the code — so almost every decision a user can see is stated in the tree, and
the L1 test passes immediately. Three of the four new questions are ones whose
reasoning exists **only** in a commit message or a diff — the shared `__ne__`
(2025), the 3.14 descriptor call (2025-07/08), the lazy submodules (2026) — and
the fourth is an L1 chosen for the richness of its ground truth, not for what
blame does with it. This is the sparse-changelog criterion's cousin (§3,
criterion 5): **the denser the documentation, the fewer L2s**, exactly as §2.4
found for changelogs.

**2. A rename resets the tool's definition identity, and the question dies with
it.** The tool follows a definition by its name inside a file. When a construct is
renamed, the lifecycle view reports a *deletion* and a *creation*: `_make_repr` →
`_make_repr_script` (2025), `_ne` → `__ne__` (2017), `_has_frozen_superclass` →
`_has_frozen_base_class` (2018) all have two half-lives. A question whose answer
requires crossing that boundary is answerable by **neither** condition, so it is
not a question (§4.1 step 4). Measured while looking for an L3: the
`_has_frozen_base_class` site blames entirely to "Drop Python 2.7", the tool's
view shows the rename, and the behaviour's actual origin is one name earlier and
invisible to both.

**3. `git blame` follows content across a delete and a re-add, and mixes eras.**
This is a fourth way blame misleads, distinct from §2.5's rewrite. `__ne__` was
deleted in 2020 and re-added in 2025; blame on its current lines reports three of
them to a 2017 commit (`cd8890c7`, "Speed up `__eq__` by generating code") because
the docstring delimiters match by content. A control that reads blame carefully
gets a *confusing* answer rather than a merely incomplete one — which is what
makes Q-D a question, and why its calibration record states the artifact.

**And one constraint that is not a finding but a rule: the six questions must not
touch §8's island.** The memory sub-experiment needs a site where the reason for
something is documented in prose but not in the code, and it uses the hash cache
and `__attrs_post_init__`. A question about the same machinery would prime the
participant for the memory question and vice versa, in both arms. The obvious
L1/L2 candidate in that area (`_make.py`'s ordering comment, line 2399) was
dropped for this reason alone, and step 7 of §4.1 checks for it.

## 3. The repository criteria

The audit's five, plus one that measurement added.

| # | Criterion | Why |
|---|---|---|
| 1 | ≥1,000 commits, ≥3 years | Below this the lifecycle, hotspot and co-change views have nothing to say, and the treatment is the tool with its main instruments switched off. |
| 2 | Python | The AST layer is Python-only in v0.x. A non-Python repository makes the two conditions unequal. |
| 3 | Contains code whose shape is not self-explanatory, with the reason recorded **in the repository** | The property being measured. Reasons that live only in an issue tracker or a PR description are unreachable by *both* conditions and cannot be questions (§5, failure mode 2). |
| 4 | Not CodeArchaeology itself | **CONFIRMED disqualification**: 39 commits over ten days, one author, no legacy. There is no archaeology in it. |
| 5 | **A sparse changelog** *(added by measurement — §2.4)* | A project that records every user-visible change in a maintained `CHANGELOG.md` turns "why" questions into greps, which flattens the instrument. The denser the changelog, the fewer usable questions. |
| 6 | Cloneable in full, from this machine | §2.2. `--filter=blob:none` and `--depth` are both disqualified. |

**On criterion 4, stated plainly:** using this project as the repository would be
worse than useless, and not only because of bias. A repository with ten days of
history has no reasons to recover, so the experiment would return a null result
that says nothing about the tool.

## 4. How a question is derived, and how its difficulty is calibrated

This is the part of the document that must be repeated for each repository, and
it is written as a procedure rather than as advice.

### 4.1 The derivation procedure

1. **Analyse the repository.** `analyze`, then `ast`. Both are one-time costs
   (1.0 s and 24.8 s on attrs) and both are re-run if the checkout moves.
2. **Find candidate sites with the tool's own views** — `hotspots` for the files
   that changed most, `structure --history` for definitions whose lives are long
   and busy, `files` for what the history contains, `cochange` for coupling that
   looks odd. A site is a candidate when its **current shape is not
   self-explanatory**.
3. **For each candidate, find the reason in the history** — `git log -S`, `git log
   --follow -p`, `git show`, and the commit message. Record the commits that
   changed the site and what each one says.
4. **Reject the candidate if the reason is unreachable from the repository.**
   A docstring that says "see GH #613" points outside; both conditions are locked
   out of here, so there is no ground truth to score against. (§5, failure 2.)
   **And reject it if reaching the answer requires following the construct
   across a rename** — the tool identifies a definition by its name, so a renamed
   construct has two half-lives and neither condition can cross between them
   (§2.6, §4.4 failure 5).
5. **Run the calibration tests in §4.2 and record the level.** The sharpest of
   them is one command: `git blame` the site. **If blame returns a commit that is
   not the origin of the construct, the site is L3 and should be kept** — a later
   rewrite has hidden the decision, and that is the gap the tool fills. If blame
   lands on the decision itself, the control has the answer in one command, so the
   site **can never be L3**: §4.2's tie-break then decides between L1 and L2 —
   L1 if the tree states the reason, L2 if only the message does. Doing this for
   one site at a time is slow on a big repository; §2.6 records the bulk form —
   blame every current definition and keep the ones whose visible lines exclude
   their origin.
6. **Write the question so that it does not hint at the answer**, write the
   ground truth with its citations, and write what a *correct*, a *partially
   correct* and a *correctly-uncertain* answer look like.
7. **Check the site against §8's island.** No question in the six may touch the
   hash cache or `__attrs_post_init__`: the memory sub-experiment uses that site,
   and a question about it would prime the participant in both directions (§2.6).

**Step 6's third clause is not optional.** A question without a written
"correctly-uncertain" form cannot be scored honestly, and the scorer will default
to marking "I don't know" as wrong — which punishes exactly the calibration this
experiment exists to measure.

### 4.2 The calibration levels, and how to measure them

Each candidate gets a level, measured and not judged. The tests are mechanical
and take a minute:

```bash
# L1 test — is the reason already in the working tree?
grep -rni "<a distinctive word from the reason>" --include="*.py" \
     --include="*.md" --include="*.rst" --include="*.txt" .

# L2 test — is it in a commit message, findable by grepping messages?
git log --oneline --grep="<distinctive word>" --all

# L3 test, first half — is it only in the diffs?
git log --oneline -S "<a distinctive line of the current code>" -- <the file>

# L3 test, second half, and the one that matters most — does blame land on the
# decision, or on a rewrite that hid it? (§2.5)
git blame -L <start>,<end> --date=short <the file>
```

| Level | The answer is | What it measures |
|---|---|---|
| **L1 — documented** | Stated in the current tree, in a file a person would grep | **An instrument control.** Both conditions should answer it. If the tool arm scores *worse* here, the tool is actively harmful and the rest of the data is beside the point. |
| **L2 — in a message** | In a commit message, found by grepping messages with an obvious word, **and `git blame` on the site lands on the decision** | Whether the tool shortens the path from "odd code" to "the commit that explains it". |
| **L3 — blame is wrong** | Nowhere but the diffs, **or** blame returns a commit that is not the origin because a later commit rewrote or generalized the construct | The discriminating question. The control's cheapest path produces a confidently incomplete answer, and the tool's `structure --history` shows the moment that was hidden. |

**Which test wins when two of them pass.** They can. A site whose reason is in a
commit message may also be named in a comment, a docstring or a changelog line,
and then the three tests disagree about it. The level is decided by the
**cheapest path that actually answers the question**, because that is what the
control has:

- A person can grep the answer out of the working tree → **L1**.
- The tree only names the thing and never says why → **L2** if a message does say
  why and blame lands on it, **L3** otherwise. A grep hit that is the code's own
  identifier (searching "lazy" and matching `_LAZY_SUBMODULES`) is not a
  statement of the reason.
- The answer is nowhere but the diffs, or blame is wrong about it → **L3**.

**The calibration record must say which grep was run and what it matched**, for
this reason: "the grep hits something" and "the tree states the reason" are not
the same sentence, and the difference is a whole level.

**Any candidate whose blame result is the decision itself can never be L3.**
Sliding it there because the message is terse would be wishful thinking, and the
rehearsal in §2.5 exists to stop exactly that.

**A composite question scores as its hardest part.** The second worked example in
§5 is three decisions spread over five years; its newest moment is documented and
its origin is only in a diff, so it is recorded as L3. Answering it requires
assembling more than one decision, and the oldest one is the one the control
cannot see.

### 4.3 The composition the question set must have

**Not five of the same kind.** The set must contain L1s and L2/L3s, because they
answer different questions:

- Fewer than two **L1** questions and the session cannot detect a tool that
  actively misleads — the failure mode that matters most.
- Everything at L1 and the experiment measures nothing but the two conditions'
  equal ability to grep a changelog.
- Everything at L3 and a null result is uninterpretable: it may mean the tool
  failed, or that the questions were unanswerable by anyone.

**Target: two L1, two L2, two L3, six questions.** Enough for a within-subject
crossover (three per arm per session) and enough for the composition rule to bite.

**Met, and this is the whole set of six.** §5 carries one entry per question with
its ground truth, its scoring forms and its calibration record:

| Level | Questions | What they measure |
|---|---|---|
| **L1** | Q-A (the `linecache` loop), Q-C (`_broken` collector) | the instrument control: if the tool arm loses here, the tool misleads |
| **L2** | Q-E (lazy submodules), Q-F (3.14 descriptor call) | whether the tool shortens the path from odd code to the commit that explains it |
| **L3** | Q-B (frozen-exception carve-outs), Q-D (the shared `__ne__`) | the discriminating pair: blame's cheapest path gives a confidently incomplete answer |

### 4.4 The seven failure modes found by doing it

Recorded because each one cost real time and each will be hit again.

1. **The reason is in the tree and the question is flat** (§2.4). The `linecache`
   loop and `CHANGELOG.md:447`. The `asdict` fast path is the same family at a
   further distance: `_funcs.py`'s `_ATOMIC_TYPES` set is unreadable without a
   reason, and `CHANGELOG.md:94` — "The performance of `attrs.asdict()` has been
   improved by 45–260%" — hands the reason over. It is a good **L1** by
   construction and cannot be used as anything else, which is why it is not in
   §5: Q-C is the same level and a richer question.
2. **The reason is outside the repository.** `_CacheHashWrapper` in `_make.py`
   is a class whose docstring ends "See GH #613 for more details". The mechanism
   is described; the *reason* is in a GitHub issue neither condition can read.
   **No ground truth exists, so this is not a question.** A related shape: a
   commit whose message is only `Fixes issue #1427 (#1428)` — but that one
   happens to carry one explanatory sentence in the body, which makes it L2 and
   not a rejection.
3. **The "restored definition" trigger barely fires** (§2.4). Four hits in 1,845
   commits, three of them nested-function artifacts.
4. **A high-churn site is not automatically a good question.** `_make.py` has 342
   commits and 122 definitions; most of its history is noise from a lint or a
   formatter. The question has to attach to a *shape someone decided*, not to a
   line that moved.
5. **A rename kills the question, and it is the quietest rejection of the four.**
   The tool identifies a definition by name, so `_ne` → `__ne__` (2017),
   `_has_frozen_superclass` → `_has_frozen_base_class` (2018) and `_make_repr` →
   `_make_repr_script` (2025) each became two half-lives, and a question that has
   to cross the boundary is answerable by neither condition. Check for it before
   spending time on the ground truth: `git log -S "<the old name>"` is the test,
   and it only works if you already know the old name — so the real check is the
   reverse: **if the tool's lifecycle view shows a `deleted` row shortly after a
   `created` row with no explanation, suspect a rename** and look at what the
   deletion commit's diff renames.
6. **In a documented repository the L1 test passes for nearly everything.** attrs
   states its reasons in a changelog *and* in the code, so a site can have an
   origin blame cannot reach and still be L1. Measured on the scan's own output:
   of the 22 ranked definitions whose visible lines exclude their origin, most
   were L1 anyway — `_Nothing`'s enum is in the changelog, `cached_property` on
   slotted classes is in `docs/how-does-it-work.md`, `Attribute.__setstate__`'s
   alias inference is in the 26.1.0 entry — and four survived. Budget for that:
   an L2 or L3 is found by elimination, not by looking harder at one site.
7. **`git blame` mixes eras across a delete and a re-add.** Distinct from §2.5:
   when a block is deleted and later restored with the same text, blame
   attributes lines to the *oldest* commit whose text matches, so `__ne__`'s
   docstring delimiters blame to 2017 while the body blames to 2025. A control
   that reads blame carefully can end up more confused than one that stops at the
   newest commit — which is precisely the discriminating behaviour Q-D measures,
   and the reason its calibration record prints the artifact.

## 5. Six worked examples, and one rejected candidate

Six usable, one rejected, and together the six meet §4.3's composition rule. Each
was found with the shipped commands or with `git` alone (§2.1), each carries its
ground truth with its citations, and every level was measured with §4.2's tests
rather than judged — including the two where the tests disagree, which is what
§4.2's tie-break is for. **Every question below is complete enough to be moved
into Appendix D as it stands.**

**Line numbers are as of the checkout §2.1 measured** (`644b4e16`, 2026-10-06),
and the file paths are the ones that checkout has (`src/attr/...`); attrs' history
moved the package into `src/` in 2023, so anything read out of a diff before that
is under `attr/...`. That is the tool's documented behaviour, not a mistake
(`file <path>` lists the earlier names), but a facilitator reading two eras of
diffs aloud should expect it.

### Q-A — the `linecache` loop (`_make.py`) — **L1, an instrument control**

**The site**, at `src/attr/_make.py:231`:

```python
    # In order of debuggers like PDB being able to step through the code,
    # we add a fake linecache entry.
    count = 1
    base_filename = filename
    while True:
        linecache_tuple = (len(script), None, script.splitlines(True), filename)
        old_val = linecache.cache.setdefault(filename, linecache_tuple)
        if old_val == linecache_tuple:
            break
        filename = f"{base_filename[:-1]}-{count}>"
        count += 1
```

**The question, as a participant would read it:** *"This function loops, renaming
`filename` until the cached entry matches the one it just built. Why? What is the
counter for, and what would break without the loop?"*

**Ground truth.** The loop makes classes with **identical** generated source share
one linecache entry, so a debugger shows one frame for them, while classes whose
source differs get `-1>`, `-2>`, … so their line numbers stay correct. Before this
change the name was derived from `repr`-based uniqueness and always advanced, so
identical classes each occupied their own entry.

| | |
|---|---|
| The commit | `3858063 Rework linecache handling (#828)`, 2021-06-30 |

## 6. The design

### 6.1 Participants

- **Six to eight people.** This is a pilot and it is written as one: report
  per-participant results and **no p-values**. With n≈6 a real difference has to
  be large to be visible, and a difference that is not visible proves nothing.
- **Split by familiarity**: at least three who have never read the target
  repository, at least two experienced Python developers. The newcomer case is
  where the tool should help most, and an expert on a repository they know is
  measuring memory rather than tooling.
- **Nobody who has read the tool's source or this document.**
- **A hard recruitment constraint, and it is not fixable here:** the tool is not
  on PyPI, so a participant needs a checkout and `uv`. Participants are therefore
  Python developers with `uv` available. Say so when reporting.
- **The facilitator may run the protocol once for logistics** — does it fit in
  ninety minutes, are the questions answerable — **and that run's data is
  discarded.** An author who knows the answers measures nothing.

### 6.2 Crossover, and the unit that is counterbalanced

Two repositories and two arms:

- Participants do repository **X** with git alone and repository **Y** with the
  tool, and the assignment is **counterbalanced**: half do X with the tool, half
  do Y.
- This separates the tool's effect from the repositories' relative difficulty,
  which is otherwise the largest confound in the design.

**If only one repository can be prepared** (§2.2 makes that likely for a first
run), the same principle applies one level down: split the six questions into two
matched halves and counterbalance those. **The cost is real and must be stated:**
with one repository, a participant who has explored half of it has learned
something about the repository before the second half, so the crossover no longer
controls the learning effect. That is a reason to prefer two repositories; it is
not a reason to skip the run.

### 6.3 Control and treatment

| | |
|---|---|
| **Control** | git + source + the repository's own documentation. `git log`, `git show`, `git blame`, `git log -S`, `git log --grep`, `git log --follow`, `git diff`, grep, plus README/CHANGELOG/docs. **The internet is off.** |
| **Treatment** | the same, plus `archaeology analyze`, `ast`, `timeline`, `hotspots`, `files`, `file`, `commit`, `structure`, `cochange`. **`explain` is configured off** — see below. |
| **Orientation** | **five minutes**, treatment arm only, and identical every session: what the commands are for, nothing about the specific repositories. A longer or improvised orientation measures the facilitator. |

**`explain` is excluded, and this is a design decision, not an oversight.**
`explain` sends the evidence to a language model. If it is in the treatment, the
experiment compares *git* against *git plus an LLM*, and a positive result cannot
be attributed to this tool — the same result would be obtained by pointing a
model at a `git show`. The deterministic layer is also the part that is
reproducible and offline, so it is the part that can be measured cleanly.

Whether the AI layer adds anything *on top of* the evidence is a **second
experiment**, with the same protocol and the treatment defined as `explain`
versus the evidence alone. It is not this one, and running them together would
leave both uninterpretable. **`explain`'s offline path** (which prints the
evidence bundle with no model configured) may be used in the treatment, because
it is deterministic and is not an AI feature.

### 6.4 Per session

| Minutes | What |
|---|---|
| 0–5 | Read the briefing (Appendix A). Sign nothing; there is no recording. |
| 5–10 | Treatment arm only: the five-minute orientation. |
| 10–70 | **Six questions, ten minutes each, capped.** The participant writes the answer, the evidence they relied on, the minutes spent, and a confidence, on Appendix C. |
| 70–80 | The Memory sub-experiment (§8). |
| 80–90 | Debrief: two open questions, and "which command did you use most". |

**The ten-minute cap is load-bearing**: a stuck participant distorts everything
else, and an answer given after forty minutes is not an answer about
comprehension. A capped question is scored as not answered, and the time is
recorded as ten.

## 7. The metrics, and the scoring rubric

### 7.1 The primary endpoint, declared before the run

**Correct-and-evidenced answers per question.** One number per question, summed
per participant per arm. Declared first because otherwise the pilot will be read
as confirming whatever it happens to show.

### 7.2 The rubric

Scored **from the written answer alone** by a scorer who did not run the session
and who has the ground truth in front of them.

| Score | Meaning |
|---|---|
| **2 — correct and evidenced** | The answer matches the ground truth **and** names evidence (a commit, a file version, a definition, a test) that exists and supports the claim. |
| **1 — correct, unevidenced** | Right conclusion, no usable evidence, or evidence that does not bear on it. |
| **0 — wrong** | Contradicts the ground truth, or asserts a mechanism the history does not support. |
| **U — correctly uncertain** | "The history does not say" or "insufficient evidence", **where that is the truth for this question**. Scored **2**. |
| **0 (not U)** | The same answer where the ground truth *does* exist. Scored 0: uncertainty is not a licence. |

**The primary endpoint counts score 2 only.**

That `U` behaves differently depending on the question is the reason §4.1 step 6
requires every question to carry a written correct / partial / uncertain form.
A scorer working that out live will get it wrong.

### 7.3 The rest

| Metric | How | Why |
|---|---|---|
| **Time to answer** | minutes per question from Appendix C, capped at 10 | Part of the claim is speed. Reported separately, never blended into the primary endpoint. |
| **Calibration** | stated confidence (0–1) minus `CE` (1 if score 2, else 0), per question | **The metric that catches the worst outcome.** A tool that makes people confidently wrong scores well on speed and correctness and is a product failure. |
| **Per-level breakdown** | the §4.2 level of each question | An aggregate hides the only interesting result: L1 flat, L3 improved, is a real finding; an average of the six is not. |
| **Commands used** | recorded by the facilitator, treatment arm | A cheap proxy for whether the tool was used, and after which command the answer arrived. |
| **Perceived usefulness** | two questions in the debrief | **The weakest metric, and labelled as such.** Self-report, politeness bias, and the participant knows what is being evaluated. |

**Never use overall accuracy alone.** Accuracy plus time rewards a tool that
makes people fast and wrong.

## 8. The Memory sub-experiment

The claim is narrow and worth testing apart from the six questions: **a memory
surfaces knowledge at the moment it is needed, where documentation requires
knowing that the documentation exists.**

**A constraint that measurement imposed, and it changed the design.** A memory
must be a *true* statement about the project that the tool cannot derive. An
outsider preparing an experiment cannot invent one — a fabricated memory is not
knowledge, and an experiment on one measures "does a made-up note help". So the
memory must restate something a person genuinely stated. The working resolution:

- **The knowledge comes from the repository's own documentation** — someone's
  statement, in the tree, which the tool cannot derive (it reads git and the AST,
  not prose). It is admissible as a memory under the v0.5 definition.
- **The test is surfacing, not availability.** Both conditions can reach it;
  the control must know to look, and the treatment gets it printed beside the
  commit it is about.

**A verified candidate for attrs**, found while preparing this:

> `docs/init.md:506` — "Note that you *must not* access the hash code of the
> object in `__attrs_post_init__` if `cache_hash=True`."

It is a real constraint, it is buried at line 506 of one document, and its
mechanism (`cache_hash` computes on first access, and `__attrs_post_init__` runs
before the object is finished) is in the code but stated nowhere. The memory
would be admitted against the definition that builds the hash, and the question
would be anchored on a commit that touches it — the unit of the tool is a commit,
and a memory surfaces when one is read.

**And this island is kept clear of the six questions.** None of them touches the
hash cache or `__attrs_post_init__`, for the reason §4.1 step 7 gives: a
participant who has just answered a question about that machinery is primed for
this one, in both arms, and the priming would be invisible in the results.

**Protocol:** one piece of knowledge, two conditions, the same question types as
§6. **Measure whether it was found at all, and how long it took**, not answer
quality — the predicted mechanism is a difference in time-to-find.

**And the honest limit:** the *retention* claim — knowledge surviving months — is
the real Memory claim and this cannot measure it. Measuring it needs a return
visit weeks later, which is a different and much more expensive study. **What
this can falsify is the cheaper half:** if a memory surfaced at the point of need
is not found faster than a paragraph in a document, then retention does not
matter.

**What would make this much better:** running it inside a team on a repository
the team owns. Then the memories are real, the knowledge is genuinely
non-derivable, and the newcomer case is real instead of staged. That is the
version worth doing, and it needs a team — which is §12.

## 9. Threats to validity

Written down before the run, because after it every one of them is a plausible
excuse.

| Threat | Where it comes from | What is done about it |
|---|---|---|
| **No statistical power** | n≈6 | Stated as a pilot. Per-participant results, no p-values, no significance claims. |
| **The scorer is the tool's author** | the same person prepared the ground truth and scores the answers | Pre-register the ground truth and the rubric (§5, §7.2) before any session; score from written answers only; have a second person independently score a sample if one is available. **If none is available, say so in the report.** |
| **The question set was chosen by the tool's author** | selection bias | The calibration tests (§4.2) are mechanical and their results are published with each question; the composition rule (§4.3) is fixed before the questions are written. |
| **Learning carries across arms** | within-subject | Counterbalance (§6.2); with one repository, state the limitation explicitly. |
| **The orientation leaks** | five minutes, delivered live | Identical script, identical for every participant, kept in the materials (Appendix B). |
| **Time-cap censoring** | the 10-minute cap | Capped answers are recorded as capped, and the rate of capping is reported per arm. A large difference in capping is itself a result. |
| **Confabulation** | participants who do not want to say "I don't know" | `U` is a scored success where it is true, and the briefing (Appendix A) says so in as many words. |
| **A participant has used the tool before** | unlikely — 0 forks, 2 stars | Ask before the session; exclude if yes. |
| **The repository is not the participant's own** | public repository | Ecological validity is lower than a real team's repo. §8 says what the better version needs. |

## 10. The pre-registered decision rule

**Declared now, before any data.** Four outcomes, and what each one means for
what gets built next.

Let `ΔCE` = mean correct-and-evidenced per question, tool arm minus control arm,
over the six questions. Let `ΔCal` = mean (confidence − CE), tool arm minus
control arm. Let `ΔT` = mean time per question.

| Outcome | Condition | What it means for the project |
|---|---|---|
| **Supported** | `ΔCE ≥ 0.20` **and** `ΔCal ≤ +0.10` | The value claim holds well enough to continue. **v0.6 gets its justification**, and the audit's portability finding gains a reason to matter. |
| **Convenience only** | `ΔCE < 0.20` and `ΔT ≤ −30%` | The tool is a speed-up, not a comprehension aid. **Narrow the README's claim to what was measured** — "faster", not "better" — and reconsider v0.6, because "AI-assisted change analysis" is sold as depth, not speed. |
| **Harmful** | `ΔCal ≥ +0.15` without a correctness gain, **or** the tool arm is worse on the L1 questions | Stop feature work. The tool is making people more confident without making them more right, and something in its presentation is doing it. **This is the outcome that matters most**, because it is the one no test can see. |
| **Null** | none of the above | The value claim is unsupported. The next thing to build is not v0.6. Go back to `docs/v0.5-product-audit.md` §11 and re-answer the third decision with this in hand. |

**And the rule that overrides all four:** a result that is null, or harmful, or
merely convenient, is a **finding and not a failure**. This project's own rule —
Evidence First — applies to itself here for the first time. If the pilot comes
back null, the correct response is to write that down and change the plan, not to
re-run it with easier questions.

## 11. Materials

Printable as they stand. **Appendices A and C are the participant's; B and D are
the facilitator's.**

*(A full kit is Appendix A–D below. They are sections of this document rather
than files of their own so that one artefact carries the whole thing; a
facilitator printing Appendix C alone has the answer sheet.)*

### Appendix A — participant briefing (read this, ask nothing else)

You are being asked to answer six questions about a codebase you have not worked
on. There is no test of you here, and nothing is being recorded.

- **You have ten minutes per question.** A facilitator will tell you when the
  time is up. If you have not answered by then, write down what you have.
- **Every question has an honest answer, and "the history does not say" is one of
  them.** If you conclude the evidence is not in the repository, write that, and
  **you will be scored as correct when you are right**. Guessing is scored worse
  than saying you do not know.
- **Write down the evidence you relied on** — a commit, a file, a version, a
  test. An answer with evidence is scored better than the same answer without,
  and this is deliberate.
- **Write a confidence from 0 to 100**, honestly. It is compared against whether
  you were right, not used to judge you.
- **Do not use the internet.** The repository and the tools you were given are
  the whole world for the next hour.
- You may stop at any time, for any reason, and you do not have to say why.

### Appendix B — the facilitator's script

**Before the session.** Clone the repository in full and run `analyze` then `ast`.
Verify `git status` is clean. Have Appendix C printed, one per participant. If
this is the treatment arm, confirm that no `CODEARCHAEOLOGY_AI_*` variable is set
— the tool must run offline.

**Briefing (5 min).** Hand out Appendix A. Read the last two bullets aloud. Ask
"any questions about the rules" and nothing else.

**Orientation (5 min, treatment arm only).** Word for word, every time:

> "The tool has ten commands. `analyze` and `ast` have already been run. These
> six read the stored history: `timeline` shows the commits, `hotspots` ranks the
> files that change most, `files` lists everything the history contains, `file`
> shows one file's life including its earlier names, `commit` shows one commit in
> full, `structure` shows a Python file's definitions and how each one changed
> over its life, `cochange` shows which files change together. `--json` is
> available on most of them. That is all of it."

**Questions (60 min).** One at a time, in the printed order. Announce the
half-way point at five minutes. At ten minutes, stop the participant and move on.

**Memory sub-experiment (10 min).** One question, per §8.

**Debrief (10 min).** Ask: "which command did you use most", "was there a moment
where the tool told you something you could not have found otherwise", and "what
would you have wanted it to show you". Write the answers down verbatim.

**After every session.** Transcribe the paper answer sheets into one file per
participant, including the times and the confidences, and score them in a
separate pass with the ground truth open.

## 12. What remains, and what only the user can do

**The question set is complete: six questions, two at each calibration level.**
Q-A and Q-C are the L1 instrument controls, Q-E and Q-F the L2s, Q-B and Q-D the
discriminating pair — each with its ground truth, its citations, its scoring
forms and its **measured** calibration record (§5). Completing it cost one
derivation pass and produced three procedural rules (§2.6, §4.1 steps 4/5/7,
§4.2's tie-break, §4.4 failures 5–7), which is what the second repository will
need: the procedure is now demonstrated end to end twice, on two different
problems, rather than once.

**What remains is not authorship.** The second repository needs its own
derivation pass and its own six questions. Everything else on this list needs
people.

**What only the user can do:**

1. **Recruit six to eight people.** This is the whole blocker. The tool is not on
   PyPI, so they must be able to run `uv` from a checkout.
2. **Choose the second repository, or accept the one-repository variant and its
   stated limitation** (§6.2). The clone is the easy part; `requests` failed to
   clone twice, so try it first and have a fallback.
3. **Decide who scores.** If it is the tool's author, §9's threat is live and the
   report has to say so. A second scorer on a sample removes it.
4. **Fix the date and run it.** Everything else on this list is preparation, and
   preparation that is not followed by a run is a document.
5. **Decide the AI question separately** (§6.3). `explain` is out of the
   treatment for a reason; if a second experiment is wanted, it is its own design.

**What this document deliberately does not do:** it does not run anything, it does
not change any code, and it does not predict the result. It also does not soften
the four outcomes in §10 — including the one where the honest conclusion is that
the tool is not worth what has been built into it.
