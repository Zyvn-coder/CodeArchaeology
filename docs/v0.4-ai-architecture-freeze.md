# v0.4 AI architecture freeze

This is Unit 4 of v0.4, and it is where the model finally enters. The problem
definition (`docs/v0.4-problem-definition.md`) fixes the question, the evidence
contract (`docs/v0.4-evidence-contract.md`) fixes what may be used to answer it,
and the explanation schema (`docs/v0.4-explanation-schema.md`) fixes the shape of
the answer. This fixes how the answer is obtained.

**What is obtained is an interpretation, and every decision below follows from
that** (`docs/v0.4-problem-definition.md` §12). The evidence is deterministic:
same repository, same database, same bytes, and a test holds it. The answer is
not, and this document is where the plumbing is arranged so the two are never
confused — one module reaches the network and nothing else does, the key is read
from the environment, the answer is never repaired, and nothing that comes back
is stored as though it were evidence.

## 1. The shape

```
CodeArchaeology Core
        │
        ↓
Evidence Builder          offline — reads SQLite and git, touches no network
        │
        ↓
Explanation Context       the bundle: FACTS / STATISTICS / ABSENCES / UNKNOWABLE
        │
        ↓
AI Provider               the only layer the network appears in
   ┌────┴────┐
Provider A  Provider B
```

Four layers, and each owns one thing:

| Layer | Owns | May not |
|---|---|---|
| Evidence Builder | Reading the stored history and assembling the context | Reach a network, or know that a model exists |
| Explanation Context | The bundle itself, as a value | Hold anything the evidence contract does not list |
| AI Provider | Getting text back from a model | See the repository, the database or git |
| Core (the command) | Parsing, validating, deriving `confidence`, rendering | Delegate any of those to a provider |

**The core is not bound to a model.** A provider is a value the command is given;
the command has no branch anywhere that asks which one it got.

## 2. The interface

One method, and its narrowness is the design:

```python
class ExplanationProvider(Protocol):
    """Reach a model and return what it said. Nothing else."""

    def explain(self, context: ExplanationContext) -> str:
        """Return the model's answer as text, or raise ProviderError."""
```

Three rules that make this interface the whole contract:

**A provider returns text, not a parsed structure.** Parsing, validating the
schema and deriving `confidence` belong to the core, so every provider gets the
identical check. A provider that parsed its own JSON would be a provider that
could quietly disagree with the others about what a valid answer is.

**A provider never sees the repository.** It receives the context and nothing
else — no path, no connection, no git handle. This is testable in the way
`definitions.py` already tests its own boundary: **read the module's source and
refuse an import outside the allowed set.** The allowed set for a provider is the
standard library's HTTP and JSON machinery, and nothing from
`codearchaeology.storage`, `codearchaeology.objects` or `codearchaeology.history`.

**A provider raises `ProviderError` for anything that stopped it from getting an
answer.** What the model *said* is never a provider error — see §7.

## 3. Where the network appears

**In exactly one module.** This is the Core First requirement made structural
rather than promised.

Everything above the provider line — the whole of v0.1 to v0.3, plus the evidence
builder and the context — runs with no network code in the import graph at all.
The command's offline path therefore works on a machine with no network, no key
and no provider configured, and it produces the same bundle the model would have
been shown.

**What the offline path prints is exactly what the model is shown.** Not a
summary of it, not a rendering of it — the same bytes, under the same section
headings. This is the rule that keeps the two paths from drifting: a reader can
put the answer beside its input and check one against the other, and a change to
the bundle shows up in both places or in neither.

**Amended in Unit 12, and the amendment is narrow.** The rule holds for every
commit that fits a model's window, which is what it was written for. A commit too
large to send whole is reduced *for the model* — `selection.py`, designed in
`docs/v0.4-context-budget.md` — and every row that was left out is counted inside
the prompt rather than left to be noticed. The evidence itself is not reduced: the
offline path and `explain --json` still carry the bundle, and the answer is
checked against what the model was shown rather than against everything the tool
holds. The two paths still cannot drift on anything the model was given whole,
which is every commit that was never too large.

**Held by a test, in the project's existing shape.** `definitions.py` refuses an
import outside its allowed set by reading its own source; the offline path gets
the same test, with the allowed set excluding every networking module. A future
unit that reaches for `urllib` one layer too high fails the build rather than
quietly making the offline path need a network.

## 4. The API key

**Environment only.** `CODEARCHAEOLOGY_AI_API_KEY`, falling back to the vendor's
conventional name (`OPENAI_API_KEY`) so a machine already configured for another
tool needs no second copy.

**Never a command-line flag.** A flag is visible in the shell's history and in the
process list, and a key that leaks into either is a key that has to be rotated.

**Never stored, never printed, never bundled.** The key does not go into SQLite,
into the context, into the output, or into an error message. This last one is not
theoretical: a provider that echoes the failed request — URL, headers, body — puts
the key in a traceback, so the error path scrubs it before the message is built,
and a test asserts that a provider failure raised with a key in scope produces a
message that does not contain it.

The rest of the settings are not secret and may also be flags; the precedence is
flag, then environment, then default.

## 5. Timeout

**A deadline, not a socket timeout.** The default is **60 seconds for the whole
call**, configurable by `CODEARCHAEOLOGY_AI_TIMEOUT`.

The distinction is the decision. A socket timeout fires per read operation, so a
provider that dribbles a byte every 30 seconds keeps a socket timeout from ever
firing while the command hangs for an hour. The deadline is wall-clock around the
whole call, and when it expires the command fails with a message naming the
deadline and the endpoint — never the key.

## 6. Retry

**Retryable:** a connection that failed, a DNS failure, a read that timed out, a
`429`, and a `5xx`. These are conditions where the same request may succeed.

**Not retryable:** `400`, `401`, `403`, `404`, and any other `4xx` except `429`.
These are the request or the credentials being wrong, and repeating them wastes
the user's money and time to fail identically.

**The numbers:** at most **2 retries** (three attempts in total), with an
exponential backoff of 1 s then 2 s, and a `Retry-After` header is honoured when
the provider sends one. All three are configurable.

**The failure says how many attempts were made.** "Failed after 3 attempts" is a
different situation from "Failed", and a user deciding whether to try again needs
to know which one they are in.

## 7. Provider failure and model failure

Two failures that look alike and are not, and the whole reason to name them
separately is that they demand opposite responses.

**A provider failure** is the call not producing an answer: the host is
unreachable, the TLS handshake failed, the deadline expired, the response was a
`500`, the body was empty, the envelope was not JSON. **The model never spoke.**

**A model failure** is the call succeeding and the answer being unusable: the text
is not JSON, it does not match the explanation schema, a `possible_reason` has an
empty `based_on`, an observed change cites evidence that is not in the bundle, a
`summary` sentence cites an id that does not exist.

| | Provider failure | Model failure |
|---|---|---|
| Who raises it | The provider | The core, after parsing and validating |
| What it means | Infrastructure | The model produced something unusable |
| Retryable | Per §6 | **Once**, and no more |
| What the user sees | The endpoint, the status, the attempt count | Which check failed and which field |

**A model failure is retried once**, because a model asked again can answer
properly, and no further, because a second failure of the same kind is not a
transient condition — it is the model not doing the job, and each further attempt
is paid for.

**The tool never repairs an answer.** It may retry (ask again) and it may refuse
(fail). It may not fix, complete, trim, re-word or drop a part of what came back.
A `possible_reason` citing an id that does not exist is a model failure; the tool
does not delete the citation and print the rest. Repairing is the tool inventing
content, which is the one thing this layer exists to prevent, and doing it
"helpfully" is how a broken answer becomes a plausible one.

**A partial answer is never printed.** Either the whole structure validates or
nothing is printed and the command exits non-zero. Half an explanation with a
note is worse than none, because the note is the part that gets skipped.

## 8. Token limits

Two limits, and neither is allowed to fail silently.

**The context is counted before it is sent.** The estimator is conservative
(roughly four characters per token, stated as the estimate it is) because there is
no tokeniser in the standard library and shipping one would add a dependency that
is model-specific besides.

**A context over the limit is a refusal, not a truncation.** The command fails and
names the size and the limit. Letting the provider truncate is the same failure as
a silently truncated diff: the model would answer about a partial bundle while
believing it had the whole one, and the answer would look exactly like a
well-supported one. This follows the evidence contract §5 rule — bounded, and the
bound is stated.

**Unit 12 added the other half of this.** A commit too large for any window is
reduced first, by a selection whose every dropped row is counted in the prompt, so
what reaches this ceiling is a limit set too low for the model rather than a
commit that is too large — and the refusal says so. See
`docs/v0.4-context-budget.md`.

**The output limit is set explicitly** and is part of the configuration. A
generation that stops at the ceiling is cut mid-JSON, which the core would then
report as a model failure when the real cause was the ceiling. The failure names
the ceiling when the response was cut rather than malformed.

## 9. Configuration

| Name | Meaning | Default |
|---|---|---|
| `CODEARCHAEOLOGY_AI_BASE_URL` | The endpoint | none — required for the online path |
| `CODEARCHAEOLOGY_AI_MODEL` | The model name | none — required for the online path |
| `CODEARCHAEOLOGY_AI_API_KEY` | The key | falls back to `OPENAI_API_KEY` |
| `CODEARCHAEOLOGY_AI_TIMEOUT` | The deadline, in seconds | 60 |
| `CODEARCHAEOLOGY_AI_MAX_RETRIES` | Retries after the first attempt | 2 |
| `CODEARCHAEOLOGY_AI_MAX_CONTEXT_TOKENS` | The context ceiling | the model's, set by the user |
| `CODEARCHAEOLOGY_AI_MAX_OUTPUT_TOKENS` | The generation ceiling | set by the user |

The prefix is `CODEARCHAEOLOGY_`, matching `CODEARCHAEOLOGY_CACHE_DIR`, which
already exists. No config file in the first version: the project has none today,
and a second place for settings is a second place for them to disagree.

## 10. The one open question: which implementation ships

The user's instruction for this unit was that the concrete providers come later:

> 具体的 OpenAI / DeepSeek / 本地模型以后再接。

That settles the architecture and leaves one thing open, because v0.4 with no
implementation is a v0.4 whose AI feature cannot be run at all.

**Recommendation: one implementation, OpenAI-compatible, over the standard
library's `urllib.request`.** One adapter reaches OpenAI, DeepSeek, Ollama, vLLM
and LM Studio, because they all speak the same HTTP shape; the differences become
configuration (`BASE_URL`, `MODEL`, `API_KEY`) rather than subclasses, which is
also what makes the diagram's "Provider A / Provider B" true without writing two
of anything. Pointing `BASE_URL` at a local Ollama is the Local First case, and it
needs no separate code path. It adds **no runtime dependency** — the tool keeps
`typer` and `rich` and nothing else, which is the line the v0.3 freeze drew.

The alternatives, and why they are weaker here: a vendor SDK adds a dependency and
a vendor; the interface with no implementation at all keeps the freeze pure but
ships an `explain` nobody can run.

**This is not decided.** It stays open until the user rules, and no code is
written until they do.

## 11. What this unit does not decide

- **Which implementation ships**, as above.
- **The command's name and its flags.** `explain <sha>` is the natural reading of
  the problem definition, but the interface is this unit's and the command line is
  the next one's.
- **The prompt.** What the model is told about the schema, and whether the schema
  is enforced by wording, by a constrained decoding mode, or by parse-and-retry,
  is the prompt unit's.
- **The rendering.** The explanation schema §9 already leaves this open.
- **Whether an explanation is stored.** Still open from Unit 1 §10.
- **The diff's bound, and whether the first version ships the diff at all.** Still
  open from the evidence contract §10.
