# v0.4 problem definition

This is Unit 1 of v0.4: the question, fixed before any decision about how to
answer it. It says what the AI layer explains, what evidence it is allowed to
use, and what would make an answer acceptable. It decides no command, no
provider and no storage — §10 lists those as still open.

## 1. The question

The first version explains **one commit**, and asks two things of it. The user's
own words, which are the target:

> 解释某一个 commit 发生了什么，以及基于已有证据可以合理提出哪些可能原因。

1. **What happened.** A faithful account of the change, in the file's own terms.
2. **Which candidate reasons the evidence supports.** Not *the* reason — the
   reasons the stored evidence is consistent with, each one marked as a
   possibility rather than as a finding.

The two parts are not equally strong, and the difference is the point. The first
is checkable: a statement either maps to a stored row or it does not. The second
is not a finding at all, because git stores no intent, and the phrasing above is
careful — the evidence *supports* a candidate, it does not establish one.

## 2. Why the commit is the unit

Three reasons, and the third is the one that matters.

**It is what git reports, and what the whole storage model is already keyed on.**
`commits`, `commit_parents`, `commit_files`, `file_versions` and
`definition_versions` all hang off a commit sha. Asking the question at the
commit needs no new data — only a new reading of what is there.

**It has a natural boundary.** A commit begins and ends; it has parents and a
message; it is the smallest unit that has an author and a date. A "file's whole
history" or a "repository" does not, which is why the questions that start with
them turn into chat (§9).

**It is where the gap is.** `git show` already answers *what changed*, line by
line, better than any model will. What no git command answers is what this change
means against everything the tool already knows about the files it touched: that
this function has been rewritten eleven times, that this file was renamed twice
and is still under its third name, that these four files have moved together in
every commit for two years. That context is what v0.1–v0.3 built, and it is the
only thing the AI layer has to offer that a diff does not.

## 3. The pipeline

```
commit  →  historical evidence  →  AI explanation
```

The middle term is the whole design. The model is not shown a diff; it is shown
the evidence, and it is shown nothing else.

## 4. The evidence one commit already has

Everything below is stored today, in schema 4. Nothing here is new data, and
nothing here is a conclusion.

### 4.1 The commit itself — `commits`, `commit_parents`

The sha, the author's name and email, `authored_at` and `committed_at`, the
message in full, and the parents. From the parents: whether this is a merge, and
what the parent commits said.

### 4.2 What it touched — `commit_files`

One row per path: the change type as git reported it (`A`, `C`, `D`, `M`, `R`,
`T`, `U`, `X`, `B`), `old_path` for a rename or a copy, the added and deleted
line counts, and `similarity` for a rename or a copy. Binary files carry no
counts, and that is recorded rather than guessed.

### 4.3 The AST layer — `file_versions`, `definition_versions`

For every Python file version in this commit: its `content_sha`, the
`parsed_at_version` that produced the row, and either that it parsed or the parse
error with its line and offset.

For every version that parsed: every definition it held — `kind`, `qualname`,
`lineno`, `end_lineno`, `decorators`, `fingerprint` — and the `change_type` the
pass cached on each row against the nearest earlier readable version of the same
file: `created`, `modified` or `unchanged`.

Three properties of those rows are part of the evidence, not footnotes to it,
and an explanation that misreads them is wrong:

- **`change_type` compares against the last version that could be read.** A
  version that failed to parse gets no definition rows at all, so an `unchanged`
  can span a failure and means "this is what the nearest readable version held",
  not "nothing happened in between".
- **A definition is identified by its kind and its qualified name, and by
  nothing else.** A function that was renamed is one definition ending and
  another beginning; the tool will not claim the two are related.
- **Absence is the evidence for a deletion.** Nothing is written to spell it out,
  so "the definition is gone" is read from the missing row.

### 4.4 The file's life — derived by `lifecycle.py`

Not stored, and rebuilt on demand: the names this file carried and when it
carried them, when it appeared, when it was last changed, what it cost in lines,
and whether it is still there. This is what turns a row of numbers into "this is
the fourteenth change to a file that has been renamed twice".

### 4.5 Repository statistics — `hotspots`, `cochange`

How often these files change relative to the rest of the repository, and which
files usually change alongside them.

These are marked apart from 4.1–4.4 on purpose. They are statistics over a file's
whole life, not facts about this commit, and a commit that touches two files that
usually move together is not a commit where one caused the other. If they are
used at all, they support a candidate reason at the weakest level in the bundle,
and they must be labelled as the correlation they are.

### 4.6 What is not available

Named so that no later unit assumes it is there:

- **The author's intent.** Git does not store it, and no amount of history
  recovers it.
- **Anything outside the repository** — the issue, the review, the discussion,
  the CI result, the incident.
- **The state of files this commit did not touch.** A version row exists at a
  commit only where the lifecycle walk recorded an event — an add, a
  modification, a rename or a delete — so the rows describe the files this commit
  moved, not the tree around them. What the rest of the repository looked like at
  that moment is not stored.
- **Whether this commit is part of a larger series.** A refactor split over ten
  commits looks like ten commits.

## 5. What an explanation is here

Two parts, in this order, and the second may be empty.

**The account.** What happened, in the file's own terms. Every sentence maps to
something in §4. This part is judged, not admired: a claim that cannot be traced
is a defect.

**The candidate reasons.** The reasons the evidence is consistent with, each
naming the evidence it rests on, each marked as a possibility. "The function was
rewritten eleven times and the last four changes each added a parameter" is a
candidate reason. "The author was under time pressure" is not, because nothing
in the bundle says it.

**Where the evidence is thin, the second part is short or absent.** That is a
correct answer, not a failure of one.

## 6. What is not an explanation

- **Intent stated as fact.** "Because the deadline was close."
- **A restatement of the message or the diff.** If the answer could have been
  written by reading `git show`, the tool added nothing. This is the failure mode
  that makes an AI feature look like it works while being worthless.
- **A verdict.** Not "this is a good change", not "this is technical debt", not a
  score of any kind.
- **A prediction.** Not what will break, not what to do next.
- **Causation from correlation.** See §4.5.
- **A reason with nothing behind it.** If the bundle does not support a
  candidate, it is not offered.

## 7. When the evidence is thin

A commit that adds three lines to a file that has never been touched has no
story. The answer must say so.

The distinction v0.3 refuses to round off is inherited here, and it is not
cosmetic:

- **"Nothing was there"** — the definition is gone; absence is the evidence.
- **"Nothing could be read"** — the file did not parse, so the tool knows
  nothing about its contents at that commit.

An explanation that runs the two together is wrong in a way a reader cannot see.

## 8. What makes an answer acceptable

At the problem level, before any interface exists:

1. Every statement in the account maps to a stored row.
2. Every candidate reason is marked as a candidate, and names its evidence.
3. Thin evidence is stated as thin rather than filled in.
4. "Nothing was there" and "nothing could be read" stay different sentences.
5. The answer contains at least one thing that reading the commit message alone
   would not give. Otherwise it is a summarizer.
6. **The input is deterministic even though the output is not.** The evidence
   bundle is the same bytes for the same commit and the same database, and it can
   be printed and inspected. That is what makes the layer testable at all, and
   it is why the contract is written on the bundle rather than on the prose.

## 9. Not in v0.4

The user's list, and it is a boundary rather than a backlog:

- **Whole-repository chat.** The unit is a commit; there is no conversation.
- **Automatic question answering**, and **multi-turn** anything.
- **An agent.** Nothing is executed, nothing is written, nothing is fixed.
- **A web UI.** v0.1–v0.3 are a CLI and v0.4 stays one.
- **Automatic repair.**
- **Call graphs and complexity scores.** Those are different features, and the
  v0.3 freeze already ruled them out of the evidence layer.
- **Non-Python definition evidence.** Python-only holds in v0.4 as it did in
  v0.3.

## 10. What this unit does not decide

Deferred to the design freeze, and listed so nothing here is read as a decision:

- How the model is reached, and whether the tool calls one at all.
- What the command is called, and what its arguments are.
- The no-AI path. Core First requires that this layer still do something useful
  without a model, and the bundle in §4 is the obvious candidate; the form it
  takes is the freeze's to choose.
- How the bundle is serialised for a model, and how large it may get.
- How a networked feature is tested in CI without the network.
- The shape of the output — prose, JSON, or both.
- Whether an explanation is ever stored.

## 11. The one hard rule

Evidence First, at the AI layer:

> **The model may use only what the bundle holds, and a claim that cannot point
> at a stored fact is not printed.**

This is not a quality setting and it does not depend on the model chosen. It is
the same rule the rest of the project already follows — every conclusion
traceable to a commit, a diff or an AST node — applied to the one layer where
inventing something is easy.
